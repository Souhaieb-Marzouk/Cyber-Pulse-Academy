Contributors

Every exercise batch on this site was written by someone who does this work for a living and gave up an evening to explain it properly, and every batch was read by someone else before it shipped. Thank you to all of them. This page is where that work is named: the authors, the reviewers, and the people who found an error and took the time to prove it with a source.

Recognition here is manual and opt-in. A contributor asks to be listed and is added, with the wording they agreed to. Nobody is ever added automatically from git history, and nobody is listed under a name, handle or profile link they did not choose. If you would rather stay anonymous, that is entirely fine: the work still counts, and the withdrawal of a credit is as easy as asking for it.

How to be credited

Four steps. The first one is the only one that takes real time, and it is the same work that makes the site worth visiting.

Do the work

Write one of the three missing batches for a topic, review a batch someone else wrote, or file a source-cited accuracy report against a page that is wrong.

Ask to be listed

Add your entry to data/contributors.json in the same pull request, or say so in the pull request or issue that carries your work. Nothing is added without that request from you.

Say what you did

One line is enough: the topic and batch number, the batch you reviewed, or the report you filed. The card shows that line rather than a job title, because the work is the point.

Change your mind freely

You can ask for your entry to be edited or removed at any time, for any reason or for no reason at all. No discussion is required and the work stays in the repository.

Review work counts. Reading a batch for technical accuracy, checking its sources, testing that an exercise can actually be completed, and correcting a wrong answer is as valuable as writing a new one, and it is credited the same way. A batch that has been reviewed by someone who knows the subject is the difference between practice and guesswork, so reviewers are named alongside authors rather than listed as a footnote.

Fields in the credit list

Each entry is one object in the array. Only name and contributions are required, and an entry missing either is skipped rather than drawn as an empty card.

Fields accepted in data/contributors.json, which are required and what each one contains
Field Required What it contains
name Yes The name or handle shown as the card title. It is used exactly as written, so a pseudonym, a first name only, or a handle on its own is all acceptable.
contributions Yes What the person did, as one line or as a list of lines. Each line becomes a bullet on the card, so keep each one short and specific.
handle No A second line under the name, usually the account handle. It is hidden when it is identical to the name.
url No The profile the card title links to. Only an absolute https:// address is turned into a link, and links open in a new tab with rel="noopener noreferrer".
role No A short label such as Batch author or Reviewer, shown as a badge above the contributions.

Reviewers and accuracy reports

The two least visible jobs on a study site are the two that decide whether it can be trusted. Both are treated as contributions here, and both earn a credit exactly like a new exercise batch does.

  • A technical review means checking the answers against a primary source, confirming the commands and configuration snippets still do what the batch claims, and saying so in the pull request. A review that finds three wrong answers is more useful than one that approves everything.
  • An accuracy report is a contributor's report that a published page is wrong. It needs a citation: the published source that contradicts the page, and the sentence or answer that is affected. A report with a source can be acted on and credited; a report without one usually cannot.
  • A clarification counts too, when a topic summary, an objective or a detection note is technically true but misleading in practice. Say what a working practitioner would expect instead, and why.

Reports and reviews are opened as issues or pull requests in the repository, following the templates and the content rules in the contribution guide. If you would rather send the correction than argue about it, a pull request with the fix and the source in the description is the fastest path there is.
