Detection Strategies (community-authored)

Twelve community-authored detection strategies for the techniques in this catalog, each written as a study topic rather than a product rule: the telemetry it needs, the logic that separates signal from noise, a language-independent pseudo-rule, the false positives that will fire in a real estate, the tuning that makes the rule survivable, and a severity that reflects the impact if the alert is true.

The twelve detection strategies

Each of the 697 strategies names the primary technique it observes, the severity it carries if the alert is true, and the three exercise batches reserved against it: triage, then build and tune, then the adversary's view of how the rule would be evaded.

What a detection strategy actually needs

A rule is the last ten percent of a detection strategy. The other ninety percent is everything that decides whether the rule survives its first month in production. Every strategy page here is written against the same six-part structure.

Telemetry
Which log source, on which hosts, at what retention, with which fields populated, and who owns the pipeline that carries it. A brilliant rule that depends on command-line auditing on hosts where it was never enabled is not a detection, it is a wish.
Logic
The condition that separates the behaviour from its benign twins, expressed in fields that actually exist, with thresholds and time windows stated rather than implied. "Unusual" is not logic until someone writes down the baseline it is unusual against.
A pseudo-rule
A language-independent statement of the condition, close enough to implement in Sigma, KQL, SPL or a cloud-native policy engine without re-deriving the reasoning. For example: process.name == "powershell.exe" AND command_line contains "-enc" AND lower(parent.name) NOT IN (management_agents) AND host NOT IN (build_agents).
False positives
The specific administrative, deployment, backup and monitoring behaviours that will match, named in advance. If the first analyst to see the alert has to work out whether it is a configuration management tool, the strategy is incomplete, not the analyst.
Tuning notes
What to exclude, what must never be excluded because it is the attack path, and what to change when the estate changes. Tuning is a maintenance commitment with a named owner, not a one-off edit during the noisy week after rollout.
Severity
What happens if the alert is true and nobody acts within the hour, plus the worst realistic loss: data, control of an identity, or availability. Severity describes impact and should not be used as a proxy for how confident you are that the alert is real.

That structure exists because a rule nobody has tuned is a rule nobody uses. An untuned rule fires on legitimate activity, the first responders learn to close it without reading it, someone adds a broad exclusion to make the queue quiet down, and within a few weeks the rule is either disabled or a standing source of contempt. The exclusions are then the interesting part of the estate: whatever got suppressed to buy peace is exactly what an adversary who reads public detection write-ups will use. Tuning notes are what keep that history visible, and the severity that is attached to the rule is what keeps someone willing to read it.
