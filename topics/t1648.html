T1648 Serverless Execution

T1648ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Serverless computing lets you run small pieces of code without owning a server. The cloud provider runs the code when something triggers it. An intruder can abuse that same service to run their own code inside your cloud account.

Why should you care?

Serverless code runs inside your cloud, close to your permissions and your data. It needs no server to look after, so it is quick to set up and easy to forget. A single function can quietly copy data, mine coins, or create new accounts. Because it looks like normal automation, it can hide in plain sight for months. Reviewing what runs in your cloud is now basic security work.

How it works, in plain steps

  1. The attacker gets cloud credentials that can create or change functions and automation flows.
  2. They upload their own code as a function, a workflow, or an app script in an office suite.
  3. They attach a powerful role to that code so it can act beyond their own permissions.
  4. They set a trigger, such as a new user, a sent email, or an uploaded file.
  5. The provider runs that code automatically whenever the chosen trigger condition happens.
  6. The code does its work, such as copying data or mining coins, using your cloud resources.

Real-world example

Imagine an office with a shared kitchen and a small robot that makes coffee when someone presses a button. Staff like it because nobody has to maintain it, and the robot holds a key to the supply cupboard. Now imagine a stranger works out how to add a new button to the panel. The button says hot chocolate, so nobody questions it. When someone presses it, the robot walks to the cupboard, takes whatever the stranger listed, and hands it over. Serverless execution is that extra button. Your cloud does the work, your permissions open the cupboard, and the whole thing looks like a harmless convenience.

Key takeaways

  • Cloud functions and automation flows are code, even when nobody manages a server.
  • Give functions only the permissions they truly need, and review roles often.
  • Log function creation and updates, then compare them with known delivery pipelines.

In more detail

Serverless execution describes abuse of cloud functions, workflow automation, and integration services to run attacker controlled code without managing a server. The code is submitted as a function, an automation flow, or a script inside a cloud office suite, and the provider runs it on demand. Because the identity that runs the function also carries an attached role, an adversary able to create or update functions can often reach further than their own account allows, which is what makes permissions such as IAM:PassRole in AWS or the service account actAs permission in Google Cloud valuable. Functions also respond to events, so a rule that fires on a new user, an uploaded file, or an incoming message turns a single deployment into durable execution. Log trails come from the provider control plane: create and update calls, deployment packages, invocation records, and the downstream interface calls the function makes. Defenders compare that activity against normal delivery pipelines, since engineers also ship functions, though rarely from a fresh identity, at an odd hour, on a payload that reaches secrets.

What you will practise

  • Explain what serverless computing is and why attackers find it useful.
  • Describe how a function's attached role can grant more access than the attacker holds.
  • Explain how event triggers let one deployment run again and again over time.
  • Identify the cloud log sources that record function creation and invocation.
  • Distinguish a normal delivery pipeline from suspicious function activity.
