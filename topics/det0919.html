DET0919 Detection of Query Public AI Services

DET0919Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Public artificial intelligence (AI) services are websites that answer questions and create content. This detection watches for computers in your network that send data to them. It catches both risky data sharing and attacker use.

Why should you care?

When you send text to a public service, you lose control of it. A worker may paste customer data by mistake. An attacker may use the same service to clean up text or write code. Both cases matter, and both look like ordinary web traffic. So you must look at who and what.

How it works, in plain steps

  1. You collect web proxy and firewall logs. These record the destination and the amount of data sent.
  2. You collect Domain Name System (DNS) queries, which show the service name being looked up.
  3. You classify the destination into a category, such as generative artificial intelligence.
  4. You identify the process and the user account behind the connection.
  5. You measure upload volume. A few kilobytes is a question. Many megabytes is a document.
  6. You alert when a blocked category, an unusual program or a large upload appears together.

Real-world example

Think of a company post box. Sending a letter is normal and fine. But if someone posts a thick folder of customer files every afternoon, the post room should ask what is inside. The address is not the problem. The amount, the sender and the timing are what draw attention. Querying a public AI service works exactly like that folder.

Key takeaways

  • The same destination can be harmless for one team and a policy breach for another.
  • Upload volume and the requesting program are the most useful fields.
  • You cannot read encrypted content, so you detect the behaviour around it instead.

In more detail

This detection strategy covers outbound access from the estate to public generative artificial intelligence (AI) services, whether that access is a careless upload of protected data or an adversary using hosted models for tooling such as text rewriting, translation or code generation. It covers technique T1682 and matters because the request leaves the organisation's control while the response can be used directly in an intrusion workflow, and because content sent to a public service is a data loss event in itself. The telemetry that makes it possible is web proxy and next generation firewall logs with server name indication and application category, Domain Name System (DNS) query logs, TLS client fingerprints, and endpoint process creation showing which program made the connection. In practice the strategy fails because most traffic is encrypted, approved assistants are widespread, and the same endpoints are used for legitimate work, so category based alerts alone generate heavy noise. Correlating destination category with the requesting account, the uploading process and data volume is what makes the alert useful.

What you will practise

  • Explain why traffic to public artificial intelligence (AI) services is relevant to both data protection and intrusion detection
  • Read web proxy, firewall and Domain Name System (DNS) logs to identify which hosts reach AI service endpoints
  • Use TLS client fingerprints and process creation records to determine which program initiated the session
  • Set upload volume thresholds that separate a single question from a bulk document submission
  • Describe the limits of detection when traffic is encrypted and inspection is not performed
  • Propose an approved alternative service and a policy path so that blocking does not push users to personal devices
