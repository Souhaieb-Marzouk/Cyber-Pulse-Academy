DET0547 Detection Strategy for T1505 - Server Software Component

DET0547Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for new files added to a server that serves web pages or databases. These files can be small programs that an attacker uses to keep access. It also watches for the web server starting a command shell, which is unusual.

Why should you care?

A web server must accept requests from outside, so it is often the first way in. A small script left behind can run commands, read files and stay hidden among many normal pages. The server trusts the file, and the file works for the attacker.

How it works, in plain steps

  1. A file monitoring agent records every new file written into the web directories and module folders.
  2. The endpoint records process starts and shows which parent process produced each one.
  3. The web server writes a log line for every request, including the path requested and the result code.
  4. Database auditing records when a built in command feature or a new function is used.
  5. The platform keeps only the file writes and process starts that do not match a deployment record.
  6. A new script that is later requested from the internet becomes one correlated alert.

Real-world example

Think of the key cabinet in an office. Every key has a label and an owner. If somebody adds an unlabelled key that opens the server room, the cabinet still looks tidy. Searching the cabinet against the key register finds it. Comparing web files against the deployment record works the same way.

Key takeaways

  • A service account starting a command interpreter is a strong warning sign.
  • Compare new files with the deployment record, not with your memory of the site.
  • The web access log tells you whether a new file was actually used.

In more detail

This detection strategy covers the addition of malicious server side components such as web shells, database extensions and application server modules, matching technique T1505. It matters because these components run with the privileges of the service that hosts them, face the internet or internal users directly, and give an adversary a stable entry point that survives reboots and patch cycles. The telemetry that makes it possible is file integrity monitoring of web roots and module directories, process creation records showing a service account spawning a command interpreter, web access logs recording requests to newly created scripts, and database audit records for command execution features. It fails in practice because deployments, plug ins and content management updates write files into those same directories constantly, so the rule needs a deployment baseline and a parent process constraint to stay usable.

What you will practise

  • Explain how a server side component such as a web shell or a database extension provides persistence
  • Identify the file integrity, process creation, web access and database audit telemetry for this detection
  • Recognise the process lineage that shows a service account spawning a command interpreter
  • Correlate a new server side file with the request that later used it
  • Write a detection rule for server side component creation and tune it against deployment tooling
