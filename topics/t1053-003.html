T1053.003 Scheduled Task/Job: Cron

T1053.003ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Cron is the classic timer on Linux and other Unix-like systems. A crontab is the list of jobs it should run. This sub-technique is when an attacker adds their own line to that list. It belongs to the Scheduled Task/Job parent and is the older cousin of the timer systems. The entry stays on disk, so the code keeps coming back.

Why should you care?

A cron entry is small and quiet, and it runs even while nobody is logged in. Many systems already have dozens of entries, so one more is easy to overlook. If the entry runs as the root account, the attacker regains full control whenever it fires. Discovering and removing these entries is a basic part of cleaning up an intrusion.

How it works, in plain steps

  1. The attacker gains a shell on a Unix-like host and looks at existing scheduled work to learn the local habits.
  2. They add an entry to a user crontab, the system-wide crontab, or a drop-in file in a cron directory.
  3. The entry names a command and a schedule, such as every ten minutes or once at reboot.
  4. The cron service reads the files and runs the command as the owner of that crontab.
  5. Output may be mailed to the local account, which can create an unexpected trail in mail logs.
  6. On appliance systems the spool file is edited directly, and the change may be lost after a reboot.

Real-world example

Think of a shared flat with a whiteboard by the door. Anyone can write a chore on it. The flatmate named at the top of the list does that chore at the stated time, without asking questions. A stranger slips in and adds a line. It asks the flatmate with the master key to open the storage room every night. The writing looks like any other chore, so nobody challenges it. Only when you compare handwriting do you see it was never part of the plan.

Key takeaways

  • Cron entries are persistent instructions, so review the command, not just the file.
  • Check every crontab location, including system directories and spool files.
  • Mail generated by a job can be the first visible sign of an unexpected entry.

In more detail

This sub-technique is persistence and recurring execution through cron, the long-standing time-based scheduler on Unix-like systems. An operator adds an entry to a crontab whose five leading fields describe minute, hour, day of month, month and day of week, followed by the command to run; a short form can also express intervals, and a keyword can replace the fields entirely with a named period such as a reboot. Entries live in per-user crontabs under a system spool directory, in the system-wide crontab, and in drop-in directories whose file names control ordering and sometimes the account used, so the same effect leaves different artefacts depending on where it is written. On appliance-style platforms such as ESXi the spool file must be edited directly because no editor tool is exposed, and such edits can disappear on reboot unless the change is also persisted elsewhere. Because packages, monitoring agents and backup jobs all install cron entries, presence alone proves nothing. Triage is about the command, the schedule, the author, and whether the entry survives re-provisioning.

What you will practise

  • Explain how a crontab expresses a schedule and a command, and where such files are stored.
  • Describe how cron differs from the at utility and from systemd timers.
  • Identify the artefacts an added cron entry leaves in file listings, logs and mail output.
  • Distinguish a hostile entry from legitimate package or backup jobs by command and schedule.
  • Explain why direct edits on appliance systems may not survive a reboot.
