T1553.002 Subvert Trust Controls: Code Signing

T1553.002Defense ImpairmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Code signing is like a wax seal on a document. A trusted company signs its software so your computer can check it came from them and was not changed. This sub-technique is when an attacker gets a real seal, or makes one, and puts it on their harmful program.

Why should you care?

Many systems are set to run only signed software. A valid signature lets harmful code pass that rule. Users also trust signed files, so they click without worry. This makes stolen signing keys extremely valuable to attackers.

How it works, in plain steps

  1. A software company creates a key pair and gets a signing certificate for it.
  2. It signs its programs so the computer can verify both the publisher and the contents.
  3. An attacker steals the private key, or buys a certificate in a false company name.
  4. The attacker signs their own harmful program with that stolen or bought certificate.
  5. The target computer checks the signature and finds that it is valid.
  6. The program runs, and the trust rules raise no alert before it starts.

Real-world example

Think of a delivery firm whose drivers carry a stamped company card to enter office buildings. A thief steals a blank card and a stamp from the depot. Now the thief walks past the lobby desk, shows a completely valid card, and is waved through. The card is genuine, the stamp is genuine, but the person carrying it is not who the card claims.

Key takeaways

  • A valid signature proves the file was signed by that key, not that the file is safe.
  • Protect signing keys carefully, because they are a direct route past application control.
  • Track certificate revocation and publisher behaviour, not just the presence of a signature.

In more detail

Code signing binds a binary to a verified publisher identity and guarantees the file has not been altered since it was signed. This sub-technique covers the theft, purchase or creation of signing material so the payload carries a signature that validates correctly, which separates it from the invalid-signature case where the check fails and leaves a visible artefact. Threat actors have taken certificates from compromised build systems, bought them from issuers using shell companies, and abused stolen tokens from hardware signing devices to produce valid signatures on demand. The result defeats application control policies that allow only signed code, defeats SmartScreen reputation prompts and reduces antivirus suspicion. Detection therefore depends less on the signature and more on the publisher's normal behaviour, on mismatches between signer name and file metadata, on short-lived or unfamiliar certificates, and on revocation and certificate transparency data.

What you will practise

  • Explain what a code signing certificate proves about a program.
  • Describe how certificates can be stolen, purchased or misissued for malicious use.
  • Explain how this sub-technique differs from the invalid code signature case.
  • Identify artefacts such as signer names, certificate validity and revocation data.
  • Recommend controls that limit the impact of a stolen signing key.
