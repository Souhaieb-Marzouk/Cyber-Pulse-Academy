DET0398 Detect Office Startup-Based Persistence via Macros, Forms, and Registry Hooks

DET0398Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for hidden changes that make Microsoft Office run extra code by itself. The code can hide in an add in, a template, or a registry setting for the Outlook mail client. The alert means Office was given a new instruction to load something it did not load before.

Why should you care?

Office starts every day on almost every desk. If an attacker can make it load their code, that code returns after every reboot. It needs no scheduled task, so it is quieter than the usual start up trick. Users will not notice a change they cannot see. Detecting the change early stops the attacker from keeping a permanent foothold.

How it works, in plain steps

  1. The monitoring agent records registry changes and file creations on each Windows computer.
  2. It sends those events to the security monitoring platform with the account, the host and the full path.
  3. The rule selects the Office add in registry keys and the start up template folders.
  4. It also flags any Office process that loads a module from a user writable folder.
  5. The alert shows the changed key or file, the account that made the change and the time.
  6. An analyst then checks the change against the approved request.

Real-world example

Think of a delivery van that arrives at the same loading bay every morning. The driver has a valid badge, so nobody questions the van. If someone quietly adds a new stop to the driver roster, the van will keep making that stop forever. The roster change is the thing worth watching, not the van.

Key takeaways

  • Office persistence is popular because it reloads automatically in a trusted program.
  • Registry keys and template files are the places to watch, not just documents.
  • You cannot alert on every Office change, so an approved add in list is required.

In more detail

This detection strategy covers persistence that hides inside Microsoft Office itself, where an attacker plants an add in, changes a default template path, writes a mail form or Outlook rule that runs code, or redirects a registry hook so the payload loads whenever the user opens a document or starts the mail client. It matters because the mechanism is the trusted productivity suite: nothing about the visible document changes, the code runs in the user context already granted, and the persistence survives reboots because Office reloads it every session. The telemetry that makes it visible is registry modification monitoring for the Office add in and load behaviour keys, file creation events in the user and machine Office start up folders, newly written template files such as the normal template, and process creation showing the Office binary loading an unexpected module. In practice it fails because administrators deploy legitimate add ins and templates constantly, so the rule needs an allow list of approved publisher paths before it can alert.

What you will practise

  • List the Office persistence locations this strategy covers, including add ins, templates, Outlook rules and registry hooks.
  • Name the telemetry sources that show registry and file changes in Office locations.
  • Explain why Office based persistence survives reboots without a scheduled task.
  • Build an allow list of approved add ins by publisher and file path.
  • Describe how to validate an alert against change management records.
