TA0002 Execution

TA0002EnterpriseExtremeTactic

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Execution is the step where an attacker actually runs code on a system they have reached. It turns access into action. They may use tools already installed on the machine, such as a scripting engine or a command prompt, instead of bringing their own program.

Why should you care?

Access alone does nothing. Attackers must run something to explore, steal data or hold systems hostage. The hard part for defenders is that normal staff and management tools run the same commands every day. A single odd command proves little. What matters is which program started it, on which machine, and what happened next.

How it works, in plain steps

  1. The attacker already has a foothold, such as a user account or a single compromised machine.
  2. They look for tools already present, because built-in tools rarely look suspicious to defenders.
  3. They start a script, a command prompt or a small program to carry out their next goal.
  4. They may set the system to run that code later, using a scheduled job or a service.
  5. Defenders see this as a chain of processes, where one program starts another.

Real-world example

Picture a kitchen in a restaurant. Being allowed inside does not cook a meal. The intruder must switch on the stove and use the pans. A clever intruder uses the restaurant's own equipment instead of carrying a portable cooker, because nobody stares at the house stove. A single person boiling water is normal. A person boiling water at three in the morning, in a closed kitchen, using the manager's keys, is worth a second look.

Key takeaways

  • Execution is running code, and it needs access before it can happen.
  • Built-in tools are popular because they blend into normal work.
  • Judge a command by its parent process, the host and what follows.

In more detail

Execution is the tactic that covers adversary attempts to run their own code or abuse legitimate command interpreters on a victim system, and it is the bridge between having access and actually doing something with it. Concrete behaviours include launching PowerShell, cmd.exe, Windows Script Host, bash or other interpreters, using scheduled tasks and service creation to trigger payloads, exploiting client applications so that a document or archive executes code, and abusing built-in administration utilities that are already trusted and signed. Defenders see this tactic in process creation telemetry, command line logging, script block logging, module and image load events, application whitelisting or WDAC events, and, depending on maturity, EDR behavioural detections rather than simple indicator matches. The central problem is that execution telemetry is enormously high volume and heavily polluted by legitimate administrative activity. Management tooling, software deployment, monitoring agents, and helpdesk automation all spawn the same interpreters and utilities that attackers prefer, often with long encoded parameters. Detection in isolation therefore fails: a single encoded PowerShell command is weak evidence, whereas the same command spawning from an Office process, on a server that never runs interactive scripts, minutes after a new service was created, is a defensible finding. Effective work on this tactic means establishing a clean baseline of what runs where, enriching process events with parent-child lineage and signer information, and then hunting deviations from that baseline rather than chasing individual suspicious commands.

What you will practise

  • Describe the range of execution behaviours, from interpreter abuse and script hosts to scheduled task and service-based triggering.
  • Interpret process lineage and signer information to separate normal administrative execution from adversary execution.
  • Explain what Windows and Linux logging must be enabled before execution telemetry is usable at all, and what is lost when it is not.
  • Build detection logic that uses parent-child relationships and host role baselines instead of unreliable single-command signatures.
  • Recognise living-off-the-land execution patterns and describe why they defeat naive blocklists.
  • Trace an execution alert through to the persistence or command-and-control behaviour that follows it.
