DET0016 Security Software Discovery Across Platforms

DET0016Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Security software discovery is when a program looks around a computer to find out which protection tools are installed. This detection watches for commands that list running programs, services or packages and then search for security product names. It catches an intruder taking stock of your defences.

Why should you care?

Before attackers change anything, they usually want to know what might stop them. Finding out which endpoint agent, logging tool or monitor is present tells them what to disable or avoid. This step is quiet and uses only built-in commands. If you can see it, you get an early warning before the damaging actions begin. It also tells you which accounts are poking at defences.

How it works, in plain steps

  1. A sensor records each new process, its full command line, its parent process and the account that started it.
  2. The rule matches commands that enumerate the system, such as process listing, service listing or installed package queries.
  3. It then looks in the same command line for names of security products, agents, drivers or monitoring vendors.
  4. A two part command often appears as a shell pipeline. So the rule also joins child processes to their shell parent.
  5. Events on the same host and account are grouped inside a short window. One discovery session then becomes one alert.
  6. The alert shows the command, the parent, the account and any later action by the same account for context.

Real-world example

Picture a burglar who walks past a row of houses and quietly notes which ones show an alarm company sign. They have not touched a single door. They are simply building a list of which houses are easier to enter. Security software discovery detection is the neighbour who notices someone reading every sign on the street.

Key takeaways

  • Finding protection tools is a preparation step, so it is worth alerting on even though it changes nothing.
  • The important context is the parent process and the account, not the command alone.
  • Inventory and scanning tools run similar commands, so plan your filters before you deploy.

In more detail

This strategy detects discovery of security software on victim hosts, mapped to ATT&CK technique T1518.001 Security Software Discovery, the reconnaissance step attackers use to learn which endpoint protection, logging agents and monitoring tools are present before they act. The detection is built on process creation telemetry enriched with command lines, because the reliable signal is an interpreter or shell listing running processes, installed services or package inventories and then filtering that output for vendor names, driver names or agent paths. On Linux the equivalents are process listing, service enumeration and package queries aimed at security agents; in cloud estates the same intent appears as API calls that enumerate security services in an account. Correlating the discovery command with its parent process and with what the same account does in the following minutes is what separates a curious administrator from an intruder mapping defences. The strategy fails most often because system inventory and vulnerability scanning agents run the same queries on a schedule, so unfiltered process listing rules drown analysts in routine noise.

What you will practise

  • Describe why attackers enumerate security software before acting on a host
  • Recognise shell and interpreter commands that list processes, services or packages for defence tooling
  • Correlate discovery commands with their parent process and account to judge intent
  • Explain how the same intent appears in cloud API calls that list security services
  • Build filters that keep scheduled inventory and vulnerability scanners out of the alert queue
