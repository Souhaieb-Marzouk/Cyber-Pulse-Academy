T1202 Indirect Command Execution

T1202StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This means an attacker uses a normal Windows tool to start a program for them. The tool acts like a middleman, so the usual command window never appears. Security settings that block the command window can be avoided this way. It is really hiding one program inside another.

Why should you care?

Many defences watch for the command window, known as cmd, or for script files. If those defences only look at the direct parent of a new program, they miss this. The middleman tool is signed by Microsoft, so it looks trustworthy. Attackers can therefore start their tools while staying under the usual alarms.

How it works, in plain steps

  1. The attacker chooses a legitimate tool that is able to start other programs as part of its normal job.
  2. Examples include forfiles, the compatibility assistant launcher and script hosting helpers.
  3. The tool is given arguments that name the program or command to run.
  4. The tool starts that program, so the direct parent is the tool and not the command window.
  5. Controls that block the command window or watch for script files may see nothing wrong.
  6. The program runs with the same rights as the tool, which may be higher than the user expected.

Real-world example

Imagine an airport queue where staff with a valid badge skip the main security line. A traveller borrows a badge and walks the staff route instead. Nothing is forced, the gate was never broken, and the guard at the main line sees only a normal day. The clue is a traveller entering through a door meant for staff.

Key takeaways

  • Always look at the parent process, because the direct parent shows who started the program.
  • A document reader or system tool that starts a shell is a strong warning sign.
  • Blocking the command window is not enough, since other tools can launch programs.

In more detail

Indirect command execution covers the use of legitimate utilities that launch other programs, so that the command line interpreter most commonly watched by defenders is never the parent process. Windows ships a number of these: forfiles can invoke a program for each item it matches, the Program Compatibility Assistant launcher can start an executable, Scriptrunner can host a script, and the Windows Subsystem for Linux components can run Linux commands from Windows. The OpenSSH client is another route, because its configuration options can cause it to run a local command when a connection is made. The attacker normally has a different goal than novelty: policy or endpoint controls that block or alert on the command interpreter, on scripting hosts, or on particular file extensions can be sidestepped by making a signed Microsoft binary do the launching, and the resulting process tree looks like administrative tooling. Analysts spot it by looking at the parent process, not the child: a document reader, an office application or a system utility spawning a shell, a scripting host or a remote access tool is unusual, and the utility's own arguments usually contain the payload path or command string. Process creation records such as Windows Security 4688 or Sysmon 1 capture that parent and child relationship.

What you will practise

  • Explain how a legitimate utility can launch a program without the command interpreter.
  • List examples of indirect execution routes, including forfiles and the compatibility assistant launcher.
  • Explain why parent and child process relationships are the key evidence for this technique.
  • Identify process creation telemetry, such as Windows Security 4688 or Sysmon 1, that captures the chain.
  • Describe why controls aimed only at the command interpreter are incomplete.
