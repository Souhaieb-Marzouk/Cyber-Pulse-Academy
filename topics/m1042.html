M1042 Disable or Remove Feature or Program

M1042Enterprise MitigationVery hardMitigation

Disable or remove feature or program is the reduction of attack surface by eliminating software, protocols, services, and interpreter features that the business does not need. It is the least glamorous control and consistently one of the most effective, because every removed component is a class of vulnerability, a persistence location, and an execution path the adversary can no longer use. In real environments it is implemented as a hardening baseline applied through configuration management: removing or blocking legacy scripting hosts and command-line download utilities where they are not required, disabling macro execution from internet-sourced documents, turning off deprecated authentication protocols and unauthenticated file sharing versions, uninstalling unused agents and management tools that carry their own privileged services, removing sample applications and default accounts from internet-facing systems, disabling unnecessary remote access features and file-transfer endpoints, and pruning optional operating system capabilities and kernel modules on servers. The control is powerful because it works before detection matters: the technique fails outright rather than generating an alert that someone must triage. It addresses user execution through document and script features, abuse of command and scripting interpreters, exploitation of public-facing applications that would not exist in a minimal build, and remote services that only function because an unnecessary protocol is enabled. It also removes the defence-impairment surface, since tooling that is not installed cannot be tampered with. The honest limitations are organisational. Nobody wants to be the team that broke a business process, so removal requests are contested, and the knowledge of who depends on a legacy component is usually incomplete. Applications are frequently reinstalled silently by a vendor update, a configuration baseline that is applied once drifts back within a quarter, and the hardened image is rarely the one used for the emergency build during an incident. Failure modes include disabling a feature only on workstations while servers keep it enabled, relying on a registry setting that a per-application local override can bypass, forgetting the disaster recovery and test environments, and removing a component with no inventory record so that no one can tell whether it came back.

What you will practise

  • Explain how to build a hardening baseline from an accurate software, protocol, and service inventory.
  • Identify the interpreter features, legacy protocols, and default components that most reliably reward removal.
  • Describe how configuration management and compliance scanning keep a hardened baseline from drifting back to default.
  • Explain how disabling an unnecessary feature changes detection requirements by removing an execution path entirely.
  • Describe how per-application overrides and vendor updates can silently re-enable a component that was disabled.
  • Explain why test, disaster recovery, and emergency build environments must receive the same baseline as production.
  • Evaluate a proposed removal against business dependency, rollback options, and residual risk, and document the decision.
