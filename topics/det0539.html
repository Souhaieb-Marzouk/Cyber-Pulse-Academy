DET0539 Detection Strategy for Cloud Application Integration

DET0539Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for a new application being connected to your cloud environment. Such an application receives a token, which is a key that lets it act inside your tenant. Attackers use this to keep access even after a password change.

Why should you care?

Cloud tenants trust applications that users approve. A token can read mail, files or directory data and it does not need a password again. Because an administrator did not create the application, nobody is watching it. This is a quiet way to stay inside a company for a long time.

How it works, in plain steps

  1. The cloud provider writes an audit record when an application is registered or when a user grants it consent.
  2. The record names the application, its publisher, the permissions requested and the user who approved it.
  3. An inventory service lists every application and token that already exists in the tenant.
  4. The platform compares each new grant with that inventory and with the approved integration list.
  5. The rule flags grants with high risk permissions, unusual publishers, or users who never approve applications.
  6. An alert shows the application, the permissions and the account that consented.

Real-world example

Think of a visitor who is given a spare office key. Once the key is cut, changing the front door code does not take the key back. Someone must find the key and remove it. An application token that a user approved is that spare key.

Key takeaways

  • An application token is durable access, and a password reset does not revoke it.
  • Review who can grant consent, not only who can sign in.
  • Inventory your tenant applications, because detection needs a baseline to compare against.

In more detail

This detection strategy covers abuse of cloud application integration, matching technique T1671, where an adversary connects an external application to a cloud tenant so that it receives a durable token and can act as a trusted first party. It matters because the resulting access survives a password reset, often bypasses multi factor authentication, and appears in logs as a legitimate integrated application rather than as a suspicious login. The telemetry that makes it possible is cloud audit records for consent grants, application registrations, service principal creation, role assignment and refresh token issuance, joined with the inventory of applications the tenant actually sanctioned. It fails in practice because business teams add approved integrations through the very same consent flow, so the detection must weigh the requesting user, the tenant of the application and the permissions requested rather than the event type alone.

What you will practise

  • Explain what cloud application integration is and why a consent grant creates persistent access
  • Identify the audit records for consent grants, application registration, service principal creation and token issuance
  • Interpret requested permissions and application publisher data to judge the risk of a grant
  • Correlate a new application with the tenant inventory and the user who approved it
  • Write a detection rule for risky consent grants and tune it against sanctioned integrations
