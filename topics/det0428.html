DET0428 Detection Strategy for Bind Mounts on Linux

DET0428Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for a Linux feature called a bind mount. A bind mount shows a folder in a second place without copying it. The rule reports when a host folder is attached into a container or another restricted space.

Why should you care?

Containers are meant to keep programs apart from the host machine. A bind mount can remove that separation in one command. Attackers use it to read host files or to escape a container. Administrators also use it in a planned way, so the source path matters. That is how you tell the two apart.

How it works, in plain steps

  1. A process asks the Linux kernel for a mount operation with the bind flag set.
  2. The kernel records the call in the audit log with the source and target paths.
  3. Container runtime logs record mounts added to a running container or to a new one.
  4. The rule filters out the standard container runtime library and image directories.
  5. It keeps mounts whose source is a host root, host device or credential directory.
  6. A remaining event becomes an alert that names the container, the source path and the user.

Real-world example

Think of a secure office where staff work in glass rooms. Each room has its own desk and its own files. A bind mount is like putting a doorway from a room straight into the records vault. The doorway is legal to build and uses no force. The building plan simply shows a new opening where none should be, and that is what the security team reviews.

Key takeaways

  • A bind mount can expose host files to a container without any exploit.
  • Judge the mount by its source path and by which context asked for it.
  • Container runtimes make many benign mounts, so a baseline is essential.

In more detail

This strategy detects mount operations on Linux that bind a path from one place in the file system into another, which an adversary uses to make host files, container images or restricted directories reachable from inside a confined process or container. It matters because a bind mount is a supported administration feature, so it needs no exploit, yet it can hand a low privileged context a view of the host root directory, of credentials, or of another container file system. Detection relies on kernel audit records for the mount system call, container runtime events for new mounts inside a pod or container, and command history or process telemetry showing the mount command and its arguments. The main way it fails in practice is that container runtimes, orchestrators and monitoring agents create bind mounts constantly, so the rule has to key on the source path and the requesting context rather than on the mount event.

What you will practise

  • Explain what a bind mount does and why it can weaken container isolation.
  • Identify the audit and container runtime fields that record a mount operation and its arguments.
  • Distinguish routine runtime mounts from mounts whose source is a host root or device.
  • Correlate a mount event with the container, the namespace and the requesting process.
  • Recognise mount sequences that precede credential access or container escape behaviour.
  • Describe the visibility lost when audit rules for the mount system call are not deployed.
