DET0201 Detection Strategy for Hijack Execution Flow for DLLs

DET0201Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for a fake library file placed near a trusted program. A library file holds code that a program uses while it runs. Windows loads the first matching file it finds in a fixed list of folders. An attacker puts a bad file early in that list. The rule watches new files and the paths a program really loads.

Why should you care?

The program that loads the bad library is genuine and signed. Security tools that check only the program name see nothing wrong. The malicious code then runs with the trust of that program. This often survives a reboot and can slip past application control lists. You need file telemetry and load telemetry together to see it.

How it works, in plain steps

  1. The endpoint agent records file creation events with the full folder path.
  2. It also records image load events, which name every module that a process uses.
  3. The detection keeps a list of library names that trusted programs commonly request.
  4. It flags a new file in a folder that is searched before the proper install folder.
  5. It confirms the finding when the trusted program loads that newly created file.
  6. Signed libraries that match a vendor install path are filtered by signature and location.

Real-world example

Imagine a hospital sign in sheet with a strict rule. Staff members sign in, then take the key for the ward they need. If two people share the same name, the first one on the list receives the key. A clever visitor writes his own name at the top of the sheet under a staff member's name. The clerk hands him the key without a second look. Library hijacking is that trick. The program asks for a name, and the attacker's file answers first.

Key takeaways

  • The trusted program is not the suspect; the loaded file path is.
  • A new library in an early search folder is the key signal.
  • Signature and path checks remove most of the noise.

In more detail

This strategy detects the planting of a dynamic link library so that a trusted program loads attacker code, covering T1574.001 DLL Search Order Hijacking. The technique matters because the loading program is a signed, expected binary, so process creation records look clean and the only visible signal is which file on disk satisfied the import. The telemetry that makes it detectable is file creation in directories that are searched before the legitimate library location, combined with image load events that record the full path of every module a process maps. The usual failure is noise: many applications ship their own libraries beside their executable, so the rule must compare the loaded path against the expected path for that specific binary instead of alerting on any write into a program directory.

What you will practise

  • Describe how the Windows library search order can be abused by a planted file.
  • Correlate file creation events with image load events on the same host.
  • Identify directories that are searched before a program's own install folder.
  • Use signature and path checks to separate vendor libraries from planted ones.
  • Explain why application control does not always stop this technique.
