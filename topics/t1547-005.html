T1547.005 Boot or Logon Autostart Execution: Security Support Provider

T1547.005PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A security support provider is a small program that Windows uses for a type of sign-in, such as passwords or smart cards. Windows loads these programs into a protected process called the Local Security Authority at startup. An attacker can add their own program to that list so it also loads.

Why should you care?

The process that loads these programs handles your passwords while you type them. A malicious program inside that process can read them. It also starts again at every boot, so the attacker keeps access. This makes it one of the most serious changes to spot on a Windows computer. If you miss it, both the account secrets and the foothold stay with the attacker.

How it works, in plain steps

  1. Windows keeps a list of security packages in two registry values under the Local Security Authority settings.
  2. At startup the Local Security Authority reads the list and loads each named library into its own process.
  3. An attacker adds a new package name to the list and places the matching library on the disk.
  4. After the next restart, that library runs inside the same process that checks passwords.
  5. A program can also ask the system to load the package straight away, without waiting for a restart.
  6. Detection compares the list with a known baseline and checks which libraries are loaded in that process.

Real-world example

Imagine a bank vault where the door only opens for approved security firms. The approved firms are written on a list in the manager's office. An attacker adds a fake firm name to the list and gives the night guard a uniform with that name. The guard opens the vault for the fake firm, and the firm can copy whatever it likes while standing inside.

Key takeaways

  • Only expected, signed security packages belong in this list, so any new entry is worth a close look.
  • Prefer monitoring the registry values and the libraries loaded in the security process, not just files on disk.
  • Do not reboot a suspect machine without capturing evidence first, because a restart loads the malicious package.

In more detail

Security Support Provider abuse loads an adversary-supplied library into the Local Security Authority Subsystem Service at boot, giving durable execution inside the process that holds authentication secrets. Windows keeps the list of providers in the Security Packages and OSConfig Security Packages registry values under the LSA control key. Adding a name and dropping the matching DLL where the loader can find it causes the library to be mapped into lsass.exe on the next start, and the AddSecurityPackage interface can trigger loading without a reboot. Code inside that process sees credentials as they are handled, including domain passwords and smart card PINs, so this is simultaneously a persistence and a credential access technique. Defenders detect it by baselining those registry values, by inspecting which modules are loaded into lsass.exe, and by correlating registry writes and file drops in system directories with subsequent LSA activity; signed, expected libraries are the only ones that belong there.

What you will practise

  • Explain what a security support provider is and why Windows loads these libraries into one protected process.
  • Identify the registry values that list security packages and explain when they are read.
  • Describe how the AddSecurityPackage interface can load a package without a reboot.
  • Detect unauthorized package registration using registry monitoring and loaded module inspection.
  • Explain why a library inside the security process can read credentials and how to limit that risk.
  • Outline a response that captures evidence before the next restart reloads the malicious package.
