DET0537 Behavioral detection for Supply Chain Compromise (package/update tamper → install → first-run)

DET0537Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for tampering with software you already trust. It watches for a package or update file that changes, then gets installed, then starts something new. That chain is how a supply chain attack hides.

Why should you care?

You install updates to stay safe, so you allow them to run without much thought. If an attacker changes an update before you receive it, your own installer becomes the delivery method. Nothing looks strange at the door, because the package carries the usual signature and the usual name.

How it works, in plain steps

  1. A file monitoring agent records the hash of every package and update file in the staging folders.
  2. When a hash changes, the agent reports the file path, the old hash, the new hash and the change time.
  3. The endpoint records the install process, its parent process and the full command line that ran.
  4. The endpoint also records the first child process that the newly installed software starts.
  5. The platform joins these three records by host and time window into one chain.
  6. A chain that shows a hash change, an install and an unexpected first run becomes one alert.

Real-world example

Think of a parcel delivery office. Every parcel is weighed and logged, and the driver trusts the label. If someone swaps the contents after the weighing but before the van leaves, the label still looks right. The only clue is that the parcel weight no longer matches the note. A changed package hash is that missing weight.

Key takeaways

  • A trusted signature proves who built a package, not what it contains now.
  • Join the file change, the install and the first run together before you decide.
  • A hash that changes outside a release window is the strongest single clue.

In more detail

This detection strategy follows the three stage shape of a software supply chain compromise, matching technique T1195: a trusted package or update is tampered with, the tampered artefact is installed by the normal mechanism, and something new runs for the first time on the endpoint. It matters because the installer is signed and expected, so reputation checks and user awareness both fail. The telemetry that makes it possible is file integrity monitoring over package caches and update staging directories, package manager and installer process creation records, and first run execution data correlated with the hash of the installed artefact. It fails in practice because software deployment is constant and legitimate, so the rule must lean on the correlation between a changed file hash and a first run child process rather than on any single installation event.

  • Distinguish an expected software release from a tampered artefact using hash baselines and release windows
  • Write a detection rule for the install and first run sequence and tune it against your deployment tooling
