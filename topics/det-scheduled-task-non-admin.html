Scheduled Task Created by Non-Admin

Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A scheduled task is an instruction Windows runs later, either once or on a repeating timetable. An administrative account is one with broad control over a computer. This detection flags tasks created by ordinary accounts. It also flags tasks set to run as a more powerful account than their creator.

Why should you care?

Tasks are a favourite way to stay on a machine, because they survive a restart. They also look like ordinary system behaviour. An attacker can register one quietly, then let Windows relaunch their program every hour or at each sign-in. Many organisations let normal users create tasks. This activity therefore sits inside allowed behaviour, so it needs its own alert.

How it works, in plain steps

  1. Windows writes an audit record whenever a new scheduled task is registered.
  2. That record names the task, the account that created it and the command the task will run.
  3. It also shows which account the task runs as, which may be more powerful than the creator.
  4. The detection compares the two accounts and checks whether the creator normally holds admin rights.
  5. It also looks at the target path, because files in user folders and temporary areas are common hiding places.
  6. High-risk tasks are correlated with what the task actually launched later, so running code can be traced.

Real-world example

Think of an apartment building where any tenant may leave a written instruction at the front desk. One tenant leaves a note for the maintenance crew. It asks them to unlock the manager's office at two in the morning. The crew is allowed to do it and the tenant is allowed to leave notes. Nothing about either action looks broken. Yet the combination is wrong, and the manager should ask why.

Key takeaways

  • Scheduled tasks are a durable way to stay on a machine across restarts.
  • Compare who created the task with the account it will run as.
  • Judge a task by its target path and command, not by its name.

In more detail

Scheduled task created by a non-administrative account detection identifies task registration activity where the creating account is an ordinary user or a service identity that has no legitimate business reason to establish persistence, autostart or system level execution on the host. The behaviour matters because scheduled tasks are one of the most reliable and least disruptive persistence mechanisms on Windows: they survive reboot, they can run under a privileged context through stored credentials, and they are frequently used for recurring beaconing, dropper staging and privilege escalation through writable task definitions. The telemetry required is process creation for the task scheduling utility along with its command line, scheduled task operational events recording task name, creating account, action to execute and the principal the task runs as, and process creation correlated to the task engine so that the executed child process can be attributed back to the task definition. The signal survives common evasion because registration is an unavoidable step: an operator may use the command line tool, a scripting interface, a management API or a signed binary proxy, but all of these result in a task definition written to the task store, and the resulting execution appears as a child of the task scheduling service. Attackers who avoid the task store by using alternative autostart locations still remove themselves from this detection's scope, which is why it belongs in a family of autostart detections rather than standing alone. The detection breaks down in practice because non-administrative users in many organisations legitimately create their own logon tasks, software installers register per-user update tasks constantly, and cloud connected productivity and collaboration clients rebuild their scheduled entries after every upgrade. Task names are also attacker-controlled, so name-based matching produces both false positives and false negatives. The workable approach is to score on the creating account's privilege relative to the task principal, the writability of the executable path referenced, and the relationship between task creation and surrounding process activity, rather than on the existence of the task alone.

What you will practise

  • Explain why the relationship between the creating account and the task principal matters more than the task name.
  • Query task registration telemetry to extract the executing path, the run-as principal and the trigger configuration.
  • Identify task definitions that reference user-writable directories, script interpreters or remote content.
  • Baseline legitimate per-user updater tasks from productivity and collaboration software in your environment.
  • Correlate task execution with the originating process tree to attribute running payloads back to the schedule.
  • Recommend hardening measures that restrict non-administrative task creation without breaking vendor updaters.
