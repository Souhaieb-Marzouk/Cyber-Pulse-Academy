Immutable Backup

Security ArchitectureHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An immutable backup is a copy of your data that nobody can change or delete for a set time. Even an administrator with the highest rights cannot remove it early. You can still read it and restore from it. The word immutable means unchangeable. It exists so that one very bad day does not destroy every copy of your data.

Why should you care?

Ransomware groups now look for backups first. If they can delete your copies, you must pay or lose the data. An immutable backup survives that attack, because the attacker cannot remove it in time. It also helps when an employee deletes important files by accident. The protected copy gives you a safe point to restore from. Without one, a single stolen administrator password can end the company.

How it works, in plain steps

  1. Backups are written to storage that accepts new data but never edits it.
  2. A retention rule locks each copy for a fixed number of days before release.
  3. The storage account stays separate, with different keys and a different team of administrators.
  4. Even a stolen backup administrator password cannot delete a locked copy early.
  5. Restores are tested on a schedule, because an untested backup is only a guess.
  6. Retention is set long enough to cover a slow and patient intrusion.

Real-world example

Think of a safety deposit box in a bank. You can add a letter, and the bank keeps it for a fixed term. During that term, not even the branch manager can open your box alone. Two keys are needed, and the rules are written down. If your house burns down, the letter is still safe at the bank. An immutable backup is that box for your data, kept far from the machine that produced it.

Key takeaways

  • Immutability must come from storage the attacker cannot administer.
  • Keep the backup account and its keys separate from production systems.
  • Restore from the locked copy on a schedule, or you do not know it works.

In more detail

An immutable backup is a copy of data that cannot be modified or deleted for a defined retention period, even by an identity that holds administrative rights over the source system. Immutability is enforced beneath the operating system, typically through object storage versioning combined with a retention lock or legal hold, through write-once read-many media, or through an append-only repository whose delete operations are denied by policy rather than by convention. It is normally paired with separation of duties, so the administrator who runs backups cannot shorten the retention window or remove the lock alone. The control exists because modern ransomware spends its early hours hunting backups and recovery infrastructure before encrypting production, which turns backup integrity into the difference between a restore and a ransom payment. The mistake is configuring immutability on the backup server's own file system, where the same compromised account can simply turn it off, and never rehearsing a restore from the locked copy. An untested immutable backup is only a hope with a retention date.

What you will practise

  • Explain what an immutable backup is and which threat it is designed to defeat.
  • Describe how object lock, versioning and write-once media enforce immutability.
  • Explain why separation of duties matters on the backup platform itself.
  • Choose a retention period that covers a realistic intrusion and recovery timeline.
  • Plan and document a restore test that uses the immutable copy.
