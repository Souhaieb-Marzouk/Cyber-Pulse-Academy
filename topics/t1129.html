T1129 Shared Modules

T1129ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A shared module is a file of ready made code that programs load when they need it. On Windows these files are called dynamic link libraries. On Linux or macOS they are called shared objects or dynamic libraries. Programs can load extra code at run time, and they do this all the time.

Why should you care?

Malware can be split into modules, so one part handles network traffic and another part handles files. Loading a module is a normal action, so it does not stand out in a log on its own. If a program loads a module from an unexpected folder, the attacker's code runs inside a trusted process. A module can also be loaded from a network path, so the payload never sits on the disk.

How it works, in plain steps

  1. The attacker places a shared module file on the system, or on a network share they can reach.
  2. Malware or a script calls the loading function, such as LoadLibrary on Windows.
  3. On Linux and macOS the same is done with dlopen, and single functions are found with dlsym.
  4. The loader reads the file and maps its code into the memory of the running process.
  5. On Windows the loader can be given a local path or a network path. The file may therefore never be stored on the disk.
  6. Malware often splits its features across several modules, such as communication, collection and execution.

Real-world example

Imagine a workshop where every bench can borrow a toolbox from the store room. Nobody inspects the toolbox closely, because borrowing is completely normal. If somebody swaps a toolbox for one with a hidden drawer, the swap is invisible. Every bench that borrows it gets the hidden drawer too. The store room log only shows that a toolbox was borrowed.

Key takeaways

  • Module loading is normal behaviour, so detection depends on the file and its path.
  • Unsigned modules loaded from temporary or user folders are a strong signal.
  • Malware may split its features across modules, so one file is not the whole picture.

In more detail

Shared modules are reusable executable libraries that a process loads at run time: dynamic link libraries on Windows, and shared objects or dynamic libraries on Linux and macOS. The technique covers the use of that loading mechanism to bring attacker code into a process, either to add functionality to malware or to have a legitimate process load a library the adversary supplied. The loader accepts a path, and on Windows that path may be a local directory or a Universal Naming Convention network path, so a module can be fetched over the network rather than written locally. The evidence is a load event rather than a file creation: module load telemetry, image load records, and a library appearing in a directory the loading process should not use. Legitimate software loads modules constantly, so the discriminators are the path, the signature, and whether the loading process normally depends on that library.

What you will practise

  • Define shared modules and name the file types used on Windows, Linux and macOS.
  • Explain how a process loads a module at run time.
  • Describe how a module can be loaded from a local path or a network path.
  • Identify load telemetry that records module use inside a process.
  • Explain why modular malware is harder to analyse than a single file.
