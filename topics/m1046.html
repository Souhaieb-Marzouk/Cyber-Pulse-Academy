M1046 Boot Integrity

M1046Enterprise MitigationVery hardMitigation

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Boot integrity checks the first programs that run when you switch on a computer. It makes sure nobody changed the firmware, the bootloader or the start of the operating system. Each step checks the next one before handing over control. If a check fails, the machine stops or warns you instead of starting quietly.

Why should you care?

Software that runs before the operating system can hide from normal security tools. An attacker who changes the boot process can keep control even after you reinstall the system. Boot integrity breaks that chain by refusing to start a changed component. It also protects disk encryption, because the key is released only when the boot looks correct. Ignoring it leaves a blind spot that is very hard to clean up later.

How it works, in plain steps

  1. Firmware stored in a chip checks its own signature before it starts the machine.
  2. It then verifies the bootloader, the small program that loads the operating system.
  3. Each stage measures the next one and records the result in a hardware chip.
  4. A hardware root of trust, usually a trusted platform module, holds those records.
  5. Disk encryption releases its key only when the measurements match what you expect.
  6. A management server can ask the machine to prove its boot state, called attestation.

Real-world example

Picture a hospital pharmacy that hands out a strong medicine in three steps. The night pharmacist checks the doctor's signature, then signs the cabinet log, then gives the tray to the ward nurse, who checks it again. Nobody can quietly swap the tray in the corridor, because every handover is recorded and verified. If one signature is missing, the medicine stays locked away. Boot integrity is that same chain of checks, moving control from firmware to bootloader to operating system. A broken link stops the process instead of hiding the problem.

Key takeaways

  • Trust must start in hardware, because software can be changed before it runs.
  • Secure boot blocks tampering, while measured boot records what happened.
  • Leaving firmware unlocked or secure boot switched off removes most of the benefit.

In more detail

Boot integrity builds a chain of trust from hardware up to the running operating system. Firmware validates the signature of the bootloader, the bootloader validates the next stage, and each stage measures or verifies the one after it, so a modified component stops the chain instead of loading quietly. Implementations combine a hardware root of trust, secure boot, measured boot, disk encryption bound to those measurements, and remote attestation where a machine reports its boot state to a management service. Operators see it in firmware settings and enrolled keys, in event logs held by the trusted platform module, in attestation reports, and in alerts or recovery prompts that follow an unexpected firmware change. The control fails when firmware is left unlocked, when secure boot is disabled for convenience, when signing keys are not maintained, and when a disk encryption key can be released without a valid measurement.
