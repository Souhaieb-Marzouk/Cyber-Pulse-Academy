T1222.002 File and Directory Permissions Modification: Linux and Mac Permissions

T1222.002Defense ImpairmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Linux and Mac computers describe file access with three groups: the owner of the file, the owner's group, and everyone else. Each group has read, write and run rights. Two common commands change these settings: one changes who owns the file, and the other changes what each group may do.

Why should you care?

These commands are used in normal administration and by software installers, so their presence is not proof of anything wrong. They are also quick and quiet, and on many systems nothing records them by default. An attacker can become the owner of a startup file, make a script runnable, or take away the rights that would let you repair the file later. This is the Unix version of the wider permission technique, and the main difference lies in the commands and the ownership model.

How it works, in plain steps

  1. The attacker finds a file they need to change but do not own and cannot write to.
  2. They check the current owner, group and rights with a command that lists file details.
  3. If their account has the privilege, they change the file's owner to themselves or to a service account.
  4. They run a second command to add write or run rights, or to remove rights from other accounts.
  5. They then modify the file, for example a shell startup file or a program that runs at boot.
  6. A recursive option lets them apply the same change to an entire directory tree in one command.

Real-world example

Think of a shared flat kitchen where each cupboard has a small card naming who keeps the key. Anyone can read the card, and the key is handed out according to it. A resident swaps the card on a neighbour's cupboard for one with their own name on it. Then they change the note that says which items in the fridge are for everyone. No lock was forced. The label was rewritten and the kitchen rules did the rest.

Key takeaways

  • Ownership matters as much as permissions, because owners may change the rules.
  • Recursive ownership changes across a home directory are worth investigating.
  • Record process activity, because these commands leave little trace by default.

In more detail

On Linux and other Unix-like systems, including macOS, access is described by a compact model: each file has an owner, a group, and a set of rights for the owner, the group and everyone else, where those rights are read, write and execute. Extended access control lists can add finer entries on top of that model in supported filesystems, but the two everyday commands that change how access is decided are the one that changes ownership and the one that changes the mode bits and any extended list. This sub-technique is the Unix branch of permission modification, and its distinct characteristic is the small, auditable command surface combined with the fact that the change is silent unless some form of process or file accounting is already in place. An adversary uses it to take ownership of a configuration or startup file they intend to modify, to make a script executable so it can be launched directly, or to strip rights from other accounts so that the original owner can no longer read, correct or remove the file. Because these commands appear in ordinary administration, package installation and deployment scripts, detection has to weigh the target, the recursive scope and the effective user. The strongest signals are ownership changes applied across a directory tree, ownership or mode changes on files under a home directory that reference remote content, changes applied to files that execute at login, and a permission change followed closely by a write to the same path by the same process tree.

What you will practise

  • Explain the owner, group and other model used for file access on Linux and Mac systems.
  • Describe the difference between changing a file's owner and changing its access mode.
  • Explain why a recursive ownership change is a stronger warning sign than a single file change.
  • Compare this sub-technique with the platform-neutral parent technique.
  • Identify the logging or auditing sources that capture permission changes on Unix systems.
