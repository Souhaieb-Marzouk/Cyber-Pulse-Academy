Terraform Drift

Cloud SecurityVery hardKeyword

Terraform drift is the divergence between the infrastructure state recorded in a Terraform state file and the actual configuration of the resources deployed in a cloud account, arising when something changes a resource outside the pipeline that created it. The change might be a console fix during an incident, a script in a legacy automation path, a provider-side default that shifted, an imported resource never brought under management, or an attacker deliberately relaxing a control such as a firewall rule or bucket policy. Drift matters because the infrastructure-as-code repository stops being a trustworthy description of reality: a plan run after drift will silently revert the out-of-band change, reviews of pull requests no longer describe the live environment, and a security control that appears present in code may have been removed in production. Detection normally relies on scheduled plans or a refresh-only plan that reports differences without applying them, remote state with locking to prevent concurrent writes, and consistent provider versions so that cosmetic differences do not obscure real ones. Handling drift requires judgement rather than blind application, because some drift is legitimate emergency remediation that should be codified back into the repository, while unreviewed drift in security-relevant attributes is an incident indicator. Mature teams track drift as a metric, alert on changes to sensitive attributes, and reconcile by importing or amending code rather than by overwriting production.

What you will practise

  • You will be able to explain how state, configuration files and live resources can diverge and why that breaks review assumptions.
  • You will be able to interpret a refresh-only plan and separate meaningful drift from cosmetic provider differences.
  • You will be able to triage unreviewed changes to security-relevant attributes as potential malicious activity.
  • You will be able to reconcile drift by importing or amending code instead of overwriting production state.
  • You will be able to describe how remote state, locking and pinned provider versions reduce false drift signals.
  • You will be able to design a drift detection cadence and reporting path for a platform team.
