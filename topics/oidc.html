OpenID Connect

Identity & AccessVery hardKeyword

OpenID Connect (OIDC) is an identity layer built on top of OAuth 2.0 that gives clients a standardised way to verify a user's identity and obtain basic profile information. It adds an identity token, a JSON Web Token whose claims describe the authentication event and the subject, and it standardises discovery through a well-known configuration document, key distribution through a JSON Web Key Set, and user information retrieval through a dedicated endpoint. Because the identity token is signed and carries claims such as issuer, audience, subject, issue time and expiry, a relying party can validate it locally without a per-request round trip to the provider, provided it verifies the signature against the published keys, checks that the issuer and audience match its own registration, enforces nonce and expiry, and refuses to accept a token signed with an algorithm it did not expect. Failures cluster in exactly those checks: accepting a token with an unexpected signing algorithm, skipping audience validation so a token minted for a different application is accepted, trusting unverified claims taken from an access token rather than the identity token, and mixing up access tokens and identity tokens in ways that lead to privilege confusion. Hybrid flows, front-channel logout, and the handling of long-lived refresh tokens each introduce their own edge cases. Operational attention belongs on key rollover in the JSON Web Key Set, because a relying party that caches keys indefinitely will fail closed or, worse, fail open depending on its error handling.

What you will practise

  • You will be able to distinguish identity tokens from access tokens and explain which claims may be relied on for each purpose.
  • You will be able to describe the mandatory validation steps a relying party must perform on an identity token.
  • You will be able to explain how discovery documents and JSON Web Key Sets are consumed and why key caching matters.
  • You will be able to identify weak configurations such as missing nonce checks, unverified issuers and over-permissive redirect URIs.
  • You will be able to troubleshoot sign-in failures using identity provider logs and token claims side by side.
  • You will be able to evaluate front-channel and back-channel logout options for session termination requirements.
