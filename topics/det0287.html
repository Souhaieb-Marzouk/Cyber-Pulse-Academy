DET0287 Exploitation for Client Execution – cross-platform behavior chain (browser/Office/3rd-party apps)

DET0287Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A client program is software you use directly, such as a web browser or a word processor. An attacker can craft a document or a web page that makes that program run their own code. This kind of attack is called client exploitation. This detection watches the signs that follow, because the flaw itself is never written to a log file.

Why should you care?

The user only has to open a file or visit a page, and no password is needed at all. The vulnerable program is usually trusted, so policy already allows it to run. Patching helps, but a new flaw can be abused before the patch reaches every machine. Watching the behaviour right after the file opens is often your only chance to catch it.

How it works, in plain steps

  1. The endpoint sensor records process creation, including the parent program and the new child program.
  2. The rule keeps the events where the parent is a browser, an office program, or a document reader.
  3. It checks whether the child is a program the parent never starts. A shell or a script engine is a good example.
  4. Image load records show which modules loaded into the parent, and whether those modules carry a valid signature.
  5. An application error record for the same process within seconds adds weight to the alert.
  6. The analyst then finds the file that was open just before, and where that file came from.

Real-world example

Picture a mailroom where a machine opens letters. Most letters are ordinary, and the machine handles them all day without trouble. One day a letter makes the machine fall over. A person climbs out of the machine instead of a letter. You would not blame the machine or its operator. You would look closely at the letter, and at the person who appeared.

Key takeaways

  • The exploitation step is invisible, so detection focuses on what happens immediately after it.
  • Parent and child process pairs are the strongest signal, and they must match your baseline.
  • Keep the document or page that was open, because it is your best evidence for response.

In more detail

This strategy detects exploitation of a client application such as a browser, an office suite, or a document reader, where a crafted file or page causes the trusted application to run attacker code. The exploitation step itself is usually a memory corruption event that no log records directly, so detection works from the consequences: a child process the application should never create, an unsigned module loaded into it, a crash or error report, and a file written to a temporary directory seconds later. The enabling telemetry is process creation with parent image and command line, image load records with signature status, and application error reporting. The strategy fails because office and browser products do start helper processes legitimately, so the rule must be precise about which parent and child pairs are actually expected in your environment.

What you will practise

  • Explain why client side exploitation is rarely visible directly in logs.
  • Identify parent and child process combinations that point to a compromised client program.
  • Use image load and signature records to spot injected or unsigned modules.
  • Correlate application error reports with process activity inside a short window.
  • Preserve the source document or page as evidence during triage.
