DET0076 Behavioral Detection of Visual Basic Execution (VBS/VBA/VBScript)

DET0076Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Visual Basic is a simple language built into Windows. Files written in it end with names such as vbs or vba. This detection looks for those scripts being run. It pays extra attention to which program started them and where the file came from.

Why should you care?

The program that runs these scripts is on every Windows computer already. The system trusts it, so it is not treated as new software. An attacker can use it instead of bringing their own tool. Scripts can also hide inside ordinary documents, which users open every day.

How it works, in plain steps

  1. A host sensor records each new process, its parent process and the full command line.
  2. The detection notes when that program is a Visual Basic script host or an Office program.
  3. It checks the parent of the script host. A document reader rarely starts a script.
  4. It records where the script file sits. Temporary and download folders are unusual places.
  5. Network and file events after the start show what the script did.
  6. Known automation accounts and approved script folders are moved to a quiet lane.

Real-world example

Think of a building with a standard key that opens the front door. Every staff member carries one, so nobody questions seeing it. A visitor borrows that key and opens a side room. The visitor leaves a note for the next visitor. The key was never suspicious. The question that matters is why a visitor held it.

Key takeaways

  • A trusted built in interpreter is attractive because it never looks like new software.
  • Check the parent process and the script location, not just the interpreter name.
  • List the scripts your business really runs, or every alert will look the same.

In more detail

This detection strategy covers execution through the Visual Basic family of interpreters, which includes the standalone Windows script hosts and the scripting engine embedded in Office documents. It matters because the interpreter is a signed, trusted component that is already installed everywhere, so running code through it avoids dropping an unfamiliar binary and often bypasses controls that only allow signed programs. The telemetry that makes it visible is process creation with full command lines and parent lineage, script engine events that identify the script file, and the file and network activity the interpreter produces in the seconds after it starts. The strongest pattern is a scripting engine whose parent is a document reader, a browser or a mail client, or a script launched from a temporary or user writable directory with an obfuscated argument list. It fails in practice for a mundane reason: Visual Basic scripts run constantly for real business tasks such as logon mappings, software packaging and internal automation, so parent lineage and file location carry far more signal than the interpreter name does.

What you will practise

  • Explain why interpreter based execution avoids many binary focused controls.
  • Identify the parent child relationships that separate document driven script execution from administration.
  • Evaluate script file location and command line obfuscation as risk factors.
  • Correlate the interpreter process with the file and network activity that follows it.
  • Build an allow list of approved automation scripts and accounts to reduce noise.
