DET0435 Detection Strategy for Hijack Execution Flow: Dynamic Linker Hijacking

DET0435Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for programs on Linux that are told to load an extra shared library before they start. A shared library is a file of reusable code that programs load at startup. The rule reports load requests that point at unusual files or folders.

Why should you care?

The extra library runs inside a trusted program and can read anything that program can read. It is a quiet way to watch or change behaviour without touching the original file. Common tools also use this feature, so context decides the verdict. The library location is often the clearest clue.

How it works, in plain steps

  1. A shell sets an environment variable that names a library to load first.
  2. The program starts and the system linker reads that variable before running the program.
  3. Endpoint monitoring records the process, its environment and the parent that set it.
  4. The rule checks whether the named library sits in a system or application directory.
  5. It also watches for writes to the system linker configuration file.
  6. A load request pointing at a temporary or home directory raises an alert.

Real-world example

Think of a delivery van that always carries its own toolbox. Before the driver starts work, a stranger swaps one standard tool for a copy that looks the same. The van, the route and the driver are unchanged. Only the tool is different, and that tool quietly copies every key it touches. Checking the toolbox is the point of this rule.

Key takeaways

  • Preloading a library inserts code into a trusted program before it runs.
  • The library path and the account that set the variable are the key details.
  • Legitimate instrumentation uses the same feature, so expect some noise.

In more detail

This strategy detects dynamic linker hijacking on Linux, where an adversary forces a process to load an attacker supplied shared library by setting the preload environment variable, by altering the library search path, or by writing to the system preload configuration file. It matters because the injected library runs inside a trusted program before its own code, so it can capture credentials, hide activity or persist without modifying the target binary. Detection depends on process telemetry that captures the environment of executed programs, kernel audit records for writes to the linker configuration, and file monitoring for new libraries in world writable locations. The main way it fails in practice is that packaging tools, container builds and some performance agents legitimately use preload for instrumentation, so the rule must weigh the library path, the writing account and the target binary.

What you will practise

  • Explain how the dynamic linker selects libraries and why preloading changes program behaviour.
  • Identify the environment variables and configuration files that influence library loading.
  • Correlate a preload value with the executed binary, its parent process and the owning account.
  • Separate approved instrumentation libraries from libraries in writable directories.
  • Detect writes to system linker configuration that would apply the hijack to every program.
  • Describe why static binaries and privileged programs resist this technique.
