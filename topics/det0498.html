DET0498 Behavior‑chain detection for T1134.003 Make and Impersonate Token (Windows)

DET0498Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

On Windows, a token is a small object that says who you are and what you may do. This detection looks for a program that copies another user token or makes a new one. It catches a process that starts acting as a more powerful user. The aim is to find privilege abuse on a single host.

Why should you care?

An attacker with a small foothold can copy a token from a powerful process. After that, the attacker acts as that user without knowing any password. Resetting passwords does not help, because no password was ever used. This move sits at the centre of many Windows intrusions, so it deserves an alert of its own.

How it works, in plain steps

  1. Windows records each logon and the token type it creates in the security log.
  2. The endpoint agent can record when one process opens another process with sensitive rights.
  3. The rule joins a process access event with a later process created under a new user.
  4. It compares the parent account with the child account and flags a change in privilege.
  5. It also checks whether the logon type fits the way that account normally works.
  6. The alert shows both accounts, the host and the command line of the new process.

Real-world example

Think of a staff canteen where each worker wears a colour coded badge. A visitor cannot buy lunch, because the till reads the badge first. Someone finds a spare badge in a coat pocket and copies its code onto a blank card. The till now accepts the card, and no password was ever needed. This detection watches for the copied badge, not for the lunch.

Key takeaways

  • Token theft needs no password, so a password reset does not stop it.
  • Correlate process access rights with a later process created as another user.
  • Learn which service accounts normally touch tokens on each server group.

In more detail

This strategy detects token creation and impersonation on Windows, where an adversary duplicates an existing access token or builds a new one so that a process can act as another user without knowing that user's password. The behaviour appears in process access events that request token related rights, in new processes created under a different user context than their parent, and in logon records that reuse a session identifier belonging to another account. Sysmon process access telemetry and Windows Security logon records supply the correlation points. It fails in practice because service accounts, backup software and remote management agents move tokens between processes by design, so the rule must learn which pairs are normal on each host group.

What you will practise

  • Explain what a Windows access token and an impersonation token are.
  • List the events that record logon type and token duplication activity.
  • Correlate process access events with child process creation records.
  • Recognise normal token use by backup and service accounts.
  • Write a pseudo-rule that flags a privilege change between parent and child.
