DET0101 Detection Strategy for Lua Scripting Abuse

DET0101Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection focuses on the Lua scripting language. Lua is a small programming language that other programs can build in to run extra instructions. The rule looks for Lua being used in places and ways that do not fit normal business work.

Why should you care?

An attacker who runs Lua code borrows the trust of whatever program hosts it. That could be a web server, a game client or a management tool with wide access. Because Lua is a normal part of those products, an allowlist often accepts it. A script is also small and easy to change, so it can hide in plain sight.

How it works, in plain steps

  1. The endpoint sensor records every new process, including the program name, its parent and its full command line.
  2. A rule checks each process for a known Lua interpreter name. Examples are lua, luajit and a product specific Lua host.
  3. It then looks at the parent process, meaning the program that started the interpreter, along with the working folder.
  4. It also watches file system events for new .lua files written in user folders, temporary folders or download folders.
  5. Network records show whether the interpreter process opened a session to an external address it does not normally use.
  6. An unusual parent, an odd script path and a new connection may line up. The rule then raises one alert with all three facts.

Real-world example

Think of a hospital where only nurses may give medicine. A cleaner is given a nurse's badge to deliver a parcel, then uses the badge to open the drug cabinet. The badge was real and the system saw a valid entry. This detection asks a simple extra question. Why was the cleaner using a nurse's badge at all, and why at this cabinet.

Key takeaways

  • Lua runs inside other products, so it inherits their permissions and their reputation.
  • Judge the parent process and the script location, not just the interpreter name.
  • A real interpreter reaching an unexpected external address deserves a fast look.

In more detail

This detection strategy targets T1059.011, command and scripting interpreter abuse through the Lua scripting language. Lua is a small, fast interpreter that is embedded in game clients, network appliances, web platforms, configuration management tools and penetration testing frameworks, so a Lua interpreter on a host or a Lua plugin directory is a normal and useful thing that an adversary can also use to run code with the trust of the parent application. Detection rests on process lineage, meaning which program started the Lua interpreter, the working directory and command line arguments, the paths where new script files appear, and outbound connections made by an interpreter process that has no business talking to the internet. It fails in practice because so much legitimate software embeds or ships a Lua engine, so the rule must be anchored to unexpected parents, user writable script locations and behavioural context instead of the presence of the interpreter alone.

What you will practise

  • Recall where Lua is commonly embedded so you can tell expected from unexpected use
  • Name the process, file and network telemetry needed to spot unusual Lua execution
  • Explain how parent process lineage separates a product plugin from a user launched script
  • Identify the script file paths that should never hold production Lua code
  • Describe how to profile a Lua host so you know its normal network destinations
  • Build a filter that keeps product runtimes quiet without hiding attacker scripts
