DET0278 Detection Strategy for T1542 Pre-OS Boot

DET0278Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches the parts of a computer that start before the operating system. It covers boot settings, the small program that loads the system, and the firmware built into the hardware. Attackers change these to hide from security tools and to survive a rebuild.

Why should you care?

Anything that runs before the operating system can switch off your defences first. It can also survive a full reinstall, which makes cleanup far harder. Most organisations collect almost no information about this layer, so incidents stay hidden. Building even a simple record of boot and firmware settings gives you a baseline to check. A change with no work order is a serious signal.

How it works, in plain steps

  1. Managed computers report boot and firmware measurements to a central service at start up.
  2. The detection stores those values as a baseline per hardware model and operating system version.
  3. It watches for changes to boot configuration made by command line tools, such as edits that disable integrity checks.
  4. It checks whether secure boot and other start up protections are still switched on.
  5. It uses file integrity monitoring on the boot partition to catch new or altered boot files.
  6. Any change without a matching hardware maintenance record is sent to the analyst with the old and new values.

Real-world example

Think of a warehouse where the night shift loads the shelves before the day staff arrive. The day staff trust whatever is already on the shelves. If someone changes the loading schedule and the goods, the day staff inherit a problem they never saw happen. Pre-boot code is that night shift.

Key takeaways

  • Pre-boot changes can outlive an operating system reinstall, so detection matters more than repair.
  • Record a known good baseline of boot and firmware values per hardware model, or you cannot spot drift.
  • Absent telemetry is the real problem here, so first make the fleet report its boot state at all.

In more detail

This strategy detects modification of the components that run before the operating system loads, including boot configuration data, boot loaders and platform firmware. T1542 matters because code placed at this layer executes before most security controls, survives operating system reinstallation, and can disable protections before they start. Detection is inherently difficult: firmware and boot configuration rarely expose rich telemetry, so the practical approach is trusted platform module measurement logs, boot configuration inventory from signed system tools, secure boot state reporting, and file integrity monitoring of boot partitions. The usual failure mode is not false positives but absent data, since many fleets report nothing about firmware or boot state at all, leaving the rule blind rather than noisy.

What you will practise

  • Describe the components that execute before the operating system and why they matter for detection.
  • Collect and interpret boot measurement logs and secure boot state reports from managed endpoints.
  • Identify suspicious edits to boot configuration, particularly changes that relax integrity or recovery settings.
  • Build a per model baseline of firmware and boot values and monitor for drift.
  • Explain why remediation of a pre-boot compromise may require firmware reflash or hardware replacement.
