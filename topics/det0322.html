DET0322 Detection Strategy for Junk Code Obfuscation with Suspicious Execution Patterns

DET0322Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Junk code means extra instructions that do nothing useful, added to a program to change its appearance. The program still works, but a signature that once matched it no longer does. This detection looks for the side effects of running code that wastes effort on purpose.

Why should you care?

Attackers change code to avoid file based signatures and reputation checks. Each change costs them effort, and that effort shows up on the endpoint as unusual resource use. Watching behaviour instead of file names keeps your detection working when the file changes. It also gives analysts a reason to inspect a program that no scanner has flagged.

How it works, in plain steps

  1. A program starts and spends time decoding or checking its own instructions before doing anything else.
  2. During that period the processor is busy, but the program makes almost no network or file activity.
  3. The endpoint agent records the process start, its parent, its command line and the libraries it loads.
  4. Your platform adds resource metrics, such as processor time compared with how long the process has existed.
  5. The rule looks for a short lived process with high processor use and low output, started by an unusual parent.
  6. It then links that process to what it does next. Examples are a new program written to disk or a first connection out.

Real-world example

Think of a courier who wraps a small parcel in twenty layers of paper. The parcel looks different every time, so the door staff do not recognise it. The wrapping takes a long time and leaves a pile of paper in the hallway. The clue is the delay and the mess, not the label on the parcel.

Key takeaways

  • Obfuscation changes how a file looks, not what its code eventually does.
  • Processor time against process lifetime is a practical behaviour signal.
  • The strongest alert joins the busy period to what the process does immediately afterwards.

In more detail

This strategy detects the execution pattern produced by junk code obfuscation, mapped to the obfuscated files or information area and recorded in the assignment as t1027-016. Junk code adds meaningless instructions and dead branches so that the file no longer matches static signatures, but the price the attacker pays is measurable: the process burns processor time on work that produces no output, and its real behaviour appears only after that work completes. The telemetry that exposes it is a combination of processor time against process lifetime, thread creation volume, library loads and the first outbound connection after the delay. The known failure mode is that compiling, encrypting and archive tools look similar, so the rule must weigh the parent process and the resulting activity rather than the resource use alone.

What you will practise

  • Explain why junk code changes detectability without changing intent
  • Describe the endpoint behaviour that decoding or unpacking produces
  • Identify the process, thread and library events needed to build this detection
  • Correlate a resource heavy start with the process's next observable action
  • Filter compilers, archivers and installers that legitimately use high processor time
  • Decide when to combine this behavioural rule with static file analysis
