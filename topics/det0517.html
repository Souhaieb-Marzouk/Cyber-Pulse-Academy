DET0517 Detection Strategy for Hijack Execution Flow through the AppDomainManager on Windows.

DET0517Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This rule looks at a small settings file that many programs read when they start. That file can tell the program to load an extra piece of code first. An attacker can edit the file so their code runs before the real program does. The rule watches for changes to those settings files and for code loading from an unexpected folder.

Why should you care?

The extra code runs inside a program that users and security tools already trust. It also runs every time that program starts, so the attacker does not need to break in again. The change is small: one settings file or one registry entry. Small changes like this are easy to overlook unless you collect the right events.

How it works, in plain steps

  1. A file monitoring agent records every new or changed settings file, with its full path.
  2. The rule keeps files that sit next to an executable and end with the configuration file extension.
  3. It also watches the registry keys where the runtime setting for the loadable component is stored.
  4. A write that comes from a user folder, a temporary folder or an unsigned program scores higher.
  5. Image load records show which code file the program actually loaded and from which folder.
  6. A settings change followed by a start of the program that loads code outside the program folder is the alert.

Real-world example

Picture a hotel front desk with a card of emergency contacts. The card tells the night receptionist whose name to call first. A stranger rewrites the card so the receptionist calls the stranger first, every night. The card is small and easy to change, and nobody checks whether the name is right.

Key takeaways

  • A configuration file can decide which code runs before the real program.
  • The write is quiet, but the effect repeats on every start of that program.
  • Monitoring both the file and the registry form of this setting closes the easy gap.

In more detail

This detection strategy covers hijacking the execution flow of a .NET application through the AppDomainManager, the sub technique tracked as T1574.014. A .NET process reads an application configuration file or a user level registry setting at startup, and those settings can name an assembly that the runtime loads and initialises before the application own code runs, which gives an attacker reliable execution whenever the trusted program starts. The telemetry that makes it visible is file creation and modification events for application configuration files next to an executable, registry writes to the runtime configuration keys, image load records showing a managed assembly loading from an unexpected directory, and the parent child relationship between the process that writes the file and the process that starts later. The strategy fails in practice because configuration files and installation writes are everyday events on managed endpoints, so the rule only works when the assembly path or the writing process is unusual for the host.

What you will practise

  • Explain how a .NET application configuration file can direct the runtime to load extra code.
  • Identify the file creation and registry events that record this change on Windows.
  • Recognise which directories are legitimate homes for application assemblies.
  • Correlate a configuration write with the later start of the affected application.
  • Describe how to verify a suspicious assembly using its signer and hash rather than its name.
  • Plan a response that restores the original configuration file and rebuilds the host if needed.
