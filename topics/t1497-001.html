T1497.001 Virtualization/Sandbox Evasion: System Checks

T1497.001StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

System checks are a way for malware to inspect the computer it is running on. It looks for details that only appear in test systems, such as virtual hardware names or analysis tools. If the details look wrong, the malware stays silent or stops.

Why should you care?

These checks let a harmful file hide during automated analysis. A file that quits at once may look harmless and reach real computers untouched. When you do see the checks in logs, they look like normal administrative commands. That makes the warning easy to miss. Knowing this behaviour helps you judge whether a quiet test result can be trusted.

How it works, in plain steps

  1. The program queries hardware details such as processor count, memory size and disk capacity.
  2. It reads adapter addresses and looks for prefixes used by virtual network cards.
  3. It checks the registry and running services for entries added by virtualisation software.
  4. It looks for monitoring tools on disk, including common analysis and packet capture programs.
  5. It checks its own folder and file names for words like sample, malware or hash.
  6. If these clues suggest a test system, it exits without running its real payload.

Real-world example

Imagine a delivery driver who is told to check whether an address is a real home. The driver looks for a name on the door, a working bell, and a car in the drive. A place with bare walls and no signs of life is probably a film set. The driver then leaves the parcel outside and goes away. Malware does exactly this with hardware and registry details before it acts.

Key takeaways

  • This sub-technique reads machine properties, unlike the parent which also watches users.
  • Virtual hardware names, adapter prefixes and missing sensors are classic giveaways.
  • Several system queries from one new program in a few seconds deserve a look.

In more detail

System checks are the branch of sandbox evasion that inspects machine properties instead of human behaviour. The sample reads attributes that are cheap to query and strongly correlated with analysis platforms: manufacturer and product strings for virtualization software, registry keys and services installed by hypervisor tools, MAC address prefixes belonging to virtual adapters, processor core counts and memory sizes that are suspiciously round or small, missing physical hardware such as fans, temperature sensors, or audio devices, and file or directory names containing words like sample or malware. Collection is often scripted through Windows Management Instrumentation, PowerShell, system information utilities, or direct registry queries, and it frequently ends with the program terminating if the host looks virtual. Detection focuses on the queries themselves, which appear as short lived utilities spawned by an unusual parent or by a freshly written executable, sometimes several discovery commands within seconds of one another. The behaviour is hard to distinguish from legitimate inventory and management software, so the meaningful signal is the combination of a new, untrusted binary, virtualisation specific lookups, and imminent self termination. Instrumented analysis environments should expose realistic hardware strings and re-check samples that quit early.

What you will practise

  • Explain how this sub-technique differs from the parent evasion technique.
  • List the machine properties that malware commonly inspects for virtualisation clues.
  • Recognise the command line and registry telemetry these checks produce.
  • Explain why these queries resemble legitimate inventory and management tools.
  • Describe how an analysis environment can present realistic hardware details.
  • Assess the risk of treating an early exit during analysis as benign.
