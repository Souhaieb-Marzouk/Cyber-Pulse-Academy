DET0377 Detection of Kernel/User-Level Rootkit Behavior Across Platforms

DET0377Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A rootkit is software that hides other software. It can make a running malicious program invisible to the tools you normally use. This detection looks for the signs of hiding, such as unusual kernel code and changes in what the system reports. It also compares two different views of the same computer.

Why should you care?

If the intruder can hide, then every clean scan result is meaningless. Your response may also be watched, so your actions become visible to the attacker. Independent sensors are the only way to see through the hiding. Finding a rootkit early tells you to rebuild a machine instead of trusting it.

How it works, in plain steps

  1. Collect kernel module and driver load events, including the signature status of each one.
  2. Collect code integrity events that record a driver failing signature enforcement.
  3. Collect boot measurement values and compare them with a stored baseline for that host.
  4. Compare the list of running processes and open ports with an independent inventory source.
  5. Look for gaps or restarts in the event log pipeline on the same host at the same time.
  6. Alert with the loaded module path, its signature status, and the process that loaded it.

Real-world example

Imagine a hotel sign in sheet where a guest can erase their own line. The book still looks neat, and the manager sees nothing wrong. You only catch it by comparing the book with the door camera. The camera is your independent sensor.

Key takeaways

  • Never build rootkit detection only from the data the rootkit can edit.
  • An unsigned or unexpectedly patched kernel module is one of the few strong early signals.
  • A mismatch between two independent views is more convincing than either view alone.

In more detail

This strategy detects rootkit behaviour, where an adversary hides their presence by modifying the kernel, loading an unsigned driver, or intercepting system calls and hiding files, processes and network connections from ordinary tools. Reliable detection cannot come from the same view an attacker has tampered with, so it relies on independent sources: kernel module and driver load events, code integrity and signature enforcement failures, boot measurement values, cross view comparison between the operating system listing and an out of band inventory, and event log gaps that suggest tampering with the logging pipeline. The technique is hard because a successful rootkit removes its own traces, so most real detections fire on the loading step, on a kernel that is unsigned or unexpectedly patched, or on a mismatch that a hypervisor level sensor reports.

What you will practise

  • Explain what a rootkit does and why local tools may report a clean system.
  • List the kernel and driver load telemetry that is available on your platforms.
  • Design a cross view comparison between a host listing and an independent inventory.
  • Interpret code integrity events and decide when they justify a rebuild.
  • Judge how a logging gap changes your confidence in every other alert from that host.
