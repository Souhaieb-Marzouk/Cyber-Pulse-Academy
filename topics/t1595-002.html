T1595.002 Active Scanning: Vulnerability Scanning

T1595.002ReconnaissanceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is when an attacker checks your systems for known weaknesses. A known weakness is a fault that the software maker has already published a fix for. The attacker looks for systems that still have the fault.

Why should you care?

This step tells the attacker which single weakness is most likely to work against you. It also pinpoints the exact system to attack. Because the checks are usually quick, an attacker can test many systems in a short time. Missing patches become a direct invitation.

How it works, in plain steps

  1. The attacker first learns which software and version each of your services runs.
  2. They compare those versions with public databases that list every known software weakness.
  3. They select the weaknesses that match your versions and rank them by how easy they are to use.
  4. They send extra test requests to confirm whether the weakness is really present.
  5. They record the affected systems, plus any protection tools that might block them.
  6. They choose the best target and prepare the attack for that one weakness.

Real-world example

Think of an inspector who walks a block of flats and checks whether each front door matches a list of locks with known faults. The inspector does not force any door. They simply note which flats use the faulty lock, and the list becomes a shortlist for a later break in.

Key takeaways

  • Unpatched, internet facing services are found quickly, so patch on a known schedule.
  • Vulnerability checks appear in web and application logs, not only in network records.
  • Run your own authenticated scanning so you fix flaws before an attacker finds them.

In more detail

This sub-technique is scanning with the intent to match a target against known weaknesses, rather than merely listing open ports. A typical run fingerprints the service, harvests version banners, then consults a vulnerability database or a local set of checks to decide whether a specific flaw is likely present, sometimes verifying with a safe probe. Adversaries often start from a vulnerability of interest and search outward for hosts that answer to it, which reverses the usual direction of discovery. Relative to its parent, the emphasis is on interpreting what the service said rather than on finding the service at all, so the network footprint looks like a normal scan while the content of the probes is tuned to particular products. Defender evidence is richest in web server and application logs where encoded exploit attempts, unusual parameters and repeated error responses appear, plus intrusion detection signatures and web application firewall blocks. The recurring difficulty is that internal patch verification scans look identical, so authorisation, schedule and source address are what separate them.

What you will practise

  • Explain how vulnerability scanning differs from simple port scanning.
  • Describe how service versions are matched against known weakness databases.
  • Identify log and alert sources that capture vulnerability probing.
  • Explain why internal patch verification scans look like hostile scanning.
  • Describe a patch management routine that removes exploitable exposure.
