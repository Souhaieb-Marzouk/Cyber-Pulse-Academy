DET0375 Detection Strategy for T1546.017 - Udev Rules (Linux)

DET0375Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Udev is the part of Linux that notices hardware. You can write a small rule file that tells it what to do when a device appears. This detection looks for new or changed rule files, and for the device manager starting programs it should not. It catches the persistence setup, not just the device.

Why should you care?

A udev rule can run a command the moment someone plugs in a device, even a harmless looking one. It survives restarts and does not need the attacker to stay logged in. Rule files are plain text that few people read, which makes them a quiet hiding place. Watching those directories closes a gap that user session monitoring misses.

How it works, in plain steps

  1. Collect file integrity monitoring events for the system udev rule directories.
  2. Collect audit records for writes to those paths, including the account and the process.
  3. Read the new rule content and look for a RUN directive that points outside approved directories.
  4. Collect process creation events where the device manager is the parent process.
  5. Compare the started program with the binaries that your packages normally run from a rule.
  6. Alert with the rule file, the command it runs, and the account that created it.

Real-world example

Think of a door log again, but this time it is a note taped inside the door frame. It says that whenever a specific van arrives, the gate should open. Nobody watches the gate, but the note does the work. Checking the rule files is checking behind the door frame.

Key takeaways

  • Udev rules are system level persistence that fire on hardware events rather than at logon.
  • The rule content, especially the RUN target path, is what makes the alert worth acting on.
  • Limited shell access plus a write to the rule directory is enough to install this.

In more detail

This strategy detects persistence through udev rules on Linux, where an adversary drops a rule file that makes the system run a command whenever a matching device event occurs, such as a specific USB device being attached. The rule files live in fixed directories and are read by the device manager, so the behaviour survives reboots and is not tied to any user session. Detection uses file integrity monitoring on the udev rule directories, auditd records for writes to those paths, process creation showing the device manager starting an unexpected program, and the rule content itself where a RUN directive points at a writable or temporary location. The main failure is that legitimate packages install udev rules, so a path match alone is noisy and the rule content is what gives the alert its meaning.

What you will practise

  • Locate the directories where Linux distributions read device manager rules.
  • Write a detection that reads rule content and flags a suspicious RUN target.
  • Correlate a rule file change with a later process start by the device manager.
  • Decide what file integrity monitoring coverage is needed to see these paths.
