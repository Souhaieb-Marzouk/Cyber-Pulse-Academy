T1548 Abuse Elevation Control Mechanism

T1548Privilege EscalationExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is when an attacker uses the normal ways a system grants higher rights, instead of breaking software. They might bypass a permission prompt, misuse a helper program that already runs as an administrator, or abuse a rule that lets one user run commands as another.

Why should you care?

A normal user account is limited on purpose, so damage stays small. When that limit fails, an intruder can change system settings, read other people's data, and switch off protections. These failures often come from old configuration drift, such as a leftover rule that nobody removed. Regular review of who can elevate, and why, closes the gap.

How it works, in plain steps

  1. The attacker runs as a normal user and looks for a path to more rights.
  2. They find a program that runs with higher rights when it is started.
  3. They make that program load or run something they control instead.
  4. Sometimes they simply show a routine prompt and the user approves it.
  5. A weak rule, such as a broad sudo entry, which lets a user run commands as another account, can grant the same result.
  6. Defenders spot it by checking which parent process started a privileged program.

Real-world example

Think of an office where only managers have a master key. A cleaner discovers that the manager's key is left in a shared drawer, so the cleaner borrows it and copies it. Nothing was broken and no alarm rang. The weakness was the plan for using keys, not the lock itself.

Key takeaways

  • Higher rights should be rare, logged, and never left lying around.
  • Review old rules that let users run commands as someone else.
  • Check which program asked for elevated rights, and whether that is normal.

In more detail

Abuse Elevation Control Mechanism describes adversary actions that subvert the way an operating system gates privilege rather than exploiting a memory-safety flaw to obtain it. The parent technique covers bypassing or spoofing user consent prompts, abusing setuid and setgid binaries on Unix-like systems, manipulating sudo configuration and policy, and any other path where a legitimate elevation mechanism is misconfigured, induced to load attacker-controlled content, or simply presented to a user as routine. On Windows the central target is the consent and credential prompt that separates a standard user session from administrative rights; on Linux and macOS it is the set of binaries, capabilities and configuration files that grant controlled privilege transitions. The mechanism is usually one of three things: a component that elevates automatically without prompting, a signed or otherwise trusted process that can be induced to load content from a user-writable location, or a configuration entry that permits a low-privileged user to run a command as another account. The artefacts are configuration and process evidence rather than exploit signatures: process creation showing unusual parentage for privileged processes, command lines invoking elevation utilities with unexpected arguments, modifications to sudoers files, setuid bits or service definitions, audit records of consent prompt outcomes, and file integrity alerts on the binaries and configuration involved. Legitimate administration generates a large volume of genuine elevation, so triage should focus on who performed the elevation, from which session and host, whether the elevated process was expected there, and whether the same account also produced other post-exploitation behaviour such as credential access or defence impairment.

What you will practise

  • Explain how consent prompts, setuid binaries, capabilities and sudo configuration each mediate privilege and where each can fail.
  • Identify configuration drift such as unexpected setuid bits or sudoers entries as an elevation risk.
  • Read process lineage for privileged processes to spot unusual parents and argument patterns.
  • Distinguish routine administrative elevation from adversary abuse using session, host and timing context.
  • Prioritise hardening of auto-elevating components and elevation policy against observed gaps.
  • Correlate elevation events with credential access, persistence or defence impairment on the same host.
