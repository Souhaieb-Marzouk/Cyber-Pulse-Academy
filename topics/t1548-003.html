T1548.003 Abuse Elevation Control Mechanism: Sudo and Sudo Caching

T1548.003Privilege EscalationExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Sudo is a Linux and macOS command that runs a single command with the rights of another user, usually the administrator account called root. Sudo can remember that you typed your password, so you do not have to type it again for a short time. An attacker can use that memory.

Why should you care?

When sudo remembers your password, it does not ask again within the time limit. If an attacker already runs code as you, they can use that open window to run powerful commands. No prompt appears, so you see nothing unusual on your screen. Sudo also keeps a policy file that decides who may run what, and a change there can hand out lasting rights.

How it works, in plain steps

  1. You run sudo with a command, and it checks the policy file to see whether you may run it.
  2. If a password is needed, sudo asks once and then records a timestamp for you and that terminal.
  3. For a set time afterwards, sudo runs further commands without asking again.
  4. Separate terminal sessions can have their own timestamps, so each one may ask separately.
  5. An attacker uses your open window to run their own privileged commands without a prompt.
  6. Detection reads the sudo log entries and compares them with what the account normally does.

Real-world example

Think of a server room with a keypad on the door. Once you enter your code, the door stays unlocked for ten minutes so you can carry boxes in and out. A colleague who is already inside can walk through the same door during those ten minutes and take anything, and the door never beeps to ask who they are.

Key takeaways

  • The credential cache in sudo is a real privilege window, so review its timeout setting.
  • Read sudo log entries and check for commands the account has no reason to run.
  • Protect the sudo policy file, because one edit there can grant lasting rights without any prompt.

In more detail

Sudo delegates command execution to other users under a policy file, and its credential cache turns that delegation into a short window of password-free privilege. After a successful authentication sudo records a timestamp for the user and terminal, and for the configured timeout further commands run without a new password prompt; separate terminal sessions are tracked independently when ticket isolation is enabled. An adversary with existing code execution on a host can therefore run privileged commands whenever the legitimate user has authenticated recently, achieving quiet elevation without any prompt appearing on screen. The alternative is to modify the policy file so a chosen account receives command rights or is exempted from password prompts entirely. Both leave readable traces: sudo logs record the command, the invoking account, and the terminal, and the policy file and its included directory can be baselined. Defenders alert on commands that do not match the account's role, on policy changes, and on privileged actions outside expected maintenance windows.

What you will practise

  • Explain what sudo does and how the policy file decides who may run which commands.
  • Describe how sudo caches credentials and what the timeout setting controls.
  • Explain how a terminal ticket affects whether a new password prompt appears.
  • Explain how an attacker with existing access uses a cached credential window to run privileged commands.
  • Detect suspicious sudo use through log review and policy file monitoring.
  • Describe how an unsafe policy rule removes the password prompt for an account.
