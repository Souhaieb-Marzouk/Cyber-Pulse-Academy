DET0350 Detecting Downgrade Attacks

DET0350Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for a connection that uses an older and weaker security setting. An attacker can push two systems to agree on a weak option. The session then works, but it is much easier to read or change.

Why should you care?

Nothing breaks when a system downgrades, so nobody notices the weaker setting. Traffic that people believe is private can then be read or altered. Old settings often allow an attacker to fake the other side of the conversation. Many networks keep old options switched on for old devices, which widens the risk. Watching the negotiated setting shows you where the weak path still exists.

How it works, in plain steps

  1. The network sensor records the security details of each new session, such as the version and the cipher suite.
  2. The rule compares those details with the minimum that your policy allows for that service.
  3. It notes the client, the server name and how often the weak option is chosen.
  4. On the authentication side, it reads the encryption type agreed for each successful logon.
  5. It also watches for configuration changes that lower a required minimum or turn off signing.
  6. A weak session that repeats, or that follows a relaxed setting, raises an alert.

Real-world example

Think of a door that can lock in two ways, one strong and one weak. The weak lock still keeps the door shut, so the building looks secure. Only a list of which lock was used each night shows the problem. That list is the handshake record.

Key takeaways

  • A successful session can still be a weak one, so always log what was negotiated.
  • Legacy devices explain many weak sessions, so baseline them first.
  • A change that relaxes a minimum setting deserves its own alert.

In more detail

This detection strategy covers Downgrade Attacks (T1689), where an adversary forces a system to fall back to an older, weaker protocol, algorithm or security setting so that traffic or authentication can be intercepted or forged. The technique matters because the weakened session usually still succeeds, so nothing fails and the victim keeps working while protection quietly disappears. Detection depends on transport layer security handshake metadata that records the negotiated version and cipher, proxy and load balancer logs that show what each client was allowed to negotiate, authentication records that carry the negotiated encryption type, and configuration change records that relax a minimum protocol or signing requirement. It fails most often because legacy devices genuinely cannot speak modern protocols, so a weak negotiation alone is not proof of an attack.

What you will practise

  • Explain how a downgrade lets an adversary weaken a session without breaking it
  • Identify handshake, authentication and configuration telemetry that records negotiated security settings
  • Define the minimum acceptable protocol and algorithm for each categorised service
  • Write a rule that flags weak negotiation and relaxed configuration as separate but related signals
  • Triage a match by checking whether a known legacy device or an approved change explains it
  • Describe the coverage lost when session metadata is only available for unencrypted traffic
