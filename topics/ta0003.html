TA0003 Persistence

TA0003EnterpriseExtremeTactic

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Persistence is everything an attacker does to keep access after a reboot, a password change or a cleanup. It explains why an incident that looks fixed can come back weeks later. Typical tricks include adding a startup entry, creating a service, or leaving a hidden account behind.

Why should you care?

If you only remove the visible problem, the attacker returns through the door they left open. Persistence also wastes your time, because you clean the same machines more than once. It can hide in places that have no obvious malware at all, such as a new account or a trusted application. Finding it means checking new durable changes against a known-good list.

How it works, in plain steps

  1. After getting in, the attacker looks for places that run automatically when a machine starts.
  2. They add their code or account to one of those places, often quietly during normal working hours.
  3. The change survives restarts, so their access returns even after the machine is rebooted.
  4. It also survives a password reset if they created a separate account or a hidden key.
  5. Defenders find it by comparing new startup items, services and accounts with an approved list.

Real-world example

Imagine you rent an apartment and the landlord asks you to leave. Instead of arguing, you quietly make a copy of the front door key. You also leave a window unlocked and ask a friend to keep a spare key. The landlord changes the main lock and believes the problem is solved. A week later, you walk back in through the window. Persistence works exactly like that. Removing the person is not enough if the spare keys still exist.

Key takeaways

  • Persistence is the attacker's spare key, and it outlives a restart.
  • Always review new startup items, services, scheduled jobs and user accounts.
  • Cleanup is only finished when every foothold is gone and tested.

In more detail

Persistence is the tactic that covers everything an adversary does to keep access across reboots, credential resets, and partial remediation, and it is the reason incidents that appear contained often resume weeks later. Behaviours in this tactic include modifying registry run keys and startup folders, installing services or daemons, creating scheduled tasks and cron entries, adding accounts or SSH authorised keys, abusing external remote services such as VPN or remote desktop gateways, planting web shells in application directories, and hijacking legitimate authentication pathways so that a token or certificate continues to work after the original password is changed. Defenders have good theoretical telemetry here because persistence usually requires a write to a durable location, and those writes are visible in registry auditing, file integrity monitoring, service and task creation events, directory service change logs, and cloud identity audit records. The practical difficulty is a very high legitimate baseline. Software deployment, agent updates, and administrators constantly create the same artifacts, so each event in isolation is weak. Compounding this, sophisticated adversaries prefer persistence that is indistinguishable from normal platform behaviour, such as a new OAuth application consent or a certificate added to an enterprise application, which may leave no endpoint trace at all. Detection therefore depends on inventories, change control correlation, and reviewing every new durable artifact against a known-good baseline, ideally with the identity and process that created it.

What you will practise

  • Enumerate the main persistence locations and mechanisms across endpoints, directories, cloud identities, and network services.
  • Explain which logging and auditing configurations are prerequisites for detecting persistence, and what gaps remain without them.
  • Correlate a newly created durable artifact with the identity and process responsible for creating it.
  • Use change management and asset inventory data to suppress expected persistence-like activity without losing genuine anomalies.
  • Recognise identity-layer persistence such as application consent, federated trust changes, and long-lived credentials.
  • Produce a remediation checklist that removes persistence rather than only the visible malware.
