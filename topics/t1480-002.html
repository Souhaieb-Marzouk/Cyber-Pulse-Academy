T1480.002 Execution Guardrails: Mutual Exclusion

T1480.002StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is a trick where malware puts a marker on a computer before it starts. If the marker is already there, the malware knows the machine is infected and stops. This sub-technique is the mutual exclusion part of a wider parent technique called execution guardrails.

Why should you care?

If a host is infected twice, the two copies fight over the same files and both may fail. A marker stops that, so the attacker keeps one clean infection running. The marker also helps the malware avoid running inside a lab where the sample is studied. For you as a defender, the marker is a useful clue because known names can be checked on live machines.

How it works, in plain steps

  1. The program builds a name for a system wide object, either written into the code or calculated the same way every time.
  2. It asks the operating system to create that object and looks at the answer it receives back.
  3. A new creation means no other copy is present, so the malware continues with its normal payload.
  4. An object that already exists means the host is already infected, so the process ends without doing more work.
  5. On Linux systems the same check may be a lock on a file, where failing to get the lock ends the run.
  6. The name may change between versions of the malware, so old published names stop being useful over time.

Real-world example

Think of a shared flat with one front door key kept in a bowl by the door. The flatmate who is already inside leaves the key in the bowl and turns the latch. A second flatmate comes home, sees the key missing and the door locked, and knows someone is already in. There is no point in both of them cooking in the same tiny kitchen at once, so the second person waits. The key in the bowl is the mutex: a simple shared signal that says this space is already taken.

Key takeaways

  • A mutex is a shared marker, not a file, so it may not appear in your normal file and process logs.
  • Known malicious mutex names are strong evidence that a host is already compromised.
  • Attackers change these names, so a missing name on a live host does not prove the host is clean.

In more detail

Mutual exclusion guardrails use a named system object, normally a mutex, as a marker that a host has already been infected. The loader creates the mutex with a fixed or algorithmically derived name and checks the creation result: a fresh handle tells it that no other copy is running, while an already-existing object tells it to exit quietly. Because the name often embeds a campaign identifier, string or handle enumeration can reveal it to defenders who have a sample to compare against. On Linux the same idea appears as an exclusive file lock on a path such as a runtime or temporary directory. The artefact left behind is the object itself, not a file or a scheduled task, so ordinary process creation logging rarely records it.

What you will practise

  • Explain what a mutex is and why malware checks for one before it runs.
  • Describe how a name based marker prevents a second infection on the same host.
  • Identify the artefacts that reveal a mutex, such as open handles and loaded strings.
  • Distinguish a malware marker from a mutex created by ordinary server software.
  • Explain how the same idea appears on Linux as an exclusive file lock.
  • Describe why a changed mutex name weakens name based detection.
