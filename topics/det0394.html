DET0394 Web Shell Detection via Server Behavior and File Execution Chains

DET0394Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A web shell is a small script placed on a web server that lets an attacker run commands through the website. This detection looks for a new file in a public website folder and for the web server starting a program afterwards.

Why should you care?

A web shell gives an attacker a doorway that survives restarts and looks like normal web traffic. The file may be only a few lines, so file scanning often passes it. Watching what the web server process does, not just the file, is what makes this detection work.

How it works, in plain steps

  1. File monitoring records every new file written inside a folder that the website serves.
  2. The rule keeps writes to script file types in those folders and notes which process wrote them.
  3. Process creation records show whether the web server later starts a shell or an interpreter.
  4. Network records show outbound connections from that host to unfamiliar addresses.
  5. A write plus a child process from the web service, or a callback, becomes one alert.

Real-world example

Think of a shop with a letterbox in the door. New letters arrive all day, so nobody watches the slot. The alarm is not the letter, it is seeing the shop owner reach through the slot and open the till from the outside, using instructions written on one of those letters.

Key takeaways

  • Match the chain of write, child process, and callback rather than the file alone.
  • A web server that starts a shell is abnormal on almost every host.
  • Keep content managed upload folders out of the alert path or the queue will never be empty.

In more detail

This detection strategy covers web shells, which are small scripts an adversary places inside a web accessible directory so that the web server runs their commands on demand. Detection works best as a chain rather than a file match: a write into a served directory, followed by the web server or its scripting engine starting a child process, followed by outbound network activity from the same host. Telemetry comes from file monitoring on the document roots, process creation records that show the web service as a parent, and server and proxy logs that record the request path and any callback address. The strategy fails in practice when a web shell is written in the same language as the application, when the server process is expected to start interpreters, or when file writes in content managed folders are constant and unaudited.

What you will practise

  • Explain why a web shell blends into normal web content and traffic
  • Identify the document root paths and script file types that matter on your web servers
  • Use process lineage from the web service account to detect command execution
  • Correlate a file write with an outbound connection to an unfamiliar address
  • Exclude legitimate upload and content management directories without losing server side coverage
  • Describe the containment steps to take once a web shell is confirmed
