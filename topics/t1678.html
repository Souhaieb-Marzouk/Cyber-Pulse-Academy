T1678 Delay Execution

T1678StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is when malware waits before it does anything harmful. It may simply sleep for a while. It may ask the operating system to run it later on a schedule. Or it may run harmless commands in a loop just to pass the time. The point is to act when nobody is watching and to confuse automatic analysis tools.

Why should you care?

Automatic analysis systems often run a suspicious file for a short time and then decide it is safe. If the harmful part starts only after that time has passed, the file gets a clean report. The same trick breaks the links between events in your logs, because the first and last steps are hours apart. Delays also let an attacker wait for a quiet period, such as a weekend, when nobody is available to respond.

How it works, in plain steps

  1. The malware starts and immediately checks its environment, often with no harmful action yet.
  2. It then pauses, either by sleeping inside its own code or by running harmless commands in a loop.
  3. One common trick is repeating a simple network test many times, which takes minutes and looks normal.
  4. Another option is to register the real payload with the operating system's scheduler so it runs later.
  5. Some samples make thousands of harmless system calls, which wastes time and fills analysis reports with noise.
  6. Once enough time has passed, the payload runs while your team is least likely to respond.

Real-world example

Imagine a thief who wants to rob a shop with a silent alarm that resets every ten minutes. He breaks a small window and then waits in the shadows. The guard checks, writes a report and goes back to his tea before the thief moves. Only then does he take the till. The alarm did its job perfectly, but it was watching the wrong ten minutes.

Key takeaways

  • A file that behaves harmlessly for a short test may simply be waiting.
  • Long gaps between related events can be deliberate and should be correlated.
  • Treat analysis timeouts and early exits as suspicious, not as proof of safety.

In more detail

Delay execution is a set of timing tricks used to keep malicious activity away from the moment of inspection and to separate events that a correlation rule would otherwise link. The simplest form is a programmatic sleep, pausing before the payload acts. A second form borrows legitimate scheduling: the actor registers the work with the operating system's task scheduler so it runs later, which also makes the trigger look like ordinary maintenance. A third form uses benign commands as filler, such as repeated pings or pointless loops, which both consumes time and can push the sample past the maximum runtime an automated analysis sandbox allows. A fourth, sometimes called API hammering, makes large numbers of native function calls purely to burn time and to flood analysis tooling with junk. Detection usually depends on sequencing rather than on the delay itself, because a sleep is invisible in most logs. What is visible is a gap: a process that starts long before it does anything meaningful, parent and child events separated by an interval inconsistent with the software's normal behaviour, scheduled task creation with a short delay and a script payload, or a newly created task whose author is not a known installer. Sandbox reports frequently note an early exit or timeout, and that timeout is itself an indicator worth following up rather than dismissing.

What you will practise

  • Explain why waiting can defeat automated malware analysis.
  • Describe how sleep calls, scheduled tasks and filler commands delay execution.
  • Explain how repetition of benign commands can exceed an analysis time limit.
  • Identify the log patterns, such as unexplained time gaps, that reveal delayed execution.
  • Explain how delays break event correlation across a long interval.
