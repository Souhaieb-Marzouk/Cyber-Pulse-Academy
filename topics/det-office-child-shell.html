Office Spawning Child Shell

Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Documents open in programs such as Word or Excel. A child process is a program started by another program. A shell is a command interpreter that can run further instructions. This detection flags a document program starting a command interpreter or scripting tool. That is often the sign of a harmful document running its payload.

Why should you care?

Attacks that arrive inside documents are still a common way intruders get in. The moment a document handler starts a shell, a harmless file becomes a live foothold. It gains that user's rights and that user's network position. Catching that single step stops the chain early. It stops before the attacker downloads tools, adds accounts, or reaches shared folders.

How it works, in plain steps

  1. Endpoint sensors record each new process along with the program that started it.
  2. The detection selects starts where the parent program is a well-known document handler.
  3. It then checks the child, looking for command interpreters and scripting tools.
  4. The child's full command line is reviewed, because web addresses and temporary folders are warning signs.
  5. The digital signature of the child program is checked, since signed system tools are often borrowed.
  6. Only child programs on a reviewed add-in list are treated as routine, and even they are logged.

Real-world example

You open a letter and it asks you to sign a form. You sign, and the letter phones a stranger to say the door is unlocked. A document is only paper until something else starts on its behalf. When a spreadsheet quietly launches a command interpreter, the file stops being a document and starts doing work. That jump is unusual, and it is exactly why this alert exists.

Key takeaways

  • A document program should not normally start a command interpreter.
  • The parent and child pair matters, even when the child is a signed system program.
  • Treat documents that arrived by email with more suspicion than files from internal shares.

In more detail

Office spawning child shell detection identifies productivity suite processes creating a command interpreter, scripting host or living-off-the-land binary as a direct child, which is the classic post-exploitation pattern following malicious document execution, macro abuse or an exploited document renderer. The behaviour matters because document-borne intrusion remains one of the most common initial access routes, and the transition from a document handler to a system shell is the moment when a contained file becomes an interactive foothold with the user's rights and network position. The telemetry required is process creation with parent process identification and full command lines, including parent integrity level, the document or template path where available, the signed status of the child binary, and file and network telemetry to establish what the child then did. The signal survives common evasion because the operating system records the parent-child relationship at process creation regardless of how the shell was invoked; an operator may use a scripting host, a signed system binary that loads script content, a component object model invocation, or a template injection that reaches the same result, but the parent remains the document handling process. The detection breaks down in practice because legitimate documents and add-ins do spawn processes: template management, document comparison, mail merge, citation managers, digital signature workflows, and vendor add-ins for accounting, legal and engineering tools all create child processes from the office application. Environments with heavy add-in use therefore require an allow-list keyed on the specific child binary, its signer and the parent's loaded modules. Coverage also depends on whether process telemetry includes suppressed or short-lived processes, since many malicious children exit within seconds, and on whether the parent process identifier is preserved rather than reused, which some collection pipelines do not guarantee.

What you will practise

  • Explain why the parent-child process relationship is a durable signal even when the child is a signed system binary.
  • Query process telemetry for office parents creating shells, script hosts or signed system binaries and enrich with signer data.
  • Build an allow-list of legitimate document add-in child processes and describe the risks of over-excluding.
  • Correlate the child process command line with follow-on network, file or credential activity to establish intent.
  • Handle short-lived child processes and process identifier reuse in collection pipelines.
  • Describe immediate containment steps and the evidence to preserve when a document-driven shell is confirmed.
