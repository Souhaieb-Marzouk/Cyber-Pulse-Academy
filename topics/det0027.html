DET0027 Detection of Web Protocol-Based C2 Over HTTP, HTTPS, or WebSockets

DET0027Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Command and control is how an attacker keeps in touch with a program running on your network. This detection looks for that contact when it hides inside normal web traffic. It catches the regular, machine like requests that a person would not make. The traffic itself is often encrypted, so the pattern matters more than the content.

Why should you care?

Almost every network allows web traffic, so an attacker does not need a strange port or protocol. Encryption means you cannot simply read the messages. However, a program checking in on a timer behaves differently from a person browsing. That difference is visible in timing, size and destination. Finding it can reveal a foothold that has been quietly present for weeks.

How it works, in plain steps

  1. The web gateway or proxy records each request, including the destination, the size, the user agent and the time.
  2. The endpoint agent records which program opened each network connection and to which address.
  3. The rule groups requests by host, destination and user agent, then measures the gaps between them.
  4. It flags groups with very steady gaps, small repeated responses and a user agent rarely seen elsewhere.
  5. It joins those groups to the process that made the connection. A browser is then treated differently from a background tool.
  6. The alert shows the destination, the interval, the process and the request shape. The analyst can confirm or dismiss it.

Real-world example

Imagine a warehouse where staff walk in and out all day at random times. One delivery van arrives every thirty minutes on the dot, takes nothing and leaves. Nobody reads the van's paperwork, but the timetable gives it away. Web protocol command and control detection watches for that van's timetable.

Key takeaways

  • Encryption hides content, so judge timing, size, destination and the owning process.
  • Regular intervals from a background process are the clearest sign of automated check in.
  • Baseline normal destinations first or the rule will flag your own business software.

In more detail

This strategy detects command and control over web protocols, mapped to ATT&CK technique T1071.001, where an adversary blends beacon traffic into ordinary HTTP, HTTPS or WebSocket sessions so that blocking outbound web access is not an option. Because the traffic is encrypted and shares ports with normal browsing, detection depends on the metadata that survives encryption: request cadence and consistency, uniform resource locator structure and length, user agent strings, server certificate and address reputation, upload and download volume asymmetry, and the process on the endpoint that owns the connection. The strongest correlations join proxy or web gateway records with endpoint network connection telemetry, so a periodic request can be tied to a specific process rather than to a browser in general. The practical failure is that thousands of legitimate applications beacon on timers to software as a service endpoints, so the rule is only workable once you baseline normal destinations per host group and score behaviour such as fixed intervals, rare user agents and connections from processes that should not use the web.

What you will practise

  • Explain why attackers choose web protocols for command and control
  • Identify the metadata fields that remain useful when traffic is encrypted
  • Measure request interval consistency and response size to spot beacon behaviour
  • Correlate proxy records with endpoint network connections to find the owning process
  • Baseline legitimate beaconing applications so the rule can be tuned by host group
