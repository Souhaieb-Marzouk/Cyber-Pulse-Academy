DET0113 Detect AS-REP Roasting Attempts (T1558.004)

DET0113Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for a special kind of Kerberos ticket request on your network. Kerberos is the system Windows uses to prove who you are. The rule catches requests made for accounts that do not need a password check first.

Why should you care?

Some accounts are set up so anyone can ask for a ticket without proving who they are first. The reply to that request is encrypted with the account password. An attacker can take that reply away and try to guess the password offline, where you cannot see the attempts. If the password is weak, the account is lost.

How it works, in plain steps

  1. A domain controller records an event when it hands out a Kerberos ticket.
  2. The event says whether the account needed a password check first, which is called pre-authentication.
  3. The rule keeps only requests where pre-authentication was turned off.
  4. It also looks at the requested encryption type, because weak types are often asked for.
  5. The rule notes the source address and the account name from the same event.
  6. Several such requests from one address in a short time raise an alert.

Real-world example

Think of a hotel front desk. A normal guest must show a passport before getting a room key. A few rooms are set up so the clerk hands over a key to anyone who asks. That key is cut to match the room lock. A thief can take the key home and file it down until it fits. The desk log shows only a normal key handover. You need a rule that flags rooms where no passport was checked.

Key takeaways

  • This attack needs no login, so failed password alerts will not show it.
  • The key clue is a ticket request for an account without pre-authentication.
  • Weak account passwords are what make the attack succeed.

In more detail

This strategy detects AS-REP roasting, an attack against Kerberos in which a request for a service ticket is made for an account that has pre-authentication disabled, so the domain controller returns a response encrypted with a key derived from the account password. An attacker who can request that response offline can crack it at leisure without ever authenticating, which makes the technique quiet and hard to spot with authentication failure monitoring alone. Detection depends on domain controller Kerberos ticket events that record the pre-authentication flag, the requested encryption type, the client address and the account, correlated with prior directory lookups of the same account. In practice it fails when pre-authentication auditing is not enabled, when the optional encryption type is not recorded, or when a single request blends into normal Kerberos volume, so rules usually need a count or a correlation window.

What you will practise

  • Explain how a Kerberos ticket request can expose an account password hash
  • Identify the fields in domain controller ticket events that show pre-authentication was disabled
  • Correlate directory lookups of an account with the ticket request that follows
  • Tune the rule so normal Kerberos volume does not drown the signal
  • Respond to an alert by finding and fixing accounts without pre-authentication
