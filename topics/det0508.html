DET0508 Behavioral Detection of Process Injection Across Platforms

DET0508Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This rule looks for one program hiding inside another running program. Attackers do this so their code looks like a normal trusted process. Nothing new is written to disk, so file scanning alone cannot find it. The rule watches the moments when one process reaches into another to read or change its memory.

Why should you care?

When code runs inside a trusted program, its activity is credited to that program. A firewall or application control list that trusts the host process will also trust the hidden code. This gives the attacker a way to keep working without dropping obvious files. Because the signal is so common in normal system activity, the rule must be built carefully to stay useful.

How it works, in plain steps

  1. The agent records every attempt by one process to open another, and lists the rights that were requested.
  2. It also records new threads that start inside a process, naming the process that created them.
  3. The rule drops pairs where both processes belong to the same product family, such as two browser processes.
  4. It then looks for memory operations that change protection flags so private memory becomes executable.
  5. Each remaining event is scored by the source process reputation, its path and how often it does this.
  6. Only a cluster of related events for one target process in a short window becomes an alert.

Real-world example

Think of an office building where only staff with badges may enter. An intruder finds a staff member, copies the badge number and walks in behind them. The door log shows a valid badge, so nobody at the door is alarmed. This rule is the guard who also notices that one badge opened two doors at once.

Key takeaways

  • Injection has no new file to scan, so detection must use behaviour and memory.
  • One process opening another is normal, so the alert needs a second signal such as a remote thread.
  • Cross platform coverage means watching process memory operations, not only Windows system calls.

In more detail

This detection strategy targets process injection, the technique tracked as T1055 in its several variants for remote thread creation and memory writing. Injection runs an attacker payload inside a process that is already trusted, so the payload inherits the host process identity, its loaded modules and often its network permissions, and file based controls never see it execute. The telemetry that makes it visible is process access reporting with the requested rights, remote thread creation events that name both the source and target process, suspicious writes into another process address space, and memory protection changes such as private memory becoming executable. The main failure mode is that the direct signal, a process opening another process, is extremely common on modern systems, so the strategy depends on pairing the access event with a memory or thread follow up and on allow listing the security and debugging tools that legitimately do this all day.

What you will practise

  • Describe how process injection lets code run under the identity of a trusted process.
  • Name the event fields that show which process opened which other process and with what rights.
  • Explain why a single process access event is weak evidence and what second signal strengthens a rule.
  • Compare injection detection on Windows, Linux and macOS using the telemetry each platform offers.
  • Allow list known security tooling so that the rule keeps meaningful volume.
  • Outline a containment step for a host where an unexpected process has written into another process.
