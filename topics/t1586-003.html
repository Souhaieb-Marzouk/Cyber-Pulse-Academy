T1586.003 Compromise Accounts: Cloud Accounts

T1586.003Resource DevelopmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is the cloud part of account compromise. The parent idea is taking over accounts that already exist. Here the account belongs to a cloud provider and it controls storage, computers or messaging. The attacker inherits the permissions that were set up for normal work. They may reach many systems at once, because cloud accounts often connect to each other. The owner usually keeps paying the bill throughout.

Why should you care?

Cloud accounts often hold data from many parts of a company in one place. A single stolen key can read storage, start machines or send messages. Service accounts are especially dangerous because they rarely change their passwords and are seldom watched. Attackers also use trusted links between suppliers and customers to enter without touching your own staff. Nobody may notice, because the activity uses valid credentials. Strong logging and regular key rotation are what make this activity visible.

How it works, in plain steps

  1. The attacker gets cloud credentials through spraying, phishing or a stolen application key.
  2. They sign in and list the users, roles and permissions they now hold.
  3. They search code and settings for more keys that were stored in plain text.
  4. They use those permissions to read stored data or to start new machines.
  5. They may keep access by creating their own key or user account.
  6. If they entered through a supplier, the trail starts outside your own logs.

Real-world example

Imagine a large office building where one master key opens the post room, the server room and the stationery store. The building manager lends that key to a contractor for a week. If the contractor loses or copies it, every room is open at once. Cloud accounts are built the same way. One set of keys can reach many services, and the locks were designed that way for convenience. That is why losing a single cloud key matters far more than losing a desk key.

Key takeaways

  • Cloud keys and roles are powerful, so treat them like master keys.
  • Rotate long-lived keys and remove the ones that nobody uses.
  • Watch control-plane logs for new keys, role changes and unusual sign-ins.

In more detail

A compromised cloud account differs from a created one because the adversary inherits permissions, trust relationships and existing data rather than building them. Enumeration usually comes first: listing identities and roles, testing what the current keys allow, and hunting for credentials left in code, configuration files or environment variables. The common paths in are password spraying against single sign-on, phishing for a session token, theft of long-lived application keys, and abuse of a service provider's account that already holds a trusted relationship with the customer tenant. Detection depends on control-plane records: new access keys, role or privilege changes, unusual sign-in locations, and object storage reads far beyond the normal baseline.

What you will practise

  • Explain how compromised cloud accounts give an attacker wide access.
  • Distinguish this sub-technique from its parent and from account creation.
  • Identify cloud audit events that show key creation or privilege changes.
  • Describe how a trusted supplier relationship can be abused for entry.
  • Recommend key rotation and least privilege practices.
