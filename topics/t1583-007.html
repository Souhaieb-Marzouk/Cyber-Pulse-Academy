T1583.007 Acquire Infrastructure: Serverless

T1583.007Resource DevelopmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Serverless means running small pieces of code on demand, without owning or managing a machine. Cloudflare Workers, AWS Lambda, and Google Apps Script are examples. This sub-technique is about an attacker creating such code as a base for their activity. The parent technique covers acquiring infrastructure in general.

Why should you care?

The attacker pays almost nothing while waiting for victims to connect. Requests go to familiar cloud provider addresses, so simple blocklists cannot help. If the function is reported, it can be removed and replaced in minutes. Detection must therefore look at behaviour, not just at the destination name.

How it works, in plain steps

  1. The attacker opens a free or low-cost account with a serverless platform.
  2. They deploy a short function that accepts requests from infected machines.
  3. The function either replies directly with instructions or forwards the request to the real server.
  4. Because the provider's name is in the address, the traffic looks like normal cloud use.
  5. The attacker changes the function's code or address often, breaking any blocklist.
  6. When noticed, the function is deleted and a new one appears under another account.

Real-world example

Think of a parcel locker in a supermarket lobby. The courier never meets the buyer. Goods are dropped into a numbered box and collected later. The locker belongs to the supermarket, so nobody questions the handover, and the courier can stop using that locker at any time.

Key takeaways

  • Known cloud provider names are not proof that a request is legitimate.
  • Regular timing and consistent size in encrypted requests are strong warning signs.
  • Cloud provider logs and billing records are key evidence when a function is abused.

In more detail

Serverless computing, in which a provider runs small functions on demand without the customer managing a machine, is acquired in this sub-technique as disposable operational infrastructure. The parent technique covers acquisition generally; here the asset is a function, worker, or script hosted under a provider's shared domain. The operator deploys code that either answers infected clients directly or relays their traffic to a real control server, and the resulting requests arrive addressed to subdomains of well-known cloud providers with valid provider certificates. Pricing by invocation keeps costs negligible during quiet periods, and deployments can be created and deleted quickly, which frustrates takedown. Because the network destination is a mainstream provider, the distinguishing evidence is behavioural: encrypted requests to a provider endpoint from processes unrelated to that provider's normal use, unusual regularity or beacon-like timing, data volumes that do not fit ordinary application traffic, and provider logs showing a recently created function whose traffic does not match the account's business purpose.

What you will practise

  • Explain how this sub-technique differs from the parent Acquire Infrastructure technique.
  • Describe how serverless functions act as relays or direct control endpoints.
  • Identify the traffic behaviours that separate abuse from normal cloud use.
  • Explain why destination-based blocking fails against serverless infrastructure.
  • Describe the provider-side records that support investigation and takedown.
