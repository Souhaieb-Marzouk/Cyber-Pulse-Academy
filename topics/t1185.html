T1185 Browser Session Hijacking

T1185CollectionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

When you sign in to a website, your browser keeps a small pass called a session ticket. Browser session hijacking is when an attacker puts code inside your browser and uses that ticket as if they were you.

Why should you care?

The attacker does not need your password, because your browser is already signed in. They can open internal company pages that trust your browser. Step by step, this can pass two step verification, because the login already happened. Your account history will show only your own name.

How it works, in plain steps

  1. You sign in to a website, and your browser stores a session ticket for it.
  2. An attacker with access to your computer injects code into the browser process.
  3. The injected code reads the tickets, cookies and certificates the browser holds.
  4. The attacker sends their own web requests out quietly through your browser.
  5. Internal sites see a trusted signed in user, so they answer normally.
  6. When the browser closes, the tunnel closes with it and little remains on disk.

Real-world example

Picture an office where staff wear a lanyard to move between floors. Someone slips a second person through the turnstile behind an employee. Every door opens for the pair because the doors only read the lanyard. The visitor never holds a badge of his own, and every log shows the employee walking around.

Key takeaways

  • The attacker borrows an existing session, so no password is needed.
  • Two step verification may not help once a session is already active.
  • Server logs will show the real user, so look for signs on the endpoint.

In more detail

Browser session hijacking is the family of behaviours in which code placed inside a running browser acts as the user rather than stealing their files. The defining mechanism is injection: a module is loaded into the browser process, or a proxy is placed in front of it, so the attacker inherits the session cookies, active logon state and client certificates that the browser already holds. What follows is usually described as pivoting. The attacker tunnels their own requests through the victim browser, so they browse internal web resources such as file shares, intranet applications, webmail or a collaboration portal from a position the server already trusts, without knowing the password and without triggering a fresh authentication prompt. Two implementation patterns are common. One injects a shared library into the browser and exposes the attacker's traffic through that connection; the other configures a local proxy that the browser is pointed at, which requires no injection at all but does require the browser to route through it. Process privileges matter, because opening another user's browser process may require administrative rights or debug privilege. The consequences for detection are unusual: server side authentication logs show only the legitimate user, so the anomaly has to be found on the endpoint, as an unexpected library loaded in the browser process, an unexpected listening socket or child process, or a browsing pattern that ignores normal working hours and interest. Where an organisation can log web proxy requests, the discriminator is the destination set and the request headers, since tunnelled requests may carry a session that is already authenticated and a client fingerprint that does not match the user's own device.

What you will practise

  • Explain how injecting code into a browser lets an attacker inherit cookies and sessions.
  • Distinguish stealing a session from stealing a password and explain the impact.
  • Describe how tunnelling requests through a victim browser reaches internal resources.
  • Identify endpoint signals such as unexpected loaded modules or browser child processes.
  • Explain why two step verification may not stop an attack on an active session.
