DET0482 Behavior-chain detection for T1134.001 Access Token Manipulation: Token Impersonation/Theft on Windows

DET0482Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Every Windows program runs with a security token that describes who it is. This plan looks for programs that borrow or copy the token of another user. Borrowing a token lets a low privilege program act as a powerful user. The detection follows the events that happen when a token is taken and then used.

Why should you care?

Attackers who already have a small foothold want a bigger one. Copying a token is a quiet way to gain administrator rights without a password. It leaves few traces compared with guessing credentials. If you only watch failed logons, you will miss this step completely. Watching token use helps you catch privilege escalation while it happens.

How it works, in plain steps

  1. The endpoint agent records process access events, which show one program opening another with a set of access rights.
  2. The rule looks for access rights that allow a handle to be duplicated, because that is what token theft needs.
  3. It checks whether the target process holds high privilege, such as a system process or a security service.
  4. Windows then logs a new logon, either an explicit credential logon or a network logon, under a new identity.
  5. The detection joins the access event and the later logon event on the same host inside a short time window.
  6. A chain that does not match known administration software is raised as a high priority alert.

Real-world example

Think of a staff canteen where each worker wears a coloured badge. One worker slips a manager badge out of an unlocked drawer and clips it to their own coat. The kitchen staff serve them the manager meal because they only look at the badge. The theft is noticed later by comparing the badge list with who actually ordered. In the same way, a stolen token is accepted by Windows because the token looks genuine.

Key takeaways

  • A token is the proof of identity that Windows trusts for a running program.
  • Copying a token avoids the need for a password or a failed logon.
  • Process access rights plus a resulting logon event are the key pair of clues.

In more detail

Token impersonation and theft abuse legitimate Windows logon and process access interfaces so that a running thread adopts the security context of another user, usually a higher privileged one, without ever knowing that user's password. The behaviour chain this strategy watches for is process access to a privileged process with access rights that allow handle duplication, followed by the creation of a new process or the use of a network logon under a different identity on the same host. The hard part is that administrative tooling, backup agents and remote management software perform similar calls, so the rule needs granted access masks, source process paths and the resulting logon events correlated before it can be trusted.

What you will practise

  • Describe how a Windows security token identifies a running process.
  • Identify the access rights that allow a process handle to be duplicated.
  • Correlate a process access event with a later logon under a different identity.
  • List the administrative tools that legitimately perform this pattern.
  • Explain why failed logon monitoring alone will not find token theft.
