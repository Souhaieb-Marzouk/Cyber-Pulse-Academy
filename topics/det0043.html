DET0043 Detection Strategy for System Location Discovery

DET0043Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches for programs that ask a computer where it is in the world. It looks for requests about the time zone, the country, or the language settings. Security teams call this system location discovery. The detection catches this early step so analysts can react before an attack grows.

Why should you care?

An attacker often checks the location of a machine first. The answer helps decide if the machine is worth attacking. It also helps the attacker guess whether a fake test network is in use. Your own staff and software do the same checks for normal reasons, so the signal is weak alone. That means you need context, not just a single event.

How it works, in plain steps

  1. A process creation event records the program name and the full command line that started it.
  2. The rule scans those command lines for queries about time zone, locale, region, or country.
  3. It notes which parent program launched the query, because that detail separates routine tools from odd ones.
  4. It compares the query against a baseline of normal behaviour for that host and that user account.
  5. Known setup helpers and clock services are filtered out so they do not raise alerts every day.
  6. Several location checks from one session inside a short window raise the alert for a human to review.

Real-world example

Think of a hotel night watchman who writes down each guest name, home country, and language. The front desk does this for every guest, so the list alone proves nothing. But a visitor at three in the morning breaks the pattern. This visitor reads the guest book three times and touches nothing else. The watchman becomes suspicious. Location discovery detection works the same way. One lookup is paperwork. Many lookups from one quiet source, at a strange hour, is worth a second look.

Key takeaways

  • Location discovery is a preparation step, so it is most useful when paired with other strange behaviour.
  • Almost every normal program asks about the time zone, so rarity and clustering matter more than the request itself.
  • A match is a prompt to investigate, not proof that an attacker is present.

In more detail

This detection strategy covers T1614, System Location Discovery, where an adversary enumerates the geographic and regional identity of a host before deciding how to act. Useful telemetry includes process creation with full command lines, Windows registry reads of the time zone and internationalization keys, and Windows Management Instrumentation queries for country and locale values. The pattern that matters is not a single field but a burst of location requests from one process or session, especially from scripting hosts on servers that rarely answer such questions. The common failure mode is volume: legitimate software asks the operating system about the time zone all day long, so a rule that fires on any location call will drown the queue and get disabled. Detection therefore depends on baselining which parent processes normally perform these lookups and scoring rarity and clustering rather than presence.

What you will practise

  • Explain what system location discovery is and why it is an early stage of an intrusion.
  • Identify the process creation and registry telemetry that records location lookups on Windows.
  • Describe how to baseline normal callers of time zone and locale information on your estate.
  • Build a pseudo rule that scores rare callers instead of alerting on every lookup.
  • Recognise the false positive sources that make this detection noisy in practice.
  • Describe how to combine location discovery with sandbox evasion signals for higher confidence.
