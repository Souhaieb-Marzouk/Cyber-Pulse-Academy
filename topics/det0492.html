DET0492 Detection Strategy for Modify Cloud Compute Infrastructure: Modify Cloud Compute Configurations

DET0492Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Cloud computing lets you create and change virtual machines by calling an interface. This plan watches for changes to how those machines are configured. Examples include turning off protection against deletion or changing what a machine runs at start up. Such changes can be normal, but they can also prepare a machine for abuse or hide evidence.

Why should you care?

An attacker with cloud rights can reshape infrastructure instead of attacking it. Switching off protection lets a machine be destroyed, taking its logs with it. Changing start up data can add code that runs every time the machine boots. These actions are allowed by design, so permission checks alone will not stop them. Reviewing the pattern of changes is how you catch them.

How it works, in plain steps

  1. The cloud provider records every configuration change in its audit service, with the caller and the resource.
  2. The detection selects the write operations that affect a virtual machine or its protection settings.
  3. It groups the changes by identity and resource over a short window, so single edits are not enough.
  4. Settings that should not change in production, such as termination protection, are given extra weight.
  5. The caller identity is compared with the automation accounts that normally perform such work.
  6. Changes without a matching change record, or made by an unfamiliar identity, are raised for review.

Real-world example

Think of a building where tenants may repaint their own office. Repainting is allowed and harmless. Removing the fire door is also a change a tenant could make. So is switching off the sprinkler system. Both destroy the safety of the whole floor. The facilities team only notices if it reviews the alteration log against the list of approved works. In the same way, judge cloud changes by what they switch off. Do not judge them only by who may call the interface.

Key takeaways

  • Cloud configuration changes can be an attack step rather than routine maintenance.
  • Disabling protections and altering start up data are the changes that matter most.
  • Compare the change log with approved change records to find the gap.

In more detail

Modifying cloud compute configurations covers changes that reshape or hide running infrastructure, such as altering instance attributes, disabling termination protection, changing metadata or machine types, and stopping or redeploying virtual machines so that logs, agents and evidence disappear with the host. The detection strategy aggregates compute control plane write events in cloud audit logs by principal, resource and time, then compares them with the change record and the principal's normal behaviour, because a single attribute change is routine engineering while a burst of protective setting changes by an unusual identity is not. Its weakness is that these are legitimate administrative interfaces, so the rule depends on a maintained baseline of automation identities and on knowing which settings should never change in production.

What you will practise

  • Explain how compute configuration changes can support an intrusion.
  • Name the settings that deserve the highest priority in this detection.
  • Aggregate compute write events by principal and resource.
  • Identify the automation identities that legitimately change compute settings.
  • Describe how to enrich the alert with change management records.
