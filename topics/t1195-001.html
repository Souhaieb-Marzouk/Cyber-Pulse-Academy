T1195.001 Supply Chain Compromise: Compromise Software Dependencies and Development Tools

T1195.001Initial AccessExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Modern software is built from many ready made parts called dependencies, and robots called pipelines assemble and test the final product. This technique is when an attacker poisons one of those parts or one of those robots.

Why should you care?

A single poisoned part can be pulled into many products by a normal update. Developers rarely read every line of a dependency they add. Build pipelines hold secret keys, so a poisoned step can steal them. The damage appears during a build, far from the user computer.

How it works, in plain steps

  1. Developers add ready made code packages to their projects instead of writing everything.
  2. Attackers publish packages with names almost the same as popular real ones.
  3. A hurried install picks the wrong name and brings in harmful code.
  4. Attackers also target build steps in the pipeline that assemble the software.
  5. Such a step can read secret keys, change the release or push more bad code.
  6. Because build steps call other steps, one poisoned step can spread widely.

Real-world example

Think of a school project where each pupil brings one ingredient for a shared cake. One pupil brings flour from an unmarked bag. The teacher checks the cake, the oven and the recipe, but never the bags. Every slice on the table is now suspect, and nobody can tell which bag caused it.

Key takeaways

  • Every dependency you add is code you choose to trust and run.
  • Build pipelines hold secrets, so they are a target in their own right.
  • Review changes to dependency files and build steps as carefully as source code.

In more detail

This sub-technique narrows supply chain compromise to the building blocks developers pull in rather than the finished product they ship. The shared code that arrives from a package registry is the first target, because a single poisoned library or a typosquatted package name can be pulled into thousands of downstream applications by a routine dependency update. Maintenance is often thin, so an abandoned package can be adopted or re-registered by an attacker, and a maintainer account can be hijacked to publish a version that looks routine. Names are chosen to be nearly identical to a popular package so that a rushed or mistyped install does the attacker's work. The second target is the pipeline itself. Continuous integration and continuous delivery components, including hosted workflow actions, execute with the credentials of the build, so code inserted into one of them can read secrets, alter release artefacts or push further malicious commits, and because workflows commonly call other workflows, one compromised component can spread across many repositories. What separates this from the parent is timing and direction: the poisoned element is used while the software is being produced, so the malicious behaviour can appear during a build on a machine that never downloaded anything suspicious by name. Detection lives in the development and build records rather than on end user endpoints: dependency manifests and lock files that change in a commit that had no reason to change them, install or build steps that contact an address unrelated to the registry, build jobs that spawn a shell or read environment secrets, and published versions whose author or signing identity differs from the project norm. Where the organisation can enforce it, pinned versions with verified hashes and a review step for adding any new dependency reduce the chance that a silent substitution reaches production.
