DET0020 Detect Shell Configuration Modification for Persistence via Event-Triggered Execution

DET0020Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A shell is the text window where you type commands. It reads setup files each time it starts, to learn your shortcuts and settings. This detection watches those setup files for changes. It catches an intruder adding a command that runs again every time you open a shell.

Why should you care?

This trick is small but lasts a long time. It needs no new service and no scheduled job, so it slips past checks that only look for those. The added command runs as the user who opens the shell, often a powerful account. It also spreads quietly to any session on the same host. Cleaning up requires knowing exactly which line was added.

How it works, in plain steps

  1. The sensor watches a short list of shell setup files. These include the per user profile files and the system wide scripts.
  2. It writes an event whenever one of those files is modified, including which process made the change.
  3. The rule checks whether the writing process is a shell, an editor or an approved management tool. Anything else is flagged.
  4. It also reads the new content where the platform provides it, looking for download and execute patterns or hidden commands.
  5. Process events are joined in, so the rule can see a shell starting soon after with an unusual parent process.
  6. The combined facts go into one alert that names the file, the writer, the account and the added text.

Real-world example

Think of a shop where the opening checklist hangs by the door. Someone adds one extra line to the checklist. Every morning the staff then unlock a back door as part of their routine. Nobody notices, because the checklist still looks like a checklist. Shell profile detection is the camera on that clipboard.

Key takeaways

  • Persistence in a profile file runs again at every login, so removal is not enough without finding the writer.
  • The writer process and account are more useful than the file path.
  • Change management tooling edits these files too, so allow it by identity.

In more detail

This strategy detects persistence through shell configuration modification, mapped to ATT&CK technique T1546.004 Event Triggered Execution: Unix Shell Configuration Modification. The attacker appends a command to a file such as a user shell profile or system wide profile script so that the command runs again every time a shell starts, which survives reboots and usually does not need a new service or scheduled task. Detection rests on file integrity monitoring or audit rules that watch shell profile paths for writes, combined with process creation telemetry showing a non interactive writer such as a web server account, a database process or a remote session appending text to those files, and a shell process subsequently launched with an unusual parent. The correlation that matters is who wrote the file, with what process, and what started a shell afterwards. The strategy most often fails because legitimate configuration management and user login scripts rewrite the same files, so the rule needs to allow known management tooling and focus on writer identity rather than file paths alone.

  • Recognise suspicious content patterns inside profile file changes
  • Correlate a profile change with the shell session that follows it
