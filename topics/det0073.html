DET0073 Detection Strategy for System Services: Systemctl

DET0073Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

systemctl is the command used to manage services on Linux. A service is a program that runs in the background, such as a web server. This detection looks for signs that someone used that command to run their own program. It also looks for that program being set to stay running.

Why should you care?

A program started as a service runs with high rights. It starts again after a reboot, so it is a lasting foothold. Normal administrators use the same command every day, so the action itself is not strange. You must therefore look at what was started and who started it.

How it works, in plain steps

  1. A host tool called auditd records each command and the account that ran it.
  2. The detection follows the parent process. This shows who started the command.
  3. The system service manager writes a log entry when a service is started or enabled.
  4. A file watcher reports new or edited unit files in the service folders.
  5. The rule joins the file write with the start action by unit name and time.
  6. Files written by the package manager or the configuration tool are filtered out.

Real-world example

Think of an office building with one master key cabinet. Staff sign the book to open a door. An intruder signs the same book and takes a key. They then fit a new lock that only their key opens. The book shows a normal entry, and every door still works. Nobody notices until the fitter asks who ordered the extra lock.

Key takeaways

  • A new Linux service is a lasting way to stay on a host, because it restarts.
  • Judge a service change by the unit file and the parent process, not the command name.
  • Package manager and automation actions are expected, so filter them before you page anyone.

In more detail

This detection strategy covers abuse of the systemctl command on Linux hosts, where an operator uses the service manager to start a program, create a new unit, or install a timer so their code survives a reboot. It matters because the service manager is a trusted broker: a unit file that it loads runs as root, is restarted automatically, and blends with the hundreds of other units a normal server carries. The telemetry that makes the abuse visible is auditd process execution of systemctl and the shell that spawned it, systemd journal entries recording unit start, enable and reload operations, and file creation or modification events under the system unit directories and their timer paths. The signal worth alerting on is a new or changed unit file paired with a start or enable action in the same short window, attributed to a process that is not a configuration management tool or a package manager. It fails in practice for a familiar reason: systemctl is used constantly by legitimate automation, so any rule that keys on the command name alone produces unusable volume.

What you will practise

  • Explain how a Linux service manager provides persistence and why that matters after a reboot.
  • Locate the unit and timer file paths that should be monitored for new or changed content.
  • Correlate an auditd command record with the unit file write and the journal start entry.
  • Distinguish package manager and configuration management activity from interactive service creation.
  • Describe triage steps for a suspicious unit, including reading the unit file and checking what it launches.
