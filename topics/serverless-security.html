Serverless Security

Cloud SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Serverless security protects small pieces of code that run only when something happens, such as a file upload. The cloud provider runs and patches the machines. Your team still owns the code, its permissions and its data.

Why should you care?

Many teams believe the cloud provider handles all security. That is only partly true. If the code is given wide permissions, one small mistake can expose a whole account. Anyone who can trigger the code can reach it, so the entry points must be checked. Secrets hidden in settings can also leak into logs.

How it works, in plain steps

  1. An event happens, such as a new file, a message or a web request.
  2. The cloud provider starts a fresh, short-lived copy of your code for that event.
  3. The code runs with an identity that holds a set of permissions you defined.
  4. It reads or writes data, then the copy is destroyed and its memory is gone.
  5. Every invocation is recorded with its identity, inputs and results for review.
  6. Your job is to limit the permissions, validate the input and keep secrets out of the code.

Real-world example

Think of a hotel front desk. Guests do not clean the building or fix the lifts; the hotel does that. But each guest still receives one room key, not a master key. Serverless code is a guest that arrives for a few seconds, does one job and leaves. If you hand that guest a master key, a mistake in their task can open every room. Good serverless security is like issuing a key for a single room and logging every door the guest opened.

Key takeaways

  • Give each function only the permissions its single job needs.
  • Treat every event source, such as a queue or a web link, as untrusted input.
  • Keep secrets in a managed secret store, never in plain settings or logs.

In more detail

Serverless security covers the controls applied to code that runs on demand in a provider-managed platform, where the customer never patches a server, never chooses a host and often never sees a network. The dominant form is the function as a service model, in which a short-lived execution environment is created per event, given temporary credentials and destroyed afterwards. That shift moves the boundary of responsibility: the provider secures the physical hosts and the runtime, while the customer stays accountable for the code, its dependencies, its identity permissions and the data it touches. Real issues cluster in a few places. Over-permissive execution roles let a small bug read the whole account. Event sources such as queues, buckets and webhooks become unauthenticated entry points. Secrets live in environment variables and then appear in logs. Long-lived credentials are baked into deployment packages instead of using the platform identity. The usual mistake is assuming that because nothing visible needs patching, nothing needs hardening, when identity and input validation matter more than ever.

What you will practise

  • Explain the shared responsibility model for serverless platforms.
  • Describe how a temporary execution identity works during a function invocation.
  • Identify serverless entry points that need authentication and input validation.
  • Recognise why environment variables are a poor place for long-lived secrets.
  • List the logging and monitoring records useful for investigating a function.
