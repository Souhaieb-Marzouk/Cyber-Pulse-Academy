Insecure Direct Object Reference

Application SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An insecure direct object reference happens when a website shows a record to anyone. You only have to change a number in the address. The server never checks whether that record belongs to you. So one customer can read the private data of another customer. The name is long, but the idea is simple, a missing permission check.

Why should you care?

Your account page may use a link such as invoice 1042. If you change it to 1043, you might see someone else's invoice. An attacker can walk through thousands of numbers in a few minutes. This kind of flaw leaks private data such as addresses, medical notes or payment details. The company may also break privacy law and lose customer trust. Fixing it is cheap, but only if you test for it.

How it works, in plain steps

  1. A page asks the server for a record and names it by a number.
  2. The server looks up that number in its database and returns the record.
  3. It never checks whether the logged-in user is allowed to see that record.
  4. An attacker changes the number by hand, for example to invoice 1043.
  5. The server then returns another customer's private data without any complaint at all.
  6. The fix is a permission check on the server for every single object.

Real-world example

Imagine a hotel where room keys are just numbers printed on a card. You book room 214, and the card says 214. If you write 215 on a spare card and the door opens, the hotel has a problem. The lock trusted the number and never asked whether this guest had booked that room. A website with an insecure direct object reference is that lock. A link such as example[.]test/invoice/1043 must be checked against your account on the server, never hidden in the page.

Key takeaways

  • Changing a number in a link should never reveal someone else's data.
  • Check permission on the server for every object, on every request.
  • Random identifiers help, but they are not a replacement for access checks.

In more detail

An insecure direct object reference is an access control defect in which an application exposes an internal object identifier, such as a database key, file name, invoice number or account identifier, and then serves the object named by the client without verifying that the requester is entitled to it. The flaw is not cryptographic: the identifier may be a plain sequence or a random-looking token, and it fails either way, because the missing control is the server-side authorisation check on the object rather than the secrecy of its name. It appears most often in REST endpoints, download and export links, attachment handlers, password-reset flows and any API that accepts an identifier as a parameter. Remediation means checking ownership or permission for every object on every request, scoping queries to the authenticated principal, using unguessable identifiers as defence in depth, and testing by replaying another user's requests. The mistake is trusting client-supplied identifiers or assuming that an unpredictable value is an access control.

What you will practise

  • Explain what an insecure direct object reference is in plain language.
  • Describe how a missing server-side authorisation check allows the flaw.
  • Distinguish horizontal from vertical access control failures in a web application.
  • Describe how to test an endpoint for object-level authorisation as a second user.
  • Choose controls that prevent the flaw without depending on secrecy of identifiers.
