Nonce Reuse

CryptographyExtremeKeyword

Nonce reuse is the failure to supply a unique per-operation value to a cryptographic algorithm that requires one, and it quietly converts otherwise sound constructions into broken ones. The consequences depend on the mode. In counter-mode authenticated encryption such as AES-GCM, reusing a nonce with the same key leaks the XOR of the two plaintexts and exposes the authentication subkey, which allows an attacker to forge messages and, in many deployment patterns, to recover plaintext outright. In stream ciphers, the same keystream is produced twice, so ciphertext XOR reveals plaintext XOR. In signature schemes that take a per-signature secret, reusing it across two different messages lets anyone recover the private key with straightforward algebra, which has caused real-world key compromises in wallets and embedded devices. Nonces are not required to be secret, only unique within the scope of a key, but they must be unpredictable wherever an attacker can influence or predict them. Production failures usually come from weak randomness on constrained hardware, virtual machine clones that resume with identical state, counters that reset after a restart or a snapshot rollback, or application code that derives a nonce from a field like a user identifier, timestamp with poor resolution, or an incrementing database value that resets. Defensive practice means deterministic nonce derivation where the standard permits it, per-message key derivation, hardware random sources, monotonic counters persisted with the key, and monitoring for the duplicate-value signatures of these faults in protocol logs and telemetry.

What you will practise

  • Explain the uniqueness requirement for nonces, IVs and per-signature secrets, and why secrecy is not the goal.
  • Describe the concrete consequences of nonce reuse in GCM, stream ciphers and ECDSA signing.
  • Identify environment-level causes of repeated nonces such as cloned virtual machines, snapshots and reset counters.
  • Design a nonce strategy using deterministic derivation or per-message keys that survives restart and scale-out.
  • Detect nonce reuse indicators in protocol telemetry, signing services and transaction records.
  • Respond to suspected nonce reuse as a key compromise event rather than a configuration defect.
