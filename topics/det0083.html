DET0083 Container CLI and API Abuse via Docker/Kubernetes (T1059.013)

DET0083Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Containers are light packages that hold an application and its libraries. Commands such as docker and kubectl are used to manage them. This detection looks for those commands being used to run code inside a container. It also watches the cluster service that sits behind the commands.

Why should you care?

A container that runs with high rights can often reach the machine underneath it. From there an attacker can read the secrets of other containers. Platform teams use these tools constantly, so the tools alone prove nothing. The useful question is who ran the command, from where, and with how much power.

How it works, in plain steps

  1. Host sensors record command line tools being started. They include the arguments.
  2. They also record whether the process used the container runtime socket directly.
  3. The cluster control service writes a record for each request. It names the caller.
  4. The detection notes requests that attach to a running container or create a privileged workload.
  5. It compares the source address and identity against the pattern normal pipelines use.
  6. Known build agents and platform maintenance accounts are placed in a quiet lane.

Real-world example

Think of a shared warehouse where every forklift driver may move pallets. One driver starts lifting sealed crates in the manager section. The same driver stacks them near the loading door. Driving a forklift is completely normal there. The alarm belongs to the crates and the door, not to the forklift.

Key takeaways

  • Container hosts hold powerful secrets, so control of them is a big prize.
  • Watch who uses the cluster interface and from where, not just which tool was used.
  • A workload created with host level rights deserves immediate attention.

In more detail

This detection strategy covers the container control plane as an execution path, where an operator uses the container command line tools or the cluster interface to run code inside a running workload, create a privileged workload, or reach the runtime socket that manages them. It matters because container hosts concentrate trust: a single privileged workload or an exposed runtime socket can hand over the node and, through the node, the credentials of every workload that runs on it. The telemetry that makes it visible is process execution on container hosts around the command line tools, runtime daemon or socket activity, and the cluster audit log that records every control plane request with the identity, user agent, source address and target object. The pattern worth alerting on is interactive style use of these interfaces from an unexpected source: a shell attaching to a running container, a workload created with host level privileges, or control plane calls from an address and identity that normally only runs pipelines. It fails in practice because the same tools are the whole point of a platform team job, so the rule must be anchored to identity, source and privilege level rather than to the tool name.

What you will practise

  • Explain why the container control plane is a high value execution path.
  • Identify the process, runtime socket and audit log telemetry available on container hosts and clusters.
  • Detect interactive attachment to running containers and workloads created with elevated privileges.
  • Correlate control plane requests with the identity, user agent and source address of the caller.
  • Describe the response options for a compromised workload, including isolation and credential rotation.
