DET0595 Detection Strategy for Exploitation for Stealth

DET0595Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Some attackers do not bring a program with them. They send a specially shaped request to a service that is already running. The service then starts doing what the attacker wants. This detection looks for the side effects. It looks for a service that crashes, a strange child program, and a flood of odd requests.

Why should you care?

File scanning cannot find a file that does not exist. If an attacker only abuses a running service, classic antivirus review may show nothing at all. The service also already has permission to do useful things, so the attacker inherits that trust. Crashes are often dismissed as bugs and closed without investigation. This detection turns those dismissed events into a pattern that someone can review with the surrounding context.

How it works, in plain steps

  1. The endpoint agent records every new process, including its parent program and full command line.
  2. The rule knows which parent programs normally start child processes, based on a baseline per service.
  3. It also collects application error and crash reports, plus service restart records.
  4. Network or host based sensors count malformed or oversized requests aimed at the same service.
  5. The rule joins these streams by host and time. A crash, an odd child process and a request burst together form one alert.
  6. A single item on its own stays at a low level so it does not drown the queue.

Real-world example

Picture a hospital sign in sheet at a ward desk. Visitors must give a name and the patient they are seeing. Now imagine nobody stopped writing when a visitor walked into a staff only medicine room. The sheet still looks normal. What gives it away is a combination of clues. An alarm sounded on the medicine room door. A nurse saw a stranger. The ward camera showed a burst of activity. No single clue proves anything. Together they tell a clear story. This detection joins the clues the same way.

Key takeaways

  • When no file is dropped, you must detect behaviour instead of content.
  • Crashes and restarts are evidence, not just maintenance noise, when they line up with other signals.
  • You need a baseline of which program may start which child process, or the alert list will be full of normal helpers.

In more detail

This strategy covers exploitation for stealth, ATT&CK technique T1211, where an adversary runs a crafted input against a vulnerable application in order to obtain code execution while leaving no file on disk and touching only a service that is expected to be busy. Detection cannot rely on payload signatures, because there may be no payload file at all. Instead it correlates three weaker signals: an application that crashes or restarts unexpectedly, a child process or unexpected library load that appears under a service that should never spawn one, and a burst of malformed or oversized requests hitting one service from a single source. Each signal alone is unremarkable, which is exactly why the technique works; the value comes from joining them in a short window on the same host. The strategy degrades badly on hosts where the service already spawns helper processes by design, and on applications that crash routinely, so baselining process parentage per service is the main prerequisite.

What you will practise

  • Explain why exploitation without a dropped file defeats content based detection
  • Describe the side effects that exploitation of a running service tends to leave behind
  • Baseline normal parent and child process relationships for the services on each host group
  • Correlate application crash, service restart and request anomaly telemetry on the same host
  • Explain why each single signal is weak and how joining them reduces false alerts
  • Escalate a suspected exploitation alert into host isolation and memory review steps
