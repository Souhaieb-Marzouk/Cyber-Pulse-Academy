DET0231 Behavioral Detection of Systemd Timer Abuse for Scheduled Execution

DET0231Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for new scheduled tasks on Linux systems. A scheduled task is a job the computer runs on its own at set times. On modern Linux, these jobs are described in small text files called unit files. An attacker can add such a file so their program runs again and again. This detection watches the folder that holds those files and the command used to turn them on.

Why should you care?

A scheduled job keeps working after a restart, so access survives reboots. Jobs placed in the system folder usually run with the highest rights on the machine. Many teams monitor the older scheduling tool and forget the newer one. Finding the new job early lets you remove the file before it runs again.

How it works, in plain steps

  1. The system audit service records when files are added or changed in the scheduling folders.
  2. The rule checks whether the new file ends with the timer or service suffix.
  3. It records the user and program that created the file, such as a shell or a web server.
  4. The rule also watches the command that reloads the task list and enables a task.
  5. Files created by the package manager or a management agent are treated as normal.
  6. An alert fires when a task appears from an interactive session or an unusual program.

Real-world example

Think of a cleaner who is given a key to an office and told to visit every night. Once the key is handed over, nobody checks again. An attacker who files the paperwork for a nightly visit gets the same quiet access. The door log shows nothing unusual.

Key takeaways

  • Systemd timers are scheduled tasks that often escape cron based monitoring.
  • The user and program that created the unit file matter as much as the file itself.
  • A timer paired with a service unit that runs a script from a temporary folder is a strong signal.

In more detail

This strategy detects abuse of systemd timers for scheduled execution, tracked as ATT&CK T1053.006, where an adversary creates a timer unit and a matching service unit so that a payload runs on a schedule and restarts itself. It matters because systemd timers are the modern replacement for cron on Linux, they run as root by default when placed in the system unit directory, and they are frequently absent from cron focused monitoring and from host integrity baselines. The telemetry that makes it detectable is auditd file watches on the systemd unit directories, process creation events for systemctl and the unit files it acts on, and service manager logs recording unit load and start activity. The main failure mode is that package managers, configuration management agents, and container platforms create and reload units constantly, so the rule must separate deployment tooling writing units from an interactive shell or a web process doing the same thing.

What you will practise

  • Explain how systemd timer and service units combine to schedule recurring execution
  • Configure auditd file watches on the system and user unit directories
  • Identify process creation events for systemctl actions that load or enable a unit
  • Distinguish units created by package managers and configuration tools from those created interactively
  • Read unit contents to judge whether an ExecStart path is legitimate
  • Respond to a confirmed malicious timer without breaking scheduled maintenance jobs
