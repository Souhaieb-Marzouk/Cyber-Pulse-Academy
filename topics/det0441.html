DET0441 Detection of Suspicious Scheduled Task Creation and Execution on Windows

DET0441Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches for new scheduled tasks on Windows. A scheduled task tells the computer to run something later, or to run it again and again. Attackers use tasks to keep their program alive after a reboot. The detection reads the task details, not just the fact that one was created.

Why should you care?

A task that runs as a system account is very powerful. It can start code without anyone logging in. A task also looks normal in a task list. Many real tools create tasks, so the details matter. The details are what let you tell a patch job from a payload.

How it works, in plain steps

  1. Windows records a new task together with its definition text.
  2. The rule reads the action, the trigger and the account in that definition.
  3. It looks for hidden settings or unusual command lines in the action.
  4. It then watches for the task engine starting that action.
  5. The child process command line is added to the alert for context.

Real-world example

Think of a note left on the kitchen wall that says feed the cat at six. The note is normal. A note that says run this sealed envelope at six, signed by no one, is worth a question. You read the note, not just the fact that a note exists.

Key takeaways

  • The task definition field is the evidence you need.
  • Hidden tasks and short repeat intervals are strong signals.
  • Correlate creation with the execution that follows.

In more detail

This strategy detects the creation and execution of suspicious scheduled tasks on Windows, a technique used for persistence, for privilege escalation through a higher privileged account and for recurring execution of a payload without any interactive logon. The headline event is 4698, which records a new task being registered and includes the task definition in its task content field, and it is far more useful than process creation alone because the definition shows the action, the trigger and the author. Supporting telemetry includes the process that created the task, the task engine service image spawning the action, and the resulting child process with its full command line. It fails in practice for two reasons: task creation on its own is extremely common in managed fleets, and when the creating process is svchost.exe, the identity behind the request is often unavailable, so attribution has to come from a logon event correlated by time and host.

What you will practise

  • Describe what a scheduled task is and how Windows records a new one.
  • Read the task content field and identify the action, trigger and author.
  • Recognise hidden task settings and disguised system task names.
  • Correlate a task creation event with the process it later starts.
  • Separate user created tasks from software deployment tasks.
  • Explain why the creating process is often shown as a shared host process.
