Kubernetes RBAC

Cloud SecurityVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Kubernetes role-based access control, often shortened to RBAC, is the rule system that decides who may do what in a Kubernetes cluster. Kubernetes is a platform that runs containers across many machines. The rules name a person or service, the actions allowed, and the scope, such as one namespace or the whole cluster.

Why should you care?

Every request to a cluster goes through one entry point, the API server. If permissions are too wide, a small compromise grows fast. Someone who can create a container can often mount a login token or a host folder. Someone who can read secrets can take credentials for other services. Tight rules limit how far one stolen identity can reach.

How it works, in plain steps

  1. A user or a service account sends a request to the cluster API server.
  2. The server checks who the caller is, including the groups they belong to.
  3. It gathers the roles bound to that identity, in the namespace or across the cluster.
  4. A role lists resources, such as pods or secrets, and verbs, such as get or create.
  5. If a bound role covers the request, it is allowed, and the action is written to the audit log.
  6. If no role covers it, the request is refused and nothing happens.

Real-world example

Picture an office with one reception desk that approves every request. A junior staff member's badge opens their own floor and the shared kitchen. A manager's badge opens more doors. Nobody's badge opens everything. If a badge is lost, the damage depends on which doors it could open, so you keep each badge as small as the job needs.

Key takeaways

  • Roles describe permissions; bindings attach those roles to people or services.
  • Creating containers or reading secrets can be a path to more access.
  • Review admin bindings regularly and remove the ones nobody needs.

In more detail

Kubernetes role-based access control is the authorisation system that decides whether an authenticated request against the API server is permitted, by matching the requester's identity and group memberships against rules that name API groups, resources and verbs. Permissions are granted through Role objects scoped to a namespace or ClusterRole objects that apply cluster-wide, and they take effect only when bound to a subject by a RoleBinding or ClusterRoleBinding. Because the API server is the control plane's single entry point, RBAC governs far more than reading object lists: a subject that can create pods can often arrange for a pod that mounts a service account token or a host path, a subject that can read secrets can obtain credentials for other workloads, a subject that can create role bindings can grant itself anything, and permission to exec into pods or read pod logs provides a direct path to application secrets and internal services. These compound paths mean that reviewing individual rules in isolation is misleading and effective privilege must be computed across the graph of bindings, service accounts and default roles. Security teams inventory cluster-admin bindings and wildcard rules, examine default service account usage, restrict who may create workloads and bindings, and monitor the audit log for privilege-sensitive verbs. Good practice pairs authorisation tightening with authentication controls, since RBAC decisions are only as trustworthy as the identity source feeding them.

What you will practise

  • You will be able to explain how roles, cluster roles and bindings combine to authorise an API request.
  • You will be able to compute the practical privilege of a subject, including indirect paths through pod creation and secret reads.
  • You will be able to identify wildcard rules, cluster-admin bindings and default service account exposure in a cluster.
  • You will be able to rewrite over-broad bindings into namespace-scoped least privilege.
  • You will be able to use audit log evidence to triage privilege-sensitive API activity.
  • You will be able to explain why RBAC tightening depends on trustworthy authentication and workload identity.
