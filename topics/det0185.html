DET0185 Behavioral Detection Strategy for Use Alternate Authentication Material: Application Access Token (T1550.001)

DET0185Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches for stolen application tokens being used by the wrong person or machine. A token is a short lived key that a cloud app uses instead of a password. The rule compares where and how a token is used against how it is normally used.

Why should you care?

Many cloud services trust a token without asking for a password again. If an attacker steals one, they can read mail and files as the application. Multi factor authentication does not help here, because no interactive login happens. This makes token theft a quiet way to keep access. Watching token usage gives you a second chance to notice.

How it works, in plain steps

  1. An application asks the identity provider for an access token.
  2. The provider records who asked, for which application, and from which network address.
  3. The cloud service logs each call that the token makes to its interfaces.
  4. The rule builds a normal profile for that application, including usual addresses and times.
  5. New usage is compared with that profile, such as a rare country or an odd user agent string.
  6. If the usage really stands out, the alert fires with the application identifier attached.

Real-world example

Think of a staff car park with an automatic gate. Each car has a windscreen tag, and the gate opens without anyone checking the driver. The gate log shows the tag number and the time. If the same tag enters two different car parks in two cities within ten minutes, the tag was copied. Nobody had to steal a key, and the gate still gave you the clue.

Key takeaways

  • Tokens skip the login prompt, so password controls cannot stop token abuse.
  • Location, user agent and permission breadth are the fields that reveal a replay.
  • Alert on the identity provider records, not only on the service that was called.

In more detail

This strategy detects abuse of application access tokens, the credential type that cloud identity providers issue to applications instead of a user password. It matters because a stolen token lets an adversary call mail, file and directory interfaces directly, bypassing the interactive sign in path where most of your controls live. Detection is built on identity provider audit records and cloud service access logs that record token issuance, the requesting application identifier, the source address and the user agent. The main practical failure is that token replay looks exactly like the application doing its job, so the rule has to compare the token context against a learned baseline of application behaviour rather than rely on any single field.

What you will practise

  • Explain what an application access token is and why it bypasses interactive sign in controls.
  • Identify the identity provider records that show token issuance and the requesting application.
  • Correlate a token grant with the subsequent service calls made using the same identifier.
  • Build a behavioural baseline of address ranges and user agents for each application.
  • Recognise high risk permission scopes such as mail read or file write granted to a new application.
  • Describe how token lifetime settings change what the detection can and cannot see.
