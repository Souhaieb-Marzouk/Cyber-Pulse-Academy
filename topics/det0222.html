DET0222 Detecting MMC (.msc) Proxy Execution and Malicious COM Activation

DET0222Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks at a Windows tool that administrators use, called the Microsoft Management Console. The tool can load extra modules and console files. An attacker can give it a harmful module, or a file from a network share. The rule watches how the tool is started and what it loads.

Why should you care?

The console tool is signed by Microsoft, so the system trusts it. When it starts, its actions can look legitimate. Attackers use trusted tools like this to avoid suspicion. A console file can also sit on a remote share, so one small file controls the loaded code. The start up details reveal the abuse.

How it works, in plain steps

  1. Process creation logs record each start of the console tool, together with its full command line.
  2. The rule checks the command line for console files and for registered module identifiers.
  3. It flags files that are loaded from network shares, web addresses, or temporary folders.
  4. It then looks at the child processes that the console starts.
  5. It compares the parent process with normal administrator behaviour on that host.
  6. A remote console file that leads to a scripting host or a temporary binary raises the alert.

Real-world example

Think of a master key that opens many doors in an office. It is trusted, so nobody questions it. If that key is copied and used by a stranger at midnight, the door log tells the story. The console tool is that master key.

Key takeaways

  • Trusted system programs can run attacker code without looking strange.
  • The command line and the file path are the strongest clues here.
  • Child processes show whether the console did something useful or harmful.

In more detail

This strategy covers T1218.014, MMC, where an actor uses the Microsoft Management Console as a signed host to run their own logic, typically by loading a console file or snap-in from a network share, a web address, or a temporary folder. Detection depends on process creation telemetry for the console host with full command line auditing, plus the child processes and module loads that follow the start. The main problem is that console files are everyday tools for administrators, so the origin of the file and the parent process matter far more than the binary name itself.

What you will practise

  • Explain what proxy execution means and why signed system tools are chosen for it.
  • Identify process creation telemetry that captures console tool command lines and child processes.
  • Recognise command line patterns that point to remote or temporary console files.
  • Distinguish routine administrator console use from suspicious invocation paths.
  • Describe how to combine parent and child process evidence into one rule.
