T1059.003 Command and Scripting Interpreter: Windows Command Shell

T1059.003ExecutionVery hardTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

The Windows Command Shell is the older text tool on Windows, started by a program called cmd.exe. You type short commands and it runs them, and batch files are simply lists of those commands saved in a file. It has been part of Windows for decades. Many maintenance tasks still rely on it today.

Why should you care?

Attackers use this shell because it is everywhere and nobody removes it. It can chain many small commands into one line, so a single short process can search a system, copy files and clean up. Legitimate installers and login scripts produce a huge amount of the same traffic. If you have no baseline of what normal looks like, you will either miss the attack or drown in false alarms.

How it works, in plain steps

  1. Something starts the command shell, and the program that started it is often the biggest clue.
  2. The full command line is recorded when the process starts, so you can read what was asked.
  3. The shell runs built-in commands and calls other small tools that already exist on Windows.
  4. Those tools touch files, services and the network, and each action leaves its own record.
  5. You rebuild the short story from the starting program, the command line and the events that followed.

Real-world example

Think of a cleaner who carries a master trolley with every tool on it. Nobody questions a cleaner pushing a trolley down a corridor, because that happens a hundred times a day. But if the trolley appears in the server room at midnight, and the same trolley turns up in three other locked rooms, you start asking questions. The Windows command shell is that trolley. The tool is ordinary, but the place and the timing give it away.

Key takeaways

  • The command shell is normal on Windows, so context matters more than the program name.
  • A document reader or web server starting a shell is a strong warning sign.
  • Keep command line logging on, because it is your main record of what the shell did.

In more detail

The Windows Command Shell, implemented by cmd.exe, is the legacy interpreter for batch files and interactive command execution on Windows. It provides built-in commands for file manipulation, process and service control, network configuration, and scheduled task creation, and it acts as a launcher for other utilities. Adversaries favour it because it is universally present, is not typically removed by hardening, and blends with a very high volume of legitimate administrative and installer traffic. Typical abuse patterns involve chaining built-in commands together with shell redirection and the command separator to perform discovery, staging, and cleanup within a single short-lived process. The artefacts left behind are concentrated in process creation telemetry. The parent process is often more informative than cmd.exe itself, because the shell is frequently spawned by a document reader, a script host, a service, or a webshell. Command lines containing long chains of separators, repeated directory traversal toward temporary or public directories, and redirection into executable file types are notable. Script Block Logging does not cover cmd.exe, so visibility depends on command line auditing, the process creation event source used by the endpoint agent, and file and registry events generated by whatever the shell touched. Batch files executed from user-writable paths leave a file creation record that may be deleted immediately afterwards. Routine use includes login scripts, software deployment wrappers, backup jobs, and diagnostic commands run by administrators. The distinguishing factors are context and sequence: an unusual parent, a service account running console utilities interactively, network share access immediately preceding shell execution, and command content that maps to discovery or staging rather than to a scheduled maintenance task. Comparing the observed command line against the standard image of the host and against known automation accounts resolves most apparent positives.

What you will practise

  • Describe how cmd.exe parses command separators, redirection, and quoting, and why that parsing shapes what appears in log records.
  • Extract and interpret parent-child process relationships that indicate a shell spawned by an unexpected host application.
  • Build SIEM-style queries that surface anomalous command shell usage while suppressing known installer and login script noise.
  • Reconstruct a short shell session from command line auditing, file creation, and registry events when no script logging is available.
  • Explain the visibility limitations of resource kit tooling historically used to log console activity and how it fails on modern systems.
  • Map observed shell behaviour to ATT&CK and document the specific telemetry gaps that remain in the environment.
