T1102.002 Web Service: Bidirectional Communication

T1102.002Command and ControlExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is a way of running a command and control channel inside a normal website. The attacker writes instructions into the website, and the infected computer reads them there. That same computer then posts the results back to the website.

Why should you care?

The traffic looks like ordinary use of a popular service, so simple blocking rules are hard to write. If you block the whole service, real employees lose tools they need. The channel also survives without any attacker owned server. Only careful watching of which program talks to the service, and how often, gives you a clue.

How it works, in plain steps

  1. The implant is pointed at a normal service, such as a forum, a chat tool or a hosted document.
  2. It asks the service for new content, for example the newest comment under one post.
  3. Hidden in that content is a command, encoded so that it looks like ordinary text.
  4. The implant runs the command and then posts the output back to the same service.
  5. The attacker reads the result and writes the next command into the same place.
  6. The result is a live, two-way conversation that travels through one trusted website.

Real-world example

Imagine you share a rented locker with a colleague instead of meeting in person. Each morning you open the locker and read the note left for you. You do your part, write the answer in the same notebook and put it back. Anyone walking past sees only someone using a public locker, yet a full conversation has taken place inside it.

Key takeaways

  • Instructions and results both travel through a legitimate service, so the domain looks harmless.
  • The pattern is regular polling with matching writes, which is unusual for most desktop software.
  • Judge the process, not just the domain: ask whether this program should talk to that service at all.

In more detail

Bidirectional communication over a legitimate web service turns a public platform into a full command channel in both directions. The implant reads tasking that the adversary has placed on the service, for example a comment, a chat message, a document or a repository entry, and then writes command output back to the same service, often as another comment, an updated file or a new repository object. Traffic therefore stays inside ordinary encrypted sessions to a domain the organisation already permits, and neither the instruction nor the result has to touch adversary owned infrastructure. The pattern is detectable mostly through behaviour and volume rather than domain reputation: a process that has no business reason to reach the platform now holds a periodic, roughly fixed interval session and alternates reads with writes of similar size. Content inspection is limited by transport encryption, so correlation between endpoint process telemetry, proxy records and account activity on the service carries most of the weight.

What you will practise

  • Explain how an implant both receives tasking and returns output through a single legitimate web service.
  • Describe the signs that a host is polling a public platform on a fixed schedule from an unexpected process.
  • Compare bidirectional web service channels with ordinary employee use of the same platform.
  • Identify endpoint, proxy and service side log sources that together reveal this channel.
  • Assess why domain blocklists alone rarely disrupt this form of command and control.
