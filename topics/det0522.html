DET0522 Detect Kerberos Ticket Theft or Forgery (T1558)

DET0522Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches for stolen or copied Kerberos tickets, and for tickets that an attacker made. Kerberos is the system Windows domains use to prove who you are without sending your password each time. A copied ticket can be used from another machine. A forged ticket can claim any identity. The alert looks for unusual ticket requests and impossible ticket details.

Why should you care?

A Kerberos ticket is a pass that a server trusts. If an attacker copies it, they can act as the real user. A password change does not stop them, because the ticket is already issued. A forged ticket can open almost any door in the domain while it lives. Normal sign-in alerts miss this, because the logon looks valid. Ticket events give you an early view of this activity.

How it works, in plain steps

  1. The domain controller writes a record each time it issues a ticket granting ticket or a service ticket. The record names the account and the source address.
  2. A collector forwards those records to the central platform. There the rule groups them by account and source host over a short window.
  3. The rule looks for a sudden rise in service ticket requests from one account. This is stronger when the account never uses those services.
  4. It also checks the encryption type field, because older weak encryption such as RC4 often means a downgrade was requested.
  5. Finally it compares ticket lifetimes, and flags tickets that stay valid far longer than your policy allows.
  6. Matching activity is enriched with the asset owner and the service names before it reaches the analyst queue.

Real-world example

Think of a hospital sign-in sheet. Staff show a badge, and the desk writes down the name and the rooms that person may enter. A thief can copy a badge from a coat and use it later. Another thief can print a badge with any name at all. The desk log still looks normal. Only the small details show the problem. One badge may be used in two places at once. Another may be valid for ten years.

Key takeaways

  • A copied or forged ticket works without a password, so password resets do not remove the access.
  • Volume, encryption type and ticket lifetime are the three details worth alerting on.
  • Baseline ticket requests per service account first, or automation will drown the queue.

In more detail

This detection strategy targets the theft of a Kerberos ticket from memory and the later use of a forged ticket, the behaviours grouped under steal or forge Kerberos tickets. A stolen ticket lets an attacker authenticate as the victim without knowing the password, and a forged ticket signed with a recovered key can grant access to any service in the domain. Domain controller Kerberos service events, ticket request volume and encryption type fields, logons that reuse an unexpected ticket, and impossible ticket lifetimes make the pattern visible. The hard part is separating automated enumeration from application behaviour that legitimately requests thousands of service tickets, so request volume must be baselined per account and per source host before thresholds are set.

What you will practise

  • Describe how a stolen Kerberos ticket lets an attacker authenticate without a password
  • Identify the domain controller event fields that record the requesting account, source address, service name and ticket encryption type
  • Explain why weak or downgraded encryption on service ticket requests is worth investigating
  • Build a per account and per host baseline of normal service ticket request volume
  • Explain why forged tickets can show lifetimes that policy does not allow
  • Write a triage plan that checks the source host, the account and the requested services before escalation
