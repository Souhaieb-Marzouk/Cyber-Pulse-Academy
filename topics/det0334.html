DET0334 Detection Strategy for T1525 – Implant Internal Image

DET0334Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches for new software images added to your own private library. An image is a saved copy of a whole system that you can start again and again. Attackers put their own image inside your library, then start it as if it were yours.

Why should you care?

Your teams trust images that come from your own library. A malicious image there spreads to every machine that uses it. It also looks like ordinary deployment work in your records. Narrowing this gap stops an attacker from hiding behind your own supply chain.

How it works, in plain steps

  1. Your image library records every upload, who did it and when.
  2. The detection looks for uploads from accounts or networks that do not normally publish images.
  3. It compares the new image with the previous version of the same name to see unexpected changes.
  4. It records where the image came from, such as a build system or a manual import.
  5. It then watches for machines or workloads started from that image within a short time.
  6. An upload followed by new workloads, from an unusual publisher, becomes one grouped alert.

Real-world example

Think of a company cafeteria that only serves food from its own kitchen. Nobody checks the food again, because the kitchen is trusted. If a stranger in a kitchen coat adds a dish to the counter, everyone still eats it. The person checking who entered the kitchen is your best control.

Key takeaways

  • Trusted internal sources need their own monitoring, because nobody re-checks them.
  • An image upload is only interesting when you link it to who published it and what used it.
  • Compare image versions, because a small change to a familiar name is easy to miss.

In more detail

This strategy detects implanting an internal image (T1525), where an adversary uploads a container image or machine image into a registry or cloud account the victim organisation already trusts, then launches workloads from it so the activity looks like a normal internal deployment. The telemetry is control plane and registry oriented: image push events, new image layer digests, registry authentication, image build or import jobs and the subsequent instance or pod creation using that image. Because the technique abuses trusted internal sources rather than external downloads, it defeats rules that only look outward. It fails in practice when push logging is not enabled, when shared build accounts are used by many teams, and when the image is modified in place without a registry event.

What you will practise

  • Explain how a trusted internal image becomes an execution path
  • List the registry and cloud control plane events that record an image being published
  • Correlate an image publish event with the workloads created from that image
  • Use image digests and layer history to spot unexpected changes to a familiar name
  • Describe why rules that only watch external downloads miss this technique
