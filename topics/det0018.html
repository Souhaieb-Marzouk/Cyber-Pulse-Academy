DET0018 Behavior-chain, platform-aware detection strategy for T1129 Shared Modules

DET0018Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A shared module is a file of reusable code that many programs load when they start. On Windows these files are called DLLs. This detection looks for a program loading a module from a place it should not, such as a temporary folder. It catches code being slipped into a trusted process.

Why should you care?

When a trusted program loads a strange module, that module runs with the trust of the program. It can hide inside a signed process and avoid simple checks. This is a common way to run code without a new visible program. It also lets an attacker keep running after other tools are removed. The behaviour is hard to spot without module level logging.

How it works, in plain steps

  1. The sensor writes an event when a new file appears, and another event each time a process loads a module.
  2. The rule first collects module files that were created outside the normal system and program folders.
  3. It then looks for load events that name exactly those file paths.
  4. The loading process must be one that normally only loads signed modules from vendor directories.
  5. The two events are joined by host and path inside a time window. A plain file copy is therefore not enough to alert.
  6. The alert lists the writer process, the loading process and the module path so an analyst can judge the intent.

Real-world example

Imagine a hospital where staff wear official badges. A visitor prints a badge that looks the same and walks into the pharmacy. Nothing about the badge is obviously fake, but nobody checked where it was made. Shared module detection is the log of a badge printed outside the badge office. It shows that badge used at a restricted door.

Key takeaways

  • Module loads happen constantly, so pair them with a file creation event to stay usable.
  • The path of the module and the identity of the loading process are the key facts.
  • Baseline the vendor module paths on your hosts, because patching changes them.

In more detail

This strategy detects abuse of shared modules, mapped to ATT&CK technique T1129, the general behaviour where a process loads code from a shared library, DLL or shared object that it should not be loading. The technique is broad on purpose: it covers loading a module from a user writable directory, planting a library where a trusted program searches first, and injecting a module into an already running process. Because legitimate software loads thousands of modules, the detection cannot alert on module loads alone; it has to be behaviour chained. A practical rule correlates a file write event that creates a module in a non standard directory with a later module load event for that same path into a different, usually trusted, process, and adds the process lineage of whoever wrote the file. The main failure mode is volume and baseline drift, since patch cycles legitimately introduce new modules from new paths, so the rule needs per host baselines and a tight allow list of vendor directories rather than a global one.

What you will practise

  • Describe how loading a shared module can run code inside a trusted process
  • Identify file creation and module load telemetry that together reveal shared module abuse
  • Use process lineage to attribute a planted module to an account and a parent program
  • Explain why module load events alone are too common to alert on
  • Plan host level baselines of legitimate module directories and signing status
