DET0572 Suspicious RoleBinding or ClusterRoleBinding Assignment in Kubernetes

DET0572Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This rule looks for new permission grants in a Kubernetes cluster. Kubernetes is a system that runs container workloads across many machines. A binding is the record that links a person or program to a set of permissions.

Why should you care?

Permissions in a cluster decide what a workload can read, change or delete. One extra binding can give an attacker control of every workload. The change is small and easy to hide among normal platform work. Reviewing it early can stop a small foothold from becoming full control.

How it works, in plain steps

  1. The platform collects the cluster audit log, which records every request to the programming interface.
  2. A filter keeps requests that create or change a role binding.
  3. The platform reads which role the binding points to, and how powerful that role is.
  4. It records who made the request, from which address and with which client tool.
  5. Each request is compared with the normal pattern for that cluster and that account.
  6. An alert fires when a powerful role is bound outside the normal deployment pipeline.

Real-world example

Think of a hotel where each key card opens certain rooms. A manager may add a new card to the system, which is normal. Now imagine a card that opens every room. It was added at night, using a contractor account. That is worth a call to the manager before the guest checks out.

Key takeaways

  • Permissions move through bindings, so watch binding creation closely.
  • The power of the bound role decides how serious the finding is.
  • Hidden workload identities need watching too, not just human accounts.

In more detail

This detection strategy addresses suspicious RoleBinding and ClusterRoleBinding assignments in Kubernetes, tracked as T1098.006, where an adversary grants a user, group or service account rights it should not hold, often by binding an existing powerful role to a new subject. It matters because a single binding can turn a compromised workload identity into cluster administrator, and because bindings persist quietly and are rarely reviewed after creation. Detection rests on the Kubernetes API audit log, which records the binding create and update requests together with the requesting identity, the source address and the user agent, plus admission controller records and role definition changes that show which permissions the binding actually confers. It fails in practice for two reasons: platform teams, GitOps pipelines and managed operators create bindings constantly, and a binding that grants an existing role through a legitimate looking subject name may never be reviewed.

What you will practise

  • Explain what a RoleBinding and a ClusterRoleBinding do in a cluster.
  • Identify the audit log fields that record a binding request.
  • Describe how to score a binding by the permissions of the referenced role.
  • Explain why service accounts are a favourite target for permission grants.
  • List the automation that legitimately creates bindings and how to allow list it.
