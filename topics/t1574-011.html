T1574.011 Hijack Execution Flow: Services Registry Permissions Weakness

T1574.011ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Windows keeps each service setting in a database called the Registry. One setting records which program file the service should run. If the permissions on that registry key are too loose, an attacker can change that setting. The service then runs the attacker program instead of the real one.

Why should you care?

This gives an attacker the same power as swapping a program file, but the file on disk stays untouched. Many services run as SYSTEM, the most powerful local account, so the attacker code runs with those rights. The change also survives reboots and can be missed by tools that only scan files. Teams often forget to check registry permissions during a build.

How it works, in plain steps

  1. A service stores its setup, including the program path, in a registry key under Services.
  2. The key permissions are too open and allow a normal user to change values.
  3. The attacker edits the program path value so it names their own file.
  4. The attacker may instead edit a failure command or a performance library setting.
  5. When the service starts or fails, Windows loads the file named in the value.
  6. The loaded file runs with the account the service uses, often SYSTEM.

Real-world example

Imagine a hotel front desk with a booking book that lists which room key opens which door. A guest finds the book unlocked and rewrites one line so their own key opens the manager office. The book looks normal and no door was changed. The manager keeps using the same office each day without noticing the new line.

Key takeaways

  • Audit registry permissions on service keys, not just file permissions.
  • Alert on any change to a service image path or failure command.
  • Treat unexpected DLL paths inside service settings as a red flag.

In more detail

This sub-technique abuses weak access control lists on service registry keys under HKLM\SYSTEM\CurrentControlSet\Services, allowing a low-privileged user to rewrite how a service starts. The most direct change is the ImagePath value, also called binPath, which names the executable the service control manager launches, but the surrounding tree offers other levers: the FailureCommand value executed when a service fails, a Performance subkey that names a performance DLL and its exported functions, and a Parameters subkey whose values can point at driver or DLL paths loaded by the service or its libraries. Because the service starts under its configured identity, any redirected load runs at that context, providing privilege escalation, and recurs at every boot or restart for persistence. The classic instance is the AutodialDLL value, whose path is loaded whenever the Winsock library is used. Detection relies on registry auditing and change monitoring of the Services tree, on command lines such as sc.exe config or a service controller changing a path, and on service image paths in process creation records that point outside expected directories or carry unexpected hashes. Any such change is rare in normal operations and highly suspicious.

What you will practise

  • Explain how service configuration stored in the registry controls what runs.
  • Identify the values and subkeys an attacker can redirect in a service key.
  • Describe the privilege and persistence impact of a redirected service path.
  • Use registry auditing and service event data to detect these changes.
  • Outline permission hardening for the service registry tree.
