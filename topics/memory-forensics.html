Memory Forensics

Incident Response & ForensicsHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Memory forensics means looking at the contents of a computer's working memory to find evidence. Working memory is the fast storage a computer uses while it is switched on, and it is often called RAM, short for random access memory. Unlike files, memory is wiped when the power goes off. Memory forensics is the careful study of that short lived data.

Why should you care?

Some harmful programs never save a file on disk, so they live only in memory. If you switch the computer off, all proof of them disappears forever. Memory also holds useful details such as network connections and secret keys. Investigators need these details to understand what happened and how far it spread. Restarting a suspect machine is an easy way to lose the best evidence.

How it works, in plain steps

  1. Treat the running computer as the crime scene and stop anyone from switching it off or restarting it.
  2. Capture the memory as one large image file, writing it to a separate external disk.
  3. Use a trusted collection tool, because running unknown software would change the memory you are saving.
  4. Load the image into an analysis tool that understands the operating system's internal structures.
  5. Rebuild the list of running programs, loaded drivers, open connections and hidden entries.
  6. Compare what you find with disk evidence and logs to build a story you can defend.

Real-world example

Think of a library reading room just before closing. The books left open on the tables show exactly what people were reading that day, and the notes beside them show what they planned next. Once the cleaners stack the books and switch off the lights, that picture is gone forever. A photograph taken before closing preserves it, but the photo is a little blurry, because people were still moving while it was taken. Some visitors read only in that room and never borrow a book, so the shelves tell you nothing about them. The photograph of the room is your memory image.

Key takeaways

  • Capture memory before any restart, because volatile evidence disappears with the power.
  • Use a trusted tool and write the image to separate media, never to the same machine.
  • Memory images are powerful but incomplete and sensitive, so handle them as protected evidence.

In more detail

Memory forensics, also called volatile memory analysis, is the acquisition and interpretation of a system's random access memory, or RAM, to reconstruct what was happening at the moment of capture. It exists because a large amount of high value evidence never reaches disk: running processes, loaded drivers and kernel modules, open network connections, injected code regions, cached credentials, encryption keys and chat or document contents held by an application. Acquisition must occur while the machine is still powered on, because powering down or rebooting destroys the entire dataset, and it should be performed with a trusted tool writing to external media so that the capture does not overwrite the memory it is reading. The resulting image is then parsed by a framework that understands operating system structures, which lets an analyst rebuild the process tree, list hidden or unlinked processes, inspect loaded modules, recover configuration and locate injected regions. Interpretation is the hard part: the image is a single, slightly incoherent instant of a live system, since the kernel kept modifying structures during capture, and residual data contains historical fragments that can mislead. Memory analysis is therefore strongest for fileless and kernel level threats and for key recovery, but it is fragile, sensitive and only as good as the moment it was taken. The common mistake is shutting the machine down to preserve it, or running collection tools directly from the suspect system.

What you will practise

  • Define volatile memory forensics and explain which evidence exists only in memory.
  • Describe correct acquisition practice, including order of volatility and trusted collection tooling.
  • Explain how process lists, loaded modules and network connections are reconstructed from an image.
  • Recognise why fileless and kernel level threats are best investigated with memory evidence.
  • Discuss the limits of interpretation, including capture inconsistencies and residual historical data.
