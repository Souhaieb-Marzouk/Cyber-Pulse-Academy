T1552.005 Unsecured Credentials: Cloud Instance Metadata API

T1552.005Credential AccessExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Cloud servers can ask a built-in service for information about themselves. This service is reachable only from inside the server. It answers with details such as the server's name and the keys it may use. This sub-technique is when an attacker on the server asks the same service for those keys.

Why should you care?

The service often hands over temporary keys for cloud storage, databases, or more servers. Those keys can turn a small foothold into a large breach. Because the service is meant to answer, there is no password to guess and no alarm by default.

How it works, in plain steps

  1. Cloud providers run a small information service inside each virtual server they host.
  2. The service answers questions about the server, such as its name and network details.
  3. It can also return temporary keys for the roles attached to that server.
  4. An attacker who reaches the server simply sends a request to the service address.
  5. Alternatively, they trick a public website into making the request on their behalf.
  6. The keys they receive let them reach cloud storage, databases, or more machines.

Real-world example

Imagine a hotel room telephone connected to reception. You can dial and ask about your booking, the wifi, or the shuttle time. If reception also answers when you ask for the master key, a guest has more than they should. The phone was installed as a convenience, and nobody checked who was calling.

Key takeaways

  • Instance metadata is sensitive, so treat requests to it as security events.
  • Requesting the metadata address from inside your own server is rarely normal.
  • Protect public web applications from requests that reach internal services.

In more detail

This sub-technique is credential collection from the cloud instance metadata service, a link local endpoint that cloud providers expose so a virtual machine can learn about itself. The service is reachable without credentials from inside the instance and commonly returns instance identity details, network configuration, attached role names, and the temporary credentials that go with those roles. Many providers also return the user data script supplied at launch, which frequently contains secrets that administrators placed there. Adversaries reach it either directly, after gaining a foothold on the instance, or indirectly by exploiting a server side request forgery flaw in a public web application so that the server itself makes the metadata request. The address is widely standardised as a link local address in the 169.254 range. Detection has two sides: process and network telemetry on the instance for requests to that address from unexpected binaries, and web application logs showing requests to it through a proxy or application. Legitimate cloud software development kits query it, so the discriminator is an unfamiliar client, an unexpected user agent, or a source that is not the instance's own management agent.

What you will practise

  • Explain what a cloud instance metadata service is and why it exists.
  • Describe the kinds of sensitive data the service can return to a requester.
  • Explain how a public web application fault can be used to reach the service.
  • Identify the process, network and web logs that reveal metadata queries.
  • Describe hardening options that limit the value of a metadata response.
