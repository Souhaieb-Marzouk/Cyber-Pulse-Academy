T1528 Steal Application Access Token

T1528Credential AccessExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An access token is a long string of characters that proves an application is allowed to use a service, working a little like a ticket. This technique is about an attacker copying that ticket and using it themselves. Because the ticket is valid, the service treats the attacker as if they were the real application.

Why should you care?

Tokens often work without a password and without the extra code sent to a phone, so there is no login step to spot. The permissions can be broad, because automation accounts usually need to reach many systems. A stolen refresh token can let an attacker keep getting fresh tickets long after the first one expires. Cloud services are shared and connected, so one stolen token can open many doors.

How it works, in plain steps

  1. The attacker gets code running inside a container, build job or cloud server.
  2. They read files and settings where the platform keeps tokens, such as disks or environment values.
  3. On cloud servers they may ask the built-in metadata service for a token tied to the role of the machine.
  4. They send that token in requests, so the service sees a trusted application making the call.
  5. In the consent path they register an application and trick a user into approving it.
  6. They may also take refresh tokens, which produce new access tokens without any prompt.

Real-world example

Think of a hotel key card that opens the gym, the pool and the car park. A guest finds one left in a room and copies it at a machine in the lobby. The doors all open normally, because the card is genuine. Staff only notice if they compare the list of cards used with the list of cards actually issued.

Key takeaways

  • A token is a password that does not look like one, so protect where it is stored.
  • Watch for tokens used from unusual places or at unusual times.
  • Review new application approvals, because consent can replace theft.

In more detail

Steal Application Access Token targets the bearer credentials that services use to call each other. An access token is presented instead of a password, so whoever holds the string is treated as the application or service account until the token expires. Theft therefore often needs no cracking and no interactive login, which is why it is prized in cloud, container, and software-as-a-service environments. Collection points include container file systems that mount service account tokens for Kubernetes API access, continuous integration and delivery runners that hold deployment credentials in environment variables or configuration, instance metadata endpoints that hand short-lived tokens to workloads with attached managed identities, local command line histories and configuration files for cloud command line tools, and password managers or proxy logs where bearers are recorded. A second path is consent rather than collection: the adversary registers an application with an identity provider and persuades a user to approve it, which issues the application a token with the permissions the user granted, and often a refresh token that keeps producing new access tokens without further prompts. Detection combines audit records and behavioural analysis, since the token itself is valid.

What you will practise

  • Define an application access token and explain why it acts as a credential.
  • List common places tokens are stored in cloud, container and pipeline environments.
  • Describe how application consent can grant tokens without any theft.
  • Identify audit records that reveal token use from a new location or identity.
  • Recommend controls such as short lifetimes, scoped permissions and approval review.
