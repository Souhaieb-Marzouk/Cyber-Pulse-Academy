T1090.004 Proxy: Domain Fronting

T1090.004Command and ControlExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Domain fronting is a trick that makes encrypted web traffic look like it is going to a harmless, popular website when it is really going somewhere else. It works by putting one name in the outer, visible part of the connection and a different name in the hidden request inside. This technique is a sub-technique of Proxy, the general idea of hiding traffic behind another computer.

Why should you care?

Blocking a bad website is easy until the traffic pretends to be a good one. Domain fronting can make malicious traffic pass through filters that allow large cloud providers, because those filters trust the visible name. It also defeats blocking tools used in some countries, so it appears in both crime and censorship research. If you ignore it, your allowlist may quietly become a tunnel for an attacker.

How it works, in plain steps

  1. A content delivery network hosts many customers and serves all of them from shared address space.
  2. The malware contacts that provider and names a friendly customer domain in the TLS handshake.
  3. A TLS handshake is the opening exchange where a client and server agree how to encrypt their talk.
  4. Inside the encrypted tunnel, the malware sends a request naming the real attacker-controlled domain.
  5. The provider reads the inner name and forwards the request to the attacker's server.
  6. Your security devices only see the friendly outer name and allow the connection to continue.

Real-world example

Picture a large shared office building with one front desk and one street address. The desk sign says City Library, so the guard at the gate waves everyone through. A visitor walks in and quietly asks the desk to send them to a private office on the tenth floor instead. The guard only ever logged the street address of the building, so every visit looked like a trip to the library.

Key takeaways

  • The visible name in a connection is not proof of the real destination.
  • Compare the certificate or handshake name with the host name inside the request when you can.
  • Allowlisting a whole cloud provider is nearly the same as allowing everything it hosts.

In more detail

Domain fronting hides the real destination of encrypted web traffic by exploiting how content delivery networks route requests. The client opens a TLS session whose Server Name Indication, the field that names the requested site during the handshake, points at a benign high-reputation domain hosted by the same content delivery network. Inside that encrypted session the HTTP request carries a different Host header naming the actual adversary-controlled domain. Because the network path and the TLS metadata agree with each other, censors and perimeter devices usually permit the connection, and the content delivery network unwraps the request and forwards it to the fronted domain. A variant known as domainless fronting leaves the SNI field empty, which may still route correctly when the network ignores blank names. Defenders detect this by comparing the SNI value and the certificate subject of a flow against the HTTP Host header seen in logs from a TLS-terminating or web proxy, and by flagging flow records that show traffic to a provider no one in the organisation normally uses.

What you will practise

  • Explain how the TLS server name and the HTTP host header can disagree in a single connection.
  • Describe why content delivery networks make domain fronting possible.
  • Recognise the log mismatches that a proxy or a terminating gateway can record during domain fronting.
  • Distinguish fronted traffic from a normal tenant of the same cloud provider during triage.
  • Describe the domainless variant and why an empty server name field may still route.
