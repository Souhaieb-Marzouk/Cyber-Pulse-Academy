Pseudonymisation

Data Protection & PrivacyHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Pseudonymisation means replacing a person's real details with a made up code. The real details are kept in a separate, protected place. Anyone using the data sees the code, not the person. If the code is joined back to the list, the person can be identified again.

Why should you care?

Data that shows only codes is harder to misuse and less harmful if it leaks. Teams can still study patterns and fix problems. It also helps you follow the law, which asks for strong protection of personal data. The protection only works if the list linking codes to people is kept apart and guarded.

How it works, in plain steps

  1. Find the fields that identify a person directly, such as a name, email address or account number.
  2. Replace each of those values with a code, such as a random number or a keyed value.
  3. Store the list that links codes to real people in a separate system with fewer users.
  4. Encrypt that list and restrict access to a small number of named people.
  5. Check that other fields, such as postcode or birth date, cannot identify anyone on their own.
  6. Delete the list when the project ends, so the codes can never be reversed.

Real-world example

Picture a school nurse who keeps a health folder for each child. The folder is labelled with a number, not a name. A single sealed page in the safe shows which number belongs to which child. Teachers can see how many children need a certain check, but they never learn who. Only the nurse can open the safe, and the page is destroyed at the end of the year.

Key takeaways

  • Pseudonymised data is still personal data when it can be linked back to a person.
  • The value of the method depends on separating and protecting the linking list.
  • Watch out for other fields that can re-identify someone without the list.

In more detail

Pseudonymisation is a data protection technique in which direct identifiers such as a name, account number or national identifier are replaced with artificial values, and the mapping that would restore them is kept separately and protected. It matters because it reduces exposure while keeping records useful: analysts can still follow one person's activity across many rows without knowing who that person is. The important distinction is that pseudonymised data is still personal data when re-identification remains reasonably possible, whereas anonymisation is meant to be irreversible. Regulators and standards therefore treat it as a risk reduction measure, not a way to escape obligations. In a real environment pseudonymisation shows up in analytics pipelines, research data sets, log and telemetry exports, shared test environments and vendor data transfers, and its strength depends entirely on how the mapping data, the key, is stored. Defeated implementations usually share one flaw: the lookup table sits in the same database, the same backup, or the same access group as the pseudonymised records, so anyone who can read one can read both. A second common error is forgetting that quasi-identifiers, such as a postcode plus a birth date plus a job title, can re-identify a person even when the key is never touched.

What you will practise

  • Define pseudonymisation and describe how it differs from anonymisation.
  • Explain why pseudonymised data usually remains personal data under data protection law.
  • Describe where pseudonymisation is used, such as analytics, testing and research data sets.
  • Explain why sharing the same system between codes and the linking list defeats the control.
  • Give examples of quasi-identifiers that can re-identify a person indirectly.
  • Describe how the linking list should be stored, restricted and eventually destroyed.
