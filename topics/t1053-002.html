T1053.002 Scheduled Task/Job: At

T1053.002ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

The at command is a tool that runs a command once, at a time you choose. This sub-technique is when an attacker uses it to run their code at a quiet moment. It leaves no lasting job behind. It is part of the Scheduled Task/Job parent technique. The difference is timing: a scheduled task keeps coming back, while at fires once and finishes.

Why should you care?

A job that runs once is easy to miss, because there is no standing entry to find later. Attackers use it to start a second stage after everyone has gone home. At can also run commands as another user, which helps an attacker who wants more power. Knowing where the queue lives tells you where to look after an alert.

How it works, in plain steps

  1. The attacker checks whether the at service or daemon is available and whether their account is allowed to use it.
  2. They submit a job with a time and a command, for example a script that starts a download.
  3. On Windows this needs the Task Scheduler service. It usually also needs local administrator rights.
  4. On Linux and macOS, permission comes from the allow and deny files. If neither file exists, only the superuser may submit work.
  5. The scheduler waits, then runs the command once at the chosen time, often as a shell.
  6. When the job completes, the queue entry disappears, which removes the obvious evidence.

Real-world example

Imagine a night porter in a hotel who can leave a written note for the morning shift. The note says to open room twelve at five in the morning and leave a parcel inside. The porter goes home, so nobody connects the parcel to them. The morning staff simply follow the note, which looks like an ordinary instruction. By the time you ask who wrote it, the note has been thrown away.

Key takeaways

  • One-shot jobs leave a fainter trail than repeating scheduled tasks.
  • Submission of the job is often the only moment you can observe it.
  • Audit the queue, the allow and deny files, and shells started by queued jobs.

In more detail

This sub-technique is scheduled execution through the at command, the queue-based scheduler that predates richer job systems on Windows, Linux and macOS. Its character is one-shot: a job is queued for a specific clock time or a delay, runs once, and then is gone, which makes it attractive when an operator wants execution at an inconvenient hour without leaving a permanent entry. On Windows the utility depends on the Task Scheduler service and, in practice, local administrator rights; the same job can also be produced without the command by calling the Win32_ScheduledJob class through Windows Management Instrumentation, which shifts the evidence from a command line to a provider and its host process. On Linux and macOS the queue is governed by files that list permitted or denied users, and where neither exists only the superuser may submit work. The artefacts are queues and their contents rather than persistent definitions, so detection leans on spotting the submission itself, watching for stray shell or interpreter processes whose parent no longer exists, and auditing shells spawned by a queued job.

What you will practise

  • Explain how the at utility differs from a repeating scheduled task on each platform.
  • Describe the permission rules that decide who may queue work on Linux and macOS.
  • Identify the artefacts left by a queued job, including the queue entry and the resulting process.
  • Recognise the Windows Management Instrumentation path that creates the same job without the command line.
  • Explain why one-shot execution is attractive for staging a second stage of an intrusion.
