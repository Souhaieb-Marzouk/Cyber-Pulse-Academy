S3 Bucket Policy

Cloud SecurityVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A bucket policy is a written rule attached to a cloud storage bucket. A bucket is a container that holds files, and S3 is one popular object storage service. The policy states who may read, write or list the files inside, and under what conditions. The provider checks it on every request.

Why should you care?

One wrong line in a bucket policy can expose a whole dataset to the world. This happens often in real incidents, and the files can be copied before anyone notices. Unlike a password, the exposure needs no guesswork. That is why bucket policy changes are treated as high-severity events and reviewed carefully.

How it works, in plain steps

  1. A request arrives asking to read, write or list objects in the bucket.
  2. The service collects the bucket policy and any identity policy for the caller.
  3. It also applies public access blocks and any organisation-wide guard rules from your company.
  4. If any of those layers contains an explicit deny, the request fails immediately.
  5. Otherwise, if a rule allows the action under the stated conditions, it succeeds.
  6. Bucket logs record the request, so you can see who read what and when.

Real-world example

Imagine a filing cabinet in a shared office. A label on the front says who may open each drawer: the finance team only, or everyone in the building. If you write everyone on the label, any visitor can help themselves. Nothing is broken, no lock is picked, yet the files are gone. A bucket policy is that label.

Key takeaways

  • A bucket policy decides who can reach the files, so review every change.
  • Keep public access blocks on unless there is a documented reason.
  • An explicit deny in any policy layer always stops the request.

In more detail

An S3 bucket policy is a JSON resource-based policy attached directly to an object storage bucket that controls which principals may perform which actions against that bucket and the objects inside it, optionally under conditions. Because it is resource-based it can grant access to principals outside the owning account, which is what makes it the standard mechanism for cross-account sharing, public content delivery, and service integrations such as logging or content delivery networks. The policy is evaluated together with identity-based policies, access control lists, block-public-access settings, and any service control policies, and an explicit deny in any of those layers prevents the action. The most consequential failure modes are well known: a wildcard principal combined with a wildcard action, a listing permission that reveals object names, a condition intended to restrict access that does not actually match the request shape, and an object that was public before public access blocks were enabled. Security teams monitor bucket policy changes as high severity events because a single edit can expose an entire dataset, and they combine policy review with classification of what the bucket holds, encryption requirements, versioning, logging and lifecycle rules. Effective practice is to prefer identity-based access and role assumption over cross-account wildcards, to enforce encryption and TLS in the policy itself, and to keep public access blocks on unless a documented exception exists.

What you will practise

  • You will be able to read a bucket policy and determine whether it permits public or cross-account access.
  • You will be able to explain how bucket policies interact with identity policies, ACLs and public access blocks during authorisation.
  • You will be able to write conditions that restrict access by encryption, transport, network origin or principal tags.
  • You will be able to identify policy patterns that expose object listings or allow unintended read and write access.
  • You will be able to triage alerts raised by bucket policy changes and public access block modifications.
