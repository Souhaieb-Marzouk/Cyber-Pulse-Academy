Broken Access Control

Application SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Broken access control means a program does not check properly what each user is allowed to do. Someone can then see or change things that belong to other people. The login may work perfectly, yet the permissions behind it are missing. This is one of the most common and most serious web problems.

Why should you care?

Your account may be safe while other people's data is not. A single missing check can let an attacker read private records or act as an administrator. Customers lose trust when their information is exposed this way. Rules and fines may also apply. Fixing one missing check is usually easier than explaining a data leak.

How it works, in plain steps

  1. A user signs in and the server gives them a session or token that proves who they are.
  2. The user asks the server for a page, a record, or an action they want to perform.
  3. The server must check the user's role and ownership before it answers the request.
  4. If that check is missing, the server simply returns whatever was requested.
  5. An attacker changes an identifier or calls a hidden endpoint and reaches other data.
  6. The program must also check permissions on every request and not only in the browser.

Real-world example

Picture a large office building where everyone has a badge. The badge proves who you are at the front door, and that part works well. The problem starts inside, because nobody checks which rooms you may enter. A visitor can walk into the finance office simply by trying doors. The badge was never the whole protection. The building also needs a rule for every room.

Key takeaways

  • Hide nothing important in the screen alone, because the server must check every request.
  • Check permissions on the server for each action and each piece of data.
  • Test access rules by trying to reach other users' data during security testing.

In more detail

Broken access control is the class of application flaws where a system fails to enforce who is allowed to do what, so a user can reach data or actions beyond their intended permissions. It covers missing authorization checks on server endpoints, insecure direct object references where an identifier such as an account number is trusted from the request, forced browsing to pages that are hidden only in the interface, horizontal privilege escalation between users of the same role, and vertical escalation into administrative functions. The weakness is not login but authorization: authentication proves who the caller is, while access control decides what that identity may touch, and a request replayed with a changed identifier must still be rejected server side. In practice it shows up as the same account reading another customer's records, an ordinary user calling an admin endpoint, or a report export that ignores tenant boundaries. The usual mistake is trusting the client, hiding a button instead of checking permissions, or enforcing rules only in the user interface and not in every backend path.

What you will practise

  • Explain the difference between authentication and authorization in a web application.
  • Describe what broken access control means and where it applies in a real environment.
  • Recognise common forms such as insecure direct object references and forced browsing.
  • Explain why hiding an interface element is not the same as enforcing a permission.
  • Describe how access control is tested during code review and security assessment.
  • State the design habits, such as centralised checks, that prevent these flaws.
