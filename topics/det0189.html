DET0189 Detection Strategy for Indicator Removal from Tools - Post-AV Evasion Modification

DET0189Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for someone changing a malicious file after a security tool has flagged it. The aim is to make the next copy harder to catch. The rule also watches for changes to the security tool itself, such as its quarantine folder or its settings. It links the detection event to what happened just after.

Why should you care?

When your tools catch something, the attacker learns what gave them away. They then edit the file and try again. That cycle can continue until they succeed. Linking the original detection to the later change gives you a strong warning. It lets you respond while the attacker is still adjusting, instead of after they slip through.

How it works, in plain steps

  1. An endpoint protection product records that it detected a file or behaviour.
  2. It takes an action, such as moving the file into quarantine.
  3. Soon after, a process modifies that same file, its folder, or the product settings.
  4. Your endpoint tool records the process, its command line and the file or registry change.
  5. The rule joins the detection record with the later modification on the same host.
  6. A close match in time and path produces a high priority alert.

Real-world example

Imagine a border checkpoint where a sniffer dog finds a hidden package in a car. The driver is sent away. An hour later the same car returns, and the dog no longer reacts. Nothing about the car looks wrong. But the officer remembers the earlier stop. That memory makes the second arrival worth a full search.

Key takeaways

  • A detection followed by tampering is a stronger signal than either event alone.
  • Attackers edit tools to defeat the exact control that caught them before.
  • Quarantine folders and product settings are high value places to watch.

In more detail

This strategy detects indicator removal from tools, where an adversary modifies or strips parts of a payload after a defensive product has flagged it, so that the next version slips past the same control. The behaviour matters because it is a direct, measurable response to detection: a host that shows a security product detection followed by tampering with the flagged file or with the security product itself is a priority signal. Detection is built on endpoint protection operational records, process creation with command lines, file system changes in security product directories, and registry writes to protection configuration. The usual failure is attribution, because legitimate quarantining, cleanup scripts and product self maintenance touch the same paths, so the rule must anchor on the detection event that preceded the modification.

What you will practise

  • Explain the cycle of detection, modification and retry that this strategy targets.
  • Identify which security product records show that a file or behaviour was flagged.
  • Correlate a detection record with a later file or registry modification on the same host.
  • Recognise tampering targets such as quarantine storage, signature files and exclusion lists.
  • Separate legitimate product maintenance and cleanup from adversary modification.
  • Describe why exclusion list changes deserve their own independent alert.
