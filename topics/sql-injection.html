SQL Injection

Application SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

SQL injection is an attack on a website through the text you type into it. SQL stands for Structured Query Language, which is the language programs use to talk to a database. In this attack a person types special text into a form. The database then treats that text as a command instead of a plain value. The website then does things its owner never intended.

Why should you care?

A database often holds the most valuable information a company has, such as customer names, passwords and payment details. If an attacker can send commands through an ordinary form, they may read, change or delete that data. They can sometimes pass a login check without knowing any password. This kind of flaw is common because it is easy to create by accident. Fixing it early is cheap, but a breach can cost a company its reputation and its customers.

How it works, in plain steps

  1. A web page asks you for information, such as a username, a search word or a filter option.
  2. The program joins your text straight into a database question instead of keeping it separate.
  3. The database reads the whole sentence, so your text can change the meaning of the question.
  4. An attacker sends text that adds a condition which is always true, so a check passes.
  5. The database then returns private rows, or the program accepts a login it should refuse.
  6. Developers stop this by sending values separately, so the database never reads them as commands.

Real-world example

Imagine a library where you fill in a request slip and hand it to the desk. The slip says: bring me the book about gardening. A dishonest visitor writes instead: bring me the book about gardening, or every member record in the building. If the clerk reads the whole slip as one instruction, they obey it. A careful library uses a fixed form with a blank line for the topic only. Whatever you write on that line stays a topic and never becomes a new instruction. Prepared statements in software work exactly like that fixed form.

Key takeaways

  • Never trust text typed by a user, and never build a database question by gluing that text together.
  • Prepared statements with parameters keep data and commands apart, which removes this flaw at its root.
  • Filtering out quotes or keywords is not a real fix, because unusual input still finds a way through.

In more detail

SQL injection is a class of input handling flaw in which untrusted data reaches a database query as code rather than as a value. It appears whenever an application builds a statement by concatenating user input into a query template, so the database engine parses attacker controlled text as part of the query structure. In real environments it shows up in login forms, search boxes, report filters and API parameters, and it persists because dynamic query building is convenient and because legacy code is rarely revisited. The mistake people usually make is treating it as an input validation problem: stripping quotes and blocking keywords is fragile and bypassable, while parameterised queries and prepared statements remove the flaw at its root by separating code from data. Detection relies on database error monitoring, unusual query latency, and web application firewall signals correlated with application logs.

What you will practise

  • Explain what SQL injection is and why databases are the usual target.
  • Describe how ordinary user input can be read as a database command.
  • Identify the coding practice that prevents the flaw at its source.
  • Recognise signs of an injection attempt in logs and error messages.
  • Explain why input filtering alone is a weak defence.
  • Describe how to test a form for this flaw safely in an approved environment.
