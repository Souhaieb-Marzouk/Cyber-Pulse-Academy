Sigma Rules

SOC & Detection EngineeringVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Sigma is a shared, vendor-neutral way to write detection rules as text. Vendor-neutral means the rule is not tied to one security product. You describe what to look for, and a translator turns it into the query language your platform understands. It is often called the common language for log detections.

Why should you care?

Most companies use more than one security platform, and each has its own query language. Writing the same rule five times wastes effort and creates five chances to make a mistake. With Sigma you write it once, review it once, and convert it as needed. It also gives your rules a shared shape, so they are easy to compare and track.

How it works, in plain steps

  1. You write the rule in a plain text format with a title, a description and an author.
  2. You state which log source the rule needs, such as Windows process creation events.
  3. You list the patterns to look for, such as a command name or a file path.
  4. You write a condition that combines those patterns, using simple words like and, or, not.
  5. A translator converts the rule into the query language of your chosen platform.
  6. You test the converted rule on real logs, because translation does not always fit perfectly.

Real-world example

Think of a recipe written in a neutral way: flour, water, salt, bake until golden. Any kitchen can follow it, whether the oven is gas or electric. A cook adjusts the timing for their own oven. Sigma rules work like that recipe. You write the detection once in neutral terms, then each platform follows it in its own local dialect.

Key takeaways

  • Write a detection once in a neutral format, then translate it.
  • Always test a translated rule on real logs before you trust it.
  • Sigma covers log detections only, so files and memory need other tools.

In more detail

Sigma is a vendor-neutral, YAML-based signature format for describing log-based detections, intended to be written once and translated into the query language of whichever SIEM or log platform an organisation runs. A rule separates two concerns that many native rule formats entangle: the detection logic, expressed as named search identifiers with field modifiers such as contains, startswith, endswith, base64offset, re and cidr, and a condition that combines those identifiers with boolean and aggregation operators. Around the logic sits metadata that makes the rule maintainable and machine-readable: a title and description, a stable id, a status, a logsource block naming the product, service or category the rule requires, references, an author, a date, a level and tags that commonly include ATT&CK technique identifiers. The logsource abstraction is what enables portability, because the translator maps product and category onto concrete field names for the target platform, for example expanding a Windows process creation rule into the vendor's specific process, command-line and parent-process fields. The pipelining feature turns Sigma into a small language for composed detections: a base rule can be chained with filters that add exclusions, or several rules combined to require correlated events. Practical advantages are reviewable diffs, reuse of a rule estate across multiple platforms, and coverage tracking. Practical limitations deserve equal weight: translation quality varies, so a converted rule must be validated on real telemetry before it is trusted; generic field mappings can lose fidelity for platforms whose schema differs substantially; and Sigma describes log detections only, so it says nothing about network, memory or endpoint-behaviour detection that never reaches a log pipeline. Treat Sigma as a shared, reviewable source of truth rather than as a guarantee of deployable accuracy.

What you will practise

  • You will be able to read and write a Sigma rule with a logsource block, named search identifiers, field modifiers and a boolean or aggregation condition.
  • You will be able to explain how the logsource abstraction enables translation to different SIEM query languages and where that mapping loses fidelity.
  • You will be able to use rule metadata to track ownership, required telemetry, status and ATT&CK technique coverage across a rule estate.
  • You will be able to compose detections with pipelining, including base rules with filters and correlated multi-rule conditions.
  • You will be able to validate a translated rule against real telemetry and identify the translation errors that break it silently.
  • You will be able to state which detection domains Sigma cannot cover and what complementary content is needed for them.
