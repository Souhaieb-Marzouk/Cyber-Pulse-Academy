DET0275 Detect Adversary Deobfuscation or Decoding of Files and Payloads

DET0275Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for the step where hidden or scrambled data is turned back into a normal file or program. Attackers hide their tools this way so that scanners do not recognise them. The decoding step is the moment the hidden item becomes usable.

Why should you care?

Most attacks need a decoding step before anything can run. That step is harder to hide than the payload itself. It also happens at a known time, which gives your monitoring a clear moment to look at. If you can catch it, the attacker must rebuild their tooling. This detection also helps you understand what a suspicious file would have done.

How it works, in plain steps

  1. The operating system records each new process together with the full command line that started it.
  2. The detection looks for command lines that decode data, such as arguments that mention a decoding routine or a certificate utility used to reverse an encoding.
  3. It also watches for new files written by that process in the following seconds.
  4. It pairs the reading of an encoded input file with the writing of a decoded output file in the same process.
  5. Script block logging, where enabled, shows the actual decoding calls made inside a script.
  6. When the decoder is a script interpreter and the output lands in a temporary or user folder, the alert is raised for review.

Real-world example

Think of a locked toolbox delivered to a workshop. Nothing inside can be used until someone opens it. The moment a worker takes out the tools, the supervisor knows a job is about to start. Watching that moment is easier than guessing what was inside the box.

Key takeaways

  • Decoding is a hinge point in the attack chain, not just a technical detail.
  • The decoder, the output location and what runs next together tell you whether the activity is benign.
  • Command line auditing and script block logging are the two settings that make this detection possible.

In more detail

This strategy detects the deobfuscation and decoding step, where an adversary turns a protected or obfuscated file, script or payload back into something that can execute. T1140 matters because it consistently appears between delivery and execution, so catching it breaks the chain at a point where the tooling is still explicit and the decoded artefact often lands on disk. Detection relies on process creation with command line auditing, on file creation events that capture the decoded output, and on script block logging where script content is available, correlated by process identifier and a short time window. It fails most often because administrators and installers decode files legitimately, so the rule must weigh which interpreter performed the decoding, where the output was written, and what ran immediately afterwards.

What you will practise

  • Explain why adversaries encode or encrypt payloads and where the decoding step sits in the attack chain.
  • Recognise command line patterns that indicate decoding, including encoding routine calls and certificate utility decode usage.
  • Correlate an encoded input file read with a decoded output file write in the same process identifier.
  • Identify which logging settings, such as command line auditing and script block logging, must be enabled.
  • Assess a decoded artefact to decide whether follow-on containment is required.
