T1686.001 Disable or Modify System Firewall: Cloud Firewall

T1686.001Defense ImpairmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

The main firewall technique covers any system that filters traffic. This sub-technique is only about the firewall inside a cloud platform. A cloud firewall is a set of rules that the provider applies to your servers. An attacker with the right cloud account can change those rules to let traffic in.

Why should you care?

A cloud firewall is often the only thing keeping a server off the public internet. If an attacker widens the rules, they can reach services that were never meant to be exposed. They can also leave a quiet path open for later. This is hard to notice, because normal teams change rules all the time. Without a record of who changed what, you may never know it happened.

How it works, in plain steps

  1. The attacker first gets cloud credentials, such as a stolen key or a live session token.
  2. They call the provider interface to read the current security groups and their rules.
  3. Next they add an ingress rule that allows traffic from any address, or create a broad new group.
  4. Sometimes they attach that group to a running instance, so the new rule takes effect at once.
  5. The provider writes each change into its audit log, together with the identity and the rule details.
  6. Miners open a port for a mining pool, and remote control tools open one for the operator.

Real-world example

Think of a block of flats with one shared front door. The caretaker keeps a list of who may enter. A thief cannot copy a key, so instead they edit the list at the desk. They add one line that says anyone may come in at any time. Nothing is broken, and the door still locks. Nobody sees a break-in, only a small change to a list. In the cloud, that list is the firewall rule set, and the audit log is the only witness.

Key takeaways

  • Cloud firewall rules live in the provider, so check the cloud audit log and not only the server.
  • A rule that allows any address is unusual and should be reviewed the same day.
  • Learn which teams and tools normally change rules, so you can spot the rest.

In more detail

Cloud firewall controls live in the provider control plane rather than on the guest host, so an attacker who holds valid cloud credentials rarely needs to touch the operating system to open a path in. They call the provider interface to add an ingress rule to an existing security group, create a permissive group, or attach a new rule set to a running instance, often widening a single port to every address or allowing all protocols. Because the change happens in the management plane, the artefacts are API audit entries, rule version diffs and configuration history rather than process creation logs from the server itself. Platform teams and autoscaling pipelines also create and edit rules, so defenders should baseline which identities and automation normally write security group policy, and treat a rule authored by a human identity, at an unusual hour, or referencing any-address source ranges as the higher-signal case.

What you will practise

  • Describe how cloud firewall rules are stored and changed through provider interfaces.
  • Explain why control plane audit logs are the main evidence for this technique.
  • Identify the rule changes that most strongly suggest malicious intent, such as any-address sources.
  • Distinguish routine automation changes from a human identity widening access outside normal hours.
  • Outline a first response for a suspicious security group change in a cloud account.
