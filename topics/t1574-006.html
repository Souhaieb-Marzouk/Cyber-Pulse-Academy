T1574.006 Hijack Execution Flow: Dynamic Linker Hijacking

T1574.006ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Before a program starts, a helper called the dynamic linker loads the shared libraries it needs. That helper also reads named settings called environment variables. An attacker can point one of those settings at their own library, so their code loads first. This is one branch of the Hijack Execution Flow parent.

Why should you care?

The attacker's library can replace common functions inside a running program. That lets it hide files and processes from the tools you use to investigate. It can also spread to every program started afterwards. Because a legitimate process carries the code, alerts often stay quiet. Checking environments and loaded libraries is the way to see it.

How it works, in plain steps

  1. A program starts, and the dynamic linker prepares the shared libraries it needs.
  2. The linker also reads environment variables, which can name extra libraries to load.
  3. Libraries named this way are loaded first and take priority over system ones.
  4. The attacker's library can replace common functions such as execve or readdir.
  5. Replacing those functions can hide files, processes and network rules from view.
  6. The setting may spread to every process started from that shell or service.

Real-world example

Imagine an office where the receptionist keeps a list of trusted visitors. Staff are allowed to add names to that list. Someone adds a name that sounds like an important contractor. The receptionist waves the visitor through and even lets them use the staff room. The visitor then edits the visitor book to remove their own entry. Dynamic linker hijacking looks like this, because a setting can add a trusted sounding library that then hides evidence.

Key takeaways

  • Loader settings can add libraries that take priority over system ones.
  • A hijacked function can hide files and processes from your own tools.
  • Compare process environments and mapped libraries against a baseline.

In more detail

Dynamic linker hijacking abuses the environment variables that a loader reads before a program starts, such as LD_PRELOAD on Linux and DYLD_INSERT_LIBRARIES on macOS. Libraries named in those variables are mapped first and take precedence over the system library that provides the same symbols, so the attacker's version of a common function runs instead of the real one. This is more than a way to load a payload: because functions such as execve and readdir can be replaced, a library can hide its own files, processes and network rules from commands like ls, ldd, iptables and dmesg, which makes later investigation misleading. The approach suits servers because setting the variable in a shell profile or a service environment reaches every descendant process, so a library injected into the Secure Shell (SSH) daemon can follow each new session. Detection compares process environments and mapped libraries against a baseline and checks the integrity of loader configuration files.
