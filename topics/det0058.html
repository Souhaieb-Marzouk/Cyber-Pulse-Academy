DET0058 Detection Strategy for Web Service: Dead Drop Resolver

DET0058Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for a computer that quietly fetches a small piece of text from a public website. The computer then connects to a new address that it learned from that text. Attackers hide their control server address inside the text. The public site is the hiding place, which people call a dead drop.

Why should you care?

Blocking bad domain names does not help when the address comes from a site your staff use every day. The request looks like normal browsing, so it slips past most filters. Catching the pattern of fetch then connect gives you a chance to react earlier.

How it works, in plain steps

  1. The web proxy records each request a computer makes, including the destination site and how much data came back.
  2. The domain name system, or DNS, log records the name the computer asked to resolve.
  3. A SIEM (Security Information and Event Management system) groups these records by computer over a short window.
  4. The rule looks for a small text fetch from a public platform that is not in the normal use baseline.
  5. It then looks for a connection from the same computer to a new external address within minutes.
  6. Both steps together raise the alert, because either step alone is just ordinary browsing.

Real-world example

Imagine a spy who never meets a contact. Instead, they read the number written inside a library book, then go to that address. The library visit is legal and boring. Only the follow up walk to the new address shows what happened.

Key takeaways

  • The hiding place is a trusted public site, so blocking bad names will not catch it.
  • The useful signal is two steps together: a small fetch, then a connection to a new address.
  • You must baseline which teams really use these platforms, or the rule will be noisy.

In more detail

This strategy detects the use of legitimate web services as a dead drop resolver, where an implant reads its command and control address from content that the operator controls on a public platform such as a social profile, a paste site or a code repository. The technique matters because the retrieval host is a trusted, well known brand that most organizations allow, so domain reputation and blocklists rarely help. Telemetry that makes it visible is web proxy and secure web gateway logs joined with DNS resolution records and firewall connection records, all keyed on the client host over a short time window. The common way this fails in practice is baseline drift: many business groups legitimately poll the same platforms, and low volume periodic fetches look identical in shape whether they are a scheduled job or an implant checking in.

What you will practise

  • Describe how a dead drop resolver uses a legitimate web service to deliver an address.
  • Identify the proxy, DNS and firewall fields needed to prove the fetch then connect sequence.
  • Correlate events by client address and time window to avoid alerting on single requests.
  • Baseline which public platforms the organization uses legitimately for business content fetching.
  • Explain why reputation based blocking alone cannot cover this technique.
