DET0138 Detection of Malicious Code Execution via InstallUtil.exe

DET0138Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

InstallUtil is a genuine Windows tool that installs and removes .NET services. A service is a program that runs in the background. Because the tool is trusted and signed, attackers can ask it to load their own code. The tool then runs that code for them. This detection looks for the tool being used in unusual ways, not for the tool itself.

Why should you care?

Security tools often allow trusted Windows programs to run without question. An attacker who borrows such a program can act without bringing an obviously strange file. The borrowed tool also appears in logs under a familiar name. That makes the activity easy to miss in a busy environment. This detection focuses on the arguments and the parent process instead of the name.

How it works, in plain steps

  1. A process record shows the utility starting with its full command line.
  2. The rule inspects the assembly path that was given to the utility.
  3. It flags assemblies loaded from a user folder, a temporary folder, or a download folder.
  4. It also flags a run with no assembly path, which is unusual for a real install.
  5. It checks which program started the utility, such as a document reader.
  6. An analyst then reviews the assembly file and the network activity from that session.

Real-world example

Think of a company van with the company logo on the side. Staff wave it through the gate without checking, because everyone knows the van. A thief paints the same logo on an old van and drives in with a load of stolen goods. The guard at the gate sees a familiar logo and looks no further. InstallUtil is that trusted van. The detection asks what the van is carrying and who is driving it, not what the logo says.

Key takeaways

  • Attackers borrow signed system tools so that the file itself looks innocent.
  • Check the assembly path and the parent process, not the tool name.
  • Real deployments run from managed paths and from deployment accounts.

In more detail

InstallUtil abuse (T1218.004) uses a signed Microsoft .NET utility that installs and uninstalls server resources, because the utility will load and run code from a compiled assembly while the process itself looks entirely trustworthy. This detection strategy therefore targets the invocation rather than the binary: process creation where the utility runs an assembly from a user writeable, temporary, or download directory, runs with no assembly path, or is started by a document reader, script host, browser, or remote management tool instead of a deployment pipeline. Supporting telemetry includes .NET runtime or application log entries for a failed assembly load, module load records showing assemblies loaded out of temporary directories, and file creation events for an assembly compiled moments earlier. It fails because deployment and update pipelines legitimately run the same utility, because the invocation can be quiet and short lived, and because command line auditing must be enabled for the decisive field to exist at all.

What you will practise

  • Explain why a signed .NET installation utility is attractive to an attacker.
  • Identify the command line features that separate abuse from a genuine installation.
  • Interpret module load and file creation records that show a freshly compiled assembly.
  • Correlate the parent process with the assembly location to raise or lower severity.
  • Describe how to baseline legitimate deployment use of the utility.
