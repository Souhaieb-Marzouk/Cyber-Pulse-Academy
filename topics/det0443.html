DET0443 Detection Strategy for Masquerading via Breaking Process Trees

DET0443Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for a process that lies about who started it. Windows records a parent for every new process. An attacker can name a trusted program as the parent. The recorded family tree then looks normal even though it is false.

Why should you care?

Analysts judge a process by its parent. An odd parent quickly looks suspicious. A spoofed parent hides that clue. Automated tools that score process trees are fooled too. Checking the identifiers against reality restores the lost clue.

How it works, in plain steps

  1. A sensor records each new process with its own identifier and parent identifier.
  2. The rule keeps both values plus the parent image name and the creation time.
  3. It compares the recorded parent with the process that really owns that identifier.
  4. It scores pairs that should rarely appear, such as an office program parent.
  5. The alert shows the claimed parent, the real parent and the short time gap.

Real-world example

Think of a sign in sheet where someone writes a manager name as the person who let him in. The name looks fine on paper. But the manager was in another building that day. You compare the sheet with the door records to find the lie.

Key takeaways

  • The parent process is a strong clue that can be faked.
  • You need both the process identifier and the parent identifier.
  • Rare parent and child pairs are the practical signal.

In more detail

This strategy detects masquerading that works by breaking the process tree, where an adversary makes a process look as if it was started by a trusted program so that analysts and tools see a benign lineage. The usual implementation selects an existing parent process and marks it as the creator, which means the recorded parent image does not match the process that really launched the child. Detection relies on process creation telemetry that records both the process identifier and the parent process identifier, on the ability to compare those identifiers against the live process table, and on knowledge of which parent and child pairs are normal. The main difficulty is that the identifiers are reused by Windows, so a mismatch alone can be harmless, which is why the rule must weigh the parent and child pairing and the time gap rather than the identifier comparison by itself.

What you will practise

  • Explain the difference between a process identifier and a parent process identifier.
  • Read process creation telemetry and extract the parent and child details.
  • Describe which parent and child pairs are plausible in your environment.
  • Recognise identifier reuse as a cause of harmless mismatches.
  • Build a scored rule that ranks rare parent and child combinations.
  • Document the claimed parent and the observed parent for each alert.
