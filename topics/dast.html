Dynamic Application Security Testing

Secure EngineeringVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Dynamic application security testing checks a running application for security weaknesses. A tool sends test requests to the live program and studies the replies. It looks for problems like broken login, weak sessions, and injection flaws, where user input changes a command. Because it tests the real thing, it sees what an attacker would see.

Why should you care?

Many security bugs only appear when the software is running and connected to real data. Static tools read code and often miss them. Dynamic testing finds configuration and login mistakes that code review cannot see. It also shows how your system behaves under real requests. Skipping it leaves a blind spot attackers happily use.

How it works, in plain steps

  1. You point the scanner at a test copy of your running application.
  2. The scanner crawls the site, following links and mapping every page it finds.
  3. It sends unusual requests, such as odd characters or missing login details.
  4. It studies each reply for signs of a flaw, such as error messages or leaked data.
  5. A report lists findings by severity so you can fix the worst problems first.
  6. You can also give the scanner a login so it can test pages behind the sign-in.

Real-world example

Think of a building inspector who does not read the blueprints. Instead, she walks through the finished house. She opens every door, turns on every tap, and checks the locks herself. She finds the window that will not close and the back door left unlocked. A dynamic scanner does the same for your website. It visits the live site like a curious guest and reports the doors that are not locked.

Key takeaways

  • Dynamic testing checks the running app, not just the source code.
  • Always scan with a login, or you will only test the login page.
  • Test a copy that matches production, never live traffic during peak hours.

In more detail

Dynamic application security testing is the automated assessment of a running application, sending crafted requests or driving a browser and analysing the responses for security weaknesses such as injection, broken authentication, insecure session handling, misconfigured headers, exposed administrative interfaces and unsafe redirects. Because it exercises the deployed artifact, DAST observes the same surfaces an attacker would, which makes it strong at finding configuration, authentication and session problems that static analysis cannot see. The trade-off is coverage and certainty in the other direction: black-box scanning only reaches what it can discover, it cannot reason about code it cannot see, and destructive or stateful techniques risk corrupting test data, so scans are usually run against a dedicated environment seeded with representative content and credentials. Authenticated scanning is the single biggest determinant of value; an unauthenticated scan of a modern single-page application typically crawls a login page and little else. For a practising engineer the operational questions are environment fidelity, credential handling, scan scope, rate limiting, and how findings are de-duplicated across runs so a repeated issue is not rediscovered as new. Pairing DAST with an API specification gives far better coverage than crawl-only scanning, and pairing it with static analysis closes the loop between code-level and runtime evidence. Common failure modes include scanning production during peak hours, scanning an environment with debug features enabled so results do not reflect production, and reporting every informational header finding as if it carried the same weight as a confirmed injection.

What you will practise

  • You will be able to explain what running the application adds over static analysis and which defect classes it uniquely exposes.
  • You will be able to configure an authenticated DAST scan with a safe test account, a scoped target and rate limits that protect the environment.
  • You will be able to evaluate environment fidelity and state why scanning a debug-enabled staging copy can produce misleading results.
  • You will be able to interpret a DAST report, separating confirmed findings from informational observations and scanner heuristics.
  • You will be able to define a de-duplication and retest process so recurring findings are tracked rather than rediscovered.
  • You will be able to combine API-specification-driven scanning with crawl-based scanning to improve endpoint coverage.
