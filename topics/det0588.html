DET0588 Detection of Remote Service Session Hijacking for RDP.

DET0588Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Remote Desktop Protocol (RDP) lets you use a computer from far away. A hijack means an intruder joins a session that is already open instead of logging in. This detection looks for a session that changes owner without a normal sign-in.

Why should you care?

The victim is already signed in, so no password is needed and no failed login is recorded. Many alert rules watch for failed logins, so they see nothing at all. The intruder then acts as the real user, with that user's access. Catching the change of session is often the only signal available.

How it works, in plain steps

  1. Windows writes an event each time a remote session is created, connected, or disconnected.
  2. A separate event records a session being redirected to another session.
  3. The rule links those events to the process and account that requested the redirect.
  4. It checks whether the account that owns the target session is the same as the requester.
  5. It also looks for an interactive session identifier appearing on a service process.
  6. Mismatches are sent to your security information and event management (SIEM) platform for triage.

Real-world example

Think of a taxi rank where each driver keeps the engine running while they take a break. A stranger does not need a key, because the engine is already on. They simply get in and drive away in another driver's car. The log at the rank shows no theft and no broken lock, only that one car left with the wrong person at the wheel.

Key takeaways

  • A hijacked session produces no authentication event, so watch session state changes instead.
  • The account that owns the session and the account that redirected it are the key fields.
  • Local administrator rights are usually required, so treat unexpected elevation as part of the same picture.

In more detail

This strategy detects T1563.002, Remote Service Session Hijacking against Remote Desktop Protocol (RDP), where an adversary takes over an existing interactive session instead of authenticating normally. Because the session already exists, no failed logon appears and the account does not change, which is why hijacking defeats most credential-based detections. The evidence comes from session state change events in the terminal services operational log, the process that performed the redirect, and the sudden appearance of an interactive session identifier on a process that should not have one. The common failure is that administrators and support tools legitimately reconnect sessions, so the acting account context and the state transition sequence must be correlated.

What you will practise

  • Explain how a remote session can be taken over without authentication
  • Locate the terminal services operational events that record session state transitions
  • Correlate a session redirect with the process, account, and host that requested it
  • Recognise the privileges required and where those rights are normally held
  • Decide when a session change is routine support work rather than intrusion
