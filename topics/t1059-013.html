T1059.013 Command and Scripting Interpreter: Container CLI/API

T1059.013ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Containers are small packaged programs that share one computer and start very fast. A container tool such as Docker or Kubernetes has a command line and an interface for managing them. This technique is about attackers using that interface to run their own commands.

Why should you care?

These tools are made for fast automated work, so unusual activity can look like normal building and testing. An attacker who reaches the interface can start their own container. They can also open a command session inside a container that already runs. Container settings often hold cloud keys, so one inspection command can hand over more access.

How it works, in plain steps

  1. The attacker reaches the container tool through its command line, its socket, or its network interface.
  2. They may use a software library instead of typing commands, which looks like normal automation.
  3. They can pull an image, which brings tools of their choice onto the host.
  4. They can start a container, or open a command session inside a container already running.
  5. Inspection commands such as listing containers reveal environment values and stored keys.
  6. In Kubernetes, the same actions are API requests that the control plane can record.

Real-world example

Imagine a block of flats where you can order a complete furnished room from the front desk. The room arrives ready to use, with furniture and tools already inside. Staff do not ask what you plan to do in it, and you can order another room whenever you like. Container tools are that front desk. They are quick, convenient, and completely silent about your reasons for ordering.

Key takeaways

  • Protect the container socket, because control of it is control of the host.
  • Turn on Kubernetes audit logging and keep the caller identity in the record.
  • An interactive session inside a production container is unusual and worth an alert.

In more detail

Container platforms expose management as an interface rather than as a graphical console, so the boundary between administration and execution is thin. On a Docker host the client talks to a daemon over a local socket or a network endpoint, and the same calls can be made from a software development kit in a language such as Python or from a plain HTTP request. On Kubernetes the control plane answers a documented API, reached through the kubectl tool, through client libraries in Go or Python, or through direct requests. Abuse follows the ordinary verbs of those interfaces. An attacker can pull images, which is a transfer of tools into the environment; build an image on the host, which runs build steps outside a container; start a container from an image of their choosing; open an interactive command session inside a container that is already running; and read container configuration and environment through inspection calls, which frequently exposes cloud credentials and service addresses. The audit trail is strong where it exists: the Kubernetes API server logs the caller identity, the verb, the resource, the subresource such as an attach or exec request, and the client user agent, and container engines log image pulls and container lifecycle events. The discriminator is usually the caller and the client: a continuous integration pipeline uses a dedicated service account with a consistent user agent, while an interactive exec into a production pod from a developer workstation, or a pod using its own in-cluster token to list secrets, does not.
