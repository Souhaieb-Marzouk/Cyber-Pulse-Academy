T1546 Event Triggered Execution

T1546PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An event is something that happens on a computer, such as a user logging in or a file being opened. A trigger is an instruction that watches for one of those events and runs a program when it happens. This technique is when an attacker sets up such a trigger to run their own code.

Why should you care?

The attacker does not need to keep any program running, so there may be nothing suspicious to see. Their code starts only when the chosen event occurs, which can be long after the break in. Many of these triggers use normal system tools, so the activity blends into everyday use. It is a hard pattern to find without the right logs.

How it works, in plain steps

  1. The attacker picks an event that happens often and reliably on the victim machine or platform.
  2. They register a trigger that links that event to a program, script, or command of their choice.
  3. The trigger is stored in a configuration store, such as a database, a registry key, or a file.
  4. When the event occurs, the system itself starts the attacker's code on their behalf.
  5. Often a normal system program runs the code as its child, which hides the true origin.
  6. The trigger stays in place, so the code runs again each time the event repeats.

Real-world example

Think of a hotel front desk with a written rule: whenever a guest asks for a taxi, call the number on this card. Someone replaces the card with their own number. No one is watching the desk all night, and no extra staff were hired. The calls only happen when a guest asks, and the desk clerk believes the card is official.

Key takeaways

  • Event triggers leave configuration behind, not a running process, so look for records and settings.
  • A trusted system program is often the parent process, which makes the payload look legitimate.
  • These mechanisms can also raise an attacker's rights when a privileged service runs the code.

In more detail

Event triggered execution covers persistence that is driven by a subscription rather than by a startup list or a schedule. The host, the shell, or the cloud platform is asked to watch for a condition, and when that condition appears the watched code runs. Windows offers WMI permanent event subscriptions and file association handlers, macOS offers launchd jobs and modified Mach-O load commands, Linux offers shell startup scripts and signal handlers, and cloud platforms offer event rules that invoke functions. Two properties separate this family from its neighbours. First, nothing in the trigger looks like a startup item, so an inventory of services and scheduled tasks can come back clean. Second, the resulting process frequently appears as a child of a trusted, signed program, which means the abnormal step is the parent, not the payload. Differentiators for the analyst are the age and provenance of the configuration, whether the referenced command line or script path matches anything in software inventory, and whether the artefact existed before the suspected intrusion window. Because these mechanisms let a higher-privileged component such as SYSTEM or a service account proxy the call, the same trigger can both persist and escalate.
