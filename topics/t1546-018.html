T1546.018 Event Triggered Execution: Python Startup Hooks

T1546.018PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This technique uses the way Python prepares itself at startup. Before Python runs your script, it reads a few small files that set up its environment. Some of those files can contain code that Python runs straight away. An attacker puts such a file in a folder that Python always reads. Then their code runs every time Python starts. This sub-technique differs from its parent because starting the Python interpreter, and not a sign in, sets off the code.

Why should you care?

Many servers run Python all day for automation, so the attacker's code runs without anyone opening a shell. The file looks like an ordinary part of a Python installation. No service, scheduled task or login script needs to change, so common persistence checks find nothing at all. If you never compare the package folders with a known good state, the change can stay in place for a very long time.

How it works, in plain steps

  1. When Python starts, it prepares its environment before it runs the script you asked for.
  2. During that step it reads path files, which are small text files ending in pth.
  3. A path file usually lists folders to search, but a line starting with import is executed.
  4. Python also imports two optional modules, sitecustomize and usercustomize, when it finds them.
  5. An attacker places a file in the site-packages folder so their code runs at every start.
  6. This keeps the attacker present on servers where Python runs often, with no service or login script.

Real-world example

Imagine a workshop where every machine has a start-up checklist pinned to the wall. The list says open the tool cupboard and check the oil. If someone adds one line, also leave the back gate open, every worker follows it at the start of every shift. Python startup files are that checklist, and the package folder is the wall where anyone with write access can pin a new page.

Key takeaways

  • Python runs code from path files and from the sitecustomize and usercustomize modules at startup.
  • A path file that contains import lines is unusual and should be checked.
  • Compare package folders with a known good state on hosts that run Python often.

In more detail

The Python interpreter performs site initialisation before it runs any user script. During that step it processes path configuration files, which are text files with the pth extension found in the site-packages or dist-packages directories: a line that begins with import is executed, not merely added to the search path. Python also imports the optional sitecustomize and usercustomize modules when they are found on the module path. An adversary places a file in one of those locations, or edits an existing one, so that their code runs on every interpreter start on the host, without needing a service, a login script or a scheduled task. The artefacts are file creation or modification inside the package directories, path files that contain import statements rather than plain paths, interpreter processes that spawn unexpected children or open network connections at startup, and startup code that runs even for a trivial command. Packaging tools and virtual environments legitimately create such files, but their content is normally a plain path, which is the discriminator.

What you will practise

  • Explain when Python performs site initialisation and why it matters.
  • Describe how a path file can contain executable code.
  • Describe the role of the sitecustomize and usercustomize modules.
  • Identify the folders where this persistence is placed.
  • Detect interpreter processes that behave strangely at startup.
  • Tell a normal packaging path file apart from a malicious one.
