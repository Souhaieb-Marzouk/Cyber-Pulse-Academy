DET0399 Detection Strategy for Scheduled Transfer and Recurrent Exfiltration Patterns

DET0399Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for data that leaves your network on a fixed timetable. Examples are every ten minutes, or every night at one o'clock. It also checks for the scheduling entry that created that timetable. The alert means a repeating transfer exists that nobody has approved.

Why should you care?

A steady timetable is a strong sign that a program, not a person, is sending data. People are irregular; scripts are punctual. Finding the schedule early lets you stop the flow and find the program that made it. It also gives you a clear artefact to remove from the computer. Without this detection, slow theft can continue for months because each single transfer looks small and ordinary.

How it works, in plain steps

  1. Endpoint monitoring records new or changed scheduled task entries, cron files and system timer units.
  2. Network devices record every outbound session with the time and the number of bytes sent.
  3. Both feeds arrive at the security monitoring platform with the host name and account.
  4. The rule looks for outbound sessions from one host that repeat at a similar interval with similar sizes.
  5. It then looks for a scheduled job or timer on that same host created shortly before the pattern began.
  6. Matching a new schedule with a new repeating transfer raises a high confidence alert for review.

Real-world example

Think of a night watchman who checks the same door at the same minute every hour. The log looks boring because it repeats. Now a second person starts checking the back gate every ten minutes. No manager scheduled that round, so the pattern itself is the clue. This detection reads the round sheet.

Key takeaways

  • Repeating on a regular interval is the signature of automated transfer.
  • Always pair a network pattern with the local schedule that could produce it.
  • Your own update and backup jobs look identical, so list them before you tune thresholds.

In more detail

This detection strategy focuses on data leaving the environment on a repeating timetable, matching the scheduled transfer technique where an adversary uses task schedulers or cron to move collected files at fixed intervals. The distinguishing evidence is not the volume of any single transfer but the rhythm: outbound sessions that recur at nearly the same interval from the same host with similar payload sizes, plus the local artefact that created the schedule. The telemetry that makes this possible is scheduled task creation and modification events, cron or systemd timer file writes on Linux, network flow records with timestamps and byte counts, and cloud storage upload audit logs. It fails most often because software update agents, monitoring checks and backup jobs are exactly this shape, so without an allow list of known periodic jobs the rule describes your own automation better than the attacker.

What you will practise

  • Describe how interval regularity distinguishes scheduled transfer from human activity.
  • Identify the local scheduling artefacts used on Windows, Linux and macOS.
  • Correlate a new schedule entry with the first appearance of a repeating outbound transfer.
  • Build an inventory of approved periodic jobs and their destinations.
  • Explain the coverage gaps when endpoint and network clocks are not synchronised.
