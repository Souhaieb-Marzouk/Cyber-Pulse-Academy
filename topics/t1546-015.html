T1546.015 Event Triggered Execution: Component Object Model Hijacking

T1546.015PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This technique changes a Windows registry entry so that a software part points to the attacker's file. Windows software is built from many parts that call each other, and each part has a long name called a class identifier. The registry says which file belongs to each identifier. An attacker edits that mapping in the current user's own area. Then any program that asks for that part receives the attacker's file. This sub-technique differs from its parent because a request for a software part, not a sign in, sets off the code.

Why should you care?

The current user's registry area can be edited without administrator rights, so this change is within reach of an ordinary account. The attacker's file then loads inside programs that people already trust. One variation even pulls a script from a remote server, so the malicious code changes whenever the attacker likes. If you never compare these entries with a known good state, the redirect can stay hidden for a long time.

How it works, in plain steps

  1. The component object model is a Windows system that lets software parts talk to each other through the operating system.
  2. Every part has a long name called a class identifier, and the registry maps it to a file.
  3. Windows checks the current user's classes area before the machine-wide area for that mapping.
  4. An attacker writes an entry in the user area that points a class identifier at their own file.
  5. When any program asks for that part, Windows loads the attacker's file instead of the real one.
  6. Some entries use the script marker, which makes Windows fetch and run a script from a web address.

Real-world example

Imagine a shared flat with a list of trusted tradespeople. The list says for plumbing, call Sam. There are two lists, one on the wall for everyone and one in your own room, and your own list wins. If a prankster edits your list so plumbing now means a stranger, every leak calls the stranger first. Component hijacking works the same way, and the list in your own room needs no special permission to edit.

Key takeaways

  • The current user's class identifier entries can override the machine-wide ones.
  • Editing them needs no administrator rights but loads the attacker's file inside trusted programs.
  • Watch for library loads from user-writable folders and for scripts fetched from the network.

In more detail

Component Object Model is the Windows mechanism that lets software components interact through the operating system, and each component is named by a class identifier that the registry maps to a library or a server. Because the registry lookup checks the current user's classes area before the machine-wide area, a component can be redirected with a write to a user-writable key and no administrator rights. A program that requests the hijacked component then loads the adversary's library instead, which gives persistent execution in many processes and, when a privileged program makes the request, a possible rise in rights. A related variation edits the type library entries that describe a component's interfaces, and can use the script moniker so that a remote script is fetched and executed whenever the component is used. The artefacts are writes under the class identifier and type library keys, image loads from user-writable paths such as the temporary or app data folders, script host processes, and outbound requests that fetch a script file. Legitimate components are registered by installation packages at a known time, so new or changed user-scope entries are the useful discriminator.

What you will practise

  • Explain what a class identifier is and where Windows stores it.
  • Describe why the per-user registry area takes priority.
  • Explain how a hijacked component gives persistence in many processes.
  • Describe the type library variation that fetches a remote script.
  • Identify telemetry for registry writes and library loads from user-writable paths.
  • Compare a legitimate install-time registration with an attacker's entry.
