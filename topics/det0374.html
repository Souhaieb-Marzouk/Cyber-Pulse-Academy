DET0374 Detection Strategy for Serverless Execution (T1648)

DET0374Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Serverless means you give the cloud provider a small piece of code and the provider runs it when needed, with no server for you to manage. This detection looks for someone creating or changing such a function so that it runs their code. It uses the cloud provider's own logs, because there is no server to watch.

Why should you care?

An attacker who deploys a function gets computing power inside your cloud account and often inherits its permissions. There is no file on a machine for your endpoint tool to inspect. Costs can also grow fast if the code is used to mine cryptocurrency. Because the provider logs every change, the evidence exists, but only if you collect it.

How it works, in plain steps

  1. Collect cloud audit records for function creation, update and delete operations.
  2. Collect identity records for new roles or policies that allow a function to be invoked or to act on other services.
  3. Collect function invocation records, including the calling principal and the source address.
  4. Compare each invocation with the principals that normally call that function.
  5. Inspect the function configuration for encoded content, external download links or unusual environment variables.
  6. Alert on a create or update event that is quickly followed by an invocation from a new principal.

Real-world example

Think of a self service laundry. You do not own the machines, you just pay and the machine runs your programme. If someone adds a new programme that also sends money to their own account, the shop owner only finds out from the machine's usage log. Cloud audit records are that log.

Key takeaways

  • In serverless environments the cloud audit log is your only reliable sensor.
  • Control plane changes plus a first time caller is the core detection pattern.
  • Baseline your deployment pipelines first, or normal releases will bury the real alert.

In more detail

This strategy detects serverless execution, where an adversary creates or modifies a function, container job, or scheduled cloud task to run their code inside the provider's infrastructure and blend in with normal platform activity. There is no host to instrument, so detection is built from control plane and data plane logs: function create and update events, identity or role changes that grant invoke rights, first time invocation of a function by a new principal, and outbound network connections from the function runtime. The pattern to alert on is a deployment or permission change followed closely by invocation from an unexpected principal, together with function code or environment variables that contain encoded content or external download references. It fails routinely because serverless work is highly automated, so deployment pipelines produce constant legitimate change that must be baselined first.

What you will practise

  • Describe why serverless computing removes the normal endpoint telemetry you rely on.
  • Identify the control plane and data plane events that reveal a new or changed function.
  • Build a rule that flags a first time invoking principal for an existing function.
  • Review function configuration for signs of embedded or downloaded payloads.
  • Explain how a function can inherit credentials and reach other cloud services.
