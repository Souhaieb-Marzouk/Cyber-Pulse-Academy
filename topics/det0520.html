DET0520 Behavioral Detection of Log File Clearing on Linux and macOS

DET0520Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This rule looks for someone erasing system log files on a Linux or macOS computer. Log files are the written records of what happened on the machine. An attacker who has already broken in may delete them so that nobody can see the earlier steps. The rule watches for commands and file changes that empty or remove those records.

Why should you care?

The log is the story of what happened. If it is removed, you cannot tell how the attacker got in or what they touched. Attackers often clear logs right after they gain higher rights, to buy time before anyone notices. Emptying one file can also break a whole chain of evidence, because records stop before the interesting moment.

How it works, in plain steps

  1. The audit subsystem records every command that runs, with its full arguments and the account that ran it.
  2. The rule keeps commands that name a system log path or a shell history file.
  3. It also watches for file deletion and truncation events on those same paths.
  4. Log rotation and container housekeeping are removed using their known parent processes and schedules.
  5. A rename or a service stop is treated as a separate signal, because it hides records without deleting them.
  6. Command evidence plus a matching file event on the same host close together becomes the alert.

Real-world example

Think of a shop that keeps a written till receipt for every sale. A cashier who has been taking money deletes the last few pages of the receipt book. The sales still happened, and the money is still gone, but the record no longer shows it. This rule watches the receipt book, not the till.

Key takeaways

  • Log deletion is a response to being discovered, so treat it as a high priority signal.
  • Rename and truncate hide records just as well as deletion, so watch all three.
  • Send logs to a central server, because local records can always be removed.

In more detail

This detection strategy covers the indicator removal technique of clearing or tampering with log files on Linux and macOS, tracked under T1685.006. On these platforms the log trail is a set of files under the system log directory, the audit records written by the audit subsystem, and the shell history files in each user home directory, and an attacker with enough rights can truncate, delete or rewrite any of them so that investigations lose the evidence of the earlier steps. The telemetry that makes it visible is process creation with command line arguments naming log paths, file deletion and file truncation events reported by the kernel audit subsystem or a file integrity monitor, audit service stop and reconfigure events, and shell history being emptied. The strategy fails in practice because routine log rotation, troubleshooting and container housekeeping touch the same files, so the rule needs the tool, the target and the account to line up before it is worth alerting.

What you will practise

  • Name the log and history file locations that matter most on Linux and macOS hosts.
  • Identify the commands that truncate, delete or rename log files and how they appear in audit records.
  • Use file deletion and file attribute change events from the kernel audit subsystem as secondary evidence.
  • Separate legitimate log rotation and container housekeeping from deliberate removal.
  • Explain why forwarding logs to a central collector changes the value of this detection.
  • Describe the escalation path when log removal appears on a server that handles sensitive data.
