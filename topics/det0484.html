DET0484 Multi-Platform Cloud Storage Exfiltration Behavior Chain

DET0484Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Cloud storage keeps files in buckets or containers rather than on a single server. This plan watches for one identity reading many of those files in a short time. Reading a few files is normal work. Reading thousands of them, from a new place, is the pattern this detection is built to catch.

Why should you care?

A stolen cloud key needs no software on your network to cause damage. The attacker can copy data straight out through the provider interface. Cloud logs often record the identity and address, which helps you trace the source. Because the traffic never touches your own network, endpoint tools will not see it. Cloud side logging is the only place this activity appears.

How it works, in plain steps

  1. The provider writes an audit record for each storage interface call, including the identity and source address.
  2. The detection groups those records by identity and by short time windows to measure how much was read.
  3. It compares the volume with a baseline for that identity, so a normal backup job does not fire the rule.
  4. A second condition checks for a permission change shortly before, such as a new key or a wider policy.
  5. The source address and the client program are compared with the addresses that identity normally uses.
  6. A chain of permission widening, sudden volume and an unfamiliar client or address becomes the alert.

Real-world example

Think of a library where members may photocopy pages. Copying a chapter for study is fine. One member copies a whole shelf in ten minutes. They use a borrowed card and they work at three in the morning. That is a different story. The librarian notices the pattern from the photocopier log, not from the books themselves. In the same way, cloud storage logs show the shape of the activity even when every single read is permitted.

Key takeaways

  • Cloud storage theft can look exactly like permitted access.
  • Volume, identity, address and client program together reveal the misuse.
  • You must enable object level logging before you can detect this at all.

In more detail

Exfiltration from cloud storage rarely needs malware: an identity with read permissions can pull large volumes of objects through the provider application programming interface, from an address the organisation has never used, using a scripting language or a synchronisation client. This strategy builds a behaviour chain across cloud audit logs, storage access logs and identity telemetry, correlating object read and list operations with the volume, the caller identity, the source address and any preceding permission change such as a new access key or a widened bucket policy. The frequent failure is that object level logging is disabled by default in several providers, so the chain collapses to identity events alone unless data event logging is turned on first.

What you will practise

  • Explain why cloud storage exfiltration is invisible to endpoint monitoring.
  • Name the audit records that capture object read and list operations.
  • Build a baseline of normal read volume for backup and application identities.
  • Correlate a permission change with a later spike in object reads.
  • Describe the coverage you lose when object level logging stays disabled.
