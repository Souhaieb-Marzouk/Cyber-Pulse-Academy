T1098.006 Account Manipulation: Additional Container Cluster Roles

T1098.006PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is a sub-technique of account manipulation. It means an attacker gives an account extra rights inside a system that runs software containers. Kubernetes is the most common such system, and it organises permissions with named roles. A binding is the link that hands a role to a user or service account.

Why should you care?

One binding can give an attacker the keys to an entire cluster, including stored passwords and every running application. These systems often hold production services, so the impact is immediate. Permissions are also easy to forget, because they live in configuration rather than in a person's account.

How it works, in plain steps

  1. The attacker obtains an account that can change access rules in the cluster.
  2. A role lists what may be done, such as reading secrets or starting new containers.
  3. A binding attaches that role to a user or service account inside the cluster.
  4. The attacker creates such a binding so their chosen account inherits the role.
  5. They may edit an existing binding instead, which is quieter than creating a new one.
  6. In managed clusters the same rights can be granted through the cloud provider instead of locally.

Real-world example

Picture a building where each floor has a rulebook and a nameplate beside every door. A contractor edits one nameplate to add a colleague's name, and copies a rulebook that allows any room. Nothing is forced and no alarm sounds, because the colleague now has a written right to enter, signed by the same system everyone trusts.

Key takeaways

  • Audit role bindings and cluster role bindings as carefully as you audit administrator accounts.
  • Remember that managed clusters may grant the same power through cloud roles.
  • Treat new bindings for service accounts as high priority alerts.

In more detail

This sub-technique of account manipulation covers granting extra permissions inside a container orchestration system, most often by binding an existing role to a user or service account. In Kubernetes, role based access control is expressed through Role and ClusterRole objects that list permissions, and through RoleBinding and ClusterRoleBinding objects that attach those roles to subjects. An adversary with enough rights creates such a binding, or edits an existing one, so that an account they control gains the ability to read secrets, create workloads or reach other namespaces. Where attribute based access control is configured instead, the equivalent move is editing the policy file that grants rights by attribute. The change may follow creation of a new account, or it may quietly extend a valid account already held by the attacker. Because managed cluster services inherit cloud identity, permissions are often granted through cloud role assignments rather than local objects, which links this behaviour to its cloud role counterpart. Detection uses the cluster audit log: creation or update events for role bindings and cluster role bindings, subjects that were not part of any change request, and bindings made by automation identities that normally never touch access control.
