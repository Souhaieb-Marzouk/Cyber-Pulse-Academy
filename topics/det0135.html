DET0135 Detection of Mail Protocol-Based C2 Activity (SMTP, IMAP, POP3)

DET0135Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Email travels using three main protocols. The Simple Mail Transfer Protocol sends mail, and the Internet Message Access Protocol and the Post Office Protocol fetch it. Attackers can hide their control traffic inside these protocols. A command from the attacker looks like an ordinary email. This detection looks for mail traffic that does not come from a mail program.

Why should you care?

Most networks allow mail traffic to leave, because work depends on it. Security tools often skip deep checks on mail ports for the same reason. So an attacker can send orders to a victim inside messages that look harmless. The traffic reaches a mail server that the attacker controls. This detection helps you find a control channel that hides in plain sight.

How it works, in plain steps

  1. Endpoint records show which program opened each network connection.
  2. The rule checks whether the destination port belongs to a mail protocol.
  3. It notes the process image, such as a browser, a script host, or an unknown program.
  4. It measures the timing, the size, and the repetition of each session.
  5. It compares the destination with the list of mail servers your company owns.
  6. An analyst then reviews the mailbox or the server to confirm what happened.

Real-world example

Think of a factory where staff may post letters at any time. The post box is emptied every day, so letters are completely normal. A spy learns this and starts sending instructions in plain looking letters to a friend outside. The letters pass the gate without trouble, because the gate staff only count envelopes. This detection is the guard who asks why a machine in the basement is posting twenty letters an hour. The letters look harmless, but the sender does not belong there.

Key takeaways

  • Mail ports are usually open, which is exactly what makes them useful to an attacker.
  • Compare the sending program with the protocol, not the port on its own.
  • Regular small sessions to an unknown mail server deserve a closer look.

In more detail

Mail protocol command and control (T1071.003) covers controller traffic that rides on the Simple Mail Transfer Protocol, the Internet Message Access Protocol, or the Post Office Protocol, because those ports are allowed outbound almost everywhere and are rarely inspected in depth. This detection strategy combines two views: endpoint connection records that attribute a mail protocol session to a process which is not a mail client, and network or proxy records that show repeated short sessions to a mail server the organisation does not own. The features that separate command and control from real mail are regularity of timing, small and consistent payload sizes, long lived sessions with periodic keepalives, and a destination absent from the mail infrastructure inventory. The strategy fails because encryption hides content, because notification services and monitoring appliances generate similar traffic, and because an attacker who uses the organisation's own cloud mailbox is indistinguishable from normal mail at the network layer.

What you will practise

  • Explain why mail protocols are attractive carriers for command and control traffic.
  • Identify the endpoint and network telemetry that attributes a session to a process.
  • Recognise timing and payload patterns that differ from a normal mail client.
  • Compare session destinations against the inventory of mail servers the organisation owns.
  • Describe how mailbox level evidence can confirm a suspected channel.
