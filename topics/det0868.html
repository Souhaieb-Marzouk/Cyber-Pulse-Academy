DET0868 Detection of Wordlist Scanning

DET0868Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A wordlist scan is an automatic search of a web site for hidden files and pages. The attacker sends many guessed web addresses and watches which ones answer. This detection catches that burst of guessing while it happens.

Why should you care?

A hidden backup file or an old admin page can give an attacker a way in. Those files are common on real web servers. Their absence is not something you can assume. If you spot the search early, you can block the source and remove the exposed file before anyone uses it.

How it works, in plain steps

  1. Your web server writes one log line for every request. Those lines go into your security information and event management system, called SIEM for short.
  2. The rule counts how many requests one source address makes in a short window, such as five minutes.
  3. It also counts how many different paths that source asked for. A scan touches many paths and few of them exist.
  4. The rule ignores normal browsing, where a visitor opens a few pages and most requests succeed.
  5. When both the request count and the failed request count pass your threshold, the system raises an alert with the source address and a sample of the paths.

Real-world example

Think of a night watchman in a hotel. Guests walk to their own room and open one door. A stranger walks the whole corridor and tries every handle, one after another. The handle log looks the same for each try, but the pattern of many failed tries from one person is the signal. You do not need to see the stranger. The log tells you a search happened.

Key takeaways

  • A wordlist scan looks like many failed requests from one source in a short time.
  • The request path and the status code are the two fields that carry the signal.
  • You must allow list your own scanners, or the alert will never be trusted.

In more detail

This detection strategy covers wordlist scanning of internet facing web services, the technique where an adversary requests thousands of guessed paths to find files, backups or admin panels that were never meant to be public. It matters because these probes return the entry point for a later attack, and the request volume is loud enough to catch. The telemetry that makes it possible is the web access log, the web application firewall event feed and the load balancer log, which together record the requested path, the status code, the user agent and the source address. This strategy fails most often because the same behaviour is produced by vulnerability scanners, health probes and marketing crawlers, so a rule without an allow list drowns the analyst in alerts and gets switched off.

What you will practise

  • Explain what a wordlist scan is and why an exposed file is useful to an attacker
  • Name the log fields that carry the signal: source address, requested path, status code and time
  • Write a threshold rule that counts distinct requested paths per source in a fixed window
  • Separate scanner traffic from attacker traffic using your asset inventory and allow list
  • Triage a web scan alert and decide whether the exposed path needs removal
