T1078.001 Valid Accounts: Default Accounts

T1078.001Initial AccessExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A default account is a username and password that comes with a device or program before anyone sets it up. It exists so the first person can log in, and it should be changed or turned off later. If it is left alone, anyone who knows the factory details can use it. This is a sub-technique of valid accounts, which covers the abuse of real logins.

Why should you care?

Many devices arrive with the same default password for every customer. A person who has never touched your network may already know it. If nobody changes it, an attacker can walk in and look like a normal user. The activity is hard to notice because every action uses a real login. One forgotten account can open a whole site or cloud tenancy.

How it works, in plain steps

  1. A vendor ships a device or program with a built-in login, such as a guest user or a support account.
  2. The person installing it leaves the factory password in place, or switches the account back on for a quick fix.
  3. An attacker scans the internet or lists internal hosts and finds a service that answers on a known port.
  4. They sign in with the published username and password, and the system accepts it as a real logon.
  5. Because the account is legitimate, the attacker can read files, change settings, or make their own account.
  6. Some default accounts appear later, such as a management service account created when two systems are joined.

Real-world example

Think of a new flat where the builder leaves a master key under the doormat for the first owner. That is fine for one day. If the key stays there for years, every person who ever read the builder manual knows where it is. You would not know someone came in, because they used a real key and the door was never broken. Default accounts work the same way: the key is real, the door is intact, and only a careful check of who used it shows the problem.

Key takeaways

  • Change or disable every default account before a device goes live.
  • Built-in names such as guest and root are targets, so watch logons to them.
  • A successful login is not proof of a friendly user.

In more detail

Default accounts are the credentials a system, appliance, or service ships with before an administrator changes anything. They include built-in operating system logins such as Guest or Administrator, provider root users in cloud and hypervisor platforms, and vendor support or service accounts created by integration. Because these identities already exist and are frequently privileged, an adversary who finds one still carrying its factory password gains access without exploiting any software flaw, so the resulting activity is a valid logon rather than an intrusion attempt. The artefact left behind is ordinary authentication telemetry, which is what makes this hard to spot. Defenders separate abuse from routine use by comparing logon records against an expected owner list, watching for first-time or odd-hour authentications to built-in names, and verifying that shipped accounts were renamed, disabled, or given unique secrets.

What you will practise

  • Explain what a default account is and why it attracts an attacker.
  • Describe how default credentials lead to access without any software exploit.
  • Identify the log sources that record authentication to built-in and vendor accounts.
  • Recognise suspicious patterns such as first-time logons to guest or root accounts.
  • List hardening steps that remove, rename, or disable accounts shipped by a vendor.
