T1137 Office Application Startup

T1137PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This technique means attackers hide their code or their links inside the settings that Microsoft Office reads when it starts. Office then runs that content each time Word, Excel or Outlook opens. The user does not have to open a strange attachment, because simply starting an Office program is enough.

Why should you care?

Office is installed on almost every work computer, so these settings exist everywhere. The settings are meant to be used, which means they are trusted and rarely reviewed. Attackers get a foothold that repeats every working day. To find it you must know what the settings normally contain on your own machines.

How it works, in plain steps

  1. Word and Excel load a base template at startup, and macros inside it run automatically.
  2. Office also reads a registry value that points to a library file to load on startup.
  3. Add-ins registered in the system are loaded next and their startup code is called.
  4. Outlook can load a home page address and needs no further user action to contact it.
  5. Mailbox rules and forms can be created in a mailbox and run actions on incoming mail.
  6. Each of these inputs is a configuration change, so a baseline of normal values is essential.

Real-world example

Imagine a shared kitchen where every flatmate follows the notes on the fridge door. Someone sticks a new note on the fridge that says to leave a copy of every delivery at flat four. Everyone reads the fridge out of habit and follows the note without thinking. The note is not food and not a locked door, it is just instructions everyone trusts.

Key takeaways

  • Persistence is placed in Office settings, so no malicious document has to be opened each time.
  • The trigger is simply starting an Office program, not opening a particular file.
  • Detect it by baselining registry values, template files, add-ins and mailbox rules.

In more detail

Office application startup covers the persistence mechanisms that live inside the configuration the Office suite loads when one of its programs opens. Instead of leaving a hostile document that a user must click, the intruder edits the components that Office reads on every launch: the base template that Word or Excel builds new documents from, the registry value that makes Office load a chosen library, add-ins that Office registers and calls at start, the Outlook home page address that can point at a remote system, and Outlook rules, forms and folder home pages that can be created in a mailbox and can act even when Outlook is closed. These are supported features used for templates, macros, integrations and mail organisation, so nothing has to be exploited and no new executable is dropped. The shared artefact is therefore configuration rather than code: registry keys under the Office branches, template and startup files in user profile paths, changed add-in registrations, and mailbox rule entries that forward, move or execute actions, all of which should be compared against a known good baseline. The reason this is grouped as one technique is that the trigger is identical for every variant, a user or an automated process simply starting an Office program, and the detection question is always which of these startup inputs changed.
