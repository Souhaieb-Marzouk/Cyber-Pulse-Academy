DET0173 Detection Strategy for Endpoint DoS via Service Exhaustion Flood

DET0173Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A service is a program on a computer that answers requests, such as a web server. This detection looks for one computer being asked so many times that it stops answering everyone. It catches a flood aimed at a single machine.

Why should you care?

Edge protections often guard the whole network, not one host. A flood aimed at one busy server can take it down while the rest of the network looks healthy. Customers see errors or a slow page and lose trust. Finding the pattern quickly lets you rate limit the traffic instead of waiting for the service to crash.

How it works, in plain steps

  1. The firewall, the load balancer and the web server each write a line for every connection they accept.
  2. Host monitoring agents also record how many open connections and half open connections a machine holds at any moment.
  3. The detection counts new connections per destination service over a short window.
  4. It then checks how spread out the sources are. Many connections from very few addresses is a stronger sign than the same count from many addresses.
  5. It looks for connections that close almost immediately, which often means clients are giving up or the server is refusing them.
  6. If the count, the source spread and the error rate all move together, the alert fires so the team can rate limit the service.

Real-world example

Think of a single ticket window at a train station. One long queue is fine and it moves. But if a crowd keeps pushing to the front and never buys a ticket, the clerk cannot serve anyone. The clue is not how many people came. It is that the queue never turns into sales.

Key takeaways

  • Host level floods are easy to miss, because edge traffic totals can look normal.
  • Read source spread and connection lifetime together with the request count.
  • Know your service baselines, or normal busy periods will trigger the rule.

In more detail

This strategy detects endpoint denial of service through service exhaustion flooding, where an adversary opens or requests services so fast that the host can no longer serve legitimate clients. It matters because the victim is a single host or application rather than the whole network, so volumetric monitoring at the network edge stays quiet while a business critical service becomes unavailable. Detection depends on connection level telemetry: firewall or load balancer connection logs, web server access logs, system socket or connection table counters collected by the host agent, and kernel or service crash records. The practical failure is that legitimate traffic spikes, retry storms and health check bursts look identical in shape to a small flood, so the rule must weigh source diversity, connection lifetime and error rate together rather than raw request volume alone.

What you will practise

  • Describe how service exhaustion differs from volumetric denial of service at the network edge
  • Identify connection level metrics and log fields that indicate a flood against one service
  • Combine request rate, source diversity and error rate into a single detection signal
  • Establish per service baselines that separate peak load from abuse
  • Plan a response that rate limits or filters without taking the service offline
