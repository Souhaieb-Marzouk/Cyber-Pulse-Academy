T1563.001 Remote Service Session Hijacking: SSH Hijacking

T1563.001Lateral MovementExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Secure Shell is a common way to log in to another computer from a command line. It can use a key file instead of a password. A small helper program, called an agent, holds that key for you. This sub-technique is about an attacker borrowing that agent or an open session. They then reach other machines as you, without your password. It is the Secure Shell part of the wider session hijacking technique.

Why should you care?

Key based logins are trusted and often not protected by a second check. If an attacker can use your agent, every machine that trusts your key may accept them. Nothing looks wrong from the server side. The login appears to come from your own computer and your own key. People often keep long lived sessions open for convenience, which gives an attacker more time to use them. That means the only clear warning may be a user saying their terminal session acted oddly.

How it works, in plain steps

  1. The user connects to a server with a key, and an agent keeps the key in memory.
  2. The session on the server stays open and keeps the user's identity and rights.
  3. The attacker gains high level access on the machine where the agent is running.
  4. They ask the agent to sign a login request, so no password or key file is needed.
  5. They can also take over an open terminal and type commands as the real user.
  6. Defenders notice work done in a session with no matching authentication record.

Real-world example

Imagine a shared flat where the front door key is kept in a bowl by the entrance. You do not carry it, you just take it when you leave and put it back when you return. A visitor who gets inside the flat can take the same key, open the door, and come and go. The landlord sees the door open normally and assumes it was you. The lock was opened by the usual key.

Key takeaways

  • The agent, not the key file, is the target, because it signs logins for you.
  • A hijacked session does no new authentication, so logins look completely normal.
  • Limit key trust, avoid unnecessary agent forwarding, and close idle sessions.

In more detail

Secure Shell (SSH) hijacking attacks the trust that public key authentication creates between machines. When a user connects with key based authentication, an agent process holds the private key in memory and signs authentication requests on the user's behalf, and the resulting session on the remote host keeps that authenticated identity for as long as it stays open. An adversary who compromises the agent, or who can reach the socket that the agent listens on, can request signatures from it and therefore log in to any host that trusts the key, without ever reading the key file or knowing its passphrase. Root access on the client host makes this straightforward, because the agent privileges and socket are then fully available, and agent forwarding widens the exposure by placing the agent socket on intermediate hosts. The adversary can also attach to a session that is already running by taking control of its terminal, which produces activity on the remote system under the legitimate user's identity. Detection is built on the oddity that no new authentication happened even though new work is being done. On the remote host, commands executed inside an existing session, or a new session that reuses an agent connection, will not be preceded by a matching authentication entry. Watching which process opened the agent socket, tracking forwarded agents onto hosts that do not need them, and correlating session and process records through host auditing tools are the practical leads, along with the telltale sign of a user complaining that their terminal behaved strangely.

What you will practise

  • Explain the role of the Secure Shell agent and how public key authentication works.
  • Describe how access to the agent socket allows logins without a passphrase.
  • Explain why agent forwarding increases the exposure of a hijacked session.
  • Identify audit records that show commands run in a session without prior authentication.
  • Summarise how this sub-technique differs from logging in normally with Secure Shell.
  • Outline hardening steps that reduce the impact of a compromised agent.
