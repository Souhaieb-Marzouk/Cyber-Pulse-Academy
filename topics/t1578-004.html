T1578.004 Modify Cloud Compute Infrastructure: Revert Cloud Instance

T1578.004Defense ImpairmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A revert means going back to an earlier saved copy of a cloud machine. The machine keeps its name and address but loses everything added since the copy was made. An attacker can use this after doing damage or spying. The recent files and logs made during their activity simply disappear.

Why should you care?

Missing recent logs make an intrusion much harder to prove and to understand. The attacker may also roll back a security update or an agent that was watching the machine. That can silently reopen a way into the system. Because a restore is a normal operation for many teams, it rarely raises suspicion on its own. You need records that live outside the machine to see what happened.

How it works, in plain steps

  1. A snapshot of the machine or its disk exists from an earlier time.
  2. The attacker, or a script they run, requests a restore of that snapshot.
  3. The cloud service replaces the current machine state with the copy.
  4. Files and logs created after the snapshot are no longer present.
  5. Security agents or updates installed later may also disappear.
  6. The machine restarts with its old name, so users notice little.

Real-world example

Imagine a whiteboard in an office used for all important notes. Someone photographs it in the morning and writes plans on it all afternoon. In the evening a helper wipes the board back to the morning picture. Anyone who walks in next day sees a tidy board and has no idea what was written and erased.

Key takeaways

  • Track restore and snapshot rollback events in your cloud activity logs.
  • Store security logs off the machine so a revert cannot erase them.
  • After any unexpected restore, recheck patches and security agents.

In more detail

Reverting a cloud instance restores a machine or its attached storage to an earlier point in time, typically by applying a snapshot through the provider console or an API call. Where deletion destroys a resource, reversion rewinds one, which is a different defensive problem: the machine keeps running and keeps its identity, but the recent contents that recorded malicious activity are gone. The same effect can be achieved less visibly with ephemeral storage that providers reset on stop or start, so a reboot may silently discard evidence without any explicit restore action. Reversion can also roll back a security agent, a log shipper configuration, or an operating system patch that was applied after the snapshot was taken, which reopens a vulnerability the adversary exploited. Detection depends on control plane events for instance start, stop, and restore operations, on snapshot application records, and on telemetry that jumps backwards, such as a host whose boot time, patch level, or agent version returns to an older state. Because legitimate teams also restore systems during recovery, the differentiator is context: a restore performed by an identity or from a location outside the normal operations pattern, or one that follows suspicious administrative activity, deserves scrutiny.

What you will practise

  • Explain what reverting a cloud instance does to machine state.
  • Describe how ephemeral storage resets can destroy evidence on restart.
  • Recognise how a revert can undo security patches or agents.
  • Identify audit events that reveal snapshot restore operations.
  • Distinguish a recovery restore from an evasion restore using context.
