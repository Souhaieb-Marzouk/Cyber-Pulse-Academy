T1136 Create Account

T1136PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Creating an account is when an attacker adds a brand new user identity to a system, a network directory, or a cloud service. That new login is not stolen, so it keeps working even after the real breaches are found and passwords are reset.

Why should you care?

Most clean-up work focuses on the accounts an attacker stole. A quiet new account can sit outside that list for months. It looks like normal staff onboarding, so nobody questions it. If the attacker gives it extra rights, they can return whenever they like. Regular access reviews are how you find accounts nobody actually hired.

How it works, in plain steps

  1. The attacker already has a foothold, meaning some access to one machine or one cloud tenant.
  2. They use normal admin tools, not a software bug, to add a new user account.
  3. The new account can be local to one machine or shared across the whole company directory.
  4. They may also create cloud identities, service accounts, or accounts for automation.
  5. If they already hold rights, they quietly add the account to a privileged group.
  6. Later they simply log in again, and the original fix no longer keeps them out.

Real-world example

Think of a hotel that changes every lock after a break-in. The thief had copied a key, so the new locks work. But while inside, the thief also added a new key card to the system and wrote a name on it that sounds like staff. The hotel keeps it active because it looks normal. The thief walks back in through the staff entrance weeks later.

Key takeaways

  • A stolen account can be fixed; a newly created one must be found.
  • Compare each new account against a real hiring or change record.
  • Review privileged group membership often, and remove what you cannot explain.

In more detail

Create Account describes adversary creation of new accounts to maintain access after an initial foothold is lost or remediated. The accounts involved can be local or domain user accounts, accounts holding administrative rights, cloud and SaaS identities, service principals, or machine accounts created through directory APIs, and they can be created on a single host, in the enterprise directory, or in a hosted tenant the organisation only partially monitors. The technique is favoured because a fresh account survives the password resets that remediation applies to compromised existing accounts, blends into the constant background churn of real onboarding, and can be granted additional rights quietly if the adversary already holds privilege. The mechanism usually involves ordinary administrative interfaces rather than exploits: command-line account management utilities, remote management protocols, directory and cloud identity APIs, and application-specific user administration consoles. The artefacts are concentrated in directory and audit telemetry, including account creation events, group membership additions, privilege role assignments, cloud provider audit records, and the authentication activity of the new identity afterwards. Benign account creation is continuous in most environments, driven by hiring, contractor onboarding, automation and service deployment, so an investigation should weigh the identity of the creator, the interval between creation and first use, the privileges requested or assigned, how naming and description conventions compare with organisational standards, and whether the creating identity was itself recently established or recently elevated. Accounts created and then used immediately, added straight into a privileged group, or authenticating from unexpected infrastructure are the cases that warrant escalation, and reviewing them against a documented joiner process is usually what separates a real incident from a noisy one.

What you will practise

  • Identify the account types an adversary can create and the visibility each provides to the defender.
  • Interpret directory, local and cloud audit records to reconstruct who created an account and when.
  • Detect create-and-use patterns by comparing account creation with subsequent authentication activity.
  • Evaluate naming, privilege and approval controls that make rogue accounts distinguishable from legitimate ones.
  • Explain how identity governance and periodic access review limit the lifetime of adversary accounts.
  • Write detection logic for privileged account creation and for sensitive group membership changes.
