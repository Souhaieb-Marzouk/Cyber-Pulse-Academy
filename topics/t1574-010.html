T1574.010 Hijack Execution Flow: Services File Permissions Weakness

T1574.010ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Services are background programs, such as a print service or update service. Each service runs one program file from disk. If that file, or the folder around it, has weak permissions, an attacker can swap the file. When the service starts, Windows runs the swapped file instead.

Why should you care?

Services usually run with far more rights than a normal user account has. So a swapped file can run as an administrator or as SYSTEM, which is the highest local account. The swap can also be very quiet, because the service name and path look normal. The machine then keeps running the attacker file after every restart. Few teams check who can write to service folders.

How it works, in plain steps

  1. An administrator installs a service and leaves the folder permissions too open.
  2. A normal user account on the same machine can therefore write into that folder.
  3. The attacker renames the real program and drops a file with the same name.
  4. The service starts, often at boot, and Windows loads the attacker file.
  5. The file runs under the service account, which may hold SYSTEM rights.
  6. It repeats each time the service starts, so the access survives a reboot.

Real-world example

Picture a hospital night desk where the medicine cabinet key hangs on a hook. The cleaner has a key to the storage room, not to the cabinet, but the cabinet lock is broken. A thief swaps the real medicine boxes for lookalike boxes. Every morning the nurse picks up a box without looking. Nothing about the routine changed, and nobody noticed the broken lock.

Key takeaways

  • Check write permissions on every service program and its folder.
  • Record hashes of service binaries so a silent swap is easy to spot.
  • Remove write rights from normal users on program directories.

In more detail

This sub-technique targets weak filesystem permissions rather than path parsing. When the folder holding a service binary, or the binary file itself, allows an ordinary user to write, an adversary can overwrite or replace that executable and let the service mechanism run it. Because the service control manager starts the image under the account configured for the service, the swapped payload executes at that account context, which may be SYSTEM or a privileged domain identity. The same property gives persistence whenever the service starts automatically at boot, triggers on an event, or is restarted on a schedule. Two variants exist in practice: replacing the existing file in place, which preserves the name but changes the content, and renaming or deleting the original and dropping a new file with the expected name. Detection therefore combines file integrity monitoring and hash comparison of service images, file creation events on service directories, and process creation records that tie a service-lifetime parent to a child image whose path or hash differs from baseline. Note the contrast with service registry weaknesses, where the configuration entry is redirected instead of the file being replaced.
