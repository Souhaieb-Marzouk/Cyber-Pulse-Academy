T1027.007 Obfuscated Files or Information: Dynamic API Resolution

T1027.007StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Most programs list the system tools they need before they run. Dynamic API resolution means a program works out which tools it needs while it is running. It finds each tool by a hidden code, then calls it. So the program file itself lists very little.

Why should you care?

Analysts often judge a program by the list of system tools it uses. That list can hint at harmful behaviour before the program even runs. If a program hides the list, this quick check gives nothing away. You must then watch the program while it runs, which takes more time and skill.

How it works, in plain steps

  1. The programmer works out which operating system functions the program needs.
  2. Instead of listing those names, they store short codes, often a hash of each name.
  3. A hash here means a short code calculated from a longer piece of text.
  4. When the program starts, it loads the system library that provides such functions.
  5. It reads the library list of functions and compares each one against its stored codes.
  6. When a code matches, the program saves that function address and calls it later.

Real-world example

Think of a chef who refuses to write a shopping list. Instead, they walk the market and check each stall against a private code. Only the chef knows what is being bought. Anyone reading their pocket would learn nothing useful. A program using dynamic resolution hides its intentions the same way.

Key takeaways

  • Dynamic resolution hides which system functions a program uses until it runs.
  • A sparse import list with library loading calls is a common warning sign.
  • Behaviour and memory analysis reveal what static import inspection cannot.

In more detail

Dynamic API resolution means a program does not declare the operating system functions it needs in its import table, but looks them up at runtime instead. Static review of the import address table is a cheap way to guess what a binary does, because an import of a process creation or memory writing function is revealing. To break that link, malware stores hashes or other encoded identifiers of function names rather than the names themselves, then walks the loaded module list and matches those hashes to find each function address, sometimes loading the providing library first. The required strings are therefore absent and the import table looks sparse or generic. Memory and behaviour become the useful evidence: a module resolving many addresses shortly after start, and calls the import table never advertised.
