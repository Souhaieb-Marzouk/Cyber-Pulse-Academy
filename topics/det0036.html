DET0036 Suspicious Device Registration via Entra ID or MFA Platform

DET0036Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

In cloud identity platforms a device can be registered, which means the platform now trusts and knows that device. This detection looks for device registrations that do not fit the normal pattern. It also looks for new sign in keys added to an account.

Why should you care?

A registered device can pass device checks at sign in. If an attacker registers a device they own, a stolen password becomes far more useful. They may keep access even after the password is changed. So this is a persistence problem, not only a login problem.

How it works, in plain steps

  1. The cloud writes an audit record whenever a device is registered or joined.
  2. It writes another record when a credential or key is added to a user or application.
  3. The rule collects both record types for the same account in a short window.
  4. It adds sign in details, such as the address the request came from and the device name.
  5. It removes bulk registrations from approved management tools and known corporate ranges.
  6. It flags registrations from unusual addresses or names that do not match your naming standard.

Real-world example

Think of a members only gym. The desk keeps a list of approved keys. At midnight, someone who is not the desk manager adds a key for a member you never met. That key should be checked before the locker room opens.

Key takeaways

  • A device object can act like a spare key, so treat registration as a persistence event.
  • Join registration data with credential additions and sign in records.
  • A naming standard for devices makes the odd one much easier to spot.

In more detail

This strategy detects suspicious device registration and the credential material added alongside it, the account manipulation behaviour tracked as T1098.005. A registered or joined device becomes an identity object that can satisfy a device based access rule and carry its own credentials, so an attacker who registers a device they control, or who adds a credential to an existing identity object, can keep access even after the user password is reset. The telemetry is directory audit data for device and credential operations joined to sign-in logs and multi factor authentication registration events. It fails in practice because onboarding tools register devices in bulk and users legitimately add their own hardware, so the operation name alone is far too common and the useful discriminators are the actor, the origin address, the device name pattern, and whether the user was recently prompted for a strong authentication method.

What you will practise

  • Explain what a registered or joined device can do at sign in.
  • Identify audit operations that create a device object or add a credential.
  • Correlate a device registration with sign-in origin and authentication method data.
  • Recognise bulk registration performed by an approved onboarding tool.
  • Describe how device registration supports persistence after a password reset.
  • Define a device naming standard that supports detection and triage.
