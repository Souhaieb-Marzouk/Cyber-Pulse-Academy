T1574 Hijack Execution Flow

T1574ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Programs ask the operating system to find and start other files. This technique means changing the answer to that request. The attacker makes the system run their file instead of the real one. The real program often still works, so nobody notices the change.

Why should you care?

Trusted programs are allowed to do many things. If an attacker's file loads inside one, it inherits that trust. Security tools may accept it because the program is known and signed. The trick can also survive a restart, so the attacker returns after a reboot. This makes the compromise deep and hard to clean.

How it works, in plain steps

  1. A program asks the operating system to locate a file that it needs to run.
  2. The operating system searches a list of places in a fixed order.
  3. The attacker places a file with the expected name in an earlier place.
  4. Configuration such as registry values or path lists can also change the order.
  5. The system loads the attacker's file and gives it the program's permissions.
  6. The program often keeps working, so the change is easy to overlook.

Real-world example

Imagine a hospital where a nurse asks the supply room for gloves. There are two supply rooms, and staff always try the nearer one first. Someone fills the nearer room with faulty gloves. The nurse takes them without checking the label, because the routine has not changed. Hijacking execution flow is similar. The system asks for a file, and the nearest copy wins. The answer is wrong, but the process looks normal.

Key takeaways

  • The system decides what to run by searching a list of places in order.
  • Change the order or the contents and a different file runs instead.
  • Compare the paths of loaded files against a known good baseline.

In more detail

Hijack execution flow is the family of tricks that change which code the operating system actually runs when a program or a library is requested. Rather than breaking a program, the attacker interferes with the lookup or loading step: the directory that is searched first, the order of library paths, a registry value that redirects a load, or an environment variable that names a library to preload. The payload then runs inside a trusted process, inherits that process's permissions, and often survives a restart, which is why the technique serves execution, persistence, privilege escalation and defence evasion at the same time. The artefacts are configuration changes, unexpected files sitting beside legitimate executables, and loaded modules whose path or signature does not match the vendor. Defenders detect it by comparing where code was loaded from against where it should have come from, and by baselining file permissions in program directories.
