T1218 System Binary Proxy Execution

T1218StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

System binary proxy execution means using a trusted program that is already on the computer to run other, malicious code. The trusted program is often signed by Microsoft, so security tools allow it. The attacker hides behind that trust instead of bringing their own program.

Why should you care?

Signature checks and allowlists are normal defences, and this technique slips past both. Many of the programs involved are needed by Windows, so you cannot simply block them. If you only look at program names, you will miss the attack. You need to look at what each trusted program is asked to do.

How it works, in plain steps

  1. The attacker chooses a signed program that already exists on the machine, so no new tool must be installed.
  2. That program has a feature for running other code, such as loading a library file or a script.
  3. The attacker supplies their own file or command as an argument when the trusted program starts.
  4. Security tools see a known, signed program start, and they often allow it without deeper questions.
  5. The trusted program then loads or runs the attacker's code inside its own process.
  6. Detections built only on file names and signatures notice nothing, so defenders must read arguments and loaded modules.

Real-world example

A company van with the firm's logo can drive through the security gate without a full search, because the guards know that van. A thief paints the same logo on a stolen van and drives in carrying stolen goods. The guard at the gate waves it through, because the logo looks correct. A guard who checks the delivery note and the driver catches the trick. Trusted Windows programs are the van, and the command line arguments are the delivery note.

Key takeaways

  • Signature checks alone cannot separate a trusted tool from a trusted tool being misused.
  • Read command lines, parent processes and loaded modules together.
  • Blocking these programs outright is usually a bad idea, because Windows needs many of them.

In more detail

System binary proxy execution covers the family of behaviours in which an adversary achieves code execution by handing work to a binary that is already present on the host and usually signed by the platform vendor. The signed image passes signature validation and often application control policies, while the actual payload is a script, library, installer package or remote object that the trusted binary loads on the attacker's behalf. On Windows the well-known carriers include script and shell utility hosts such as rundll32, regsvr32, mshta, msiexec, cmstp, installutil, regsvcs and regasm, odbcconf, verclsid, control and hh.exe; on Linux, general-purpose tools with command execution or output redirection features, such as split, serve a comparable role. The distinguishing telemetry is rarely the binary name, because these programs appear constantly in normal operations. It is instead the argument and module context: command lines that name remote URLs, script prefixes, unusual library exports or paths in temporary and user-writable directories, image load events showing unsigned or user-writable modules mapped into a signed process, and child processes that do not match the expected behaviour of the carrier. Legitimate use tends to originate from installers, the operating system or managed deployment tooling, references trusted paths, and produces no unexpected network traffic, so defenders compare the invocation source, the referenced file and the resulting process tree rather than blocking the binary itself.
