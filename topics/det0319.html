DET0319 Detection Strategy for T1136.003 - Cloud Account Creation across IaaS, IdP, SaaS, Office

DET0319Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for new accounts created in cloud platforms. It also covers identity services, such as a new user in a cloud tenant. Cloud accounts are often created through a programming interface rather than by a person clicking. Attackers create them so they keep access even after the first account is reset.

Why should you care?

A new account may not appear on any staff list, so nobody expects it. It can be given permission to read data or to create more accounts. Because it is created in the cloud, there is no file or program to find on any laptop. Catching it early removes a quiet way to stay inside your environment.

How it works, in plain steps

  1. Each cloud provider writes an audit record for every management action, including account creation.
  2. The record names the action, the account that performed it, the new account and the source address.
  3. Your platform collects these records from every provider you use.
  4. The rule filters for account creation actions on identity services and cloud tenancies.
  5. It then checks who created the account and whether that identity normally does this work.
  6. It also looks for follow up actions. Examples are a new access key, a privileged role or a first sign-in.

Real-world example

Think of a members-only gym where the front desk issues key fobs. A manager's login can create a new fob without paperwork. The intruder makes a fob, uses it at quiet hours, and returns the manager's login. The member list still looks correct, but one extra fob works every night.

Key takeaways

  • Cloud accounts leave management plane audit records, not endpoint files.
  • Compare the creating identity with your provisioning inventory before alerting.
  • What happens after creation, such as new credentials, is often the clearest signal.

In more detail

This strategy detects the creation of cloud and identity provider accounts, the account creation behaviour recorded in the assignment as t1136-003. Cloud accounts are attractive because they can be created without any endpoint change, they often inherit default permissions, and they survive password resets applied to the compromised human identity that created them. Detection depends on management plane audit records from each provider, which name the API action, the actor, the target principal and the source address, joined to later events where the new account receives credentials or privileged roles. The recurring failure is that provisioning automation creates accounts constantly, so the rule must weigh the creating identity, the provider's tenancy context and what happens to the account afterwards.

What you will practise

  • Describe why attackers create cloud accounts instead of modifying existing ones
  • Identify the audit events that record account creation in cloud and identity platforms
  • Correlate a created account with the credentials or roles it receives afterwards
  • Build a provisioning inventory of approved automation identities for comparison
  • Explain how default permissions on new accounts raise or lower severity
  • Test the rule with a harmless account created in a sandbox tenancy
