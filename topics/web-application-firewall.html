Web Application Firewall

Application SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A web application firewall is a filter that sits in front of a website. It reads each request before the site sees it. If the request looks like an attack, the filter blocks it or logs it.

Why should you care?

Websites take input from strangers, and that input is often used to attack the site. Fixing every line of code takes a long time. A filter in front can stop common attacks today while developers fix the real problem.

How it works, in plain steps

  1. Traffic for the site is sent to the filter first, not straight to the site.
  2. The filter decodes the request, including hidden encodings in the text.
  3. It compares the request with attack patterns and with normal daily behaviour.
  4. Suspicious requests are blocked, allowed with a warning, or only logged.
  5. Clean requests pass to the site, and the site sends back its answer.
  6. Administrators read the logs and tune the rules to cut false alarms.

Real-world example

Picture a hospital night desk that checks every visitor before they go upstairs. The clerk asks who you are visiting and writes your name down. Most visitors pass in seconds. Someone carrying a toolbox at three in the morning gets stopped and questioned.

Key takeaways

  • A web application firewall filters web traffic and does not fix bad code.
  • Rules need tuning, because strict rules block real users as well.
  • It still needs to read encrypted traffic to inspect it properly.

In more detail

A web application firewall is a reverse proxy placed in front of a web application that inspects HTTP and HTTPS requests and responses and blocks those matching attack patterns or violating a learned model of normal behaviour. The mechanism differs from a classic network firewall because it parses the application layer: it normalises encodings, decodes parameters, and evaluates rules against the request line, headers, cookies and body, which is why signature-based engines can spot injection payloads that a packet filter would pass. Deployed inline it terminates or forwards TLS, so the appliance must be given the private key or be trusted to re-encrypt, and that key handling is a real operational constraint. It shows up as a managed cloud service, a module in a load balancer, or an open source engine with a community rule set. The mistake people usually make is expecting it to remove the need to fix code: rule sets produce false positives that break normal traffic, and a determined attacker tunes payloads until they look legitimate, so the firewall is a compensating control and a detection source, not a repair.

What you will practise

  • Explain what a web application firewall inspects and where it sits in a request path.
  • Compare signature-based and behaviour-based detection rules.
  • Describe how transport encryption affects the ability to inspect traffic.
  • Explain why a web application firewall is a compensating control rather than a fix.
  • Recognise the operational cost of false positives in rule tuning.
