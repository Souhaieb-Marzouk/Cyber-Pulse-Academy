DET0347 Detection Strategy for Masquerading via Legitimate Resource Name or Location

DET0347Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for a program that uses a trusted name or a trusted folder. An attacker may name a harmful program after a normal Windows part. They may also put it in a folder where you expect only system files.

Why should you care?

People trust names and folders. If a program is called the same as a Windows component, many tools will allow it. A quick look at the file name will not raise any doubt. This trick also helps an attacker hide among the many system processes that run all day. To catch it, you must check the full path and the file signature, not only the name.

How it works, in plain steps

  1. The system logs every new process together with the full path of the program that started it.
  2. The rule keeps the process names that belong to the operating system or to a trusted vendor.
  3. It then checks the folder, because those names should come from one expected location.
  4. A match from a temporary, downloads or user folder is treated as suspicious.
  5. The rule also reads the original file name inside the program and the signature on it.
  6. When the name, the folder and the signature do not agree, an alert is raised.

Real-world example

Think of a building where the cleaners wear a uniform and carry a pass. A stranger can buy a similar uniform and walk past the desk. The uniform alone convinces nobody who checks the pass. The file path and the signature are your pass check.

Key takeaways

  • Judge a program by its path, its signature and its name together.
  • A system process name outside the system folder is a strong signal.
  • Allowlists based only on file names will let masquerading through.

In more detail

This detection strategy covers Masquerading by matching a legitimate resource name or location (T1036.005), where an adversary names a payload after a trusted system or vendor component, or drops it into a directory that users and tools already trust. The technique matters because analysts, allowlists and application control policies often key on file names and paths, so a trusted looking name can buy the attacker execution and time. Detection depends on process creation telemetry that carries the full image path, the original file name from the version resource, the signing state, and on file creation records inside system or program directories. It fails most often because legitimate third party software also places binaries in trusted looking paths.

What you will practise

  • Explain how trusted file names and trusted folders are used to avoid scrutiny
  • Identify process and file telemetry fields that reveal a mismatch between name, path and publisher
  • Establish the expected install locations for system binaries and approved applications
  • Write a rule that combines image path, original file name and signature state instead of the name alone
  • Triage a match by hashing the file and checking it against known good software inventory
  • Describe the coverage gap when application control already blocks user writable directories
