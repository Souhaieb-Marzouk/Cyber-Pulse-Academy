DET0418 Windows DACL Manipulation Behavioral Chain Detection Strategy

DET0418Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Windows files and folders have a list that says who may read, change or delete them. That list is called a permissions list. This detection looks for someone changing that list in a way that helps an attacker. Examples are granting full control to a broad group or taking control of a system file.

Why should you care?

Changing permissions is a quiet way to keep access to a computer. It can also let an attacker replace a trusted program with their own copy. Defenders may not notice because permissions are changed by real administrators too. A weak permission on a system file can undo other protections. Following the order of events helps you tell a support fix from abuse.

How it works, in plain steps

  1. Windows can record when permissions on a file or folder change. This works only when auditing is switched on for that object.
  2. Each record shows the object path, the account that made the change and the entry added or removed.
  3. The rule selects changes on sensitive paths, such as system folders and service binaries.
  4. It notes the account and the program used, for example a command line permission tool or a script.
  5. It then looks for what happened next on the same path. An example is a file being replaced or a service restarting.
  6. When a broad permission is granted on a sensitive path, the analyst gets one alert. It shows that change and everything after it.

Real-world example

Think of a shop that keeps its cash in a locked drawer. The manager holds the key. Someone copies the key and gives it to a temporary worker. The drawer is then opened after hours. The copied key is the permission change. The after hours opening is the next step. Together they tell a clear story.

Key takeaways

  • A permission change on its own is usually normal, so look for the chain that follows it.
  • Sensitive paths matter most: system folders, service binaries and security tooling.
  • Record the account and the tool used, because that is what makes the chain reviewable.

In more detail

This strategy covers the modification of Windows file and directory permissions, tracked as T1222.001, where an adversary changes a discretionary access control list to keep access to a file, weaken protections on a sensitive path or lock out defenders. It matters because permission changes are a persistence and defence evasion primitive that quietly widens who can read or replace critical files, and because the change itself is a legitimate administrative action that appears daily in most estates. The telemetry that makes detection possible is object access auditing with permission change records, process creation records for the built in permission utilities, file system change events, and the security descriptor change events that the operating system writes when an access control entry is added or removed. The main way it fails is that deployment tools and administrators change permissions constantly for ordinary reasons, so the rule has to be built as a behavioural chain: who changed permissions, on which path, which entry they added, and what happened to that path afterwards.

What you will practise

  • Explain what a discretionary access control list is and what changing it allows.
  • Identify the Windows events that record a permission change and the fields they contain.
  • List the sensitive paths where a permission change should always be reviewed.
  • Correlate a permission change with a following file replacement or service action.
  • Recognise admin tooling that legitimately changes permissions at scale.
  • Describe how to scope auditing so the log volume stays manageable.
