DET0388 Detection Strategy for T1548.002 – Bypass User Account Control (UAC)

DET0388Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

User account control is the Windows feature that asks for permission before a program runs with full administrator rights. A bypass is a way to get those rights without the question appearing. This detection looks for the record changes and program starts that a bypass needs.

Why should you care?

A bypass turns a limited user into a full administrator, so every later step becomes easier. The user sees no prompt, so the activity looks ordinary. Catching the record change that a bypass depends on gives the team a chance to respond before the new rights are used.

How it works, in plain steps

  1. The monitoring agent records changes inside registry keys under the current user profile.
  2. The rule keeps changes in the parts of the registry that trusted signed programs read at launch.
  3. Process creation records show a signed system program starting from a parent that is not elevated.
  4. The rule checks the integrity level and token details to confirm the new process runs at a higher level.
  5. A matched change plus a matched elevation in the same short window becomes one high priority alert.

Real-world example

Think of a locked records room that opens only with a supervisor card. A visitor finds that the door also opens when a particular form is left on the desk inside. No alarm sounds and no card is used. The guard only notices because someone changed the contents of that desk.

Key takeaways

  • A bypass leaves traces in the current user registry, not in the system wide policy.
  • The strongest alert pairs a suspicious record change with a signed program starting at a higher level.
  • Recording process integrity level is a prerequisite, so check that field is populated.

In more detail

This detection strategy covers user account control bypass, where an adversary escalates from a normal user to an administrator level context without the consent prompt that the operating system would normally show. The behaviour is visible in three places: registry keys under the current user profile that trusted signed binaries read when they launch, elevation of a system binary by a non elevated parent, and changes to the control settings that govern when prompts appear. Registry modification auditing, process creation records with integrity level and token details, and endpoint elevation telemetry supply the evidence. The strategy most often fails because the allowed keys are so numerous that a rule without a tight baseline either misses the specific key in use or buries the analyst in registry noise, and because many endpoint agents do not record the integrity level of the launching process.

What you will practise

  • Explain the difference between a consent prompt and an automatic elevation decision
  • Identify the registry locations that trusted signed binaries consult at launch
  • Use process integrity level and token information to confirm an unexpected elevation
  • Correlate a registry change with the elevated process start that follows it on the same host
  • Recognise legitimate installers and management agents that elevate without a prompt
  • Describe the collection changes needed when a sensor does not record integrity level
