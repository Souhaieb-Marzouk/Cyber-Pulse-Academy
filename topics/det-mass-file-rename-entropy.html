Mass File Rename With High Entropy

Detection StrategyExtremeDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Entropy is a measure of how random a piece of text looks. This detection watches for one program renaming or rewriting hundreds of files very quickly. The new names look like random strings and share the same ending. That pattern is the fingerprint of ransomware encrypting your files.

Why should you care?

Encryption runs fast because the attacker wants it finished before anyone notices. Catch the wave while it is still running, and you can stop the program. That saves the files it has not reached yet. Miss it, and recovery may mean restoring from offline copies or paying. This is one of the last chances to interrupt an attack.

How it works, in plain steps

  1. Your endpoint tools or file auditing record who changed which file, and when each change happened.
  2. Events are grouped by the program that made the change, over short windows such as ten minutes.
  3. The detection counts how many files that one program touched inside the window.
  4. It compares that number against what is normal for that program on that kind of machine.
  5. It then checks whether the new names look random or share one odd file extension.
  6. A high rate plus random names plus files touched across several folders is treated as critical.

Real-world example

Imagine a person walking along every library shelf and rewriting each book title as a random code. They work through the whole room in minutes, never pausing and never reading anything. A normal archivist may relabel many books too. But they work slowly, one section at a time, and keep names people can read. Speed, randomness and coverage are what give the intruder away.

Key takeaways

  • Watch the rate as well as the name, because encryption is bulk work done fast.
  • Random names plus one shared extension make a rename wave far more suspicious.
  • Names alone are not enough, since build and backup tools rename files in bulk too.

In more detail

Mass file rename with high entropy detection identifies a single process rapidly modifying, renaming or extending the names of many files across one or more directories where the resulting names exhibit high character entropy and consistent suffix patterns, which is the observable fingerprint of automated data encryption for impact. The behaviour matters because it is one of the last chances to interrupt an intrusion before recovery becomes expensive: once the rewrite completes across servers and backups the organisation is reduced to restoring from offline copies. The telemetry required is file system auditing or endpoint file-operation telemetry that captures the acting process, the parent process, the original and resulting file names, the operation type and the directory, together with process creation records for identity and a time-series aggregation capability so that rate per minute can be computed rather than evaluated file by file. The signal survives common evasion because the operation is inherently bulk and inherently fast; even a deliberately throttled encryptor must rename or rewrite thousands of files within a short window to be effective, and slowing down enough to avoid rate thresholds extends the attack to an impractical duration. Directories excluded from encryption to preserve a ransom note still produce a distinctive cluster of untouched paths. The detection breaks down in practice because legitimate software performs bulk rename operations routinely: archive extraction, media transcoding pipelines, document management migrations, development build systems, and backup rotation all write or rename many files quickly. Distinguishing them requires examining name entropy, suffix uniformity, the presence of an accompanying note file, whether the process deleted or created recovery artefacts, and whether shadow copies or backup services were affected in the same window. Coverage gaps also arise where telemetry is sampled, where network attached storage does not forward file auditing, and where the target is a database file rewritten in place rather than renamed, which produces far fewer file events.

What you will practise

  • Describe the file-system event patterns that distinguish automated encryption from ordinary bulk processing.
  • Compute a per-process rename and write rate from file telemetry and choose thresholds that balance delay against detection.
  • Measure name entropy and suffix uniformity and explain why they distinguish encrypted output from archive extraction.
  • Correlate mass file modification with recovery inhibition activity such as deletion of local backup state or shadow copies.
  • Plan containment decisions including process termination versus host isolation and the effect of each on evidence quality.
  • Produce a written incident timeline for a ransomware event using file, process and service telemetry.
