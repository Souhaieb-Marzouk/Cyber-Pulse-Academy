DET0249 Behavior-chain detection for T1610 Deploy Container across Docker & Kubernetes control/node planes

DET0249Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for new containers being deployed, especially ones with extra powers. A container is a small sealed box that runs one program on a server. Deploying means starting such a box, often through a tool like Docker or Kubernetes. Attackers deploy their own box to run code and to reach the rest of the cluster. The rule watches who deploys, how often, and with what permissions.

Why should you care?

A container can be given access to the host file system or to keys that manage the whole cluster. That turns one small deployment into control of many servers. Companies start containers all day, so the act itself is not unusual. The clues are the account, the speed of the deployment and the powers attached to it.

How it works, in plain steps

  1. A user, a pipeline or an automated controller asks the platform to run a container.
  2. The image is pulled and the platform records a create request with the image and settings.
  3. The runtime starts the container and writes its own event with the container identifier.
  4. Policy records show whether the request was allowed and which rules applied to it.
  5. Runtime sensors report the processes started inside that container.
  6. The rule joins these records and flags deployments with host mounts, extra powers or a new deploying account.

Real-world example

Think of a large office where every team may book a meeting room. Booking a room is normal. Booking the server room, at midnight, with a key you were never issued, is not. The room is the container, and the key is the extra permission attached to it.

Key takeaways

  • Deploying a container is running code, so identity and privilege matter most.
  • Join the platform record with the runtime event using the container identifier and image digest.
  • Host path mounts and extra powers turn a small deployment into a large one.

In more detail

This strategy detects the deployment of containers used as an execution platform, following the chain from image pull to container create and start, and then to the privileges and mounts the container receives across Docker hosts and Kubernetes clusters. The technique matters because deploying a container is equivalent to running a process on someone else's server, and the runtime often supplies the privileges, host path mounts and service account tokens that turn a simple deployment into cluster wide access. Detection depends on Kubernetes audit logs, container runtime daemon events, admission and policy decision records, and runtime process telemetry tagged with container identifiers. The main way it fails is volume, because orchestrators create containers constantly, so the rule must key on the deploying identity, its normal rate, the security context and the mounted host paths.

What you will practise

  • Describe what deploying a container means from a security point of view.
  • Identify Kubernetes audit and container runtime records that record a deployment.
  • Explain the role of the container identifier and image digest when joining records.
  • List the privilege settings and mounts that increase the risk of a deployment.
  • Baseline the normal deployment rate for each service account and namespace.
  • Recognise controller driven deployments that should not raise alerts.
