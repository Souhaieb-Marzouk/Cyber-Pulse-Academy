T1027.002 Obfuscated Files or Information: Software Packing

T1027.002StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Software packing means squeezing or scrambling a program so its real instructions are hidden. A small helper part, called a stub, runs first. The stub rebuilds the program in memory, and then the real code starts. Both legitimate software and malware use this packing method.

Why should you care?

A packed file does not look like the original program, so known signatures no longer match. The real code appears only in memory, which many tools do not examine closely. Attackers can pack the same harmful program in new ways again and again. Normal software is packed too, so judge the whole behaviour and not packing alone.

How it works, in plain steps

  1. The attacker runs a packer over a working program file.
  2. The packer compresses or encrypts the original code and adds a small stub.
  3. When the file starts, the stub runs first and rebuilds the real code in memory.
  4. The stub then hands control to the rebuilt code so the program behaves normally.
  5. Some packers translate the code into a form that only their own runtime can execute.
  6. Because the file looks different each time, simple signature checks often fail.

Real-world example

Think of a flat-pack bookshelf that arrives in a sealed box. What arrives is a box of panels and screws, not a shelf. You follow the instructions and build the shelf at home. A guard looking at the box sees only wood, not furniture. Packing a program is like that, because the shape appears after unpacking.

Key takeaways

  • Packing hides the real code until it runs and changes file signatures.
  • High randomness, few imports, and an early unpacking stub are common clues.
  • Legitimate software is packed too, so combine this clue with other behaviour.

In more detail

Software packing compresses or encrypts an executable so its real code is not readable or statically recognisable until it runs. A packer performs the transformation, and well-known examples include UPX and MPRESS, though custom packers are common because they avoid the artefacts popular tools leave behind. At runtime a small stub runs first, unpacks the original code into memory, and transfers control to it, so the file on disk and the image in memory differ greatly. Virtual machine based protection goes further, translating the original instructions into a format only an embedded interpreter can execute. Defenders spot packed samples by high entropy, few imports, odd section names, and a stub that allocates and writes executable memory early. Legitimate installers are often packed too, so packer presence alone is not proof of malice.
