M1033 Limit Software Installation

M1033Enterprise MitigationVery hardMitigation

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Limiting software installation means only approved programs are allowed on work computers. Users ask for what they need, and somebody checks and approves it. Everything else is blocked, whether the user installs it by accident or on purpose.

Why should you care?

Most malware arrives as a program that somebody runs, often without knowing what it really does. Free tools from the internet may carry hidden code or contain serious bugs. If anyone can install anything, you quickly lose track of what runs in your network. A simple approval step removes a large number of easy attack paths.

How it works, in plain steps

  1. You build a list of the software that is approved for each type of computer.
  2. You set a rule that only programs on that list may be installed or run.
  3. When a user needs something new, they send a short request to the support team.
  4. Support checks the request, tests the software, and adds it to the list if it is safe.
  5. The system logs every blocked attempt, so you can see what people are trying to install.

Real-world example

Think of a company kitchen with a locked cupboard and a shared shopping list. Anyone can ask for an item, and the office manager buys what the team has agreed on. Nobody can walk in and fill the shelves with whatever they like. The kitchen stays tidy, nobody eats something spoiled, and there is a record of what was bought and why. Software approval works in the same way.

Key takeaways

  • An approval workflow matters as much as the blocking technology, or users will find workarounds.
  • Review your allowed list regularly, because old approved software becomes a target over time.
  • Blocked installation logs are a useful signal of user behaviour and of attacker attempts.

In more detail

Limiting software installation is an application control mitigation that keeps unapproved executables, installers and packages off endpoints by policy rather than by user discipline. The mechanism combines a management decision about who may approve software with a technical allowlist that names the publishers, hashes or paths permitted to run, and it is enforced at the point of installation or at the point of execution. Real environments implement it through endpoint management agents, operating system application control features, package repositories for servers and mobile device management profiles for phones, usually with a request and approval workflow so users are guided rather than simply blocked. Evidence appears as blocked installation events, approval records, inventory reports that show what is actually installed, and the exceptions granted to individuals, which are worth reviewing because exceptions become the attack path. The frequent misunderstanding is that an allowlist is a one-off project; publishers update software constantly, so the list needs an owner, a test path and regular review, or teams will quietly bypass it.

What you will practise

  • Explain how application allowlisting reduces the impact of malicious or unwanted software.
  • Describe the difference between blocking installation and blocking execution.
  • Outline an approval workflow that keeps business users productive.
  • Identify where exceptions accumulate and why they need periodic review.
  • Summarise the endpoint and server tooling that enforces software policy.
