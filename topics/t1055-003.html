T1055.003 Process Injection: Thread Execution Hijacking

T1055.003Privilege EscalationExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A thread is the part of a process that actually runs instructions. This sub-technique is when an attacker captures a thread that is already running. They then change what it will do next. It is part of the Process Injection parent technique. The difference is that no new thread is started.

Why should you care?

Many detection rules look for a new thread appearing in another process. This method avoids that signal, so those rules stay quiet. The host process was started normally, so the process creation record looks clean too. Catching it needs thread level and memory level detail, which many teams do not collect by default.

How it works, in plain steps

  1. The attacker chooses a running process and opens a handle to one of its threads.
  2. They stop that thread so its current position is saved and it will not run while they work.
  3. They put their code, or a reference to it, into the target process memory.
  4. They rewrite the saved position so the thread will continue at the attacker's code.
  5. They let the thread run again, and it executes the new code as if it had always been there.
  6. The process keeps its name and its loaded modules, so it looks unchanged from the outside.

Real-world example

Think of a guided bus following a fixed route. Someone stops the bus at a quiet stop while the driver takes a break. Then they swap the printed route sheet for a different one and start the bus again. Passengers see the same bus, the same driver and the same timetable board. The bus simply drives somewhere new. Only a record of the unscheduled stop shows that anything changed.

Key takeaways

  • Watching only for new remote threads will miss this method.
  • A suspend and resume pair on an existing thread is a strong clue.
  • Thread level telemetry and process access events are needed to see it.

In more detail

This sub-technique takes over a thread that already exists instead of creating a new one. The injector obtains a handle to a thread in the victim process, suspends it, writes its payload or a path into the target address space, and then rewrites the thread's saved processor state so that when the thread resumes it executes attacker code from the new location. Because the same thread continues rather than a fresh one appearing, the observable footprint differs from the remote thread approaches: the interesting evidence is a suspend and resume pair, a context change recorded against a thread that was already running, and execution continuing in a process whose modules never changed. The pattern is close to process hollowing in intent, but the target is a process that was started normally, which matters for triage because the process creation event looks entirely ordinary and there is no suspended process to explain. On Windows the relevant signals come from thread level telemetry such as thread creation and remote thread events, process access events that grant thread control rights, and memory writes into a live process, correlated against the module list of the target at the time.

What you will practise

  • Explain what a thread is and how taking one over differs from creating a new one.
  • Describe the suspend, write, redirect and resume sequence in plain behavioural terms.
  • Explain why the process creation record for the victim looks completely ordinary.
  • Identify the thread level and process access telemetry that exposes the takeover.
  • Compare this technique with process hollowing and state the practical difference for triage.
