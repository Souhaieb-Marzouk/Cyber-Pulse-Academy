DET0262 Detection Strategy for Dynamic Resolution through DNS Calculation

DET0262Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Every website call starts with a name lookup, called Domain Name System resolution. The Domain Name System turns a name into a numeric address. Some malicious programs do not store the name they need. They calculate it from a changing number, such as the current date. This detection looks for name lookups that follow a pattern of calculation rather than a normal browsing habit.

Why should you care?

A fixed bad domain can be blocked by a list. A domain that is calculated changes every day, so the list is stale immediately. This is why intruders use calculation to keep their channels alive. The lookups still have to happen, and they leave records on the resolver. Those records show the shape of the activity, even when every single name is new. Analysing the shape gives defenders a way to catch channels that never reuse a name.

How it works, in plain steps

  1. The resolver records each lookup with the requested name, the client address, and the answer it gave.
  2. The rule splits each name into its labels and checks the letters and numbers in each part.
  3. It counts how many different names one client requests under the same parent domain.
  4. A high count of unique names in a short time is a strong sign of calculation.
  5. A high share of names that do not exist adds weight, because calculated names often miss.
  6. Where the detail is collected, the alert links back to the program that made the lookups.

Real-world example

Think of a courier who must guess a house number from a rule. Each day the rule changes, so the number changes too. The courier knocks on many wrong doors before finding the right one. The neighbours see a stranger trying every door on the street. They do not know the rule, but they see the pattern. Resolver logs show the same thing: many guesses and very few correct answers.

Key takeaways

  • Calculated names change, but the lookup pattern stays the same.
  • Count unique names per client and per parent domain over a short window.
  • A high rate of non-existent names is as useful as the names themselves.

In more detail

This detection strategy covers dynamic resolution through domain calculation, tracked as T1568.003, where the malicious program derives its command and control domain by computing it, often from its own address or from the current date, instead of storing a fixed name. The result is a name that is valid for a short period and changes constantly, which defeats static blocklists. Detection relies on resolver query logs and endpoint name resolution telemetry, looking for high volumes of unique subdomains under one parent, unusual numeric or hexadecimal labels, and a heavy share of non-existent answers. It fails when the client bypasses the corporate resolver, when the host uses a public encrypted resolver, or when a legitimate service genuinely uses random subdomains.

What you will practise

  • Explain how a calculated domain differs from a fixed command and control domain
  • Measure unique subdomain counts per client host over a rolling window
  • Interpret the non-existent answer ratio as a signal of automated name generation
  • Link name lookups to the process that requested them
  • Identify clients that bypass the corporate resolver and lose coverage
