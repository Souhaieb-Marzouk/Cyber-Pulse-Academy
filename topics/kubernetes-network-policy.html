Kubernetes Network Policy

Container & Kubernetes SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Kubernetes is a system that runs software in small units called pods. A network policy is a cluster rule that says which pods are allowed to talk to which other pods. You write the rule using labels, which are simple name tags that you stick on pods. It works like a guest list for each group of pods.

Why should you care?

By default, every pod in a cluster can usually reach every other pod. So one broken web page can quietly read your database or payment service. That freedom makes a small mistake grow into a large incident. A network policy cuts those hidden paths and leaves only the ones the application truly needs. It also limits how far an attacker can move after taking over a single pod.

How it works, in plain steps

  1. Each pod gets labels, such as app equals web, which are just name tags used for matching.
  2. You create a policy that selects those labels and lists the peers that may connect to them.
  3. Peers are also chosen by labels, and you add ports such as a database port number.
  4. The policy is stored in the cluster as a declaration of intent, not as a running filter.
  5. The network plugin on each node reads the declaration and programs real filtering rules.
  6. Any traffic that no rule allows is dropped, but only for pods that a policy already selects.

Real-world example

Picture an office building where every room has a door, but no rules about who may enter. Anyone from any floor can walk into the finance office and read the files. Now the building manager gives each room a label, such as kitchen or records, and puts a guest list on every door. The list says the record room only accepts the archivist, and the kitchen only accepts the cooks. Rooms with no list still let anyone in, which surprises people. You must also remember to let staff reach the building directory, or nobody can find a room name.

Key takeaways

  • Policies only add permissions, so there is no separate deny rule to write.
  • A pod is protected only after some policy selects it; until then everything is allowed.
  • Remember egress, including name resolution, or your application will break.

In more detail

A Kubernetes network policy is a namespaced object that declares which pods may send traffic to, or receive traffic from, which other endpoints in a cluster. Rules are written with label selectors rather than addresses, so a policy attaches to a group of pods by label and describes allowed peers, ports and protocols. Enforcement is not performed by the Kubernetes control plane itself: the policy is a declaration, and the container network interface plugin on each node programs the actual filtering rules. The semantics people most often get wrong are additive, allow only behaviour. There is no explicit deny rule, policies never override one another, and a pod is isolated only once at least one policy selects it, so an unmatched pod accepts traffic from anywhere. Traffic that no rule permits is dropped for a selected pod, which means a default deny posture starts with a policy that selects all pods and allows nothing in return. Because egress is also in scope, teams must deliberately allow name resolution and other platform services or applications break. Network policy governs layer three and four connectivity inside the cluster; it does not encrypt traffic, inspect application requests, or cover host networked pods and external endpoints, so it complements rather than replaces service identity and mutual authentication.

What you will practise

  • Explain what a Kubernetes network policy controls and why label selectors replace addresses.
  • Describe the role of the container network interface plugin in enforcing a policy declaration.
  • State the allow only, additive semantics and what makes a pod isolated.
  • Explain how to build a default deny posture and why egress, including name resolution, needs explicit rules.
  • List the limits of network policy compared with encryption and application layer controls.
