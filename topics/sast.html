Static Application Security Testing

Secure EngineeringVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Static application security testing reads your source code without running it. It searches for dangerous patterns, such as secret keys written into the code. Modern tools also follow data from user input to a risky command. It runs on every commit, so problems appear while they are still cheap to fix.

Why should you care?

Most security bugs start as small coding mistakes. Finding them in review by hand is slow and easy to miss. Static testing checks every line each time you save, so nothing slips through unnoticed. It also finds problems on code paths that your tests never touch. Ignoring it means paying for fixes after release, when they cost far more.

How it works, in plain steps

  1. You connect the tool to your code repository, usually in the build pipeline.
  2. The tool parses the code and builds a map of how data moves.
  3. It then checks that map against hundreds of rules for dangerous patterns.
  4. When user input reaches a risky command, it raises a finding.
  5. You review each finding and confirm whether an attacker could truly reach it.
  6. You fix real problems and mark false alarms with a reason and a date.

Real-world example

Think of a proofreader who checks a recipe before anyone cooks it. She reads every line and circles a dangerous instruction, like adding cleaning fluid to a cake. Nothing has been baked, so the fix is just rewording a sentence. Static testing is that proofreader. It reads your code before it ever runs and circles the lines that could hurt you later.

Key takeaways

  • Static testing reads code, so it finds bugs before anything runs.
  • Expect false alarms; triage each finding instead of trusting the count.
  • Gate only on new high-confidence findings, not on old backlog noise.

In more detail

Static application security testing is the automated analysis of source code, bytecode or binaries without executing the program, looking for patterns that indicate a security defect such as injection sinks reached by untrusted input, unsafe deserialisation, hard-coded cryptographic material or broken access control. Modern SAST engines combine pattern matching with dataflow and taint tracking, so a rule can follow a value from a source such as an HTTP parameter through assignments and function calls to a sink such as a database query. Because it works on the code itself, SAST can find defects on code paths that no test exercises, and it can be run on every commit, which makes it attractive as a pull-request gate. Its central limitation is the false positive rate: without whole-program context and runtime configuration, the engine cannot know whether a path is reachable or whether a sanitiser it cannot model already applies. For a practising engineer the discipline is therefore triage, not detection. A workable programme baselines existing findings, gates only on new high-confidence rules, tunes rules per repository, suppresses with expiring annotations, and assigns rule ownership so that noisy rules are fixed rather than ignored. The common failure modes are treating the raw finding count as a metric, enabling every rule at once and drowning the team, running SAST only on a nightly build so feedback arrives too late to change the design, and allowing unbounded suppressions that silently disable entire rule classes. Pairing SAST with dependency analysis, dynamic testing and code review covers the gaps each tool leaves.

What you will practise

  • You will be able to explain how taint tracking differs from pattern matching and what each approach can and cannot detect.
  • You will be able to configure a SAST scan as a pull-request gate that blocks on new high-confidence findings without failing on legacy debt.
  • You will be able to triage a SAST finding by tracing reachability and confirming whether a modelled sanitiser applies.
  • You will be able to write a suppression with a justification, an owner and an expiry date instead of a permanent ignore.
  • You will be able to explain why raw finding counts are a poor programme metric and what to measure instead.
  • You will be able to state which defect classes escape static analysis and which complementary testing technique covers each.
