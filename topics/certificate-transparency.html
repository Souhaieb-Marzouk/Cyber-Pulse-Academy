Certificate Transparency

CryptographyHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Certificate transparency is a public record of certificates that secure websites. Authorities must add each certificate they issue to open lists that anybody can read. These lists are built so entries cannot be removed or changed later. Security teams watch the lists to spot certificates they did not ask for.

Why should you care?

A certificate can be issued by mistake or by a trick, and your browser may trust it. Without a public record, nobody would ever know it existed. With this record, you can find out and ask for it to be cancelled. Attackers lose the safety of working in the dark. Watching the lists turns an invisible problem into something you can see.

How it works, in plain steps

  1. A certificate authority issues a certificate that names the domain of a website.
  2. The authority then sends that certificate to several independent public log servers.
  3. Each log returns a signed promise, called a timestamp, that it will include it.
  4. The certificate carries those promises, and the browser checks them before trusting it.
  5. Anyone can read a log and look for names they own or recognise.
  6. Monitoring tools raise an alert, and the team can ask for the wrong certificate to be cancelled.

Real-world example

Think of a public notice board outside a town hall. Every licence the town issues must be pinned there for everyone to read. You cannot remove a notice later, and anyone may check the board. If someone issues a licence in your name, you will see it on the board. Seeing it does not stop the licence, but it lets you act.

Key takeaways

  • The logs record certificates publicly and cannot be quietly changed.
  • Browsers now expect proof of logging, so authorities cannot skip it.
  • Monitor the logs for your own domains to catch certificates you did not request.

In more detail

Certificate transparency is a public logging system for transport layer security certificates that requires certificate authorities to submit issued certificates to independent, append-only logs and to include proof of that submission in the certificate itself. Because the logs are append-only and cryptographically verifiable, an entry cannot be quietly removed or rewritten, and because they are public, anyone can monitor them for certificates issued for domains they care about. The design changes the trust model: a certificate authority that quietly issues a fraudulent or mistaken certificate can no longer do so in secret, because the record is visible to monitors and browsers. Client policies now require that a certificate be accompanied by signed certificate timestamps from a set of logs before a browser accepts it, which turns logging from a courtesy into an enforced condition. The practical value for a defender is monitoring: watching logs for the organisation's own domain names and brands reveals misissuance, unauthorised subdomains, and preparation for phishing. The common mistake is to assume transparency alone prevents a rogue certificate, when it only guarantees disclosure, so detection still depends on someone actively watching the logs and reacting to what appears there.

What you will practise

  • Explain what certificate transparency is and the problem it was created to solve.
  • Describe why the logs are append-only and how that supports trust.
  • Explain the role of signed timestamps in a certificate that a browser accepts.
  • Describe how an organisation monitors logs for misissued certificates on its domains.
  • Explain the limits of logging, which reveals misissuance but does not prevent it.
  • Outline the response steps when an unexpected certificate is found for your domain.
