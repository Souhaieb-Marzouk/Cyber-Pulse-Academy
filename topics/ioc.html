Explained in plain language

Written for beginners. No security background needed.

Simple definition

An indicator of compromise, or IOC, is a clue that a system may already be hacked. Examples include a strange file, a harmful web address or an unusual login time. It is technical evidence, not proof on its own. You should treat each clue as short lived, because attackers change them often.

Why should you care?

Indicators are easy to share and easy to load into your tools. That makes them popular. They also go stale very fast. An attacker can move to a new web address in minutes. If you treat a list of clues as a permanent blocklist, two bad things happen. You get flooded with false alarms, and you believe you are protected when you are not.

How it works, in plain steps

  1. Collect the clue from a report, a log entry or an alert that your tools produced.
  2. Add context. Note which attacker, which campaign and when it was first seen.
  3. Decide the type. Some clues are single values, some are derived, and some describe behaviour.
  4. Give it a validity window, because a single value may stop being useful in hours.
  5. Push it to the right place. Strong clues can be blocked, while weak ones are only hunted.
  6. Review and retire old indicators so your lists stay small and trustworthy.

Real-world example

Imagine a police appeal showing a suspect's car number plate. The plate is useful today. The suspect can swap plates tonight, so that appeal ages fast. A witness description is stronger. It says the suspect always limps and always wears a red cap. That behaviour may last for months. An IP address is the number plate, and a behaviour pattern is the description. Both help, but they age very differently.

Key takeaways

  • An indicator is a clue that something may be compromised, not proof that it is.
  • Indicators expire quickly, so give each one a validity window and review it.
  • Avoid blocking broad shared hosting addresses, because that breaks normal traffic.

In more detail

An Indicator of Compromise (IOC) is a forensic or telemetry artefact that provides evidence a system, account or network has been compromised, ranging from a file hash or hostile domain name to an anomalous authentication pattern or a registry key created by a loader. IOCs are the most shareable and the most perishable product of threat intelligence. They are trivially expressible in structured patterning, easy to push into a SIEM or EDR, and quick to automate, which is why they dominate machine-to-machine sharing; they are also the easiest thing for an adversary to change. A domain can be rotated in minutes, a payload recompiled to a new hash in seconds, and infrastructure can be rented and discarded. Treating an indicator list as a permanent blocklist therefore produces both alert fatigue and a false sense of coverage. Mature programmes classify indicators as atomic, computed or behavioural. Atomic values such as an IP address, domain name or file hash are volatile and should carry a short validity window and a confidence rating. Computed indicators, such as a hash of a decoded malware configuration or a distinctive transport fingerprint derived from a family, survive longer and support hunting. Behavioural indicators describe sequences of action and overlap heavily with adversary techniques. Operationally, an indicator is only useful when it is enriched with context: which actor family used it, which campaign, when it was first and last observed, and whether it is a genuinely exclusive artefact or a shared hosting address. Low-specificity indicators, especially IP addresses from commercial hosting or content delivery ranges, should drive hunts and correlation rather than blocklists, because blocking them breaks legitimate traffic. Indicators also age, so a feed that has not been reviewed recently should be filtered by first-seen date before it is trusted. Finally, defenders should be able to state which detection each indicator feeds and how it will be retired, because an indicator whose only consumer is a dashboard produces no security value.

What you will practise

  • You will be able to classify indicators as atomic, computed or behavioural and explain the operational lifetime and confidence each class deserves.
  • You will be able to build an indicator lifecycle covering enrichment, validation, deployment, review and retirement instead of permanent blocking.
  • You will be able to write detection and hunting logic that consumes indicators with context rather than matching bare IP addresses.
  • You will be able to explain why low-specificity indicators from hosting and content delivery ranges cause false positives when blocked.
  • You will be able to describe how indicators are expressed in structured patterning and shared through collections and feeds.
  • You will be able to assess a threat feed for freshness, specificity and overlap with existing coverage before onboarding it.
