T1556.007 Modify Authentication Process: Hybrid Identity

T1556.007PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Many companies use the same account on their own servers and in cloud services. Special bridge software keeps those two accounts in step. This technique means an attacker changes that bridge, so cloud sign-ins are approved without a real password.

Why should you care?

The bridge server is trusted by the cloud service, so its decisions are accepted without question. One change there can grant access to cloud mail, files, and administration tools. The access survives password resets, because the cloud still trusts the bridge. These servers are few, important, and often watched less carefully than domain controllers.

How it works, in plain steps

  1. A company keeps one user identity in two places: its own directory and a cloud service.
  2. Bridge components copy the identity and check passwords on behalf of the cloud provider.
  3. One option forwards each cloud sign-in to a small agent running on a local server.
  4. Another option uses a federation service that issues a trusted statement about the user.
  5. An attacker who controls those servers can add code that approves every request.
  6. They can also record the passwords that pass through the bridge for later use.

Real-world example

Imagine an embassy where a translator confirms the identity of every visitor for the host country. The host country trusts that translator completely. Now somebody replaces the translator with a person who approves every visitor and writes down their names and passwords. The host country still accepts each approval, because it comes from the trusted desk. Nothing in the visitor records looks unusual, and the impostor keeps working until somebody inspects the translator directly.

Key takeaways

  • Hybrid identity bridge servers are as sensitive as domain controllers and need the same care.
  • Monitor module loads and configuration changes on authentication agents and federation servers.
  • Cloud sign-in logs can reveal blanket approvals and impossible travel patterns.

In more detail

Many organisations keep one identity for each user across an on-premises directory and a cloud identity provider, and the glue between them is a set of synchronisation and authentication components. Microsoft environments, for example, can share identities through password hash synchronisation, pass-through authentication, or Active Directory Federation Services, and other cloud platforms also hand authentication to a federation service and receive a token describing the user and their privileges. This sub-technique targets those bridge components rather than the cloud service itself. An adversary who controls the on-premises server that validates cloud sign-ins can make it approve every attempt and record the credentials it receives, and an adversary who controls a federation server can change its configuration to load a module of their choosing so that authentication succeeds without a valid password. The effect is persistent privileged access to cloud resources, reached through infrastructure that cloud-side controls treat as legitimate. Evidence sits on the on-premises hosts: unexpected modules inside the agent or federation service, altered service configuration files, and agent software that no longer matches its vendor package.
