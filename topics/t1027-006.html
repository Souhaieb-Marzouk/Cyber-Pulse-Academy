T1027.006 Obfuscated Files or Information: HTML Smuggling

T1027.006StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Usually a harmful file is sent to you and saved on your computer. HTML smuggling hides that file inside a web page instead. When you open the page, your browser builds the file itself. So the file arrives without ever travelling as a file.

Why should you care?

Security tools often check files as they travel over the network. If no file travels, those tools have nothing to inspect. The page looks like normal web content, such as text or a script. Your browser then creates the harmful file on your own machine, so the download is much harder to spot.

How it works, in plain steps

  1. The attacker turns the harmful file into text, using a common encoding called base64.
  2. Base64 here means a way to write any data as plain letters and numbers.
  3. That text is placed inside an ordinary looking web page.
  4. You open the page, and your browser runs the small script it contains.
  5. The script turns the text back into a file inside the browser memory.
  6. The page starts a download, so your own computer saves the file.

Real-world example

Imagine a letter that arrives as a list of numbers. The post office only inspects parcels, so the letter passes freely. At home you follow the numbers and build the parcel yourself. Nothing parcel shaped ever went through the post. HTML smuggling hides a file in plain web text in the same way.

Key takeaways

  • HTML smuggling builds the payload in the browser, so no file crosses the network.
  • A page download with no matching file transfer in the logs is a useful clue.
  • Watch for new executable or archive files appearing in download folders.

In more detail

HTML smuggling builds the payload inside the victim's browser instead of sending it across the network as a file. The delivery page carries the harmful bytes as encoded text, commonly a base64 string inside a script, a JavaScript blob, or a data URL, and the browser turns that text back into a file-like object on the fly. Because the response is ordinary HTML and JavaScript, content filters that inspect download names, file types, or known malicious binaries have nothing to block. A download is then triggered locally, often through a programmatic click on a link with a download attribute or through a legacy save function, so the resulting file appears to come from the user's own machine. Web proxy logs show a page fetch with no matching file transfer, followed by a new executable or archive in a download directory.
