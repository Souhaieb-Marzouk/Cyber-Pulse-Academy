DET0283 Behavior-chain detection for T1134 Access Token Manipulation on Windows

DET0283Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An access token is a small record that tells Windows who a running program is. Every running program carries one of these records. Attackers can copy a token from another program so their code runs as a more powerful user. This detection looks for programs that act as a user who never signed in on that computer.

Why should you care?

A stolen token lets an attacker act as an administrator without knowing any password. Password changes and multi factor prompts do not stop this, because no new sign in happens. The activity often looks like a normal service or an ordinary program on the system. Catching the mismatch between identity records and process records is one of the few reliable ways to see it.

How it works, in plain steps

  1. The sensor collects process creation events, which name the account that started each new program.
  2. It also collects sign in events, which record the account, the logon type and the impersonation level.
  3. A separate record shows when a logon receives powerful rights, such as the right to debug programs.
  4. The rule joins these sources by account name and by computer, inside a short time window.
  5. A process that runs as an account with no matching sign in on that host is scored as suspicious.
  6. High confidence alerts add a second signal, such as a powerful right granted to the same process.

Real-world example

Imagine a staff car park where every car has a badge on the windscreen. A guard checks each badge against the list of people who signed in that morning. Most badges match a name on the list, and the guard waves the car through. If a car arrives with a valid badge, yet nobody with that name signed in, the guard asks why. Token manipulation creates exactly that gap between the badge and the sign in sheet.

Key takeaways

  • The strongest signal is a process acting as a user who has no sign in record on that computer.
  • You need both process records and sign in records, because neither one proves anything alone.
  • Build a baseline of service accounts that legitimately run programs as other users.

In more detail

This strategy detects access token manipulation on Windows by correlating identity evidence with process evidence, rather than trusting either source alone. An access token is the object that carries a process security context, and adversaries duplicate, steal, or impersonate tokens so a process runs as another user, often a highly privileged one, without authenticating. The enabling telemetry is process creation with the creating account and token details, logon events carrying logon type and impersonation level, records of special privileges assigned to a logon, and token right adjustment records. The strategy fails in practice because service accounts and scheduled tasks legitimately run as other users, so the rule needs a baseline of which accounts may appear as a process owner with no matching logon on that host.

What you will practise

  • Describe what an access token is and how a process obtains one.
  • Identify the event fields that link a process to a sign in identity.
  • Explain why impersonation and token theft leave a gap between identity and process records.
  • Correlate process creation, logon and privilege assignment events in a SIEM.
  • Reduce false positives using a service account baseline instead of blanket exclusions.
