DET0147 Detection Strategy for Cloud Service Hijacking via SaaS Abuse

DET0147Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Cloud services charge for what you use. An attacker who steals a key can borrow your account. They can send spam, run heavy jobs, or mine currency on your bill. This detection looks for a sudden jump in how much a service is used.

Why should you care?

The damage appears as a huge invoice, a blocked sending domain, or throttled services. Your own users lose access while the attacker profits. Because the activity uses real logins and real interfaces, ordinary security alerts often stay silent.

How it works, in plain steps

  1. The cloud provider records every management action and every API call with the identity that made it.
  2. Usage records show how many messages, jobs, or machine hours were consumed and by which resource.
  3. The detection compares today's usage with the normal pattern for that same account.
  4. It also checks whether new resources, keys, or regions appeared just before the jump.
  5. When usage breaks the baseline and a new credential is involved, it raises an alert.

Real-world example

Imagine a company fuel card. Spending a little more in a busy month is normal. The driver spends ten times the usual amount at three in the morning. The stations are places the driver never visits. That is a clear sign the card was copied. Cloud usage records are that fuel card statement.

Key takeaways

  • Cloud abuse often looks like normal use, only much larger.
  • Compare usage against each account's own history, not a global number.
  • Watch for new keys or resources appearing beside the usage spike.

In more detail

This strategy addresses T1496.004, resource hijacking delivered through software as a service abuse, where an intruder uses a victim tenant, subscription, or account to send bulk email, run compute jobs, mine currency, or call paid interfaces on someone else's bill. Detection is inherently cloud native: provider audit logs for administrative and API activity, service usage and billing metrics, tenant level message or job records, and identity logs for the principals involved. The hard part is that the abuse travels over legitimate provider interfaces using valid credentials, so there is no exploit signature to match. The rule therefore has to be a rate and quota anomaly rule, scoped by principal and by resource, with a solid business baseline behind it.

What you will practise

  • Explain how resources inside a cloud tenant can be hijacked for an attacker's benefit
  • Identify the audit and usage telemetry that exposes abnormal consumption
  • Build a per account baseline for messages, jobs, and compute spending
  • Correlate usage spikes with new credentials, resources, or regions
  • Describe containment steps that stop abuse without breaking the business
  • Set severity based on financial, reputational, and service impact
