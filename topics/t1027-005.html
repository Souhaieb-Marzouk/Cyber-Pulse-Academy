T1027.005 Obfuscated Files or Information: Indicator Removal from Tools

T1027.005StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Sometimes a security tool catches a harmful program and blocks it. The attacker may then change that program to remove what the tool noticed. The attacker sends the changed version again later. So the same attack returns in a new shape.

Why should you care?

If your detection depends on one detail, it stops working once that detail changes. The attack is not gone, it has only changed its clothes. Teams that do not notice the change may think the problem is solved. You need detection that follows behaviour, not only a single known marker.

How it works, in plain steps

  1. A security tool detects a harmful file and blocks or deletes it.
  2. The attacker learns, or guesses, that one specific detail caused the detection.
  3. They edit the tool to remove that detail while keeping the harmful behaviour.
  4. The changed version is sent again, often to the same or a similar target.
  5. The old detection no longer matches, even though the activity is the same.
  6. A careful team notices new fingerprints with the same behaviour and updates its rules.

Real-world example

Picture a shoplifter caught on camera because of a bright red hat. Next week the same person returns without the hat. The guards still work, but the old description no longer matches anyone. Only someone watching behaviour, not clothing, sees the same thief. Removing an indicator from a tool works like taking off the hat.

Key takeaways

  • Attackers change tooling after a detection, so single indicators expire quickly.
  • Similar behaviour with a new file fingerprint is a strong signal of revision.
  • Prefer behavioural detection, and treat published indicators as short lived.

In more detail

Indicator removal from tools describes an intruder revising their own tooling after learning that a defensive product detected it. The trigger is usually feedback: a quarantined file, a blocked execution, a killed process, or simple knowledge that a target runs a particular security product. The revision is narrow and deliberate, aimed at the specific signature that fired, whether that is a unique byte string, a file hash, a tool name, or a recognised code pattern. For the defender the consequence is that an indicator burned once tends to stop working on the next wave, so detections built on a single static artefact age quickly. Analysts see the pattern as version drift: similar behaviour and similar infrastructure, but a new file hash or a slightly altered binary. Durable detection therefore leans on behavioural chains and infrastructure rather than one file signature.
