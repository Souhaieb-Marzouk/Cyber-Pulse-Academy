T1055.004 Process Injection: Asynchronous Procedure Call

T1055.004Privilege EscalationExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An asynchronous procedure call is a task that Windows lets a thread do later, when the thread is ready. This sub-technique is when an attacker puts their own task in that queue so the target thread runs it. It is part of the Process Injection parent technique. The difference is this. The attacker does not start a thread or take one over. Instead they wait for the target's own thread to pick up the work.

Why should you care?

The attacker's code runs inside a process you trust, so your allow lists may not help. Because nothing visibly starts running at the moment of injection, the link between cause and effect is easy to miss. Understanding the queue helps you connect two events that look unrelated. One version of this method runs the code before the target process finishes starting. That can slip past tools which only check a program once it is fully loaded.

How it works, in plain steps

  1. The attacker opens a handle to a thread in the process they want to use.
  2. They write their code into that process, or prepare it somewhere the process can reach.
  3. They add an entry to the thread's queue that points at that code.
  4. Nothing runs yet, because the queue is only read when the thread becomes alertable.
  5. The thread reaches a waiting point and then takes the queued entry, which runs the attacker's code.
  6. A variant queues the call on a brand new suspended process. Another stores the code in a shared system table first.

Real-world example

Picture a hospital night desk with a tray for messages. Staff only read the tray when the corridor goes quiet. Someone slips a note onto the tray asking for a drug cabinet to be opened. The nurse follows it when things calm down, exactly as normal procedure allows. Nobody saw who put the note there, and the tray is emptied by morning. The only connection is between an odd visitor at two in the morning and the cabinet being opened at four.

Key takeaways

  • Execution can happen later than the injection that caused it.
  • Queuing work into another process is rare, so it is worth alerting on.
  • Correlate process access events with code that runs soon afterwards.

In more detail

This sub-technique uses the asynchronous procedure call queue, a normal Windows mechanism that lets a thread defer work until it is in a state where it can safely run that work. The attacker writes code into the victim process and then queues a pointer to it on a thread of that process, and the payload executes when the thread next enters an alertable wait, which many processes do routinely while waiting for input, timers or network events. Because the delivery is a queued item rather than a new thread, the execution explanation is subtle, and the queue itself is not durable, so the artefact often has to be reconstructed from process access, memory writes, and the timing of subsequent execution. Two well known variations change where the queue is used: one queues the call on a freshly created process that is still suspended before its entry point runs, so the payload executes ahead of any security hooks the process would normally load, and another stores the payload in a shared system table first and uses a queued call to trigger it, which removes the need to write executable code into the target at all. Detection focuses on how often legitimate software queues calls into another process, which is rare, and on the correlation between an access event and later unexpected code inside the target.

What you will practise

  • Explain what an asynchronous procedure call is and when queued work actually runs.
  • Describe how the queued delivery differs from starting or hijacking a thread.
  • Explain how the suspended process variant runs code before a program finishes loading.
  • Identify the access, memory and timing evidence that points to queued execution.
  • Explain why the delayed execution makes cause and effect hard to connect in logs.
