T1547 Boot or Logon Autostart Execution

T1547PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is persistence built into the way a computer starts. The attacker sets their program to run automatically at boot, at logon, or when a session changes. These are normal operating system features, so the change often hides among hundreds of other startup entries.

Why should you care?

If you only clean the infected file, this entry starts it again after the next restart. That is why an incident can seem to return. Startup locations also run early and sometimes with high rights. The fix is not to remove everything, but to know what changed recently and why.

How it works, in plain steps

  1. The attacker gains access and wants their code to survive a restart.
  2. They add an entry to a startup list, a registry key (a settings store on Windows), or a scheduled task.
  3. The entry points to a file they control, often in a user-writable folder.
  4. After a reboot or logon, the system runs that file automatically.
  5. The code may start with the rights of the user or of the system itself.
  6. Defenders compare today's startup list against a known good baseline from the same machine.

Real-world example

Think of a building where the front door is checked every morning. The attacker does not fight the guard. They add their own key to the cleaner's keyring, so their helper walks in at 6 a.m. with the cleaning crew. Every morning the guard sees a normal start of day. Only a careful list of who holds keys would show the extra one.

Key takeaways

  • Removing malware is not enough; remove the entry that restarts it.
  • Keep a baseline of startup entries and review every difference.
  • Be suspicious of startup entries that point at user-writable folders.

In more detail

Boot or Logon Autostart Execution covers persistence achieved by configuring code to run automatically when a system starts, when a user logs on, or when a session state changes. Rather than one mechanism, the parent technique collects the many autostart surfaces an operating system offers: registry keys and startup folders on Windows, launch agents, launch daemons and login items on macOS, init scripts, systemd units, cron entries and shell profiles on Linux, plus vendor extension points such as print monitors, authentication packages, security support providers and browser helper components. Adversaries favour these locations because they are legitimate features, they execute early or in a privileged context, and they are frequently ignored by users and asset owners alike. The evidence is largely static and configuration-based: registry values pointing at unusual binaries, new or modified service and unit definitions, changes to shell startup files, scheduled tasks with logon triggers, and file creation in autostart directories. Because thousands of such entries are legitimately present on any mature endpoint, the useful question is not whether autostart entries exist but whether one changed recently, points to an unsigned or user-writable location, runs with higher privilege than the account that created it, or coincides with other incident activity on the same host. Baselines built from known-good images, combined with change tracking on autostart locations and file integrity monitoring, reduce an unmanageable list to a small set of reviewable differences. That same baseline supports recovery, because persistence removal during containment has to be complete without breaking the legitimate startup software an organisation depends on.

What you will practise

  • Enumerate the principal autostart locations on Windows, Linux and macOS and the privilege each confers on the executed code.
  • Use baselining and change tracking to reduce autostart review to a manageable set of differences.
  • Interpret endpoint telemetry for processes launched at boot, logon or session state change.
  • Judge suspicious autostart entries by path writability, signature state, parent privilege and recency.
  • Plan persistence removal during containment without breaking legitimate startup software.
  • Write detection logic for new autostart entries that reference user-writable or unsigned binaries.
