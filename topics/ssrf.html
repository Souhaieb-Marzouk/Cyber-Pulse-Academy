Server-Side Request Forgery

Application SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Server side request forgery is a flaw where a website fetches a link on your behalf. The server is the computer that runs the website. In this attack a person gives the site a link that points at a private machine inside the company. The site itself makes the request, so the private machine trusts it.

Why should you care?

Computers inside a company network often have weak protection because they expect only friendly traffic. If a public website can be tricked into sending requests there, an outsider can reach them without breaking in. Cloud systems also offer a special internal address that hands out secret keys to anything that asks. That means one careless link can expose powerful passwords. The risk is easy to miss, because the website looks like it is only downloading a picture.

How it works, in plain steps

  1. A feature accepts a web address from a user, for example to import an image or check a link.
  2. The server opens that address on its own behalf, using its own network position and its own accounts.
  3. The target machine sees a request from a trusted neighbour, so it answers without asking questions.
  4. The attacker points the address at an internal service, such as an admin page or a cloud metadata address.
  5. The reply travels back through the website and reaches the attacker, leaking internal detail.
  6. Defences resolve the name first, allow only known destinations, and block redirects to new addresses.

Real-world example

Think of a hotel front desk that agrees to fetch anything a guest asks for. A guest says: please collect the envelope from the manager office on the fourth floor. The manager sees a staff member at the door and hands it over. The guest never entered the staff area, but they still received the private letter. The hotel rule should be that the desk collects only from the public lobby. Software needs the same rule about which addresses it may fetch.

Key takeaways

  • If your server can fetch any address a user supplies, that user can borrow your server's trust.
  • Blocklists of host names fail, because redirects and address tricks slip past them.
  • Resolve the name, allow only known destinations, and do not follow redirects to new hosts.

In more detail

Server-side request forgery is a flaw in which an application fetches a remote resource using a destination that an attacker controls, so the request is issued by the server itself with the server's network position and credentials. Because that server usually sits inside a trusted zone, the attacker can use it to reach internal services, cloud instance metadata addresses and administrative interfaces that are not exposed to the internet. It appears wherever software accepts a link: image importers, link previews, webhook testers, document renderers and file fetchers. The mistake people make is validating the destination with a string comparison against a blocklist of hostnames, which fails against redirects, alternate address encodings, and names that resolve to internal addresses. Sound handling resolves the name first, checks the resulting address against an allowlist, and refuses redirects to new destinations.

What you will practise

  • Explain what server side request forgery is and why the server's position matters.
  • Describe how an internal service can be reached through a public application.
  • Explain why a blocklist of host names is an unreliable control.
  • Identify application features that commonly accept user supplied addresses.
  • Describe an allowlist approach that resolves names before fetching.
  • Recognise log evidence of unexpected internal requests from an application.
