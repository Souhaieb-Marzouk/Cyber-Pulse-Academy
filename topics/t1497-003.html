T1497.003 Virtualization/Sandbox Evasion: Time Based Checks

T1497.003StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Time based checks use the computer clock to spot a test system. Analysis tools often speed up time so long waits finish quickly. Malware measures how much time really passed and compares it with the wait it asked for. If the numbers do not match, it stops.

Why should you care?

Attackers add long delays so that automated analysis gives up before the harmful step happens. Speeding up the clock is a common shortcut in analysis, and this check is designed to catch it. When the check succeeds, a dangerous file can appear harmless. Time manipulation can also hide activity from logs that rely on timestamps.

How it works, in plain steps

  1. The program reads the system clock or a counter that shows how long the system has run.
  2. It then asks the operating system to pause for a set number of seconds.
  3. When it wakes, it reads the clock again and calculates the real elapsed time.
  4. It compares that value with the pause it requested and checks for a mismatch.
  5. A much shorter elapsed time means the clock was sped up, so it assumes a sandbox.
  6. It may also compare reported uptime with file timestamps to find faked time.

Real-world example

Imagine a night guard asked to watch a warehouse for one hour. The guard checks two clocks and sees only ten minutes have passed. The guard knows the promised hour was fake. A thief tests the guard that way before entering. Malware tests the clock in the same manner before it shows its real behaviour.

Key takeaways

  • This sub-technique measures time rather than reading system or user details.
  • Speeding up sandbox time is a shortcut that attackers actively detect.
  • A process that exits shortly after sleeping may have failed a timing check.

In more detail

Time based checks use the clock to decide whether the host is real. Rather than reading hardware or watching the user, the sample measures how time behaves around its own execution, sampling the system clock or an uptime counter before and after a delay and comparing the observed interval with the interval it requested. Analysis platforms often compress long waits so that a sample which sleeps for hours can be observed in minutes; that acceleration, or a heavily manipulated timestamp, is exactly what this technique looks for. Typical mechanics include reading tick counts or file time values as a sanity check and, more tellingly, calling a sleep function and recomputing elapsed time, then abandoning execution if the measured duration is far shorter or far longer than expected. Telemetry is thin because the operations are ordinary library calls, so defenders lean on indirect evidence: processes that sleep and wake on implausible schedules, large differences between internally reported uptime and externally observed process age, and clock adjustments on hosts that should receive time from a controlled source. Sandbox operators can defeat the check by letting real time pass, by keeping internal clocks consistent, and by logging when a sample exits shortly after a sleep, which is a strong hint that a timing test failed for the adversary.

What you will practise

  • Explain how time based checks differ from the other evasion sub-techniques.
  • Describe how a sleep call and clock sampling reveal an accelerated environment.
  • Explain why long delays are used to outlast automated analysis windows.
  • Identify indirect telemetry such as sleeping process behaviour on a host.
  • Describe how analysis platforms can present consistent time to a sample.
  • Explain the effect of clock manipulation on log based detection.
