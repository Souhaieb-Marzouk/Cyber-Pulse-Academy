T1059 Command and Scripting Interpreter

T1059ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A command and scripting interpreter is a built-in tool that runs typed commands or small programs, such as a command shell or a scripting language. Every operating system has them, and administrators use them daily. Intruders abuse the same tools because they are already installed and trusted. Nothing new has to be downloaded, so fewer alarms sound.

Why should you care?

Because these tools are legitimate, blocking them outright would break normal work. Intruders can therefore run commands, gather information and fetch more tools without ever placing an obvious virus file on disk. The traces they leave are in the command line and the process that started it. If you do not log those details, you lose the evidence you need.

How it works, in plain steps

  1. The intruder needs a way to run something, often through a document, a script or a scheduled job.
  2. They start a built-in interpreter, such as a Windows shell or a Unix shell.
  3. The commands may be typed, read from a file, or hidden inside encoded text.
  4. Encoded text is a scrambled form that the interpreter turns back into commands as it runs.
  5. The interpreter then downloads or creates the extra tools that the intruder wants next.
  6. Logs record the interpreter, its arguments and the child programs it started.

Real-world example

Think of a repair worker who arrives with no tools at all. They do not need to smuggle anything past the door, because a full toolbox already sits in the building and everyone is allowed to use it. They open the toolbox and fix, or break, whatever they like. Afterward the toolbox looks exactly as it did before.

Key takeaways

  • Built-in shells and scripting tools are useful to you and to intruders alike.
  • The command line and the parent program are the details that reveal misuse.
  • Turn on script logging so you can read what actually ran, not just that it ran.

In more detail

Command and Scripting Interpreter describes the abuse of native command interpreters and scripting runtimes to execute code on a target host, chain further actions, and stage additional payloads without necessarily writing a conventional executable to disk. The parent technique covers interpreters such as PowerShell, the Windows command shell, Unix shells, Python, JavaScript engines and platform-specific automation hosts, and it appears on Windows, Linux, macOS, network appliances and inside container and cloud execution contexts wherever a shell or runtime is reachable. At a mechanism level the adversary runs an interpreter interactively, passes commands as arguments, or loads script content from a local file, a remote share, or an encoded blob that is decoded into memory at execution time. The telemetry this produces is rich but noisy: process creation records showing interpreter binaries with unusual parent processes, command lines containing encoded or obfuscated arguments, script block and module logging on Windows, process accounting and execve audit records on Linux, shell history files, and the child processes the interpreter subsequently spawns. Investigators separate malicious from benign use by examining the parent-child relationship, the user and session context, the working directory and destination of any download, whether the interpreter was launched by a service or scheduled task, whether logging captured the full script content, and whether the same interpreter and argument pattern recurs across hosts at a rate that matches an automated campaign rather than an administrator. Change windows, software deployment tooling and signed management agents explain a large share of legitimate interpreter invocations, so the bar for escalation should be unusual lineage, unusual content or unusual timing rather than the mere presence of the interpreter.

What you will practise

  • Describe how interpreters such as PowerShell, the Windows command shell and Unix shells are invoked and how their command lines differ from routine administrative use.
  • Identify the process-creation, script-block, module and shell-history telemetry that records interpreter execution across Windows and Linux estates.
  • Explain how encoded or obfuscated interpreter arguments are surfaced in logging and where visibility gaps typically appear.
  • Distinguish adversary interpreter abuse from legitimate automation, configuration management and software deployment activity.
  • Design detection logic that keys on process lineage, argument content and cross-host recurrence rather than on interpreter presence alone.
  • Assess how interpreter logging configuration and constrained language modes change both visibility and attacker cost.
