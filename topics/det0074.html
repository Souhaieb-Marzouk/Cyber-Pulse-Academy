DET0074 Detect Use of Stolen Web Session Cookies Across Platforms

DET0074Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

When you sign in to a website, the site gives your browser a small token. That token is called a session cookie. Your browser shows the token with each request instead of your password. This detection looks for the same token being used from two different places.

Why should you care?

A person who steals that token can use the site as you without your password. The site cannot tell the difference, because the token is the proof. Sign in logs often stay quiet, because no new sign in happens. Watching where a token is used is one of the few ways to catch this.

How it works, in plain steps

  1. The web server writes a log line for each request. That line includes the cookie and browser name.
  2. The sign in service records the address, device and browser used when the session was created.
  3. The detection builds a picture of each account. It notes the usual browsers and addresses.
  4. It then compares each later request against that picture, using the session token as the link.
  5. If one token appears from two addresses at once, the pair is treated as suspicious.
  6. A browser name that has never been seen for that account raises the score further.

Real-world example

Think of a hospital sign in sheet at the ward door. A visitor signs in, takes a badge and walks to a patient. Later the same badge number appears at a second entrance at the same time. Someone else is wearing it. The sheet looks normal, because every entry has a badge number. Only the timing and the place give the trick away.

Key takeaways

  • A session token works like a password, so anyone holding it is treated as the user.
  • Watch where a token is used, because the sign in log may show nothing at all.
  • Learn each account normal browsers and addresses before you alert on changes.

In more detail

This detection strategy targets the reuse of a stolen web session token, where an operator imports a cookie taken from a victim browser and reaches a web application without ever knowing the password. It matters because a session cookie is a bearer credential: the application cannot tell the real user from anyone holding the same value, and the sign in is not repeated, so password changes, lockouts and most authentication alerts never fire. The telemetry that makes this visible is the web tier access log that records the session cookie, user agent and source address on every request, the identity provider sign in log that records device and location context at the moment the session was created, and network flow or proxy records that link the request source to a host or address range. The reliable pattern is one session identifier appearing from two source addresses, or from a source address whose user agent and device context do not match the original sign in, inside the lifetime of that session. It fails in practice because mobile networks, corporate proxies and privacy features change source addresses and user agent strings on perfectly normal traffic, so the rule needs a baseline of each account's browser and address history before it can rank anything.

What you will practise

  • Explain why a session cookie behaves as a bearer credential and bypasses later authentication checks.
  • Identify the log fields that allow one session identifier to be traced across different requests.
  • Correlate web access logs with identity provider sign in records using session, device and address fields.
  • Describe how to baseline an account normal browser and network context to rank anomalies.
  • Outline the response steps for a suspected stolen session, including revocation and scope review.
