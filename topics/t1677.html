T1677 Poisoned Pipeline Execution

T1677ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is when an attacker changes the automatic build process instead of the finished software. Many teams use a robot that builds and tests their code whenever someone saves a change. That robot holds passwords and keys for releasing software. An attacker who can change what the robot does can steal those keys.

Why should you care?

Build systems are trusted by everyone, so they often hold the most valuable credentials in the company. A single change there can affect every product the team ships, not just one server. Some attacks need no special access at all. Anyone who can open a change request from a copy of the project might start the build. If the build runs on a machine inside your network, that machine becomes the attacker's starting point. Reviewing build changes carefully is therefore a security control, not a formality.

How it works, in plain steps

  1. The attacker looks at how your build robot is configured and which passwords it can reach.
  2. In the direct case, they edit the pipeline file and copy secrets to their server or into a build file.
  3. In the indirect case, they leave the pipeline file alone and change a script or test the build runs.
  4. In the public case, they open a change request from their own copy. That starts part of the build without any repository access.
  5. If that build gives secrets to outsiders, the attacker's code can read and leak them.
  6. When the build runs on a company machine, that machine may also become a foothold.

Real-world example

Think of a post office sorting office. All the parcels are sealed and inspected before they arrive. The attacker does not touch a parcel. He gets a job changing the label printing instructions, so every parcel is quietly addressed to his own depot. The parcels look untouched, the customers are happy, and the whole flow ends up in the wrong hands.

Key takeaways

  • Build systems hold release credentials, so they deserve the same protection as production.
  • Changes to build scripts and pipeline files must be reviewed by a person, every time.
  • Never give secrets to builds started by changes from outside your project.

In more detail

Poisoned pipeline execution attacks the build system rather than the deployed application, because the build job holds the credentials, tokens and network position that the finished product does not. Three shapes are commonly described. In direct execution the actor edits the pipeline definition itself, adding a step that ships build secrets to a remote endpoint or exports them as a downloadable build artefact. In indirect execution the actor leaves the pipeline file alone and instead edits something the pipeline consumes, such as a makefile, a test, a linter configuration or a helper script. In public execution the actor has no repository access at all and opens a pull request from a fork that runs a workflow, which is dangerous when the workflow trigger grants secrets to fork-originated code, when the build checks out attacker-controlled content, or when the pipeline treats inputs such as branch names as safe. Self-hosted runners amplify this, because a job that executes attacker-supplied code lands on a host inside the organisation's network. The evidence is in source control history and build logs: changes to pipeline or build files by unexpected authors or via merged pull requests, build steps that print or upload environment values, and secrets appearing in artefact storage. Legitimate builds change the same files, so the differentiator is review: whether the change to the build logic was reviewed by a human who understood it.

What you will practise

  • Explain why build pipelines hold high value credentials for an attacker.
  • Distinguish direct, indirect and public pipeline execution scenarios.
  • Describe how untrusted change requests can obtain build secrets.
  • Identify source control and build log evidence that reveals a poisoned pipeline.
  • Explain how self-hosted build runners turn a pipeline change into network access.
