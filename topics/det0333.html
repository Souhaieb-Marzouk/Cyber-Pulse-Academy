DET0333 Cross-Platform Detection of Scheduled Task/Job Abuse via `at` Utility

DET0333Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches a Unix scheduling tool called at. It runs a command one time, later, at a chosen moment. Attackers use it to delay their actions or to survive a restart. The detection sees both the job being created and the job being run.

Why should you care?

Delayed commands are hard to spot because the cause and the effect are far apart in time. A quiet job that runs at midnight can look harmless during the day. Because at jobs are one-off, they leave less trace than recurring schedules. Catching them closes a quiet persistence path.

How it works, in plain steps

  1. The system records the command that was typed and the user who typed it.
  2. The detection looks for the at client being used to queue a job, including the time argument.
  3. It then watches the spool folder where queued jobs are stored as files.
  4. The job files are read to see which command will run and under which account.
  5. Later, the scheduling service starts the command, and that start is linked back to the queued job.
  6. Jobs sent from a scripting context, from a web server account or with encoded content are escalated to an analyst.

Real-world example

Think of a library where you can reserve a study room for a future hour. Most reservations are students booking ahead. But look at a reservation made by someone who never enters the building. The room is next to the archive, and the hour is closing time. That is worth a call to the front desk.

Key takeaways

  • One-off scheduled jobs are quieter than recurring ones, so they need their own rule.
  • Link the job submission to the job execution to build a complete story.
  • The submitting account and its parent process are the strongest context you have.

In more detail

This strategy detects abuse of the at job scheduler (T1053.002), which exists on Linux, macOS and other Unix-like systems and executes a command once at a chosen future time. Attackers use it for delayed execution and for persistence that survives a reboot long enough to run their payload, and it is quieter than cron because no recurring entry remains after the job fires. Detection uses process creation of the at client, job file creation in the spool directory, the at daemon starting the queued command, and shell history or audit records that show the pipeline used to submit the job. It fails because at is rarely used in modern fleets, so a single legitimate maintenance job from an administrator looks identical to abuse until you add parent process, submitting user, and command content context.

What you will practise

  • Describe how the at scheduler differs from cron in trace and persistence value
  • Locate the telemetry that records job submission, job storage and job execution
  • Correlate a queued job file with the process that later runs it
  • Judge a job by submitting user, parent process and command content
  • Draft a rule that covers at while tolerating approved maintenance jobs
