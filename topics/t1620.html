T1620 Reflective Code Loading

T1620StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Reflective code loading is a way to run harmful code inside a program that is already running. The code is put straight into memory instead of being saved as a file. The program then jumps to that memory and starts running the hidden code.

Why should you care?

Files leave traces that security tools can scan and block. When code lives only in memory, there is no file to inspect and no download to stop. This helps an attacker stay hidden for longer and makes an investigation harder. It also lets the attacker keep the payload scrambled until the last moment. If your team only watches files on disk, you will miss this activity completely.

How it works, in plain steps

  1. The attacker already has a foothold, often through a script that a trusted tool such as PowerShell runs.
  2. The script asks the operating system for a block of memory inside its own process.
  3. It copies the payload bytes into that memory and marks the region as executable.
  4. The script calls a loading function, such as Assembly.Load, to turn those bytes into runnable code.
  5. Control passes to the payload, which runs with the name and permissions of the host process.
  6. Nothing new appears on disk, so the only traces are memory pages, loaded modules and system calls.

Real-world example

Picture a shared office building with a strict front desk. Every visitor must sign in, show a badge, and be written into the visitor log. Now imagine a person who never enters through the lobby at all. They arrive inside a delivery van that is already allowed in. They simply step out once the van is parked. The front desk never records them, because as far as the desk knows, only the van came in. Reflective code loading works the same way. The harmful code hides inside a program that already has permission to run. The controls that check new files never notice it. You only find it by looking inside the building, not at the door.

Key takeaways

  • Code can run without ever becoming a file on disk, so file scanning alone is not enough.
  • Watch for executable memory with no matching file, and for odd module loads in trusted programs.
  • A trusted program doing strange things is often more suspicious than an unknown program.

In more detail

Reflective code loading places executable content directly into the memory of an already running process instead of writing a file to disk and starting it as a normal thread or shared library. The payload may be a compiled binary, an anonymous file that exists only in RAM, or position-independent shellcode. The host process allocates a region of memory, copies the bytes in, marks it executable, and transfers control to it, so the code runs under the identity and reputation of a legitimate process such as PowerShell. Because nothing is dropped on disk, file-based detection has very little to work with. Defenders instead lean on memory scanning, private executable memory regions with no backing file, telemetry for allocation and protection changes, and script block or module load logging. Legitimate software also loads code dynamically, so the discriminator is usually the combination of an unsigned payload, an anomalous parent process, and no corresponding file on disk.

What you will practise

  • Explain what reflective code loading is and why it leaves few traces on disk.
  • Describe how a process allocates memory and runs a payload inside itself.
  • Identify the log sources, such as Sysmon event 1 or script block logging, that can reveal this activity.
  • Distinguish legitimate dynamic code loading from malicious in-memory execution.
  • List the memory artefacts an analyst can inspect during an investigation.
