ECDSA

CryptographyVery hardKeyword

ECDSA is the elliptic curve analogue of the Digital Signature Algorithm, producing signatures whose security depends on the hardness of the elliptic curve discrete logarithm problem rather than integer factorisation. A signature is generated from a private scalar, a per-signature secret nonce, and the message hash; verification uses the public point and the curve parameters. Because the security per bit is higher than RSA, ECDSA keys are far smaller for equivalent strength, which is why it dominates TLS certificates, code signing, SSH keys and hardware-backed authentication on mobile devices. The critical operational property is that the nonce must be unique and unpredictable for every signature made with a given private key. Reusing a nonce across two signatures over different messages allows the private key to be recovered algebraically from the two signatures alone, and this is not a theoretical concern: it has happened repeatedly through flawed random number generation and through code paths that derive the nonce deterministically but incorrectly. Other practical hazards include weak or duplicated entropy on embedded devices, curve parameters that are not the standardised NIST or Curve25519 family, malleable signature encodings that break naive transaction or protocol logic, and libraries that accept a public key without validating that it lies on the curve. Defensive practice therefore centres on vetted libraries, deterministic nonce generation, hardware key storage, and inventorying where signatures are produced.

What you will practise

  • Explain how ECDSA signing and verification use the curve, the private scalar and the per-signature nonce.
  • Describe how nonce reuse across two signatures reveals a private key and what evidence of that failure looks like.
  • Compare ECDSA key sizes and performance with RSA and state where each is still the better operational choice.
  • Validate curve parameters and public key encoding during a review of a signature verification implementation.
  • Recognise malleable signature encodings and explain why canonicalisation matters to protocol logic.
  • Plan a migration from classic curves to modern alternatives while preserving certificate and key continuity.
