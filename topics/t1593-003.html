T1593.003 Search Open Websites/Domains: Code Repositories

T1593.003ReconnaissanceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is when an attacker searches public code repositories for information about you. A code repository is an online place where developers store and share program code. Some of that code, and the notes around it, is visible to everyone.

Why should you care?

Developers sometimes save passwords, keys or internal addresses in code by accident. Anyone can search for them. The code also shows which tools and versions you use, which points to known weaknesses. Even deleted files often stay in the history, so a quick cleanup is not enough.

How it works, in plain steps

  1. The attacker searches public repositories for your organisation's name, domain and employee names.
  2. They read the code to learn which languages, frameworks and libraries your teams prefer.
  3. They look for configuration files holding server names, addresses or connection details.
  4. They search the history for secrets that were deleted from the current version of a file.
  5. They check who contributed and collect names and email addresses for later targeting.
  6. They use any working secret they find to log in, or exploit a known flaw in a listed library.

Real-world example

Think of a workshop where apprentices practise on a scrap bench in the yard. Most of the scrap is harmless, but someone once left a spare key to the store room in a toolbox on that bench. The bench is public, so the key is public too, even after the toolbox is moved.

Key takeaways

  • A committed secret is exposed forever in history, so rotate it rather than delete it.
  • Enable secret scanning and treat every alert as a real incident.
  • Keep internal addresses and hostnames out of sample and test files.

In more detail

This sub-technique is public source code discovery, where adversaries mine hosted repositories for what a victim's engineering culture and history reveal. Useful material includes programming languages and frameworks in use, third party dependencies with known flaws, internal hostnames and service names appearing in configuration samples, contributor names and email addresses, and secrets committed by accident such as application programming interface tokens or database connection strings. The mechanism is ordinary repository search, both through the web interface and through version control clients, plus historical commits that remain retrievable long after the file was deleted. This differs from the parent, which covers open websites generally, and it must not be confused with collection from private internal repositories, which requires access. Repository audit logs and organisation level secret scanning alerts are the primary defender artefacts, along with notification from the hosting provider when a credential is detected in a public push. Rotating any exposed secret is the only reliable fix, because history and forks preserve the old value.

What you will practise

  • Explain why public code repositories expose organisational and technical detail.
  • List the types of sensitive data commonly found in committed code.
  • Describe why deleting a file does not remove the secret from repository history.
  • Explain the difference between public repository search and collection from private code stores.
  • Describe a response process for a leaked credential, starting with rotation.
