DET0154 Detect Screensaver-Based Persistence via Registry and Execution Chains

DET0154Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A screen saver is the moving picture shown when a computer is idle. Windows can be told to run any program at that moment. This detection watches the setting that names the program and the moment the program starts.

Why should you care?

Idle time is easy to arrange. An attacker only has to wait for the user to step away. The program then starts with the user's own permissions. It starts again after every restart because the setting is stored. A small setting change becomes lasting access.

How it works, in plain steps

  1. The detection watches the registry value that stores the screen saver program path.
  2. It records which process wrote the new value and when.
  3. It checks whether the program named in the value is signed and in a normal location.
  4. It then watches for that program starting with the screen saver host as parent.
  5. A setting change and a matching execution from an unusual path together raise the alert.

Real-world example

Think of an office that plays music when the room is empty at night to deter mice. A prankster rewires the timer so that instead of music, the door unlocks. Nothing looks different on the timer panel, but the action tied to the idle moment has changed. That is exactly how this technique works.

Key takeaways

  • Idle time can trigger code, so treat the trigger as persistence.
  • The screen saver path should only name a signed system program.
  • Watch both the setting change and the later execution.

In more detail

This strategy covers T1546.002, screensaver based persistence, where an intruder points the screen saver setting at a program so that code runs when the session goes idle. Detection is built on registry modification events for the screen saver value, the security policy that governs whether a screen saver requires a password, process creation records whose parent is the screen saver host, and file creation events for the executable named in the setting. The pattern is strong because the screen saver value normally names a signed executable inside the system directory, so a value pointing anywhere else is unusual. The failure mode is that third party screen saver software and some management tools change the same value legitimately, so the rule needs the signer and the writing process to stay accurate.

What you will practise

  • Explain how the screen saver setting can be turned into an execution trigger
  • Locate the registry value that stores the screen saver executable path
  • Collect registry modification, process creation, and file creation telemetry
  • Correlate a setting change with the process that later starts on idle
  • Separate legitimate screen saver software from attacker configured paths
  • Set severity based on the persistence gained and the account involved
