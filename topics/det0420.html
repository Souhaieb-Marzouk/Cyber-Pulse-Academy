DET0420 Detect User Activity Based Sandbox Evasion via Input & Artifact Probing

DET0420Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A sandbox is an automated system that runs a file to see what it does. Some malicious files check whether a real person is using the computer before they act. If nobody moves the mouse or opens a document, they stay quiet. This detection looks for programs that wait for signs of a real user and then wake up.

Why should you care?

Automated analysis is how many teams check unknown files quickly. A file that waits defeats that check and looks harmless. The same trick delays the attack inside a real company, which also delays your response. The waiting period is a clue you can see if you keep records long enough. It also explains surprising activity hours after a file was first opened.

How it works, in plain steps

  1. The endpoint sensor records when each program starts, who started it and how long it stays alive.
  2. It also records file reads in document folders and any network connection the program makes.
  3. The rule looks for a program that starts with no further activity, then becomes active much later.
  4. It checks whether the later activity follows a user session action, such as a screen unlock or a document open.
  5. It compares the process with the normal list for that computer, because many legitimate agents poll in the background.
  6. When the quiet period, the wake up and the later activity line up, an alert shows the analyst the timeline.

Real-world example

Think of a burglar who waits in a parked car. The burglar waits until the street goes quiet and someone walks past the house. Sitting still proves nothing on its own, and cars park on the street all the time. The watchman writes down the time the car arrived and the time it moved. The gap between those notes makes the report useful.

Key takeaways

  • Long gaps between a program starting and doing anything useful are the core signal.
  • Record timestamps carefully, because the delay is the evidence.
  • Know your polling agents, since they also wake up on a schedule.

In more detail

This strategy covers user activity based sandbox evasion, tracked as T1497.002, where an adversary delays execution or changes behaviour until it observes signs of a real user, such as mouse movement, recent documents, a scrolling window or an interactive session, in order to avoid automated analysis. It matters because a sample that waits for human input will look inert in a sandbox and benign in telemetry, so defenders must observe the long tail of behaviour that starts after an artificial delay or after an interaction. The telemetry that makes detection possible is endpoint sensor process and window event data: process creation with parent and user context, window focus and input event records where the platform exposes them, file access records for recent document folders, and network connection events that follow the delay. The main way it fails is that interactivity signals are rarely logged, so detection usually leans on timing and on the process that suddenly wakes up, which means coverage depends on how completely the endpoint sensor records user session state.

What you will practise

  • Explain what a sandbox is and how a check for user activity defeats it.
  • Identify the endpoint records that show a program starting and later becoming active.
  • Measure the gap between process start and the first meaningful child or network event.
  • Recognise the user session signals an adversary may look for, such as input or unlocked state.
  • Separate legitimate scheduled polling from activity that follows a user interaction.
  • Describe how to retain endpoint data long enough to see delayed execution.
