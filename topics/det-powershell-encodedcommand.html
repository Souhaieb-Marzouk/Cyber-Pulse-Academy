Suspicious PowerShell EncodedCommand

Detection StrategyVery hardDetection Strategy

Suspicious PowerShell EncodedCommand detection identifies execution of PowerShell where the command payload is supplied as a Base64-encoded string rather than readable script text, typically through the -EncodedCommand parameter, its documented short forms, or by piping decoded content into Invoke-Expression. The behaviour matters because encoding is one of the cheapest and most common ways an operator hides intent from casual console review, from simple string-based content filters, and from responders reading a process list under time pressure. The telemetry required is process creation with full command line captured, ideally from endpoint detection agents or Windows Security event 4688 with command line auditing enabled, plus PowerShell script block logging and module logging where available so the decoded body can be reconstructed after the fact. The signal survives common evasion because the encoding step happens before the shell ever evaluates the script, so the obfuscated string is what appears in the process command line; variants that read an encoded blob from a file, an environment variable, or a remote download still produce a distinctive parent-child pattern and an unusually high proportion of non-alphanumeric characters. It also survives because legitimate administrative tooling rarely needs encoding at all. The detection breaks down in practice on three fronts: automation platforms and configuration management agents use encoded commands perfectly legitimately and at high volume, so baseline allow-listing by parent process and signing certificate becomes mandatory; short payloads produce short command lines where entropy and length thresholds are unreliable; and adversaries who switch to script block logging evasion, downgrade attacks against logging policy, or in-memory assembly loading can leave a decoded payload that never appears in the command line at all, which is why this rule should be paired with script block content analysis and AMSI-related telemetry rather than used alone.

What you will practise

  • Explain what PowerShell command encoding does at the shell level and why the encoded form, not the decoded script, is what appears in process-creation telemetry.
  • Write a query that correlates encoded-command execution against parent process, user context and host role to separate automation from interactive abuse.
  • Identify which command-line tokens indicate encoding and describe how each family of tokens behaves across PowerShell editions.
  • Assess when command-line length and character-distribution heuristics add value and when they produce unacceptable noise.
  • Describe how script block logging and module logging recover intent that the encoded command line conceals.
  • Recognise logging-policy tampering and language downgrade behaviour as an escalation signal alongside the initial encoded execution.
  • Prioritise encoded-command alerts using follow-on activity such as network egress, credential access attempts or scheduled task creation.
