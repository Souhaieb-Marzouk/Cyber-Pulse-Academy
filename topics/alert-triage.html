Alert Triage

SOC & Detection EngineeringVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Alert triage is deciding which security alarms matter. Your monitoring tools raise many alerts, far more than anyone can investigate. Triage means reading each one quickly and choosing what to do next: investigate it, pass it to a colleague, or close it as harmless.

Why should you care?

A busy company can produce thousands of alerts every day. If nobody sorts them, real attacks hide inside the noise and nobody notices. If you investigate everything, you finish nothing and you burn out. Triage is the skill that keeps the queue moving without letting the serious things slip through. It is also the part of security work that most people are actually hired to do.

How it works, in plain steps

  1. Read the alert and work out what actually happened, not just what the rule says.
  2. Add context: which machine, which user, and whether this has happened before.
  3. Compare it with normal behaviour for that asset, so you know if it stands out.
  4. Decide the priority, then either investigate further, escalate, or close it with a written reason.
  5. Record what you decided and why, so the next analyst does not start from zero.

Real-world example

Think about a busy hospital monitoring desk at night. Alarms beep constantly, and most of them are minor: a loose sensor, a patient who rolled over, a machine that needs a new battery. A good nurse does not run to every beep, and does not ignore them either. They look at the patient, the readings together and the recent history, then decide. Only then do they call the doctor. Alert triage works the same way. One odd login is probably nothing. The same login followed by a brand new administrator account is a reason to act immediately.

Key takeaways

  • Triage is a decision, not a reading exercise. Every alert ends with an action and a reason.
  • Context decides meaning: the same event can be routine on one host and alarming on another.
  • Closing an alert as benign is a correct outcome, as long as you can explain why.

In more detail

Alert triage is the work of taking the queue of alerts a monitoring platform has produced and deciding, one by one, which of them deserve investigation, which can be closed, and which need to be escalated to someone else. It is deliberately not the same as detection engineering, which writes the rules, or incident response, which handles the confirmed incident. Triage is the judgement layer between the two, and it is where a security operations centre spends most of its analyst hours. The difficulty is not reading a single alert: it is that the same alert means different things depending on the asset, the user, the time of day and what else happened in the same window. An encoded PowerShell command on a build server is routine automation; the identical command on a finance workstation that has never run one is a genuine lead. Good triage therefore rests on three things: enough environmental context to know what normal looks like, a repeatable process so that two analysts reach comparable decisions, and the discipline to close alerts without guilt when the evidence says they are benign. The most common failure is not missing a clever attack, it is drowning in volume and closing the queue without reading it.

What you will practise

  • Explain the difference between detection, triage and incident response, and where the boundaries sit.
  • Gather environmental context for an alert quickly, using asset, identity and history data.
  • Make and record a defensible triage decision: investigate, escalate, or close as benign.
  • Recognise the failure modes that cause missed incidents, including queue-driven closure and alert fatigue.
