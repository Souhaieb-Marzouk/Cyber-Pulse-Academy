DET0825 Detection of Drive-by Target

DET0825Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for a website that is set up to harm its visitors. The attacker places the trap first and sends people to it later. The rule watches for users who pass through several odd redirects to one page. It also watches for office programs or browsers starting unusual child processes.

Why should you care?

The visitor needs to do nothing except open the page. There is no attachment to inspect in advance. You cannot see the trap from the outside, so you must watch what happens to your users. Early warning lets you block the domain and check which devices were affected.

How it works, in plain steps

  1. The web gateway records each request with the address, the referrer and the full page path.
  2. Redirect chains are rebuilt from those records, so a user path through several unrelated sites becomes visible.
  3. Resolver logs show first time lookups of newly registered domains from corporate devices.
  4. Endpoint detection records process trees. A browser or document reader that starts a script host is unusual.
  5. The rule selects users who reached a low reputation page after many redirects. It also selects a browser that started a child process.
  6. Matching devices are isolated for review, and the domains are added to the block list.

Real-world example

Think of a footpath where someone has loosened one paving stone. Nothing looks wrong until a walker steps on it. The person who loosened the stone never returns to the path. This detection checks the ankles of the walkers, not the stone.

Key takeaways

  • Compromised visitors are the only reliable signal, because the trap sits outside your control.
  • A long redirect chain through unrelated domains is a strong warning sign.
  • A browser or document reader that starts a script host is worth an immediate look.

In more detail

This detection strategy covers the drive by target step, where an adversary prepares a website that compromises visitors and then sends traffic to it, usually by injecting a redirect into a legitimate but weakly maintained site, by buying an expired domain, or by hosting a page that checks the visitor before delivering an exploit. It matters because the preparation is silent, so the practical detection sits on the victim side: proxy and network logs showing a small number of users redirected through a chain of unrelated hosts to a page that serves script, intrusion detection alerts for exploit delivery, endpoint records of browser or plug in child processes, and domain monitoring for newly registered or recently re-registered lookalike sites. The telemetry that makes it possible is secure web gateway records with referrer chains, domain name system resolver logs, endpoint detection and response process trees, and intrusion detection signatures for known exploit kits. Detection fails because legitimate advertising and content networks redirect users constantly, and because the exploit page often serves harmless content to the wrong visitor.

What you will practise

  • Explain how a drive by target page differs from a phishing message.
  • Identify the proxy, resolver and endpoint records that reveal a drive by visit.
  • Write a rule that combines redirect chain length with domain age and process behaviour.
  • Describe how to isolate a device that may have run exploit code.
  • Explain how domain monitoring supports blocking before users are sent to the page.
