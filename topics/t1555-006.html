T1555.006 Credentials from Password Stores: Cloud Secrets Management Stores

T1555.006Credential AccessExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A cloud secrets manager is an online service that stores passwords, keys, and tokens for your cloud systems. Applications ask the service for a secret whenever they need one. This technique means an attacker with enough cloud rights asks the service for those secrets as well.

Why should you care?

One cloud secret can open a database, a storage account, or an entire second cloud environment. A central store is convenient, but it also concentrates risk in one place. The cloud provider records every secret read, so the evidence usually exists if you look for it. Without monitoring, an attacker can quietly collect secrets that keep working long after the first host is cleaned.

How it works, in plain steps

  1. Teams move passwords and keys out of files and into a managed cloud secret store.
  2. Applications receive a role or identity that lets them request specific secrets by name.
  3. The application calls the provider interface and receives the secret value in return.
  4. An attacker who steals such an identity can make exactly the same request.
  5. They list the available secrets first, then read the ones with the widest permissions.
  6. Cloud audit logs record each read together with the identity, address, and time.

Real-world example

Think of a bank where a clerk fetches items from the vault for customers. You do not need to open the vault yourself; you show a badge and ask. Real customers ask for one small box each day. A thief with a copied badge walks in and asks for every box in the building. The clerk writes each request in a log book. The theft is recorded in full, but nobody ever reads that log. The bank only notices later, when customers report that their boxes are empty.

Key takeaways

  • A secrets manager hands out credentials by design, so permissions are the real control.
  • Cloud audit logs record every secret read, so alert on unusual identities and volume.
  • Give each workload access to only the small set of secrets that it truly needs.

In more detail

Cloud secrets managers are central services that hold API keys, database passwords and tokens so that applications no longer keep them in plain text files or environment variables. Because the service is designed to hand out secrets to authorised consumers, an attacker with the right permissions does not need to break any encryption. They call the same interface that legitimate workloads use, for example a get-secret-value operation in AWS, a secrets describe command in GCP, or a key vault secret show command in Azure. Access can come from stolen high privilege cloud credentials or from a compromised workload whose role already allows reading secrets. The activity is recorded in the provider audit trail, where successful secret reads carry the calling identity, the source address and the user agent. The hard part is separating abuse from routine automation, because deployment pipelines and autoscaling services read secrets constantly. Useful signals are a human identity reading many secrets, a read from an unexpected region or address, a sudden spike in volume, or reads that are not followed by normal application behaviour.
