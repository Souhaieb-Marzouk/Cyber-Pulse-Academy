T1574.014 Hijack Execution Flow: AppDomainManager

T1574.014ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A .NET program runs inside areas called application domains. A special class, the application domain manager, decides how those areas start and which code files, called assemblies, load into them. An attacker can make a program load a harmful assembly at startup. To the user, the program still looks and behaves mostly normal.

Why should you care?

The harmful assembly runs inside a trusted program, so it gets the same rights and the same access to data. Security tools may see only the trusted program starting as usual. Attackers use this to keep access on a machine and to hide their code. If the program runs with high rights, the harmful code does as well.

How it works, in plain steps

  1. A .NET program starts and creates one or more application domains.
  2. Configuration beside the program or an environment setting names the manager and assembly.
  3. An attacker edits that configuration to name their own assembly.
  4. The runtime reads the setting and loads the named assembly into the process.
  5. The attacker assembly runs with the rights of the host program.
  6. Because the host started first, the load looks like ordinary startup.

Real-world example

Think of a club with a guest list at the door. The manager checks the list and reads out names for the doorman. Someone quietly adds a name to the list. The doorman lets the extra guest in with the same welcome as everyone else. The manager reads the same list as always and suspects nothing.

Key takeaways

  • Protect configuration files that sit beside .NET programs.
  • Baseline which assemblies each managed program normally loads.
  • Investigate managed assemblies loaded from temporary or user folders.

In more detail

This sub-technique hijacks assembly loading inside the .NET runtime by abusing the application domain manager. Every managed process creates application domains, and the AppDomainManager class decides how those domains are set up and which assemblies are loaded into them. An adversary can influence that decision in two related ways: by supplying a custom manager and domain so that a malicious assembly is loaded and executed inside a target process, or by tampering with a .config file or a process environment setting so that an otherwise benign managed application loads an assembly named by the attacker when the runtime initialises. Because the host application starts the load itself, the payload inherits the host identity and privileges, and the activity appears within an already trusted process, which is why the behaviour is hard to separate from normal startup. Detection focuses on file integrity of configuration files beside managed binaries, unexpected assembly names in configuration, loads of managed assemblies from user-writable or temporary directories, and .NET startup or assembly load telemetry correlated with the launching parent process. Sibling sub-techniques instead alter a service path, a service registry key, or the profiler setting.
