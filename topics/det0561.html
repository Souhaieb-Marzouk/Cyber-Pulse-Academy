DET0561 Detect malicious IDE extension install/usage and IDE tunneling

DET0561Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An integrated development environment is a program where developers write and test code. Extensions are add ons that give it new features. This detection looks for extensions installed from unexpected places, and for the editor starting programs it should not start.

Why should you care?

The editor already has access to source code, stored credentials and company systems. An extension runs with those same rights. Developers can usually install extensions without asking anyone. One bad extension can quietly copy code or open a remote connection.

How it works, in plain steps

  1. The editor records each extension installation and update, including the extension name, version and publisher.
  2. The endpoint agent records files written into the extension folder and programs started by the editor.
  3. The rule looks for extensions installed from a file or a folder instead of the official marketplace.
  4. It also looks for the editor starting network tunnelling tools or command interpreters, which normal editing does not need.
  5. A SIEM, which is a central system that collects and searches log events, joins the installation record with the later process and network activity.
  6. An extension that is both recently installed and starts a tunnel or a script raises a high confidence alert.

Real-world example

Think of a shared kitchen where anyone may add a gadget to the counter. One gadget looks useful, but it also has a small camera pointed at the notice board. Nobody checked the box it came in. This detection inspects the delivery label and watches what each gadget does after it is plugged in.

Key takeaways

  • The editor's privileges become the extension's privileges, including any stored credentials.
  • Watch the extension host process tree, because that is where extension behaviour actually appears.
  • Marketplace installation is normal, so the signal is off marketplace sources, new publishers and editor started tunnels.

In more detail

This strategy covers User Execution or Software Extensions: Malicious IDE Extension, where an attacker publishes or plants an extension for a code editor so that the developer installs and runs it with the editor's own privileges. It matters because integrated development environments, the tools programmers write code in, usually hold credentials, source code, signing keys and network access, so a single extension can reach a large portion of a company's intellectual property. The telemetry that makes it visible is extension installation and update records from the editor and its marketplace, file creation inside the extension directory, process creations whose parent is the editor's extension host, and network connections from editor child processes including tunnelling tools. It fails in practice because developers install extensions freely, most organisations have no allow list, and the malicious behaviour often happens inside the editor's own process tree where ordinary endpoint rules rarely look.

What you will practise

  • Explain why code editor extensions are a viable supply chain and execution path.
  • Identify the installation, file creation and process events that record extension activity.
  • Recognise editor child processes such as tunnelling tools and interpreters that are abnormal for editing work.
  • Build an approved extension list per team and alert on off marketplace installations.
  • Correlate an extension installation with the first process or network connection it produces.
  • Describe the response steps for a suspicious extension, including removal, credential rotation and code review.
