T1137.006 Office Application Startup: Add-ins

T1137.006PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An add-in is a small extra program that plugs into Word, Excel or Outlook to add a feature. Office loads add-ins automatically when it starts. This technique is when an attacker hides their own code inside an add-in so it runs every time you open Office.

Why should you care?

You trust Word and Excel, so you also trust what they load. An add-in runs with your rights and your access to company files. Because add-ins are normal and many exist, a new one rarely looks strange. It also keeps working after you restart your computer.

How it works, in plain steps

  1. Office supports several kinds of add-ins, and each kind is loaded from its own place.
  2. Each add-in is registered, so Office knows its file and where it lives.
  3. The attacker writes an add-in file and registers it in your user profile or registry.
  4. From then on, Office loads that file every time the program starts.
  5. The add-in code runs inside the Office program with your user rights.
  6. It may also hide itself so it does not show up in the normal add-in list.

Real-world example

Think of a workspace where each employee may fix a personal lamp onto their desk. Facilities check the lamps once a year. Someone fits a lamp that also opens a side door in the wall behind the desk. Every morning the lamp is switched on with the office lights, and the door quietly unlocks.

Key takeaways

  • Add-ins load automatically at startup, so no user action is needed to run them.
  • They execute inside the trusted Office program with the signed in user rights.
  • Keep a baseline of expected add-ins and alert when the list changes.

In more detail

Office add-ins are loadable components that the Office applications pull in at startup to extend their features, and because they are loaded automatically and run inside the trusted Office process, they are an attractive persistence slot for an attacker who already has write access to a user profile or the registry. Several distinct loaders exist: Word and Excel add-in libraries, Visual Basic for Applications add-ins, Component Object Model add-ins registered under the Office keys, automation add-ins, Visual Studio Tools for Office add-ins, and Outlook add-ins. They differ in where they are registered and which host loads them, but the shared behaviour is that the add-in path is recorded in the registry or in a user profile location, and the code inside executes with the privileges of the signed in user each time Word, Excel, PowerPoint or Outlook opens. Office may also block add-ins that it considers unsafe, and users can be prompted to approve a new one, so an attacker often times the write to a moment when the prompt will look routine or uses a location that needs no prompt at all. The artefacts a defender works with are therefore registry keys under the Office add-in locations, unusual dynamic link libraries in user writable folders, and Office processes loading libraries from paths that the software vendor never uses. Comparing the current add-in inventory against a known baseline is what separates malicious additions from the legitimate integrations that organisations install on purpose.
