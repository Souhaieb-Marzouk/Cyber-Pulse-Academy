Hashing Algorithms

CryptographyHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A hashing algorithm turns any piece of data into a short code of fixed length. The same data always gives the same code, and even a tiny change gives a completely different one. You cannot turn the code back into the original data. People use it like a fingerprint to check that a file has not changed.

Why should you care?

You often need to know that a file or message arrived unchanged. A hash lets you compare a short code instead of the whole file. It also lets a system store a password without keeping the password itself. If a weak hashing algorithm is used, an attacker can build two different files with the same code. Then a signature or an update check can be fooled. Choosing the right algorithm is a real security decision.

How it works, in plain steps

  1. The algorithm breaks the input into blocks and mixes each block together.
  2. It repeats rounds of simple maths so every input bit spreads everywhere.
  3. The final result is a digest of fixed size, such as 256 bits.
  4. Changing one character in the input changes most of the output digest.
  5. Two different inputs should almost never produce exactly the same digest value.
  6. Password storage also adds a random salt and a slow, memory-heavy function.

Real-world example

Think of a library that keeps a card for every book. The card shows a short fingerprint of the book, built from its title, size and text. If someone swaps a page, the fingerprint changes and the librarian sees it at once. You cannot rebuild the whole book from the fingerprint, but you can check that this is the same book. A salt is like giving every copy its own private code. Two copies of the same book then never share a fingerprint.

Key takeaways

  • A hash is a one-way fingerprint, not encryption, because you cannot reverse it.
  • Never store passwords with a fast hash, use a slow salted one instead.
  • Replace old algorithms such as MD5 and SHA-1 wherever signatures or integrity matter.

In more detail

A hashing algorithm maps an input of any length to a fixed-length digest that behaves as a fingerprint: the same input always yields the same digest, a one-bit change produces a completely different digest, and recovering the input from the digest should be computationally infeasible. Hash functions carry integrity checks, digital signatures, certificate fingerprints, password storage, key derivation and content addressing in container registries. Security depends on collision resistance, so older algorithms are no longer acceptable where two different inputs must never share a digest, while they may remain tolerable for non-adversarial checksums. The mistake is using one fast general-purpose hash everywhere, especially for passwords: speed is a feature for integrity checks and a liability for credential storage, which needs a unique salt and a deliberately slow, memory-hard construction. Choosing the wrong property for the job is the real failure, not the algorithm name alone.

What you will practise

  • Explain what a hashing algorithm does and how a fixed-length digest is produced.
  • Distinguish hashing from encryption, encoding and compression.
  • Explain why collision resistance matters for signatures, certificates and updates.
  • Describe how salting and deliberately slow hashing protect stored passwords.
  • Select an appropriate hash for integrity checks, password storage and content addressing.
