T1036.001 Masquerading: Invalid Code Signature

T1036.001StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is a trick where an attacker copies the signature details of a real signed program onto their own file. A code signature is a digital stamp. It proves who made a program and that nobody changed it. The copied file looks signed, but the stamp is broken.

Why should you care?

People trust a program when they see a familiar company name on it. An invalid signature can still show that name in a file properties window. Some security tools show the name and forget to check the stamp properly. So the attacker gets trust they did not earn. A careful check of the file will still fail.

How it works, in plain steps

  1. The attacker finds a real program that a trusted company has already signed.
  2. They copy the signature data block and the publisher details out of that file.
  3. They paste that data into their own malicious program.
  4. The file now shows a familiar company name when a user looks at it.
  5. Any proper signature check fails, because the file contents no longer match the stamp.
  6. Some tools display the publisher name without ever running that check.

Real-world example

Imagine a night guard at a hospital desk who checks badges by looking at the logo. A visitor copies a real doctor badge design onto a blank card. The guard sees the logo and waves the person through. A scanner at the door would still reject the card, because the hidden code inside does not match.

Key takeaways

  • Always check whether a signature is valid, not just whether one is present.
  • A familiar publisher name on a file is not proof of anything by itself.
  • Look for unsigned files that still carry vendor names and certificate data.

In more detail

Invalid code signature masquerading is the practice of copying the embedded signature metadata of a genuinely signed program onto an unsigned or modified payload so that it presents a recognisable vendor name, certificate subject and signer information to users and tools. The file never validates: the digest no longer matches the content, or the certificate chain is broken or untrusted. The value to an attacker is social and telemetry-based rather than cryptographic, because a properties dialog or a file-reputation lookup may still display a familiar publisher while enforcement relies on numeric signature status. Defenders distinguish it from legitimate software by checking the actual validation result per file, watching for signer metadata that disagrees with the file hash or the software inventory, and comparing the publisher on disk against the signed baseline for that vendor. Unsigned binaries carrying vendor strings, copied countersignatures and mangled Authenticode blobs are the useful artefacts; a validly signed but revoked or expired signature is a separate problem and should be triaged differently.

What you will practise

  • Explain what a code signature proves and why a copied one fails validation.
  • Describe how signature metadata can be transplanted from a signed file to an unsigned one.
  • Identify which file properties and artefacts a defender should inspect.
  • Distinguish an invalid signature from a genuinely signed binary that was simply revoked.
  • Choose validation status, rather than publisher name, as the basis for a detection rule.
