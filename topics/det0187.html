DET0187 Detect Disabled Windows Event Log

DET0187Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection catches anyone turning off the Windows event log on a computer. The event log is the built in diary of what the computer did. When it stops, your security tools lose their main source of evidence. The rule watches for the service being stopped, disabled, or changed.

Why should you care?

Almost every Windows alert you receive is built from event log records. Switch that off and the machine becomes invisible while it keeps running. Attackers often do this right before they act, so a disabled log is a strong warning. It is also easy to reverse, and you can restart logging quickly. Noticing it early protects every other detection you own.

How it works, in plain steps

  1. A user or script changes the event log service so it no longer runs or no longer starts.
  2. Windows records the service change, or a registry write to the service start value.
  3. The audit policy change event fires if the audit settings themselves were altered.
  4. Your monitoring tool notices that the host has stopped sending normal log records.
  5. A heartbeat check compares each host against the records it usually sends every hour.
  6. A service change plus missing records produces one clear alert about that host.

Real-world example

Think of a shop with a till that prints a receipt for every sale. A thief cannot easily stop the till, so instead they unplug it. The sales still happen, but the paper trail stops. The manager notices something faster than the missing money. The roll of paper has not moved all afternoon. Every other till in the shop is still printing.

Key takeaways

  • Silencing the event log removes the evidence for nearly every other Windows detection.
  • A missing heartbeat from a host is itself an alert, not just a data problem.
  • Watch the service start value in the registry, because that change survives a reboot.

In more detail

This strategy detects attempts to disable or degrade the Windows event log service and the audit policy that feeds it. It matters because the event log is the substrate almost every other Windows detection depends on, so silencing it blinds the rest of your monitoring without touching a single security product. Detection is possible through service state change records, registry writes to the service start value, audit policy change events and gaps in expected log volume. The main failure in practice is that service tuning for performance and legitimate log size management produce similar signals, and that once the service is disabled the affected host stops sending the very telemetry that would report it, so absence of data must itself be treated as an input.

What you will practise

  • Explain why the Windows event log is a shared dependency for most Windows detections.
  • Identify service state change, registry and audit policy records that reveal log tampering.
  • Configure a per host log heartbeat to detect missing telemetry as a signal.
  • Distinguish deliberate service disabling from performance tuning and log size management.
  • Correlate the account and process responsible for a service configuration change.
  • Describe how forwarding logs off host limits the impact of a local log shutdown.
