T1563.002 Remote Service Session Hijacking: RDP Hijacking

T1563.002Lateral MovementExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Remote Desktop lets you use another computer's screen, mouse, and keyboard over a network. Windows tracks each of these connections as a numbered session. This sub-technique is about an attacker attaching one of those existing sessions to themselves. They do not need the user's password and the user may not be asked to approve anything. It is the remote desktop part of the wider session hijacking technique.

Why should you care?

If the stolen session belongs to an administrator, the attacker inherits those rights straight away. A disconnected session is the easiest target, because its owner has walked away and is not watching the screen. Windows does not record a normal logon for the attacker, so common login alerts do not fire. The genuine user may simply be pushed out of their own session. That often looks like a technical glitch rather than an intrusion. Without session level monitoring, this movement between machines can pass completely unnoticed.

How it works, in plain steps

  1. The attacker first needs System level rights on the machine that holds the sessions.
  2. Windows keeps each remote desktop session under a number that can be listed.
  3. They choose an existing session number, ideally one that is already disconnected.
  4. They run tscon.exe with that session number, then attach that session to them.
  5. The session continues with all the original user's rights and opened applications.
  6. Defenders see a reconnection event but no new logon for the attacker's account.

Real-world example

Think of a hospital night desk with a row of phones. Each phone connects to a doctor who is on call. A staff member with a master pass can pick up a phone that is already connected and continue the call. The doctor on the other end hears the same familiar line and carries on giving instructions. Nobody dialled a new number and no password was spoken at any point.

Key takeaways

  • tscon.exe reconnects an existing session, so no password prompt and no logon event occur.
  • A disconnected administrator session is the most valuable and easiest target.
  • Alert on unusual session reconnections and keep idle sessions short.

In more detail

Remote Desktop Protocol (RDP) hijacking takes over a remote desktop session that already exists on a Windows host. Remote Desktop Services keeps each interactive session addressable by a numeric session identifier, and an account whose context has System level privileges can reconnect an existing session to a different connection without presenting that user's credentials and without generating a prompt. The practical consequence is that a session belonging to a helpdesk operator, a server administrator, or a domain administrator can be reattached to the attacker, who then continues working with all of that session's rights, including access to mapped drives, saved credentials, and administrative tools. Sessions can be hijacked whether they are active or disconnected, locally or remotely, and disconnected sessions are especially attractive because their original user is not watching. Detection rests on the fact that a session changes hands while nothing about authentication changes. A reconnection or a session state change appears in Terminal Services operational logging, but there is no accompanying successful logon from the attacker and no failed logon either, which is precisely why authentication based alerting stays quiet. The stronger signals are a session reconnection recorded for an account that is not the person currently at the keyboard, process execution under a session identifier that no longer belongs to its original user, and the legitimate user being disconnected without explanation. Because the technique uses native operating system tooling, blocking the binary is not practical, so the response depends on limiting idle and disconnected sessions, restricting who holds System rights, and alerting on unusual session reconnection patterns.

What you will practise

  • Define RDP session hijacking and explain why it needs no user credentials.
  • Describe how Windows numbers interactive sessions and why those numbers matter.
  • Explain what tscon.exe does and why it is not practical to simply block it.
  • Identify Terminal Services log records that show a session changing hands.
  • Explain why authentication based alerting fails to detect this technique.
  • Outline controls such as session timeouts, restricted System rights, and session auditing.
