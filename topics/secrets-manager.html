Secrets Manager

Cloud SecurityVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A secrets manager is a service that stores sensitive values such as passwords, API keys and certificates. API keys are strings that let one program call another. Instead of hiding these values in code or config files, your program asks the service for them at run time, and the service checks permission first.

Why should you care?

Passwords and keys written into code or config files spread everywhere: laptops, build logs, backups and code repositories. Once leaked, they often stay valid for years. A secrets manager keeps them in one guarded place, gives each workload its own credential, and can change them on a schedule. It also records who read which secret and when.

How it works, in plain steps

  1. You store a secret in the service and write a policy saying who may read it.
  2. The service encrypts the value using a key that it manages for you.
  3. When your program starts, it proves its identity, often using its cloud workload identity.
  4. It asks for the secret by name and receives the value over an encrypted connection.
  5. A rotation schedule can create a new password and update both the store and the target system.
  6. Every read is written to a log, so unusual access can be spotted.

Real-world example

Think of a hotel safe at reception. Guests do not carry the master key in their pocket, and staff do not write the combination on the wall. When you need something from your box, you show your ID and a clerk opens it for you. The safe also keeps a record of each visit. That record is how you notice a stranger asking for your box.

Key takeaways

  • Never store passwords or keys in code, images or config files.
  • Give each workload its own secret so you can revoke it alone.
  • Rotate secrets on a schedule and watch the access logs for odd reads.

In more detail

A secrets manager is a managed service for storing, controlling access to, and automatically rotating credentials such as database passwords, API keys, tokens, certificates and private keys, so that applications retrieve them at runtime instead of embedding them in code, images or configuration files. The service encrypts stored values with a key management service key, authorises retrieval with the platform identity system, versions every change, and can run scheduled rotation by invoking a function that creates a new credential and updates both the secret store and the target system. The security value comes from removing long-lived static secrets from build artefacts and repositories, from giving each workload a distinct credential that can be revoked individually, and from producing an audit trail of which identity read which secret and when. Practitioners must still address several hard problems. Workloads need a trustworthy identity to authenticate to the store, which in cloud environments usually means instance or workload identity rather than a bootstrap credential, otherwise the initial secret simply moves rather than disappearing. Caching matters because a rotated credential must not break running services, and rotation must be atomic enough that the old value stops working only after the new one is distributed. Also important are scoping read access so that one compromised workload cannot read every secret, detecting secrets that leak into repositories and images, and monitoring for unusual retrieval patterns.

What you will practise

  • You will be able to explain how runtime retrieval, versioning and automatic rotation remove static credentials from build artefacts.
  • You will be able to scope secret read access so a single compromised workload cannot reach unrelated credentials.
  • You will be able to design a rotation flow that avoids outages from caching and in-flight connections.
  • You will be able to use workload identity to authenticate to the store without a bootstrap secret.
  • You will be able to triage alerts on abnormal retrieval volume, cross-account reads and secret policy changes.
  • You will be able to respond to a leaked secret by rotating, revoking and confirming the old value no longer authenticates.
