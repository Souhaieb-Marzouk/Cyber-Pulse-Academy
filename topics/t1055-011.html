T1055.011 Process Injection: Extra Window Memory Injection

T1055.011Privilege EscalationExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Extra Window Memory injection runs an attacker's code inside another program that is already open. Windows gives every window a small private storage area, called extra window memory. That area can hold a pointer, which is a number showing where something can be found. The attacker puts code in the program's memory and stores its address in that area.

Why should you care?

When code runs inside a trusted program, security tools often trust it too. The attacker may also gain that program's permissions for as long as it runs. If the program is an administrator, the attacker becomes one as well. The method avoids the system calls that defenders watch most closely. A machine you believe is healthy may already be controlled by someone else.

How it works, in plain steps

  1. A program registers a window class, which is a template describing how its windows look and behave.
  2. When registering the class, the program may ask for up to forty bytes of extra memory per window.
  3. Windows attaches that small memory block to each window and provides functions to read and write it.
  4. The attacker writes a payload into shared memory inside the target process, not into the window block.
  5. The attacker stores a pointer, which is a memory address, in the extra window memory of that window.
  6. When the program returns control to that stored address, the attacker's code runs inside the trusted process.

Real-world example

Think of a busy hotel reception desk on a winter evening. Each room has a small pigeonhole behind the counter, just big enough for one folded note. The clerk trusts anything written on those notes. A thief cannot walk behind the counter, so he slips a note into pigeonhole 214 instead. The note says the parcel for that room is in the back storeroom. When the clerk serves room 214, he reads the note and fetches that parcel. The shelf was never meant for that guest, but the clerk does not know. He is still the trusted clerk running a normal errand. The cameras see nothing unusual at all, because the clerk looks completely normal.

Key takeaways

  • Malicious code can run inside a normal program without a new process ever appearing.
  • The window memory block is tiny, so it usually holds a pointer rather than the payload itself.
  • Watch for window behaviour that points outside the known program files on disk.

In more detail

Extra Window Memory injection abuses a small block of storage that Windows attaches to every window belonging to a registered window class. When a class is registered, the developer may request up to 40 bytes of extra window memory for each window instance, and that space is read and written through documented window programming interfaces. Because the block is large enough to hold a 32-bit pointer, an adversary can place a payload elsewhere in the shared sections of a target process, store the address of that payload in the extra window memory, and then hand execution control to it. The payoff is arbitrary code running inside a live, trusted process under that process's security token, which can mean both access to its memory and higher privileges. Detection is difficult because the payload is not written with the heavily monitored cross-process write and remote thread calls, so defenders look instead at unusual cross-process memory activity, anomalous reads and writes of window memory fields, window procedures that point outside any loaded module, and behavioural tooling that flags a window whose callback address is not backed by a mapped image.
