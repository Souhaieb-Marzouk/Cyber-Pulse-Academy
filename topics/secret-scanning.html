Secret Scanning

Secure EngineeringVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Secret scanning looks for passwords, keys, and access tokens that were left in the wrong place. These secrets often end up in source code, build logs, or setup files by mistake. The scanner compares what it finds against patterns for known key formats. It warns you so the secret can be replaced before anyone else uses it.

Why should you care?

A key in your code is like a house key taped to the front door. Anyone who reads the repository can copy it. Deleting the line is not enough, because every clone and backup still holds the old copy. You must treat the key as leaked and replace it. Rotating fast limits the damage an attacker can do.

How it works, in plain steps

  1. A pre-commit hook checks your changes before they are saved to history.
  2. A hook is a small script that runs automatically at a set moment.
  3. It looks for key patterns and for random-looking text with high entropy.
  4. Entropy means the text looks random and unpredictable, which real keys usually do.
  5. Continuous scans then check the whole repository, its history, and its logs.
  6. If a live key is found, you revoke it first and clean up afterwards.

Real-world example

Imagine you write your bank card number on a sticky note and stick it to your monitor. You notice a week later and throw the note away. Is your card safe? No, because anyone who walked past could have photographed it. A secret committed to code works the same way. The right response is not just deleting the line. You call the bank and get a new card.

Key takeaways

  • A secret in version control is leaked; replace it, do not just delete it.
  • Scan before committing, then keep scanning history and build logs.
  • Move secrets into a secrets manager and use short-lived credentials.

In more detail

Secret scanning is the practice of detecting credentials, API keys, tokens, private keys and other sensitive material that has been committed to source control, embedded in build artifacts, written into logs, or left in configuration files and container layers. It operates in three places: pre-commit or pre-receive hooks that block a secret before it enters history, continuous scanning of repositories and pipelines that catches what got through, and artifact and runtime scanning that finds secrets baked into images or exposed through debug endpoints. Detection usually combines high-confidence provider-specific patterns with entropy heuristics and verification calls that confirm whether a discovered credential is still live. For a practising engineer the critical insight is that a secret written to version control should be treated as disclosed, because rewriting history does not undo the copies already fetched by every clone, fork and CI cache. The response is therefore rotation first, cleanup second, and only then rewriting history if it is worth the disruption. Effective programmes pair scanning with a secrets manager, short-lived credentials issued by workload identity, and pre-commit enforcement so the cheap prevention happens before the leak. The usual failure modes are scanning only the default branch, ignoring pipeline logs and issue attachments, alerting into a channel nobody owns, and treating the problem as solved once a scanner is installed while long-lived static keys remain the primary authentication method.

What you will practise

  • You will be able to explain why a credential committed to version control must be treated as disclosed and rotated rather than merely deleted.
  • You will be able to design a layered detection approach covering pre-commit hooks, repository history, pipeline logs and container images.
  • You will be able to distinguish high-confidence provider patterns from entropy-based heuristics and assess the false positive cost of each.
  • You will be able to write an incident runbook for a live credential exposure covering revocation, rotation, scope review and log analysis.
  • You will be able to evaluate whether an organisation's credential strategy reduces secret sprawl or merely detects it after the fact.
  • You will be able to identify the blind spots of a scanner that only inspects the default branch of a repository.
