T1567 Exfiltration Over Web Service

T1567ExfiltrationExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is sending stolen data out through ordinary online services, such as file sharing sites, code repositories, webmail, or workplace chat tools. Because these services are allowed and encrypted, the transfer looks much like normal work traffic. The attacker avoids using strange servers that defenders might block.

Why should you care?

Blocking unknown destinations does not help when the data leaves through a service you already trust. The payload is encrypted, so you cannot read it in transit. You can only compare the size, timing, and frequency of uploads against normal behavior. This is often the last stage before public release, so detection here limits real damage.

How it works, in plain steps

  1. The attacker has already gathered data and put it into one file or archive.
  2. They sign in to a normal cloud or file sharing account, sometimes a free one.
  3. Data is uploaded over an encrypted connection, exactly like a routine backup.
  4. They may instead move files into a personal folder inside company systems.
  5. Sharing links are then sent out, or an outside app is granted access to the files.
  6. Defenders compare upload volume per user against that user's normal pattern.

Real-world example

Think of a postcard versus a sealed courier parcel. Guards at the gate read postcards, so nothing private travels that way. A courier van with a company logo passes without a second look. The thief loads boxes into that van and drives out. Nothing was hidden or forced; the escape route was simply one everyone already trusted.

Key takeaways

  • Watch how much each account uploads, not just where it connects.
  • Review external sharing and app permissions on cloud services regularly.
  • Encrypted traffic still leaves clues in volume, timing, and destination.

In more detail

Exfiltration over a web service moves data out of an environment through legitimate, publicly available or tenant sanctioned online services rather than through adversary controlled infrastructure. The mechanism sidesteps the assumption that egress to unknown destinations is the thing worth blocking. Instead, the transfer goes to a code repository, object storage bucket, file sharing site, paste service, webmail account, messaging platform or collaboration tool that either already appears on an allow list or is indistinguishable in a proxy log from ordinary collaboration. Two patterns dominate. The first uses the provider's public interface or web front end from an endpoint or server, uploading data with an authenticated or anonymous session over an encrypted channel. The second abuses services already provisioned inside the organisation, where the adversary has obtained an account and moves data into a personal folder, shares it externally, or grants a third party application permission to read it. Telemetry sits at three layers. Network and proxy logs show upload volume, session duration and destination service, but the payload is encrypted, so detection depends on comparing volume and frequency against the user's or host's baseline. Cloud and software as a service audit logs are richer: file creation, download, external sharing, permission changes, mailbox rule creation and third party application consent grants are recorded with actor, time and client application. Endpoint telemetry captures the preceding collection and staging steps, such as archiving directories, exporting mailboxes, reading databases or capturing screen content. The challenge is baseline noise. Synchronisation clients, build pipelines, backup products, log shippers and ordinary document collaboration generate large uploads continuously. Investigators distinguish malicious use by whose account is acting, whether the destination or sharing scope is new for that user, whether volume departs sharply from history, whether activity occurs outside working hours or from an unusual client, whether a new application consent appeared shortly before, and whether staging activity is visible on the source host at the same time. Sanctioned service visibility is only useful if the organisation has inventoried which services it actually uses.

What you will practise

  • Explain how legitimate web services and tenant sanctioned applications can serve as exfiltration channels.
  • Use cloud and software as a service audit logs to identify uploads, external sharing and permission changes by actor and client.
  • Baseline per user and per host upload volumes to detect transfers that hide inside encrypted traffic.
  • Detect malicious third party application consent as a precursor to data access and transfer.
  • Correlate endpoint collection and staging artefacts with service side upload activity.
  • Prioritise sanctioned service abuse over generic egress alerts using data classification and account context.
