DET0080 Exploit Public-Facing Application – multi-signal correlation (request → error → post-exploit process/egress)

DET0080Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A public facing application is any service that anyone on the internet can reach. A company website is one example. This detection looks for someone attacking such a service and succeeding. It does that by watching for three things close together in time.

Why should you care?

These services sit on the edge of your network. They are attacked every day by automated tools. Most attempts fail and should be ignored. A few succeed, and those give an attacker a place inside your network. Telling the two apart quickly protects the rest of the estate.

How it works, in plain steps

  1. The web server writes a log line for each request. That line includes the path and response code.
  2. The error log notes crashes, exceptions and requests the application could not handle.
  3. The host sensor records new processes. It also records which process started each one.
  4. The detection looks for a request that the application rejected or failed on.
  5. It then looks for a process whose parent is the web server.
  6. It adds weight for a new outbound connection or a write into a web directory.

Real-world example

Think of a bank teller window with a camera above it. A single odd request is normal, because customers ask strange questions all day. What matters is the sequence. First a strange request, then the till drawer opens by itself. Finally a person walks out of the staff door. Each detail alone means little, but together they tell a clear story.

Key takeaways

  • One layer of evidence is not enough for a public service, because scanning is constant.
  • A web process starting a command shell is the clearest sign that an attack worked.
  • Filter your own scanners first, or the request layer will drown everything else.

In more detail

This detection strategy addresses exploitation of an internet facing service by correlating three signals that are weak on their own: a suspicious or malformed request, a burst of server errors or crashes on the same service, and post exploitation behaviour on the host. It matters because every public application is scanned constantly, so a rule that alerts on exploit style requests alone produces volume no team can triage, while a rule that waits for obvious malware on the host arrives too late. The telemetry that makes correlation possible is the application or reverse proxy access log with request line, response code, source address and a request identifier, the web server error log, and endpoint process creation on the same host showing a shell or interpreter with a web server process as its parent. The pattern that justifies an alert is the same host and account appearing in more than one of those layers inside a short window, especially when a new outbound connection or a file write to a web directory follows. It fails in practice in two directions: noisy scanning activity floods the request layer, and a skilled operator who abuses a legitimate application feature never generates a malformed request at all.

What you will practise

  • Explain why single signal detection on internet facing services produces unusable alert volume.
  • Identify the request, error and process telemetry available on a typical public application host.
  • Correlate a failed exploit attempt with post exploitation process activity on the same host and account.
  • Use change detection on web directories and new outbound connections as confidence boosters.
  • Describe the containment sequence for a suspected compromise of an edge service.
