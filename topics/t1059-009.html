T1059.009 Command and Scripting Interpreter: Cloud API

T1059.009ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Cloud platforms such as AWS, Azure and Google Cloud are managed by sending requests to an interface called an API. An API is a way for one program to ask another program to do something. This technique is about attackers using those requests to run their own commands.

Why should you care?

Once an attacker holds a valid cloud key or session, they can work without touching a single server console. They can start new machines, run commands on existing ones and copy data out. The cloud does record these requests, but only if logging is switched on and someone reviews it.

How it works, in plain steps

  1. The attacker gets hold of a credential, such as a cloud access key or a stolen browser session cookie.
  2. They send requests to the cloud API, often using a command line tool such as the AWS CLI.
  3. Some platforms offer a cloud shell, which is a ready-made terminal that runs inside the browser.
  4. Requests can create new virtual machines or run commands on machines that already exist.
  5. Each request is signed with the credential, so the cloud records which identity made it.
  6. They can also use software libraries written in Python instead of typing commands.

Real-world example

Imagine a large warehouse where nothing moves without an order form. The form is simple. It says who you are, what you want, and it carries a signature stamp. Staff fill the orders without ever meeting anyone. If somebody copies a manager's stamp, their orders look completely normal. A cloud API key works like that stamp. The platform obeys the request, and only the order book shows what really happened.

Key takeaways

  • An API key is a password, so protect it and rotate it like one.
  • Turn on cloud audit logging before you need it, not after an incident.
  • Judge suspicious cloud calls by who made them, from where, and how often.

In more detail

Cloud providers expose nearly every management action as a signed request to a public interface, so an attacker holding a valid credential can execute without ever opening a shell on a server. The same surface is reachable through a provider command line tool, a browser-based cloud shell that runs as a managed container, a PowerShell module, or a software development kit in a language such as Python. Because those calls are authenticated by the credential itself, the identity recorded in the provider audit trail is the stolen user or role, not the attacker. Typical abuse includes creating compute instances, using agent or run-command services to push a script onto an existing instance, invoking serverless functions, changing identity and access management policies, opening network paths, and reading stored secrets. The evidence is the provider audit log, which records the caller identity, the action name, the target resource, the source address, and usually a user agent string. The defender separates abuse from automation by looking at the caller, not the action: a deployment pipeline or infrastructure-as-code role makes predictable, repeated calls from a stable address, while a credential that has never called an enumeration or instance-creation action before, from a new address or an unusual user agent, stands out sharply.
