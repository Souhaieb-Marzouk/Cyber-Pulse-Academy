T1098.001 Account Manipulation: Additional Cloud Credentials

T1098.001PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is a sub-technique of account manipulation, and it means an attacker adds their own login key or password to a cloud account. The extra credential works even after the original stolen password is changed. The attacker then keeps access while the real owner believes the problem is fixed.

Why should you care?

Resetting a password feels like solving the problem, but it does nothing to a key the attacker added. These keys often live for months and are rarely reviewed. If nobody checks for new credentials, the attacker can return quietly long after the incident is closed.

How it works, in plain steps

  1. The attacker gains access to a cloud account that has rights over other identities.
  2. They add a password or certificate to a service principal, which is a non-human application identity.
  3. In infrastructure clouds they create or import an SSH key pair for a server.
  4. They may create a long-lived access key that works for a program instead of a person.
  5. They can also create a console login profile so the identity gets a normal password.
  6. The cloud records each creation, including who asked, from where and for which identity.

Real-world example

Think of a hotel that changes the guest room code after every checkout. A cleaner quietly adds a second code of their own to your door. Reception changes the first code, hands you a new one and marks the room secure. The cleaner still walks in at night using the code nobody knew about.

Key takeaways

  • Rotating passwords is not enough; also review and remove unexpected keys and certificates.
  • Know which service identities should hold credentials and which should not.
  • Alert on credential creation from new addresses, tools or accounts.

In more detail

This sub-technique of account manipulation focuses on adding new authentication material to identities that live in a cloud directory or infrastructure platform, so the adversary keeps a way in that survives password resets. In Azure and Entra ID the additions typically take the form of password or certificate credentials on service principals and application registrations. In infrastructure as a service platforms the same goal is reached through key objects: importing or creating an SSH key pair on a compute service, registering an operating system login key through a cloud command line, creating a long-lived access key for an account, or creating a console login profile so the identity gains a password. The distinguishing feature is that the added credential is new, is owned by the adversary, and is often several steps away from the account the attacker originally compromised. Detection compares audit entries for credential creation against the owning identity's normal behaviour: automation accounts that suddenly hold keys, key creation from an unusual address or client, credentials created outside deployment pipelines, and any use of a credential whose creation was never reviewed.

What you will practise

  • Explain how this sub-technique differs from the parent account manipulation technique.
  • Describe common behaviours, including adding keys to application identities and creating access keys.
  • Identify cloud audit records that show credential creation and the identity it was added to.
  • Distinguish legitimate deployment automation from adversary credential creation.
  • Describe why password rotation alone does not remove access added this way.
