T1587.002 Develop Capabilities: Code Signing Certificates

T1587.002Resource DevelopmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is when an attacker makes their own digital certificate to sign their software. Signing software is like sealing a letter with wax, so the reader knows it was not opened. A real certificate comes from a trusted authority that checks who you are. An attacker can create one for themselves. It looks official, but nobody verified the attacker's identity. Tools and users may still treat signed files as safer.

Why should you care?

People are told to trust signed software, so a signature can be enough to get a file opened. Security tools may also lower their guard for signed code. A self-signed certificate gives an attacker that appearance for almost no cost. It also helps a file survive small changes, because a valid signature looks deliberate rather than damaged. If your team checks only whether a file is signed, and not who signed it, this trick works. Checking the issuer and the certificate chain is the defence.

How it works, in plain steps

  1. The attacker creates a key pair and a certificate naming their own made-up company.
  2. They sign the certificate with its own key instead of asking a trusted authority.
  3. They attach that signature to an executable, a script or an installer.
  4. Some systems and users see a valid signature and treat the file as trustworthy.
  5. Attackers may copy details from real companies so the certificate looks familiar.
  6. Defenders can spot it because the certificate chain does not reach a trusted root.

Real-world example

Imagine a parcel that arrives with a wax seal stamped with a company logo. The seal is unbroken and the logo looks right, so the courier hands it over. What nobody checks is who applied the seal. Anyone with a stamp can press wax. A self-signed certificate is that homemade stamp. It proves the parcel was not opened after sealing, but it proves nothing at all about who sent it. Good practice is to ask who made the stamp, not only whether the wax is whole.

Key takeaways

  • A signature proves integrity, not that the author is trustworthy.
  • Check the issuer and the certificate chain before trusting signed files.
  • Alert on files signed with certificates created shortly before use.

In more detail

This sub-technique covers creation of code signing certificates, usually self-signed, before a payload is signed. Code signing attaches a cryptographic signature to an executable or script so that a recipient can check the stated author and confirm the file has not changed since it was signed. The trust decision is the weak point: many users, and some tools, treat any valid signature as a positive signal without checking whether the issuing authority is one the organisation recognises. A self-signed certificate satisfies that surface check while proving nothing about the author. Detection therefore centres on the certificate itself, including issuer, validity window, subject details, whether the chain reaches a trusted root, and whether one thumbprint appears on unrelated files.

  • Describe why users and security tools may over-trust signed files.
