New Service Installation

Detection StrategyVery hardDetection Strategy

New service installation detection identifies the creation of a Windows service or the modification of an existing service's binary path where the referenced executable is not part of an approved software baseline, which is a common and durable route to both persistence and privileged code execution. The behaviour matters because a service installation requires administrative rights to complete, so it evidences either privileged access already obtained or an elevation technique that has just succeeded, and the resulting service starts automatically or at boot, granting the payload execution in a system context that survives logoff and often survives reboots. The telemetry required is service installation auditing events with the service name, image path, start type and account, process creation records for the binaries that install services including their full command line and parent, file creation or write telemetry for the referenced executable so its origin can be established, and signature and reputation enrichment for that file. The signal survives common evasion because the operating system must still record the service in its configuration store for the service to run; an operator may install it through a signed management binary, through a remote procedure call from another host, through a scripting interface, or by modifying an existing service's path rather than creating a new one, and all of these leave configuration and process evidence. The detection breaks down in practice because legitimate software installs and upgrades services constantly, and software deployment systems, monitoring agents, database engines and security products all create services as part of normal operation. Service names are attacker-chosen and often imitate vendor conventions, so name matching alone is weak, and remote installation through management interfaces can attribute the change to a system account rather than the initiating user, blurring accountability. Durable tuning therefore depends on matching the service image path to a signed binary in an approved directory, on noticing services that point into user-writable locations, temporary directories or script interpreters, and on treating modification of an existing service path as equivalent in severity to creating a new one.

What you will practise

  • Describe the event sources that record service creation and modification and the fields needed to assess risk.
  • Evaluate a new service by image path, signer, parent process and the account the service will run as.
  • Detect modification of an existing service binary path as a persistence technique distinct from creation.
  • Recognise service installations that reference scripting interpreters, temporary directories or remote paths.
  • Correlate service creation with the process that installed it and reconstruct the execution chain afterwards.
  • Recommend least privilege controls that constrain who may install services and from where.
