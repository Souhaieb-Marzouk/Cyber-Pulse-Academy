DET0302 Port-knock → rule/daemon change → first successful connect (T1205.001)

DET0302Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Port knocking is a secret pattern of connection attempts. The computer ignores each attempt. If the attempts arrive in the right order, the computer quietly opens a real service for that visitor. This rule looks for that whole story. It watches for many ignored attempts from one address. It then looks for a change on the target and one successful connection from the same address.

Why should you care?

A hidden service is hard to find by scanning. Defenders often think a closed port means a safe port. Port knocking can quietly open a management service that then accepts a remote login. The knock itself is silent by design. The only way to catch it is to watch the order of events rather than any single alert.

How it works, in plain steps

  1. The firewall logs each connection it refuses, with the source address, the port and the time.
  2. The rule groups refusals from the same source address. It checks whether several different closed ports were tried in order.
  3. On the target host it watches for changes to firewall rules or to a small service that listens quietly.
  4. It waits for an allowed connection or a successful login from that same source address shortly afterwards.
  5. It links the knock, the change and the login into one case and raises a single alert.
  6. Analysts then review what that service is and whether the source address is known.

Real-world example

Think of a door with three plain buttons and no sign. Nobody reacts to one press. If you press them in a special order, a latch clicks open for ten seconds. The building log would show three wasted presses. Then it would show one person walking straight in. The presses alone mean nothing. The open door right after them is the story.

Key takeaways

  • Port knocking hides a service behind a secret order of refused connections.
  • Detection needs refused connection logs, configuration change records and the first successful connection, joined by source address.
  • If drops are not logged on your firewalls, this detection is impossible, so check that first.

In more detail

This detection strategy covers the port knock sequence pattern of T1205.001, where an adversary sends a specific series of connection attempts to closed ports and the host or network device responds by opening access, after which the first successful connection to the now exposed service arrives. It matters because a port knock is deliberately designed to look like background scan noise, and it turns a hardened host into one that briefly listens on a hidden port for a single trusted source. The telemetry that makes it visible is the combination of firewall or packet filter deny logs showing an ordered series of rejected connection attempts from one source, configuration change records showing a rule or daemon edit on the target, and the subsequent allow and successful connection from that same source. In practice this detection fails when the firewall does not log dropped traffic, when virtual machine or cloud security group changes are not captured, or when the knock is spread over hours so that the correlation window misses it.

What you will practise

  • Explain what port knocking is and how it differs from an ordinary port scan.
  • Identify the deny logs, configuration change records and allow logs needed for this correlation.
  • Build a rule that groups refused connections by source address and checks for an ordered sequence of ports.
  • Correlate a detected sequence with a later configuration change or authentication on the target host.
  • Assess which network devices and hosts in your environment log dropped traffic and which do not.
  • Describe containment steps such as blocking the source and reviewing what the opened service exposed.
