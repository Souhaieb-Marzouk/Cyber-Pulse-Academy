DET0318 Detection Strategy for Exfiltration to Code Repository

DET0318Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for company data being sent to an online code hosting service, such as a public repository site. People use these services to store source code. An attacker can use the same service to hide stolen files inside a project.

Why should you care?

Most networks allow code hosting sites, so this route often bypasses blocks that stop unknown file sharing services. Traffic is encrypted, so a network scanner cannot read the file. The upload also leaves a record on the service side, which you can request. Catching it early limits how much data leaves.

How it works, in plain steps

  1. A developer or an attacker sends a request that writes data into a remote project, called a push.
  2. The web gateway logs the destination address, the path and the amount of data sent.
  3. The code hosting service keeps its own audit log of who pushed what, and when.
  4. Your platform collects both the gateway logs and any organisation level audit events you can export.
  5. The rule looks for pushes from accounts or networks that normally do not push, especially with large data volumes.
  6. Analysts then compare the actor, the repository and the timing against the list of approved developers.

Real-world example

Think of a company that lets staff post parcels through a courier everyone trusts. Most parcels are spare parts. Someone starts sending sealed boxes of company files through that same courier. The loading bay trusts the courier, so it never checks. The audit is simply the courier's own delivery book.

Key takeaways

  • Trusted code hosting services give attackers a route that is usually allowed.
  • Push volume and actor identity matter more than the destination address.
  • Export the service side audit log so you can confirm what was uploaded.

In more detail

This strategy detects data being moved out of the environment into a source code hosting service, the exfiltration over web service behaviour recorded in the assignment as t1567-001. The pattern is attractive to attackers because code repositories are usually allowed through egress controls, accept arbitrary file types inside a commit, and can be written to with a token that looks like ordinary developer traffic. Detection depends on joining proxy or firewall records of push operations to code hosting domains with repository audit events that name the actor, the repository and the volume of change. The practical difficulty is that your engineering teams do the same thing legitimately with personal repositories, so the rule has to separate sanctioned organisation repositories and identities from everything else.

What you will practise

  • Explain why code hosting services are used for data exfiltration
  • Identify gateway, identity and repository audit telemetry relevant to pushes
  • Distinguish sanctioned engineering activity from anomalous uploads
  • Write a detection that scores destination, actor and transfer volume together
  • Describe the request process for repository audit data during an investigation
  • Assess which data classification levels require this rule to run at high severity
