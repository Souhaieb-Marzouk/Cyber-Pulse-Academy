LSASS Handle Access

Detection StrategyExtremeDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

LSASS is a Windows process that holds login secrets in memory while people are signed in. A handle is a request for permission to work with another running program. This detection looks for unusual programs asking for a handle to LSASS. It focuses on requests that allow reading its memory, the step before stealing passwords.

Why should you care?

If an attacker reads the memory of that process, they can walk away with password hashes or login tickets. Those can be reused to sign in as other people. They also allow movement between machines, without touching the victim again. This happens early, right after an intruder gets a foothold. Catching it early breaks the chain.

How it works, in plain steps

  1. When you sign in, Windows stores secret material inside the LSASS process so other programs can use it.
  2. An attacker who already has a foothold asks the operating system for a handle to that process.
  3. The request includes which rights are wanted, and reading memory is one of those rights.
  4. With auditing or an endpoint sensor in place, that handle request is recorded with both programs named.
  5. Your detection filters out the known security and backup products that legitimately read process memory.
  6. What remains, especially an unsigned program started from a user folder, is treated as urgent.

Real-world example

A hospital keeps a locked office with the master keys to every ward. Staff walk past it all day without a thought. One afternoon a visitor in a borrowed uniform asks the desk for that key. They say they only want to look inside. The request itself is the warning. No thief needs to break the door down when the key can be handed over politely.

Key takeaways

  • The LSASS process is a prime target because login secrets live inside it.
  • An unsigned program in a user folder reading that process is a red flag.
  • You need a sensor or special auditing turned on, because ordinary logs miss it.

In more detail

LSASS handle access detection identifies non-standard processes opening a handle to the Local Security Authority Subsystem Service with access rights that permit reading its memory, which is the prerequisite step for extracting cached credential material on a Windows host. The behaviour is high value to an attacker because a successful read yields password hashes, Kerberos tickets or plaintext secrets that can be reused elsewhere in the estate, so it typically appears in the credential access phase shortly after a foothold and before lateral movement. The telemetry required is kernel-level process access auditing, delivered either through a native audit policy that emits object access events for the target process or through an endpoint detection sensor that records source process, target process, requested access mask and granted access, alongside process creation records so the requesting binary can be resolved to a file path, signer and parent. The signal survives common evasion because the access itself is the operation the attacker needs; even fully fileless tooling that never writes a payload to disk must still open the handle and request read permissions from the kernel. Tools that duplicate an existing handle from a privileged process or that inject into a trusted signed binary create a different anomaly in the same telemetry family, where the request originates from an unexpected source image. The detection breaks down in practice because legitimate security products, backup agents, monitoring tools and administrative utilities all read process memory, so the access mask alone is not sufficient and must be combined with source process reputation, signer validity, and whether the source executable lives in a user-writable directory. Sensor coverage is also uneven: without kernel driver telemetry or configured audit policy the event may simply not exist, and access mask values reported by third-party tools vary, so tuning must be done against the actual field semantics of the deployed pipeline rather than against a generic specification.

What you will practise

  • Explain which Windows access rights indicate an attempt to read process memory versus normal handle usage, and why the distinction drives severity.
  • Build a query that returns source process, requested access mask and signer status for handle opens against the credential process.
  • Establish a benign baseline of security products, backup agents and management tooling that legitimately read process memory in your estate.
  • Detect handle duplication and injection-into-trusted-process variants that do not originate from an obvious credential dumping binary.
  • Decide when to escalate to host isolation based on concurrent signals such as new service creation or outbound authentication from the same host.
  • Describe which audit policies and sensor capabilities must be deployed before this detection has any chance of firing.
