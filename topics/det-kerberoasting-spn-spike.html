Kerberoasting SPN Request Spike

Detection StrategyExtremeDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Kerberos is the system Windows uses to prove who you are on a network. A service ticket is a small pass the domain controller issues so you can use a service. A service principal name is the label for that service. This detection flags one account asking for tickets to an unusual number of different services in a short time.

Why should you care?

Every service ticket is encrypted with the password key of the service account behind it. An attacker may request any ticket they are entitled to receive. They take those tickets away and crack the keys offline at their own pace. No server is touched, so nothing looks broken. Spotting the broad sweep of requests is often your only early warning.

How it works, in plain steps

  1. Every service account in a directory has a name, and clients use that name to ask for access.
  2. An attacker first lists the service names that exist, then requests a ticket for each one.
  3. The domain controller issues the tickets, because any signed-in account may ask for them.
  4. Each ticket is encrypted with the target service account's secret, so it can be cracked offline.
  5. Your detection counts how many distinct services one account asked for inside a short window.
  6. One account asking for many services is urgent, but spikes from machine accounts rank lower.

Real-world example

Think of a hotel reception desk that hands out spare keys. Any guest may ask for the key to the room they booked. Now imagine one guest asking for a copy of every room key in the building. They take the whole set away. Nothing was stolen on the spot, because the plan is to copy the keys elsewhere. That is why the number of requests matters.

Key takeaways

  • A request for many service tickets by one account is a strong warning sign.
  • Real users rarely sweep a whole directory, so weight human accounts as high risk.
  • Rotate the passwords of targeted service accounts once an alert is confirmed.

In more detail

Kerberoasting SPN request spike detection identifies a single account requesting service tickets for an abnormal number and diversity of service principal names within a short window, which is the defining pattern of offline cracking of service account credentials in a Kerberos environment. The behaviour matters because the request path is entirely legitimate: any authenticated principal may ask the domain controller for a service ticket, and the returned ticket is encrypted with the service account's key, so an operator can take the encrypted material away and crack it at leisure without touching the target host at all. The telemetry required is domain controller Kerberos service ticket issuance events including the requesting account, the target service name, encryption type and source address, combined with account metadata that identifies which of the targeted principals are user accounts with registered service names rather than genuine computer accounts, and privilege data showing which of those accounts hold elevated rights. The signal survives common evasion because the volume and diversity of requests is what distinguishes the attack; an operator who requests a single ticket for a single service looks exactly like normal application behaviour, so the detection is strongest against the broad sweep and weaker against careful targeting. Requesting only weak encryption types, or filtering for targets whose keys are crackable, still produces a cluster of requests that differs from baseline in target diversity and encryption negotiation. The detection breaks down in practice because service ticket volume is enormous in some environments and legitimate application servers, monitoring platforms, backup software and vulnerability scanners request tickets across wide service populations every day. Ticketing patterns are also bursty and change with business cycles, so static thresholds age badly. Effective tuning requires per-requesting-account baselines, suppression of host and service accounts that behave like scanners, and a focus on requests originating from workstation subnets or interactive user sessions, where wide service ticket acquisition has no routine explanation.

What you will practise

  • Explain the Kerberos service ticket request flow and why the request itself is authorised and therefore invisible to access control.
  • Build a per-account baseline of service ticket request volume, target diversity and encryption type distribution.
  • Distinguish interactive user requests from machine and service account requests and prioritise the former.
  • Identify which targeted service accounts hold elevated privileges so that crackable findings can be risk ranked.
  • Describe the response options for a suspected roasting event, including service account credential rotation and detection of subsequent reuse.
  • Assess how encryption type negotiation and targeted requests change the detectability of the technique.
