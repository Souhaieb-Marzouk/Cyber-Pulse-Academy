T1547.006 Boot or Logon Autostart Execution: Kernel Modules and Extensions

T1547.006PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A kernel module is a piece of code that can be added to the deepest part of the operating system, called the kernel. On Linux these are loadable kernel modules; on macOS they are kernel extensions. Attackers can use them to start code at boot and to hide what they are doing.

Why should you care?

The kernel controls memory, files, and network traffic. Code running there outranks every security tool on the computer. It can hide its own files and processes, so the tools you trust may report that everything is fine. Malicious kernel code may also remove or change log entries. This is why module changes deserve careful review, and why a live scan is not always enough.

How it works, in plain steps

  1. The kernel loads extra code on demand, and some of that code is loaded automatically at every boot.
  2. On Linux, module files live in a system directory and are listed in configuration so they load at startup.
  3. On macOS, kernel extensions are signed and verified before the system agrees to load them.
  4. An attacker adds or replaces a module so their code runs with the highest privileges at boot.
  5. Once loaded, the module can hide files, processes, and connections from normal system tools.
  6. Detection uses a known-good module list, signature checks, and offline analysis of the disk.

Real-world example

Think of a building where you can add a new switch to the basement control panel. The switch can redirect any wire in the building. Someone adds a switch that hides one office from the floor plan, so visitors, cleaners, and even the security guard walk past a door that is no longer drawn on the map.

Key takeaways

  • Code at kernel level can hide its own traces, so treat a clean live scan as weak evidence.
  • Keep an inventory of expected modules and check signatures regularly on Linux and macOS.
  • If you suspect a kernel rootkit, analyse a copy of the disk instead of trusting the running system.

In more detail

Kernel modules and extensions are the mechanism by which code enters the most privileged layer of the operating system, and attackers use it for both boot-time persistence and concealment. On Linux a loadable kernel module can be placed in the module tree and referenced from a configuration file so it loads on every boot; because it executes in kernel space, it can filter system calls and hide files, processes, and network sockets from user-space tools. macOS kernel extensions work in the same spirit but are constrained by code signing: kexts must be signed with a developer identity that Apple authorises, and with System Integrity Protection enabled the signature is checked before the extension is added to the auxiliary kernel collection. Since macOS Catalina, kernel extensions are deprecated in favour of system extensions, yet they remain supported as legacy components. Detection relies on a maintained inventory of expected modules, signature or authenticity checks, file integrity monitoring of the module directories, and offline inspection when a rootkit is suspected, because a kernel-level rootkit can hide the very evidence a live scan would collect.

What you will practise

  • Define loadable kernel modules and kernel extensions, and explain why they run at the highest privilege level.
  • Explain how a module can be registered so the kernel loads it at every boot on Linux.
  • Describe how macOS verifies kernel extension signatures and what changed with system extensions.
  • Detect unauthorized module loading using inventory comparison, signature checks, and file integrity monitoring.
  • Explain why kernel-level code can conceal files, processes, and network activity from live tools.
  • Plan an offline investigation for a suspected kernel-mode rootkit.
