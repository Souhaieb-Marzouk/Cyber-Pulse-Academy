T1546.009 Event Triggered Execution: AppCert DLLs

T1546.009PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This technique hides an attacker's code inside a shared library that Windows loads when any program starts another program. The list of these libraries is stored in one registry value. Because starting programs happens all the time, the attacker's code runs again and again. This is a sub-technique because one specific Windows function, and not a sign in, sets the code off.

Why should you care?

A single registry value can place the attacker's code inside many different processes on the same computer. Some of those processes run with higher rights, so the same trick can also raise the attacker's level of access. The change is small and often goes unnoticed, because no new file has to appear at startup. Ignoring it means the intruder keeps coming back after every cleanup.

How it works, in plain steps

  1. Windows keeps a list of extra libraries in a registry key under the Session Manager area.
  2. Every time a program asks Windows to start another program, it calls a function such as CreateProcess.
  3. For those calls, Windows loads each library named in the list into the new process.
  4. An attacker adds the path of their own library to the list, which needs administrator rights.
  5. The library then runs inside many processes, so the code returns after each restart.
  6. Because some of those processes hold higher rights, the same entry can also increase the attacker's access.

Real-world example

Imagine a post office with one notice board. The board says that whenever a clerk opens a new counter, a named extra worker must be let in to help. Every clerk reads the same board, so that worker walks into every counter in the building without a key of their own. If someone rewrites the name on the board, a stranger enters everywhere at once. The application certificate list is that board, and one small registry value decides who joins every new process.

Key takeaways

  • One registry value, named AppCertDLLs, controls libraries loaded into many new processes.
  • Watch for the same unsigned library loaded by unrelated programs.
  • The list is empty by default, so every entry deserves an explanation.

In more detail

The AppCertDLLs value under the Session Manager area of the registry holds a list of libraries that Windows loads into every process which calls one of the process creation interfaces, such as CreateProcess, CreateProcessAsUser, CreateProcessWithTokenW or WinExec. Because starting a child process is so common on a desktop, a library added to that list is loaded into a wide range of processes, giving the adversary both persistence across reboots and a chance to run inside a more privileged process. The artefacts are writes to that specific registry value, an unsigned module appearing in image load records across many unrelated process identifiers, and modules loaded from user-writable folders rather than the system directory. The value is empty on a default modern Windows build, so any entry is worth explaining; legitimate entries are rare and usually tied to a documented compatibility or security product.

What you will practise

  • Explain which Windows functions cause application certificate libraries to load.
  • Describe how the same registry entry provides both persistence and higher rights.
  • Identify the registry value and the telemetry that record this change.
  • Recognise an unsigned library loaded by many unrelated processes.
  • Compare this sub-technique with its parent and with AppInit libraries.
  • Suggest one control that prevents unauthorised entries in that value.
