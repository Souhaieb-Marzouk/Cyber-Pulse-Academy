T1021.004 Remote Services: SSH

T1021.004Lateral MovementVery hardTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Secure Shell, usually shortened to SSH (Secure Shell), is the standard way to log in to Linux and other Unix-like computers over a network. It gives you an encrypted text session, so nobody watching the network can read what you type. It can also run a single command or copy files.

Why should you care?

SSH runs on almost every server and network device, so it is always available to an intruder. It can authenticate with a password or with a key file. A stolen key lets an attacker log in without knowing any password at all. Because the session is encrypted, a network monitor sees only scrambled data. Your only real evidence is on the computers themselves, so you must collect it before it is deleted.

How it works, in plain steps

  1. A server runs an SSH service, which waits for connections on a network port.
  2. A user or an attacker connects and proves who they are, either with a password or a key file.
  3. The server accepts the proof and opens an encrypted session, so commands now run as that account.
  4. From that machine the intruder can reach the next one, especially if a trusted key sits there.
  5. Each hop leaves a login record on the target and a client record on the source machine.

Real-world example

Picture an apartment building where the front door, the basement and the roof all use the same key. A cleaner loses that key, and a stranger picks it up. There is no forced entry, no broken window and no alarm, only a person quietly using doors that open because the key fits. SSH with shared keys behaves the same way. One copied key file can open dozens of servers, and each login looks completely ordinary to the machine.

Key takeaways

  • SSH logins are encrypted, so network monitoring cannot tell you what happened inside a session.
  • Check who connects to whom, and treat a service account opening a shell as suspicious.
  • Protect and rotate key files, because a stolen key needs no password to work.

In more detail

Secure Shell is the standard encrypted remote login and command execution protocol on Unix-like systems, and it is also widely enabled on network devices, hypervisors, and appliances. It supports interactive sessions, single command execution, port forwarding, and agent-based authentication, all of which an adversary can use after obtaining valid credentials or private keys. Lateral movement commonly begins from a host the adversary already controls, using either a stolen key or a replayed password, and then proceeds host to host along the paths that trust relationships and automation accounts permit. Because SSH traffic is encrypted and the daemon runs on nearly every server, network inspection alone yields little. Useful artefacts are on the endpoints. The SSH daemon logs accepted and failed authentications together with the source address, the account, and the authentication method used, which distinguishes public key acceptance from password acceptance. The client host records the execution of the SSH client process with its full argument vector, exposing destination hosts and any remote command string, and shell history may show the same. Where the client host retains user key material, file access to private keys appears in file integrity monitoring or process telemetry. Host-based session recording, if deployed, captures the interactive commands themselves, and the target's process accounting shows what executed inside the session. Legitimate SSH use is continuous in most environments, especially for automation, deployment, and monitoring. The distinguishing features are direction and account fit: administrative hosts connecting outward is normal, application servers connecting to unrelated database or domain infrastructure is not, and interactive sessions by service accounts that normally only run automation are strong indicators. Failed authentication bursts followed by a success, connection attempts to many hosts from one source, and use of keys that belong to a different host all warrant escalation.

What you will practise

  • Explain how accepted key and password authentication records differ and what each proves about adversary access.
  • Reconstruct an SSH movement path from client process arguments, daemon logs, and session recordings on multiple hosts.
  • Identify automation accounts and trust relationships that create silent, credential-driven movement paths.
  • Correlate failed authentication bursts with subsequent successful logins to detect credential-driven approaches.
  • Distinguish legitimate deployment and monitoring traffic from interactive adversary sessions using timing and target fit.
  • Map SSH lateral movement to ATT&CK and rank key management, bastion, and segmentation controls by effectiveness.
