T1546.016 Event Triggered Execution: Installer Packages

T1546.016PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This technique hides an attacker's code inside an installer package. An installer package carries the files and the instructions needed to put a program on a computer. The instructions include small scripts that run before and after the copy. Those scripts often run with the high rights the user gave the installer. An attacker edits a script or builds a package that looks real. The script then starts the attacker's program. This sub-technique differs from its parent because the installation itself, and not a sign in, sets off the code.

Why should you care?

People expect an installer to change the system, so they grant it high rights without much thought. A script inside the package inherits those rights and can install a service that starts at every boot. The package may carry a real program as a disguise, so the user sees the expected result. If you never check package signatures or script behaviour, one installation can leave an attacker permanently on the machine.

How it works, in plain steps

  1. An installer package holds the files and the instructions needed to put a program on a machine.
  2. The instructions include scripts that run before the copy and after it finishes.
  3. Those scripts often run with the high rights that the user granted to the installer.
  4. Each system uses its own format, such as pkg on macOS, msi on Windows and deb on Linux.
  5. An attacker edits the script inside a real package, or builds a package that looks genuine.
  6. The script then starts the attacker's program or installs a service that starts at boot.

Real-world example

Imagine a furniture delivery. The van brings a wardrobe and a note that says before assembly, unlock the store room. The note carries the shop stamp, so the fitters follow it without question. If someone swaps the note inside the van, the fitters still obey and open the store room. Installer scripts are that note. They arrive with the package and run with the trust you gave the installer.

Key takeaways

  • Installer packages carry scripts that run before and after the copy.
  • Those scripts often inherit the high rights granted to the installer.
  • Check the signature of a package and watch what its scripts start.

In more detail

Installer packages bundle the files and the instructions an operating system needs to place software on a host, and those instructions include scripts that run before and after the copy step. On macOS a package uses preinstall and postinstall scripts that execute as root, on Linux the deb and rpm formats use maintainer scripts named preinst, postinst, prerm and postrm that also run as root, and on Windows the installer service runs custom actions described inside the package. Because the user grants elevation to the installer, those scripts inherit the same high level of rights. An adversary modifies the script inside a genuine-looking package, or builds a package that imitates a trusted one, so the script runs their payload or installs a service, daemon or launch daemon that starts at boot. The artefacts are installation events, unexpected child processes spawned by the installer process, files written outside the expected application directory, and a package or payload that fails a signature or notarisation check. Installers legitimately spawn processes, so content, signature and destination are the discriminators rather than the spawn alone.

What you will practise

  • Explain what an installer package contains on each major platform.
  • Describe when pre-install and post-install scripts run and with what rights.
  • Name the script types used by macOS, Windows and Linux packages.
  • Identify telemetry for installation events and unexpected child processes.
  • Explain how a package script can install a service that persists.
  • Verify a package with signature and notarisation checks.
