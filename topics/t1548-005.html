T1548.005 Abuse Elevation Control Mechanism: Temporary Elevated Cloud Access

T1548.005Privilege EscalationExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Cloud systems let an account borrow extra permissions for a short time. Examples are a temporary admin window, acting as another account, or handing a role to a service. This technique is when an attacker uses those borrowing features instead of creating a new permanent admin.

Why should you care?

Borrowed permissions are real permissions, so the attacker can reach data and services far beyond their own account. Because the feature is designed for daily use, the activity often looks normal in logs. Blocking it too late means the attacker has already reached storage, mail, or databases.

How it works, in plain steps

  1. A cloud administrator grants an account the right to request extra roles for a short period.
  2. The account asks for the role, and the system either approves it automatically or waits for a person.
  3. Some setups let an identity create temporary keys or act fully as another account.
  4. Other setups let an identity attach a powerful role to a service it controls.
  5. The attacker then drives that service, so actions appear to come from the service, not the attacker.
  6. Every step is a normal feature call, so only careful baseline comparison shows the abuse.

Real-world example

Think of a hotel where the front desk can issue a day pass to the spa or the gym. The pass is valid, printed by the real system, and it expires at midnight. A guest who learns how to request passes can spend the day in rooms they never paid for. Nothing was broken into, and every door accepted a genuine pass. The hotel only notices by comparing who asked for which pass, and when.

Key takeaways

  • Borrowed cloud permissions are genuine permissions, so treat them as sensitive access.
  • Impersonation hides the real actor because actions are logged under the target identity.
  • Log and review who requests temporary roles, and alert on unusual pairs of accounts.

In more detail

This sub-technique describes adversaries abusing the permission structures that cloud providers build for short-term privilege, rather than granting themselves permanent roles. Just-in-time access requests, account impersonation, and role passing all create a token or session that carries rights the requesting identity does not normally hold. Abuse is subtle because every action uses a legitimate provider feature: a user with the token creator role mints credentials for a service account, a service account with domain wide delegation acts as a mailbox owner, or an identity with the role passing permission attaches a powerful role to a resource it controls and then drives that resource. The artefacts are control plane audit records such as role assumption, token generation and impersonation events, split across the identity provider and the resource provider. The discriminator is baseline: compare the requesting principal, the target identity, the source address and the time of day against normal patterns, because a denied or unusual pairing stands out even though each individual call is valid.

What you will practise

  • Explain what just-in-time cloud access, impersonation and role passing are.
  • Describe how an attacker gains short-term elevated access without creating a permanent role.
  • Identify the cloud audit events that record token generation, role assumption and impersonation.
  • Explain why impersonated actions can be misattributed to the target account.
  • List the configuration choices that keep these features from becoming escalation paths.
