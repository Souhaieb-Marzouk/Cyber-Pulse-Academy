T1553.003 Subvert Trust Controls: SIP and Trust Provider Hijacking

T1553.003Defense ImpairmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

When Windows checks a file signature, it asks a small helper component to do the work. These helpers are called SIPs, short for Subject Interface Packages. This sub-technique is when an attacker replaces or reconfigures a helper so it reports a bad signature as good.

Why should you care?

If the checker itself can be changed, then every signature check on the machine becomes unreliable. Harmful files and drivers can pass rules that should block them. The change is only a registry entry, so it is quick and quiet. Detecting it early is much easier than cleaning up afterwards.

How it works, in plain steps

  1. A program asks Windows to verify a file signature through one standard interface.
  2. Windows looks up a registered helper package that knows how to read that format.
  3. The helper reads the signature and returns either a pass or a fail answer.
  4. An attacker edits the registry entry so a different library is loaded instead.
  5. The replacement library reports success for files whose signatures are actually bad.
  6. Application control and scanning tools then accept that false answer as truth.

Real-world example

Imagine a bank where a clerk checks signatures on cheques. The clerk does not examine them personally but passes each one to a specialist seated behind a screen. If someone swaps the specialist for an accomplice who approves every cheque, the clerk keeps working exactly as before. The cheques are still checked, the process still looks normal, and every forged signature passes.

Key takeaways

  • Signature verification on Windows depends on registered helper components.
  • Treat unexpected changes to those registrations as a serious integrity event.
  • Compare registered values against a known-good baseline from a clean system.

In more detail

On Windows, Authenticode signature checking runs through the WinVerifyTrust interface, which delegates the actual work to Subject Interface Packages, known as SIPs. Each SIP understands one file format, such as portable executables, PowerShell scripts or installers, and each is registered under a globally unique identifier with a dynamic link library and an entry point function that performs the verification. This sub-technique tampers with that registration so the trust decision is made by adversary-controlled code, or so a signature that should fail is reported as valid. The behaviour is a registry modification, so the parent technique's broader focus on trust policy and certificates becomes a specific hunt for changes to SIP registration keys and to the trust provider settings that specify which providers validate which actions. Legitimate updates to these values come from operating system servicing, which is what makes unusual or unexpected values stand out.

What you will practise

  • Explain what WinVerifyTrust does during a Windows signature check.
  • Describe the role of Subject Interface Packages in validating different file formats.
  • Explain how this sub-technique differs from simply stealing a signing certificate.
  • Identify the registry locations where SIP and trust provider settings are stored.
  • Recommend baselining and monitoring so unexpected signature component changes are visible.
