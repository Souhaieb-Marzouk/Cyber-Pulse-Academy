DET0533 Detection Strategy for Poisoned Pipeline Execution via SaaS CI/CD Workflows

DET0533Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A build pipeline is the automatic system that turns code into a released product. This detection looks for changes that make the pipeline run code from an untrusted source. Attackers do this to reach the secrets the pipeline uses, such as deployment keys. The alert fires when a pipeline definition changes without review, or when a run is triggered by outside code.

Why should you care?

The build system often holds the highest value secrets in a company. It can sign and publish software that customers trust. If an attacker runs code inside a pipeline, they can change the product itself, not just one server. The change needed is often a few lines in a text file, so it can look like normal work. Watching the definition, the trigger and the secrets together is how you spot the difference.

How it works, in plain steps

  1. The version control audit log records each commit that changes a pipeline definition file, with the author and the branch.
  2. The build platform records each run with its trigger type, source branch, actor and target environment.
  3. The rule joins those records and looks for a definition change that reached the default branch without the normal review.
  4. It adds a second condition for runs triggered by a pull request from a fork or by an untrusted contributor.
  5. Cloud identity records show which short lived tokens the runner received, and which secrets it could read.
  6. The alert names the changed file, the author, the run and the secrets at risk. The responder can then rotate those secrets first.

Real-world example

Think of a factory that makes medicine. The recipe book is kept in a locked office, and the machines trust the recipe completely. Someone edits one line so the machine adds the wrong ingredient. The machine follows the book exactly as written. The detection is not about the medicine that comes out. It is about who wrote in the recipe book, and when.

Key takeaways

  • A build pipeline usually holds the secrets that protect production, so it is a high value target.
  • The signal is a pipeline change without review, or a run triggered by untrusted code.
  • Rotate the secrets a compromised run could read before you investigate anything else.

In more detail

This detection strategy targets poisoned pipeline execution, where an attacker changes a build or deployment definition so that untrusted input runs with the pipeline's rights and secrets. The change is often a small edit to a workflow file on the default branch, or a trigger that runs on a pull request from a fork, and the result is code execution inside the build environment with access to deployment credentials. Version control audit logs for pipeline definition changes, build run metadata showing the trigger type and the actor, and cloud identity records for tokens issued to the runner supply the evidence. The rule fails because developers edit pipelines every day, so change context and approval status must be correlated rather than the edit alone.

What you will practise

  • Explain why a build pipeline is a high value target for attackers
  • Identify the audit fields for commits that change pipeline definition files, including author, branch and review state
  • Describe which trigger types let code from a fork or an outside contributor run inside the pipeline
  • Correlate a definition change with the runs and tokens it produced
  • Explain why secret rotation comes before deeper investigation after a suspected pipeline compromise
  • Choose filters that allow routine pipeline work without hiding unreviewed production changes
