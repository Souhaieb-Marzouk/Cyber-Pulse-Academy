DET0010 Behavioral Detection of Event Triggered Execution Across Platforms

DET0010Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An event trigger is a rule that tells the system to run something when a certain thing happens. Many programs use this, for example to start a helper when you log in. An attacker can add their own rule, so their code runs automatically later. This detection watches the places where such rules are stored.

Why should you care?

The attacker does not need to keep a program running. The system starts the code at the right moment, and it looks like part of normal startup. The code inherits the rights of whatever fired the trigger, which is often a powerful service. Because the trigger may only fire at the next login or restart, the gap between the setup and the effect gives you time to respond. That time is only useful if you catch the setup.

How it works, in plain steps

  1. Your endpoint agent records writes to the registry keys and files where trigger definitions are stored.
  2. It records the process that made each write, along with its parent and the account it used.
  3. The detection matches those writes against a list of trigger locations that are common attack targets.
  4. It compares the new entry with a baseline, so a first time entry is treated as more interesting than a known one.
  5. It then waits for the trigger to fire and matches the resulting process start back to the saved record.
  6. The linked pair of registration and execution produces one alert that shows both halves of the story.

Real-world example

Think of a door that opens when a smoke alarm sounds. A maintenance worker can add a new device to the alarm system. The system then opens the door for whoever is standing there. Nobody forced the door. The alarm did exactly what it was told.

Key takeaways

  • Event triggered execution runs through normal system mechanisms, not through a launched attack tool.
  • Watch the registration points, because the payload may not run for hours or days.
  • Linking a new registration to its later execution turns two weak signals into one strong one.

In more detail

This strategy detects event triggered execution, where an adversary attaches their code to a system event so the operating system runs it for them (T1546, Event Triggered Execution). Instead of launching a program, the attacker registers an action that fires later, for example when a user logs on, when a debugger starts, when a shell opens, or when a container lifecycle stage runs. This matters because the execution inherits the trust and privileges of the host process that fires the trigger, and because nothing runs until the event occurs, which defeats detections that only watch for a process starting. Detection depends on monitoring registration points rather than payloads, and the practical difficulty is volume: legitimate software registers at the same locations daily.

What you will practise

  • Define event triggered execution and explain how it differs from direct process execution.
  • Identify the system registration points commonly abused for persistent triggers.
  • Describe the telemetry needed to observe both registration and later execution.
  • Explain how a baseline of expected registrations reduces false positives.
  • Correlate a trigger registration with the process started when the event fires.
  • Compare trigger mechanisms across operating systems and platforms to build broad coverage.
