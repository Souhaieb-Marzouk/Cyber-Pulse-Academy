DET0023 Obfuscated Binary Unpacking Detection via Behavioral Patterns

DET0023Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Packing means squeezing a program into a smaller or scrambled form, like a suitcase with a lock. The program must unpack itself in memory before it can run. This detection looks for that unpacking behaviour rather than the file itself. It catches hidden code while it is waking up.

Why should you care?

A packed file often looks like nothing at all, so file based checks miss it. The unpacking moment is when the code finally becomes active and visible in memory. That moment is a rare and useful chance to see what is really running. It does not depend on knowing the packer or its name. If you watch behaviour, you also catch packers you have never seen before.

How it works, in plain steps

  1. The sensor records process starts, memory allocation calls and loaded modules for each running process.
  2. The rule watches for a process asking for memory that can be both written and executed. Normal programs rarely do this.
  3. It checks whether that process came from a temporary or user writable folder instead of a program directory.
  4. It then looks for a module load, or execution starting at an address, that has no matching file on disk.
  5. These facts are grouped by process identifier, so a single process must show the whole sequence to raise an alert.
  6. The alert shows the parent process, the file path and the memory facts. An analyst can then decide if it is a real packer.

Real-world example

Picture a delivery crate that is sealed and unlabelled. The useful moment is not when the crate sits in the hallway. It is when someone opens it and the contents appear. Packed binary detection is the bay camera that records the crate being opened and what came out.

Key takeaways

  • Watch behaviour after the program starts, because the file on disk is not informative.
  • Writable and executable memory in a normal process is a strong hint of unpacking.
  • Installers do this legitimately, so location and host role decide severity.

In more detail

This strategy detects software packing and unpacking behaviour, mapped to ATT&CK technique T1027.002, where an adversary compresses or encrypts a payload so that static inspection of the file on disk reveals almost nothing, then unpacks it in memory at run time. Because the file on disk is a stub, detections that rely on strings or file hashes rarely help; the detection has to watch what the process does after it starts. The observable pattern is a short sequence: a small executable starts from a temporary or user writable location, allocates memory that is both writable and executable, writes unpacked content into it, and transfers control there, often followed by a module that has no backing file on disk. Correlating process creation, memory protection and image load events on the same process is what separates this from ordinary applications. The main practical failure is that installers and updaters legitimately pack their payloads, so the rule is only usable when it is scoped to hosts and directories where self modifying code is unexpected.

What you will practise

  • Explain why a packed executable is hard to judge from the file on disk
  • Identify memory protection and module load telemetry that reveals unpacking at run time
  • Group events by process to build a behaviour chain rather than alerting on single events
  • Separate legitimate installer unpacking from malicious in memory execution
  • Describe how parent process and file location adjust the severity of an alert
