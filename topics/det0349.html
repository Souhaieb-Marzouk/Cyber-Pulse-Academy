DET0349 Detection Strategy for Content Injection

DET0349Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for content that changes while it travels across the network. The page or file that arrives is not the same as the one that the server sent. Attackers can add code this way without breaking into the server itself.

Why should you care?

The user sees the right web address, so nothing looks wrong to them. An update file can be replaced in transit and still look normal in the browser. This kind of attack can reach many users at once from one weak point on the path. The evidence is in the difference between the sent content and the delivered content. Catching it protects both the user and the software supply chain.

How it works, in plain steps

  1. A network sensor or proxy copies the details of each response, such as its size, type and hash value.
  2. The rule compares that fingerprint with what the origin published or with a known good value.
  3. It also reads the transport security details, because the wrong certificate on the right name is a clue.
  4. On the endpoint, the rule checks the hash of the file that was saved after the download.
  5. Events are joined by user, host, destination name and time to build one delivery story.
  6. A mismatch raises an alert, unless an approved inspection device explains the change.

Real-world example

Think of a sealed medicine box sent by post. The label on the outside is correct, so the pharmacy accepts it. Only when the box is opened does the wrong content appear. Checking the seal is like checking the hash, and the seal is the only thing that proves the contents.

Key takeaways

  • Compare what was sent with what arrived, because the address can still look correct.
  • Certificate details and content hashes are the strongest evidence.
  • Know which devices in your network are allowed to rewrite traffic.

In more detail

This detection strategy covers Content Injection (T1659), where an adversary inserts or alters content inside a network communication so that a user or an automated update process receives something other than what the origin published. The technique matters because it can deliver code or a fake update without ever compromising the origin server, and because the user sees the correct address in the browser while the payload is already changed. Detection depends on network sensor or proxy logs that record response size, content type and hash, transport layer security handshake details such as the certificate issuer, endpoint file records that hash the delivered file, and name resolution logs. It fails most often because legitimate inspection proxies and caching layers also rewrite content.

What you will practise

  • Explain how content can be altered in transit without compromising the origin server
  • Identify network, certificate and endpoint hash telemetry that exposes a mismatch
  • Document the inspection proxies, caches and content delivery services that legitimately rewrite content
  • Write a rule that compares the delivered content fingerprint with the expected origin value
  • Triage a match by confirming the origin hash with the vendor or site owner
  • Describe the coverage lost when traffic is encrypted and cannot be inspected
