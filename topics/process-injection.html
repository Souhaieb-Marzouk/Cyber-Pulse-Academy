Process Injection

Endpoint & MalwareExtremeKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Process injection is a way of putting harmful code inside another program that is already running. The code then runs under that program's identity and permissions. To the operating system, the activity appears to come from a trusted program rather than from anything suspicious. It is a technique, not a complete piece of malware.

Why should you care?

It helps an attacker hide in plain sight, borrow permissions the running program already has, and survive simple cleanups. It also breaks the assumption that a program's name tells you what the program is doing. Injection alone does not steal data or spread. It is a step that makes later steps easier. Knowing how it works helps you tell real intrusions apart from the many legitimate products that also use it.

How it works, in plain steps

  1. The harmful code picks a running program on the machine to hide inside.
  2. It asks the operating system for permission to work with that program.
  3. It reserves space inside the program's memory and copies its code there.
  4. It marks that memory as something the processor is allowed to run.
  5. It makes the program start executing the new code instead of its own.
  6. The code now acts with the trust and permissions of the host program.

Real-world example

Imagine a courier who is allowed into every floor of an office building. A stranger slips a sealed envelope into the courier's bag and writes a new delivery note. The courier, still trusted and still wearing the right badge, walks the envelope to a restricted floor. Security sees a familiar courier doing a normal job. Process injection is that envelope. The host program keeps its good name while carrying out someone else's instructions.

Key takeaways

  • Injection hides harmful code inside a program that is already trusted.
  • Watch for executable memory that is not backed by a file on disk.
  • Some legitimate software injects too, so confirm the context before reacting.

In more detail

Process injection is a family of techniques in which code is placed into the address space of another running process so that it executes under that process's identity, privileges and trust context. Attackers use it for three overlapping reasons: to hide malicious execution inside a legitimate process that security tooling already trusts, to inherit access tokens and privileges the injected process already holds, and to survive elementary cleanup because the host process is not the malicious file. The general mechanism is consistent across implementations even when the specific interfaces differ: obtain a handle to a target process, allocate or repurpose memory inside it, write the payload, change that memory to an executable state, and redirect execution there. Variants differ in how visible each of those steps is — remote thread creation requires cross-process handles and leaves distinct artefacts, while approaches that use shared sections, asynchronous procedure calls, or the process's own already-loaded libraries produce different telemetry. Detection depends heavily on visibility into memory and into cross-process operations, so defenders combine endpoint sensor callbacks, memory scanning for executable regions that are not backed by a file on disk, thread creation anomalies, and behavioural signals such as an unexpected process making network connections or reading credential material. Injection alone is not an objective; it is an enabler that usually appears adjacent to credential access, defence evasion and command-and-control. Understanding the mechanism precisely is what allows an analyst to decide whether a flagged event reflects a genuine intrusion or one of the many legitimate products that also inject code.

What you will practise

  • Describe the generic injection sequence from handle acquisition and memory allocation to execution redirection.
  • Compare common variants by the artefacts each produces and the visibility each gives a defender.
  • Distinguish malicious injection from legitimate application, accessibility and security product behaviour.
  • Detect unbacked executable memory regions and anomalous cross-process thread creation on a live host.
  • Correlate injection events with credential access and command-and-control activity to build an incident narrative.
  • Map injection techniques to their ATT&CK sub-techniques and explain the defensive value of that mapping.
