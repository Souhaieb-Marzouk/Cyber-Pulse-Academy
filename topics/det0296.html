DET0296 Detect Adversary-in-the-Middle via Network and Configuration Anomalies

DET0296Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This rule looks for signs that someone has quietly placed themselves in the middle of your network traffic. It watches for strange network answers. One example is a second device that claims to hand out network settings. It also watches for sudden changes to trust settings on a computer. Together those signs suggest traffic may be passing through an attacker instead of going straight to its destination.

Why should you care?

When an attacker sits in the middle, your encryption does not protect you fully. The attacker can copy a login session and use it later. They may not even need your password. On a normal day nobody adds new trust settings or answers network requests. Catching these small changes early can stop a full account takeover.

How it works, in plain steps

  1. Network devices and switches send records about address lookups, address claims and link changes to your central logging system.
  2. The rule looks for a claim that should come from one device only, but now comes from several. Two different devices may answer the same address request.
  3. On the hosts, the rule watches trust stores, proxy settings and name resolution settings for unexpected changes.
  4. It also watches authentication records for successful logins from a new network address soon after one of those network events.
  5. It joins these records by time and by network segment, usually within a short window of a few minutes.
  6. If a network anomaly and a configuration change appear together, the system raises one alert for an analyst to review.

Real-world example

Think of a hotel front desk that hands out room keys. A stranger stands beside the desk and starts handing out their own keys. Guests still get into their rooms, but the stranger now knows every room number. The night manager would notice two people giving out keys at one desk. That is what this rule watches for, plus the moment a guest's key stops working.

Key takeaways

  • Adversary-in-the-middle means an attacker quietly sits between two systems and copies or changes what passes by.
  • One strange network event is usually not enough. The rule looks for a network change plus a trust or login change.
  • You need switch, address and certificate records to see this, so check that those sources are really collected.

In more detail

This detection strategy covers adversary-in-the-middle (AiTM) activity, where an attacker inserts themselves between a client and a server to read or alter traffic. It is mapped to technique T1557 and matters because a successful AiTM position defeats encryption in practice: session cookies, credentials and authentication codes can be relayed or captured even when the protocol is encrypted end to end. The telemetry that makes detection possible is the combination of network protocol anomalies (rogue Dynamic Host Configuration Protocol, or DHCP, servers, unexpected Address Resolution Protocol, or ARP, replies, unusual Link-Layer Discovery Protocol, or LLDP, and spanning-tree topology changes), host configuration changes (new root certificates, proxy settings, name resolution or routing changes) and authentication events that suddenly arrive from a new network location. In practice the main failure mode is noise and blindness: AiTM often produces no single dramatic event, so the detection depends on correlating weak signals within a short window, and if certificate inventory, Dynamic Host Configuration Protocol snooping or wireless controller logs are not collected, most of the pattern is invisible.

What you will practise

  • Explain what an adversary-in-the-middle position is and how it changes the value of stolen session data.
  • Identify the network telemetry sources that reveal rogue network service answers on your segments.
  • Recognise host-side trust changes, such as new root certificates or proxy settings, as AiTM indicators.
  • Correlate a network anomaly with a later authentication event from an unexpected network address.
  • List the collection gaps that would leave this detection blind in your own environment.
  • Describe how to tune the rule so normal network churn does not create daily alerts.
