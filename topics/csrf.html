Cross-Site Request Forgery

Application SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Cross-Site Request Forgery is a trick that makes your browser act on a website you are already logged in to. The attacker never learns your password. Your browser sends the request because it trusts the site. The site trusts the request because your cookie came with it.

Why should you care?

A site that trusts any request with your session cookie can be made to act for you. An attacker can change your settings or move your money. You may not notice, because the action looks normal in the site's records. Long login sessions make the problem worse. Strong defences stop the browser from making silent requests on your behalf.

How it works, in plain steps

  1. You sign in to a website, and the site gives your browser a session cookie.
  2. That cookie stays in your browser and is sent with every later request to the site.
  3. An attacker builds a page that quietly sends a request to the same website.
  4. You open the attacker page while you are still logged in to the real site.
  5. Your browser adds the cookie by itself, so the site accepts the request as yours.
  6. Anti-forgery tokens and same-site cookie rules make the site reject requests like that.

Real-world example

Picture a hotel front desk that knows you by your room key. You leave the key on the counter while you read a notice. A stranger slides a form across the desk and asks the clerk to charge your room for a new television. The clerk sees your key lying there and approves the charge, because the key was present. The clerk never checked whether you wanted the television. That is the heart of request forgery: the presence of your credential was treated as permission. A good clerk would also ask for a spoken password, and would ignore any instruction that arrived without it. Anti-forgery tokens play the role of that spoken password.

Key takeaways

  • Being logged in is not the same as agreeing to every request your browser sends.
  • Sites should use anti-forgery tokens and strict cookie settings on sensitive actions.
  • Log out of sensitive sites, and avoid browsing other pages while signed in to them.

In more detail

Cross-Site Request Forgery (CSRF) is a web application flaw in which a victim's browser is tricked into sending an authenticated request that the user never intended to make. It works because browsers attach a site's session cookie to every request for that site, no matter which page caused the request. An attacker hosts a page that silently submits a form, or loads an image, pointing at the vulnerable application, and the victim's existing session supplies the credentials. The usual mistake is treating CSRF as an input validation bug, or confusing it with cross-site scripting (XSS): CSRF abuses the browser's automatic trust in the user's cookie, while XSS abuses the site's trust in content it renders. Defences are anti-CSRF tokens bound to the session, SameSite cookie attributes, and re-authentication before sensitive actions.

What you will practise

  • Explain what Cross-Site Request Forgery means and why a browser session matters.
  • Describe how a forged request reaches an application without the user's knowledge.
  • Distinguish request forgery from cross-site scripting and from weak authentication.
  • Identify the controls that prevent forged requests in a web application.
  • Recognise missing anti-forgery protection during a code or design review.
