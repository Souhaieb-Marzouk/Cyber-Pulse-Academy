DET0260 Detection Strategy for Forged Web Credentials

DET0260Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A web credential is the proof a browser shows to a website so the site knows who you are. A cookie is a small piece of that proof, and a token is a larger one. Forging a credential means making a fake proof that the site accepts. This detection compares what the identity provider issued with what the website accepted.

Why should you care?

When a forged credential is accepted, the attacker does not need a password or a second factor. The activity looks like a normal signed-in user, so most login alerts stay quiet. This often follows a key theft, and the damage can spread to every application that trusts the same identity provider. Reconciling both sides of the sign-in is one of the few ways to see it. It also tells you which applications are affected.

How it works, in plain steps

  1. The identity provider logs each successful sign-in and the token or assertion it issued.
  2. The application logs each request, together with the cookie or token value it received.
  3. The rule links the two records by user name, source address, and a short time window.
  4. A valid session must have a matching sign-in record, so a request without one is suspicious.
  5. The rule also flags a token whose signing certificate or issuer is not the expected one.
  6. Repeated alerts from one account raise the severity for the analyst.

Real-world example

Think of a concert wristband. Staff put it on your wrist at the gate, and it proves you paid. A forger can print a wristband that looks right, and the venue only checks the band at the door. A careful venue keeps a list of band numbers issued at the gate. Any band at the door that is not on that list is fake. Forged web credentials work in the same way.

Key takeaways

  • A forged credential produces a session with no matching sign-in at the identity provider.
  • You need logs from both sides: the issuer and the application.
  • Certificate and issuer checks catch assertions that were modified in transit.

In more detail

This detection strategy covers forged web credentials, tracked as T1606, where an adversary creates or modifies a token that a web application will accept as proof of identity. The two well documented forms are forged session cookies and forged federation assertions, and both share one signature: the application accepts an identity that the identity provider never authenticated. Detection therefore works by reconciling identity provider sign-in records with application session records, keyed on the user, the token or session reference, and a tight time window. It fails when the application does not log token validation details, when session identifiers are missing from access logs, or when the cookie is replayed from the same network as the legitimate user.

What you will practise

  • Explain what a web credential is and how it can be forged
  • Identify the identity provider and application fields needed for reconciliation
  • Correlate issued tokens with accepted sessions using user, address, and time
  • Detect unexpected signing certificates on federation assertions
  • Describe the limits of detection when cookie values are not logged
