T1027.014 Obfuscated Files or Information: Polymorphic Code

T1027.014StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Polymorphic code is malicious software that changes its own shape each time it runs. The job it does stays the same, but the code that performs it looks different. This is a sub-technique of Obfuscated Files or Information, which is about hiding content from security tools. Because the shape changes, a scanner that remembers old patterns may not recognise the new version at all.

Why should you care?

Many security tools block a file by remembering its exact code, called a signature. If the code changes every run, those signatures stop working. Attackers can send the same harmful program many times and each copy looks brand new. This can also make it hard for you to link two alerts to one attacker. You have to judge software by what it does, not only by how its file looks.

How it works, in plain steps

  1. The attacker builds a part of the program called a mutation engine.
  2. Each time the program starts, the engine rewrites parts of its own code.
  3. It may swap instructions, reorder small blocks or add useless steps that change nothing.
  4. It can also keep the real code hidden and build a fresh working copy in memory.
  5. The rewritten code runs, so the program behaves the same as before.
  6. Every run produces a different file hash, so old signatures no longer match.

Real-world example

Think of a person who changes their coat colour, hat and walking route each day. They still go to the same office. Colleagues who know only the coat colour lose track of them. Yet the person still arrives at the same desk at nine and does the same job. To recognise them, you watch where they go and what they do, not the colour of the coat. The disguise changes daily, but the routine does not.

Key takeaways

  • A new file hash does not always mean a new threat, so look for repeated behaviour across hosts.
  • Watch the actions of a program, such as persistence, network use and child processes, not only its file hash.
  • Expect mutation to be combined with packing and encrypted payloads in the same sample.

In more detail

Polymorphic code changes its own runtime footprint every time it executes, so the byte sequence a scanner learns from one sample does not describe the next run. Implementations range from mutation engines that rewrite instructions, reorder functions and swap equivalent instructions, to code that builds its working form at run time from an encrypted or encoded template. The functional behaviour stays the same while the representation shifts, which is precisely the weakness of hash and static signature matching: each new variant carries a different file hash and often a different size, even though the delivered effect is identical. Metamorphic variants go further and rewrite the body without keeping an encrypted copy. Mutation engines are commonly paired with packing, command obfuscation and encrypted payloads, so several layers of change occur before the real code runs. Detection therefore shifts to what the software does rather than how it looks: process behaviour, child processes, persistence artefacts, network patterns, imported functions, entropy and section structure, plus correlation of many near-identical hosts producing the same suspicious behaviour with different hashes. Keeping hashes as context rather than as the sole verdict is the practical lesson.

What you will practise

  • Explain what polymorphic code is and why it defeats static signature matching.
  • Describe how a mutation engine changes code each run while keeping the behaviour the same.
  • Explain how this sub-technique differs from packing and from encrypted or encoded files.
  • Identify artefacts, including changing hashes, entropy and section structure, that suggest mutation.
  • Describe a behavioural detection approach that works when file based signatures fail.
