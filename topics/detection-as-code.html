Detection as Code

SOC & Detection EngineeringVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Detection as code means treating your security detection rules like software source code. Rules live in a shared code repository instead of being clicked into a console. Every change is reviewed by another person and tested automatically. This gives you a clear history of what changed, who changed it, and why.

Why should you care?

Detection rules are small programs, and small programs break. Someone edits a shared part, and ten unrelated rules quietly stop working. Without a written history, nobody can tell when a rule changed or who approved it. Version control and automated tests catch these mistakes before an attacker benefits from them.

How it works, in plain steps

  1. You write each detection rule as a text file and store it in a code repository.
  2. The file includes metadata: what the rule finds, which logs it needs, and who owns it.
  3. When you want to change a rule, you open a pull request that a colleague reviews.
  4. An automated pipeline checks the rule's syntax and runs test data through it.
  5. The test data includes events that should match and events that should never match.
  6. Only after the checks pass does the pipeline deploy the rule to the live platform.

Real-world example

Think of a restaurant kitchen with a shared recipe book. Any chef who wants to change the soup recipe writes the change on paper, and the head chef reads it first. If the new recipe is bad, the old page is still there. Nobody scribbles over the book in secret. Detection as code is that recipe book for security rules. You can always see what the soup used to be.

Key takeaways

  • Store detection rules in a repository, not only inside a tool console.
  • Every rule needs an owner, a purpose and a review date.
  • Test rules with good and bad sample events before you trust them.

In more detail

Detection as code is the practice of managing detection content, meaning rules, correlation logic, enrichment mappings and the tests that validate them, with the same engineering discipline applied to application source code. Detection logic lives in a version control repository rather than being clicked into a console. Changes arrive as reviewed pull requests with an author, a reviewer and a written rationale. Every rule carries structured metadata: an identifier, a description, the ATT&CK techniques it addresses, the required log sources, a severity and a documented owner. A continuous integration pipeline validates syntax against the target platform's schema, lints for required fields, checks that referenced log sources exist, executes unit tests against sample events that should and should not fire the rule, and then deploys through environments in a controlled fashion. The benefits are concrete rather than aesthetic. History answers when a detection changed, who changed it and why, which is exactly what an incident review needs. Tests catch the regression where a well-meaning edit to shared logic silently breaks unrelated rules. Portability improves because content expressed in a vendor-neutral format can be translated to several query languages instead of being rewritten by hand. The genuine difficulties are also concrete: keeping the tests' sample telemetry representative of production, handling secrets and environment-specific values without committing them, preventing repository drift from what is actually deployed in the console, and staffing the review process so that it does not simply become an approval rubber stamp. Detection as code therefore succeeds only when the pipeline and the review culture are real, not when a repository is created and left to diverge.

What you will practise

  • You will be able to explain how version control, peer review and automated validation change the lifecycle of a detection rule.
  • You will be able to author a rule with structured metadata that identifies its owner, required log sources, severity and ATT&CK coverage.
  • You will be able to write positive and negative test cases for a rule and explain why both are required to catch regressions.
  • You will be able to build a continuous integration check that validates rule syntax and schema before deployment.
  • You will be able to detect and remediate drift between the content repository and the rules actually deployed in production.
  • You will be able to design a review process that produces substantive feedback rather than routine approval.
