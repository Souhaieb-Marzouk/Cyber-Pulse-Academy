DET0330 Detection Strategy for T1546.016 - Event Triggered Execution via Installer Packages

DET0330Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches the software that installs and updates programs. Attackers change that software so their own code runs during a normal update. It catches who started a program, not only which program started.

Why should you care?

Updates run with high privileges, so their scripts can do almost anything. Users and tools trust them, and they are rarely watched closely. If an attacker lives inside the update path, they get execution again and again. This detection protects one of the most trusted steps on a computer.

How it works, in plain steps

  1. The operating system records the installer process and every program it starts.
  2. The detection builds a parent and child view, because installer scripts normally spawn only known helpers.
  3. It watches the files that describe how packages install, such as installer databases and script lists.
  4. It compares those files against a recorded hash and alerts when they change.
  5. It flags installation scripts that start a command shell, a scripting interpreter or a network tool.
  6. Both signals are grouped by host so the analyst sees a tampered package source plus the code it ran.

Real-world example

Think of a hotel that leaves a welcome card in every room. A thief does not rob rooms one by one. He changes the printing order so every new card contains a key request. The manager notices only when the reports show cards being printed in the middle of the night.

Key takeaways

  • Watch the installer itself, because it runs with high privileges and is widely trusted.
  • Changing the package mapping is more durable than shipping one malicious package.
  • Installation scripts that start shells or download tools deserve immediate attention.

In more detail

This strategy detects event triggered execution through installer packages (T1546.016), where an adversary changes a package manager so that installing or updating a package runs their code as part of the installation. On macOS the installer runs preinstall and postinstall scripts with elevated rights, so a modified package or a modified package mapping turns a routine update into attacker execution. On Windows and Linux the equivalent is a tampered installer database or a repackaged management agent. Detection depends on file integrity monitoring of installer subsystems, process creation showing installation scripts spawning shells or network tools, and unusual parent-child relationships under the installer process. It fails silently when only the generated malicious package is monitored, because the tampered mapping itself is the durable artifact.

What you will practise

  • Explain how installer packages provide a durable execution trigger
  • Identify the file paths and databases that control package installation on each platform
  • Correlate an installer process with unusual child processes and network activity
  • Use file integrity monitoring to find tampering with the packaging subsystem
  • Describe why monitoring only suspicious packages is insufficient coverage
