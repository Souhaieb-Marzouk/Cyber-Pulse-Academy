T1574.012 Hijack Execution Flow: COR_PROFILER

T1574.012ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Many Windows programs are built with a framework called .NET. That framework can load an extra helper library, called a profiler, to measure how code runs. Windows finds this helper through a setting named COR_PROFILER. If an attacker sets that value, the framework loads the attacker library into the program instead.

Why should you care?

The setting can apply to one program or to every .NET program on the machine. So one change can plant code in many places at once. If the affected program runs as an administrator, the attacker library gets those rights too. The feature is a normal part of the framework, so antivirus tools may treat the load as expected behavior. Quiet, wide and repeated execution makes this a serious risk.

How it works, in plain steps

  1. Windows stores environment settings, including the profiler name, in the registry.
  2. A .NET program starts and the runtime reads those settings as it loads.
  3. The runtime then loads the library that the setting points to.
  4. An attacker sets the value and supplies their own library path.
  5. Every managed program that starts afterwards loads the attacker library.
  6. If the variable is set only inside one process, just that process is affected.

Real-world example

Think of a school where the principal says every classroom must use one visiting teacher. A stranger quietly changes the name on that instruction sheet to their own name. Now every class lets that stranger in, in every room, every day. The teachers follow the same instruction as before and see nothing unusual.

Key takeaways

  • Treat changes to .NET runtime environment settings as high risk.
  • Check where profiler settings exist and remove the ones you do not need.
  • Watch for unexpected library loads in .NET programs that never use profiling.

In more detail

This sub-technique abuses the .NET Framework profiling feature rather than a Windows service or path. When the CLR starts inside a process, it reads the COR_PROFILER setting and loads the named profiling component, with the DLL location supplied separately in COR_PROFILER_PATH from .NET Framework 4 onward. Those variables can be defined at machine scope, user scope, or only inside a single process, so an adversary can either persist across sessions by writing them into the registry environment area and registering a component object model class, or affect one process by setting the variables in memory before launch. Because the profiler is loaded into every managed process that starts the runtime, the payload runs widely and quietly, and if a target process is elevated the payload runs elevated as well. Profilers are a legitimate developer and diagnostic feature, so the behaviour resembles normal tooling. Detection depends on baselining where such variables are expected, monitoring registry values for runtime and environment settings, and watching for unusual DLL loads into managed processes, especially in hosts that never use profiling, plus process creation records showing environment settings passed to short-lived launchers.

What you will practise

  • Describe how the .NET runtime selects a profiler library when it starts.
  • Explain the difference between machine-wide, user-wide and process-only settings.
  • State why a profiler load can look legitimate to many security tools.
  • Identify the registry and process evidence that reveals profiler abuse.
  • Suggest baselines and controls that reduce this exposure.
