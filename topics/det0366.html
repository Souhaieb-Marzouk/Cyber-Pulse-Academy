DET0366 Detection Strategy for Double File Extension Masquerading

DET0366Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks at file names that contain two extensions, such as a name ending in both a document extension and an executable extension. An extension is the last part of a file name, like pdf or exe, and it tells Windows which program opens the file. The trick makes the file look like a document while it is really a program.

Why should you care?

People trust what they see at the end of a file name. A file that looks like an invoice may actually run code when it is opened. A hidden direction character can even make the name display in the wrong order, so the safe extension appears last on screen.

How it works, in plain steps

  1. File creation, rename and download records are collected with the full file name and path.
  2. The rule splits the name at each dot and counts how many known extension parts it contains.
  3. It also checks for direction control characters, which a normal file name never needs.
  4. Files that came from mail attachments, archives or browser downloads are treated as higher risk.
  5. If the file is then executed, the process record confirms the file was a program, and the alert is raised.

Real-world example

Think of a parcel with two labels. The top label says books and the label underneath says fireworks. The courier reads the top label and waves it through the front gate. Only the person who peels the label back sees what is really inside.

Key takeaways

  • Read the whole file name from the computer, not from the screen.
  • Direction control characters in a file name are almost always a sign of trickery.
  • A two extension file that then runs as a program is the strongest confirmation you can get.

In more detail

This strategy detects double file extension masquerading, the T1036.007 sub-technique of Masquerading, in which a file is named so that a benign extension appears to be the last one, for example a document name followed by an executable extension, or a right-to-left override character reverses the displayed order of the extensions. The behaviour shows up in file creation and rename telemetry, mail gateway attachment records, archive and container file listings, and subsequent process creation when the file is executed. Detection succeeds by parsing the file name rather than by trusting the shell, normalising unicode direction control characters and counting the extension chain. It fails in practice because many legitimate applications ship installers and helper files with two extensions, and because file names alone carry no intent, so the rule must look at where the file came from and what runs it.

What you will practise

  • Explain how double extensions and direction control characters deceive users
  • Parse file names programmatically instead of relying on the operating system display
  • Correlate file creation records from downloads, archives and mail attachments with later execution
  • Recognise legitimate two extension file names and why they are filtered
  • Write a rule that survives renaming by watching the executed file rather than the archived name
  • Describe user awareness advice that supports the technical detection
