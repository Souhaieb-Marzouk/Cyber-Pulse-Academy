T1059.004 Command and Scripting Interpreter: Unix Shell

T1059.004ExecutionVery hardTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A Unix shell is the text command tool on Linux, macOS and similar systems. Common examples are bash (Bourne Again Shell), sh (Bourne shell) and zsh (Z shell). It runs single commands and whole scripts, and it can join tools together with pipes. On these systems it is the main way people administer a machine.

Why should you care?

Because the shell is the normal way to manage a Linux server, its presence proves nothing. An attacker who reaches a web server can use the very same shell to look around, download tools, and add a scheduled job that survives a reboot. The tricky part is that automated software also opens shells all day. You need to know which services may run a shell on which host, or every alert looks plausible.

How it works, in plain steps

  1. A program starts a shell on the server, and the parent program is the most useful clue.
  2. The system records the command and its arguments when each new process starts.
  3. The shell can chain tools with pipes, so one short command line may do several different jobs.
  4. The attacker may download a tool, run it, then hide a scheduled task or a startup script.
  5. You compare the account and the host against your baseline to decide whether this should happen.

Real-world example

Picture a large shared workshop where everyone is allowed to use the power tools. A visitor picking up a drill attracts no attention at all. But if that visitor is not on the staff list, drills three cabinets open, and a new lock appears on the back door, the picture changes. A Unix shell is that workshop. Nothing about the tool is wrong, so you judge the person, the hour and the mess left behind.

Key takeaways

  • On Linux and macOS the shell is normal, so watch the account and the parent process.
  • A web server or database service opening a shell is rarely good news.
  • Shell history files can be edited, so do not rely on them as your only evidence.

In more detail

A Unix shell is a command interpreter such as sh, bash, zsh, ksh, or dash that provides an interactive interface and a scripting language for Unix-like operating systems, including Linux, macOS, and the BSD family. It exposes pipelines, redirection, job control, variable and command substitution, and access to the full set of system utilities, which together make it a complete execution environment. Adversaries use it to run reconnaissance, download and stage payloads, establish persistence through cron or shell profile files, and pivot to remote hosts using the same credentials. Because the shell is the primary administrative interface on these systems, its presence is normal and only behaviour inside it differentiates intent. Telemetry comes from several layers. Process execution auditing via the kernel audit subsystem, EDR process telemetry, or container runtime logs captures the argv of each spawned process, and the parent-child tree shows whether a shell was launched by a web server, database service, or container entrypoint. Shell history files record interactive commands but are trivially edited and often disabled. Scripts written to disk leave file creation and permission change events, and interactive shells frequently write to /tmp, /var/tmp, or the home directory, which may appear in file integrity monitoring. Audit records for executed syscalls supplement process data where the agent does not capture full argument vectors. Legitimate shells are everywhere: package installers, container entrypoints, health checks, and administrator sessions. Investigations therefore anchor on context rather than on the interpreter. Shells spawned by internet-facing daemons, execution under an account whose normal role is non-interactive, odd execution paths, base64 decoding pipelines, and outbound connections immediately following shell creation are the reliable signals. Building a baseline of which service accounts execute shells on which hosts converts a very noisy dataset into a workable detection surface.

What you will practise

  • Explain how shell features such as pipelines, substitution, and redirection shape both behaviour and the arguments visible in telemetry.
  • Interpret process execution audit records and reconstruct a shell command sequence from parent-child lineage.
  • Assess how shell history, container logs, and file integrity monitoring each contribute to or mislead an investigation.
  • Distinguish shells spawned by internet-facing services from routine administrative or automation-driven execution.
  • Design a service account and host baseline that reduces false positives for shell execution detections at scale.
  • Map observed Unix shell behaviour to ATT&CK and identify which residual gaps require additional instrumentation.
