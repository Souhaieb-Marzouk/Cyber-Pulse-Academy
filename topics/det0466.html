DET0466 Detection of Script-Based Proxy Execution via Signed Microsoft Utilities

DET0466Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches trusted Microsoft script engines. Two common ones are the console script host and the Windows script host. An attacker can put harmful code in a script file. They then ask a signed, trusted program to run that file. The trusted program looks innocent in a list of running processes.

Why should you care?

Many security tools trust programs that carry a valid Microsoft signature. If an attacker can make such a program run their script, the activity may pass unnoticed. This turns ordinary administration tools into a disguise. Detecting it means watching what the trusted program was asked to do, not only its name.

How it works, in plain steps

  1. The endpoint records every new process, including the full command line and the parent process that started it.
  2. The detection selects events where the running image is a known script host.
  3. It reads the command line and the script file path from the event and checks whether the location is expected.
  4. It compares the parent process to a list of approved parents, such as the software deployment agent.
  5. A scoring step raises the alert when the script sits in a user folder or a mail attachment.
  6. The analyst opens the script file and the parent process history to decide whether the run was approved.

Real-world example

Picture a building where only staff with a company badge may enter. A visitor cannot get through the front door. But a staff member can carry a parcel inside for the visitor. The door log only records the staff member. The script host is that staff member, and the script file is the parcel. This detection reads the parcel label.

Key takeaways

  • Signed system utilities are tempting because their signature is trusted.
  • Command line and parent process are the fields that show what the trusted binary was asked to do.
  • A trusted binary running a script from a user-writable folder deserves a look.

In more detail

This strategy detects abuse of signed Microsoft script hosts and similar trusted utilities to run attacker-controlled code, which maps to the system script proxies technique. The idea is that a binary already trusted by the operating system and possibly by application allowlisting loads and executes a script file, so the malicious logic lives in the script rather than in the executable. Detection depends on process creation telemetry that keeps the full command line and the parent process, plus script block or script file content logging where it is enabled. It fails most often because legitimate administrators use the same script hosts for logon scripts, software deployment and scheduled maintenance, so a rule that simply names the binary will drown the analyst in known-good automation.

What you will practise

  • Name common signed Windows script hosts and explain why an attacker would use them.
  • Explain which process creation fields are needed to spot script proxy execution.
  • Write a rule that keys on the script path and parent process rather than only the binary name.
  • List the benign administrative patterns that produce the same process shape.
  • Describe how script content logging adds evidence after an alert fires.
