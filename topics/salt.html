Salt

CryptographyHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A salt is a random value added to a password before it is hashed. A hash turns text into a fixed code that cannot be reversed. The same password with different salts gives completely different codes. Salts are stored next to the hash, because the system needs them to check a login later. Salts are not secret.

Why should you care?

If you store plain hashes of passwords, two users with the same password get the same code. An attacker who steals the list can spot those matches. Worse, they can precompute codes for millions of common passwords and look them up instantly. A salt per user destroys both tricks. Remember, though, a salt does not slow down guessing. You still need a slow password hashing method.

How it works, in plain steps

  1. When a user sets a password, the system generates a random salt for that account.
  2. The salt is combined with the password and passed through a slow hashing function.
  3. The system stores the salt and the resulting hash together in the database.
  4. Each account gets its own salt, so identical passwords produce different hashes.
  5. At login, the system reads the stored salt and repeats the same calculation.
  6. If the new hash matches the stored one, the password is correct.

Real-world example

Imagine a school that files student forms by exact wording. Two students who write the same sentence end up in the same folder, which is a privacy problem. So the school adds a random cover page to each form before filing. Now the same sentence lands in a different place every time. The cover page is not secret, but it stops anyone grouping students by what they wrote.

Key takeaways

  • Use a unique random salt for every stored password, never one shared salt.
  • A salt stops precomputed lookups, but only a slow hash slows down guessing.
  • Store the salt beside the hash, since it is not secret and you need it later.

In more detail

A salt is a unique, non-secret random value that is combined with an input before hashing so that identical inputs produce different digests, and it is a mandatory component of any password storage scheme. Salting defeats precomputed lookup structures such as rainbow tables and prevents an attacker who obtains a password database from learning which accounts share a password, because the same password hashed under different salts yields unrelated digests. Salts must be generated with a cryptographically secure random source, must be long enough to make collisions across a large user base statistically irrelevant, and must be stored alongside the resulting hash so verification remains possible. Salting does not slow down guessing, so it must be paired with an adaptive, memory-hard password hashing function; a salted fast hash is still a fast hash. Other contexts use the term differently. In key derivation a salt binds derived material to a context or generation, and in signature schemes a random per-signature value is sometimes loosely called a salt even though its uniqueness requirements are far stricter and its exposure is catastrophic rather than merely weakening. Common implementation defects include a single global salt shared by every account, salts derived from the username or a timestamp with insufficient entropy, truncated salts, salts generated with a non-cryptographic random function, and migration routines that re-hash existing passwords with a fixed salt during a framework upgrade.

What you will practise

  • Explain what salting prevents and what it explicitly does not protect against.
  • Specify correct salt generation, length and storage requirements for a password authentication system.
  • Choose an adaptive password hashing construction and tune its cost parameters for a production workload.
  • Identify defective salt handling during code review, including shared, derived or truncated salts.
  • Distinguish a password salt from a key derivation salt and a per-signature nonce, and apply the right rules to each.
  • Plan a credential store migration that rehashes existing passwords without weakening them.
