DET0531 Detection Strategy for Additional Cloud Credentials in IaaS/IdP/SaaS

DET0531Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for new passwords, keys or secrets added to an existing account in a cloud service. Attackers do this so they can return later, even if the first password is changed. The alert fires when a key or secret is created for an account that does not usually need one. It also fires when the creator is not an approved automation tool.

Why should you care?

Losing a password is annoying for an attacker. A secret key that nobody knows about can keep them inside for months. Extra credentials often look like normal application setup, so they pass a quick review. If you remove only the first account, the added key still works. Watch who creates credentials, and for which identity. That is one of the few ways to break the chain early.

How it works, in plain steps

  1. Cloud audit records capture every identity change, including who made it, from where, and which identity was changed.
  2. The rule keeps the operations that create or update long lived credentials. Examples are access keys, login profiles and application secrets.
  3. It removes events caused by known automation roles, deployment pipelines and single sign-on provisioning connectors.
  4. The remaining events are scored by how rarely that actor performs the operation and how privileged the target identity is.
  5. The rule also checks the source address, because a first time creation from a new address is more interesting.
  6. High scoring events raise an alert naming the target identity, the new credential and the source address.

Real-world example

Think of an office where each worker has a locker key. Someone copies a key for an empty locker that nobody checks, and keeps it. The supervisor later changes the worker's own key, but the copy still opens the locker. The detection is not about the copied key being used. It is about the moment a second key was cut for that locker.

Key takeaways

  • Extra credentials survive password resets, so removing the first account is not enough.
  • Automation roles create credentials every day, so the actor and the target identity must be correlated.
  • Track both the target identity and the source address to spot an unusual creation.

In more detail

This detection strategy covers the creation of extra credentials for an existing cloud or directory identity, the behaviour behind additional cloud credentials. An attacker who already has a foothold adds an access key, an application secret or a login profile so that access survives a password reset and looks like a legitimate application integration. Cloud provider audit records for identity and access management changes, identity provider audit events for application credential updates, and directory service account changes supply the evidence. The rule fails when it alerts on every credential creation, because automation accounts, build pipelines and onboarding workflows create credentials constantly, so the actor, the target and the timing must be correlated before alerting.

What you will practise

  • Explain how added cloud credentials give an attacker persistence that survives a password reset
  • Identify the audit operations that create long lived credentials in a cloud provider control plane
  • Describe the equivalent events in a directory service, such as a new account or a new group member
  • Correlate the actor, the target identity, the operation and the source address in one rule
  • Build an allow list of automation roles and expected creation schedules
  • Explain why a credential created shortly after an unusual logon deserves priority triage
