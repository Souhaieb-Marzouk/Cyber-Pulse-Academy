DET0167 Firmware Modification via Flash Tool or Corrupted Firmware Upload

DET0167Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches for changes to the software built into the hardware itself, known as firmware. Attackers can flash a modified firmware image onto a machine. This code runs before the operating system starts.

Why should you care?

Firmware sits underneath the operating system, so reinstalling the system does not remove a firmware implant. Security features such as secure boot may be turned off in the same change. Ordinary security agents often cannot inspect it. The tool used to write firmware is not secret, which means the defence has to be detecting the write itself.

How it works, in plain steps

  1. Firmware is updated by a program that opens the firmware device and writes a new image.
  2. The operating system records that the program ran and which account started it.
  3. Device level auditing records access to the firmware or memory device files.
  4. The platform records measurements of the firmware early in the boot process.
  5. The detection links the write to a change in that measurement or to secure boot settings.
  6. An analyst confirms whether an approved update was scheduled for that machine.

Real-world example

Think of a building where every tenant changes the locks on their own flat door. One tenant also replaces the lock on the main entrance, which the landlord controls. All the flat keys still work, but someone now has control of the building itself.

Key takeaways

  • Firmware writes survive operating system reinstallation, so treat them as high impact.
  • Allow updates only in scheduled windows, from approved tools, on approved hardware models.
  • A changed boot measurement with no change record is a strong sign of tampering.

In more detail

This strategy detects modification of platform firmware, either by running a flash utility that writes the firmware store or by uploading a firmware image that has been altered or corrupted. The covered technique matters because firmware runs before the operating system and sits below every agent, so a modified image can persist across reinstalls, disable secure boot verification and hide code where standard endpoint tools cannot see it. Firmware update tooling, device access auditing and platform integrity measurements make this possible, because a flash write requires a user space process with access to the firmware device and often changes the measurement recorded at boot. The main failure mode is that legitimate vendor updates use the same tools and produce the same writes, so the rule must baseline update windows, expected tooling and the models in the estate, and treat any write outside that baseline as an incident rather than a change.

What you will practise

  • Explain why firmware modification persists across operating system reinstallation and agent removal.
  • Identify the processes and device access patterns that indicate a firmware flash or dump.
  • Use boot time integrity measurements to find firmware changes that occurred outside an update.
  • Build an approved baseline of update tools, hardware models and maintenance windows.
  • Describe why physical access and privileged drivers are usually required for this technique.
