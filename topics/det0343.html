DET0343 Direct Network Flood Detection across IaaS, Linux, Windows, and macOS

DET0343Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for a sudden flood of network traffic aimed at one target. The traffic comes from many sources at the same time. The goal of the flood is to make a service too busy to answer real users.

Why should you care?

A flood stops people from working, so the impact is immediate and visible to everyone. It can hide a quieter attack that runs at the same time. The traffic is hard to trace because it comes from many places. A good rule tells you which service is under pressure in the first minutes. That head start decides whether you can filter the traffic or must fail over to a backup site.

How it works, in plain steps

  1. Network devices and cloud platforms summarise traffic into flow records, which describe conversations between hosts.
  2. Each record carries the source, the destination, the port, the number of packets and the number of bytes.
  3. The rule groups those records by destination and by short time windows, such as one minute.
  4. It compares the rate in each window with the normal rate for that destination from the last few weeks.
  5. A rate far above the baseline, especially with many distinct sources, raises an alert.
  6. An analyst checks whether a planned event or a software rollout can explain the change.

Real-world example

Think of a shop with one till and one queue. Twenty normal shoppers are fine. Three hundred people arriving at once stop real customers from paying. The shop does not need to know every person in the crowd to know it has a problem. The flow record is the queue count at the door.

Key takeaways

  • Compare the current rate with a learned baseline instead of a fixed number.
  • Many sources hitting one destination is the strongest sign of a flood.
  • Check the change calendar before you call it an attack.

In more detail

This detection strategy covers Direct Network Flood (T1498.001), where an adversary aims a high volume of traffic at one host, service or network link to exhaust bandwidth or connection state. The technique matters because it degrades or removes availability for real users, and because the traffic is often sourced from many hosts so per host thresholds stay quiet. The telemetry that makes it visible is flow level records such as NetFlow or IPFIX, cloud virtual private network flow logs, load balancer and edge device metrics, and interface counters on servers. The main failure mode is a poorly set baseline, because backup jobs, video calls, software updates and content distribution traffic all look like floods for a short time.

What you will practise

  • Explain how a direct network flood consumes bandwidth or connection state for a target
  • Identify flow, edge device and cloud telemetry that exposes a volumetric attack
  • Build a per destination and per service baseline that accounts for backups and updates
  • Write a rule that alerts on rate change and source diversity rather than a single traffic value
  • Triage the alert by confirming with service owners and checking the change calendar
  • Describe the coverage gap when only one telemetry source, such as flow records, is available
