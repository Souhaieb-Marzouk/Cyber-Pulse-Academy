Cross-Site Scripting

Application SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Cross site scripting is an attack where an attacker's code runs inside a trusted website in your browser. The code runs as if the website itself wrote it. That means it can read what the page can read and act as you. It usually happens when a site shows user text without cleaning it first.

Why should you care?

The running code can steal your session, change what you see, or submit forms in your name. It can also spread, because stored code is shown to every visitor of that page. Users cannot easily notice it, since the page address looks correct. For a business, this can mean stolen accounts, damaged data and lost trust. Preventing it is a basic duty for anyone who builds web pages.

How it works, in plain steps

  1. A page takes something a user typed, such as a comment or a name, and stores it.
  2. Later the page puts that text straight into the page code without cleaning it.
  3. An attacker sends text that includes code, and the browser cannot tell it apart from the site's own code.
  4. The browser runs that code as part of the trusted page, with the visitor's session.
  5. The code can then read page content, send requests as the visitor, or change what is shown.
  6. Developers stop this by encoding text for the place it appears and by adding a content security policy.

Real-world example

Imagine an office noticeboard where anyone may pin a note. A visitor pins a note that looks exactly like an official company memo, with the company logo and letterhead. Staff read it and follow its instructions, because it appears to come from management. The noticeboard itself is trusted, so nobody questions the note. Cross site scripting works in the same way. The website is the noticeboard, and the attacker's text is the forged memo.

Key takeaways

  • Clean text for the exact place it appears, such as the page body or an attribute. Do this cleaning when you display the text, not only when you save it.
  • Blocking the word script is not enough, because many other tags and attributes can run code.
  • Add other layers such as a content security policy and cookies that scripts cannot read.

In more detail

Cross-site scripting is an injection class in which attacker-controlled content reaches a victim's browser and is interpreted as executable script within the origin of the vulnerable site, so the code inherits that site's cookies, tokens and same-origin privileges. It appears in three practical shapes: stored, where the payload is persisted and later served to many users; reflected, where it is echoed back in the immediate response; and browser side, where client code copies attacker-influenced data into a dangerous sink such as an HTML writing interface. The root cause is context, because the same string is harmless in one part of a document and executable in another, which is why blocking a tag name or sanitising only on input fails. Defences combine context-aware output encoding, templating that escapes by default, sanitisation of permitted markup, a content security policy with nonces, and cookies marked HttpOnly and SameSite to limit what stolen script can reach. The mistake is treating this as an input validation problem rather than an output handling one.

What you will practise

  • Explain what cross site scripting is and why the browser trusts the injected code.
  • Distinguish stored, reflected and browser side variants of the attack.
  • Describe where unsafe output handling creates the weakness.
  • Identify defensive measures such as context aware encoding and safe templating.
  • Explain how a content security policy and cookie flags reduce the impact.
