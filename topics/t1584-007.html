T1584.007 Compromise Infrastructure: Serverless

T1584.007Resource DevelopmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is when an attacker takes control of a small piece of cloud code called a serverless function. Serverless means the cloud company runs the code for you and you pay only when it runs. The attacker does not own the server. They change someone else's function, so traffic still comes from a trusted cloud company.

Why should you care?

Network blocks often allow traffic to big cloud providers because normal business depends on them. Code that runs inside that provider is invisible to those blocks. One changed function can act as a relay for many victims at the same time. Because the attacker pays nothing for servers, cleaning up the function is the only way to stop the flow. Few teams review function settings after the first deployment, so the change can live for months.

How it works, in plain steps

  1. The attacker finds a weakly protected cloud function, often through a leaked key or a misconfigured permission.
  2. They replace or edit the code so that it forwards requests to a system they control.
  3. The provider then runs that code whenever the function is called, using its own network.
  4. Infected machines talk to a normal-looking cloud address and never see the real backend.
  5. Logs inside the cloud account record the new deployment and unusual outbound connections.
  6. Only a review of the control plane and invocation logs shows that the function changed.

Real-world example

Imagine a hospital night desk that takes calls for many departments. The desk is trusted, so nobody questions a call that comes through it. One night someone quietly swaps the desk's forwarding sheet. Now every call for the pharmacy is sent to a private number outside the hospital. Patients still dial the same main line and hear the same greeting. The building, the number and the staff all look correct. Only a check of the forwarding sheet shows that the calls leave the building.

Key takeaways

  • Serverless code runs on someone else's computer, but an attacker can still change it.
  • Allowing cloud domains does not prove that the code behind them is honest.
  • Review function code, permissions and outbound traffic after every unexpected change.

In more detail

Instead of renting a server, the adversary gains control of a serverless function, a small piece of code that a cloud provider runs on demand, and lets the provider's own network carry the traffic. A tampered function can answer infected hosts directly or forward their requests to an adversary-controlled backend, so the client only ever talks to a familiar cloud hostname. The artefacts live in the control plane and in execution logs: unexpected function deployments, edited environment variables, sudden outbound connections from the function's execution role, and invocation counts that climb outside normal hours. Legitimate functions change through named developers and change control, so an unauthorised deployment that no ticket explains is the clearest signal.

What you will practise

  • Describe how a compromised serverless function can relay command and control traffic.
  • Explain why traffic to a major cloud provider is hard to judge by domain name alone.
  • Identify the cloud control plane logs that record function changes and deployments.
  • Compare a hijacked function with one that was deployed through normal change control.
  • Suggest review steps that would catch unauthorised function changes early.
