XML External Entity Injection

Application SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

XML External Entity injection is a weakness in programs that read XML. XML is a text format used to move data between systems. An attacker can put a special instruction inside the XML. A careless program then fetches a file or address it should never touch.

Why should you care?

The program may reveal internal files or passwords kept in configuration. It may also reach private servers that the outsider cannot see. The damage comes from the program trusting the document itself. One single request is enough to start the trouble.

How it works, in plain steps

  1. The application accepts an XML document from a user or partner system.
  2. The document includes a declaration that defines a special named value.
  3. That declaration points the parser at a local file or a remote address.
  4. The parser fetches the target and puts its contents into that named value.
  5. The application uses the value and may show it back to the sender.
  6. Attackers learn internal details or reach services hidden from the internet.

Real-world example

Imagine a library request form that allows you to ask for one book. A clever reader writes that this book should be copied from the manager's office. A helpful clerk follows the instruction without checking and hands the folder over. The clerk only ever reads the form.

Key takeaways

  • Turn off external entity and document type processing where you can.
  • Treat XML from users or partners as untrusted input, just like any form field.
  • Check every library that parses XML, not only the obvious entry point.

In more detail

XML External Entity injection is a class of application flaw that occurs when an XML parser is allowed to resolve external entity declarations supplied inside a document the attacker controls. The mechanism is the document type definition: XML permits a document to declare reusable entities, and some declarations may point at an external resource such as a local file or a remote URL, which a permissive parser then fetches and substitutes into the document before the application reads it. Because the substituted value becomes part of the parsed data, an application that echoes or processes that field can be made to disclose file contents, and because the parser performs the fetch itself, it can also be used to reach internal services that are not exposed externally; some parsers expand entities recursively, which consumes memory. In real environments the risk sits in runtimes and libraries that keep document type definition processing enabled by default, including older enterprise integration layers, document converters and some software development kits. Detection relies on watching for documents containing entity declarations and on errors or timing differences from outbound fetches. The mistake people usually make is patching one endpoint while other libraries in the same application still parse untrusted XML with the same permissive settings.

What you will practise

  • Explain what XML External Entity injection is in plain terms.
  • Describe how document type declarations cause a parser to fetch extra resources.
  • Recognise the difference between file disclosure and server-side request forgery impact.
  • Identify the parser configuration changes that remove the risk.
  • Explain how logging and outbound traffic monitoring help detect attempts.
