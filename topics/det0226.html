DET0226 Detection Strategy for Masquerading via File Type Modification

DET0226Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection catches files that pretend to be a different kind of file. A file type is the last part of a file name, such as the letters after the final dot. An attacker can add a second ending. They can also change a Windows setting, so a program looks like a picture or a document. You then open it, and code runs instead.

Why should you care?

People and computers both decide how to open a file by looking at its name. If that name is misleading, the wrong program opens the file and the safety checks are skipped. Email filters that block one file type can be bypassed by adding a harmless looking ending in front. This trick is cheap to perform and hard for a user to notice at a glance.

How it works, in plain steps

  1. The endpoint agent records every new file, including the full name and its ending.
  2. The rule looks for names that carry two endings, where the last one can run code.
  3. Separately, the agent records changes to the Windows settings that link a file ending to a program.
  4. The rule checks whether a changed link points to a scripting host or a temporary folder.
  5. It then looks for a process starting from that changed file type, within a short time.
  6. An alert means the file was not only renamed but actually executed.

Real-world example

Imagine a parcel with two labels. The top label says books, so the mail room waves it through. Underneath, a second label says live animals. The mail room only read the top label, and the true contents were never checked.

Key takeaways

  • Double file endings, and changed file ending settings, hide the true type of a file.
  • Alert only when the misleading type is followed by an actual execution.
  • Users cannot see the difference, so detection must not depend on them.

In more detail

This strategy detects masquerading through file type modification, tracked as ATT&CK T1036.008, where an adversary changes how a file is presented or interpreted so that its true type no longer matches its appearance. Two common shapes are double extensions on email attachments, such as a document name ending in a second dangerous extension, and writes to the Windows registry that alter the executable path or perceived type associated with a file extension. It matters because the entire trust decision made by a user or by an application is based on that appearance, so one registry value or one renamed file defeats controls that only look at the name. The telemetry that makes it detectable is file creation with the full path and extension, registry value set events on the file association areas, and process creation showing the interpreter that actually ran the file. The main failure mode is noise: installers, browsers, and synchronisation clients legitimately write extension associations, so the rule must correlate the association change with an execution of the affected file type instead of alerting on either event alone.

What you will practise

  • Describe how Windows associates a file extension with the program that opens it
  • Identify file creation events whose path contains a second executable extension
  • Detect registry modification of file association keys that redirect an extension to a script host
  • Correlate a file type change with the process creation that follows it
  • Baseline legitimate extension changes made by browsers and software installers
  • Explain to end users why a visible file name is not a reliable trust signal
