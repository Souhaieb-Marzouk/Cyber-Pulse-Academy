DET0300 Detection Strategy for Reflective Code Loading

DET0300Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Normally a program is stored as a file on disk. The operating system reads that file before running it. Reflective loading skips the file step. The code is placed straight into the memory of a running program. This rule looks for that pattern. It is a common way to run malicious code while leaving nothing on disk.

Why should you care?

Many defences check files as they are created or opened. If the malicious code never becomes a file, those checks never see it. The code also borrows the identity of a trusted program, so other tools may trust it. Memory activity is harder to watch. You need special sensors and a clear picture of what normal looks like.

How it works, in plain steps

  1. A sensor inside the operating system reports when a program asks for new memory and marks it as runnable.
  2. The same sensor reports when a program loads a code module and whether a matching file exists on disk.
  3. The rule looks for a memory region that is filled from a network or file source and then made runnable.
  4. It also checks whether the loaded module has no file behind it, which is the clearest sign of reflective loading.
  5. Script engine logs can add evidence when a script loads an assembly or module from a block of text.
  6. The system combines these facts with the process name and its parent, then alerts if the pattern is unusual.

Real-world example

Imagine a visitor who wants to enter a building. The usual way is to sign the register at the front desk, so a record exists. Instead, the visitor walks in beside an employee and signs nothing. Security can still notice a person entering with an employee who expected no guest. That mismatch is the clue, not the missing form.

Key takeaways

  • Reflective loading runs code from memory so that no file appears on disk.
  • Detection depends on memory and image load telemetry, not on file scanning.
  • The strongest signal is a code module in memory that has no matching file on disk.

In more detail

This detection strategy covers reflective code loading, mapped to T1620, where an adversary loads a module or assembly directly into memory from a buffer or a remote source instead of writing it to disk and letting the operating system loader run it. It matters because this is a primary way attackers avoid file based detection: nothing lands in a folder, so antivirus scanning of new files and simple file creation rules see nothing, yet the code executes with the trust of the host process. Useful telemetry includes process access and memory allocation events, image load events where the module has no backing file on disk, and the script block and module logging that records in-memory loading calls. The main way it fails in practice is that legitimate software also allocates and executes memory, so the detection lives or dies on behavioural context such as which process is doing it, whether the region was made executable, and whether the module has a valid on-disk counterpart, which requires deep telemetry that many environments do not collect.

What you will practise

  • Explain reflective code loading and why it defeats file based detection.
  • Identify the memory allocation, process access and image load telemetry needed to detect it.
  • Interpret the difference between a module with a backing file on disk and one without.
  • Use script engine logging to spot in-memory loading performed through scripting languages.
  • Describe why this technique is common in post-exploitation frameworks and what that means for triage.
  • List the collection gaps that would leave this detection blind on your endpoints.
