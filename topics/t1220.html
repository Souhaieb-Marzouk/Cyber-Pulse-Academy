T1220 XSL Script Processing

T1220StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

XSL is a language that describes how to turn data in one file into a formatted document. It can also contain small programs. Attackers put their harmful program inside such a file and use a trusted Windows tool to run it. The tool then looks like the thing doing the work.

Why should you care?

The tool that performs the transformation is a normal, trusted program, so rules that block unknown software may not stop it. The harmful code sits inside a data file rather than a program file, and the file can be named to look like a picture or a document. Many scanning tools look for script inside documents, not for script inside style files. This makes the technique a quiet way to run code while the security programme watches the wrong place.

How it works, in plain steps

  1. The attacker prepares two files, one holding data and one holding the style rules with an embedded script.
  2. A trusted transform tool is placed on the system, since it is not part of a default Windows install.
  3. The tool is called with the data file and the style file, and the script runs during the transformation.
  4. Because a style file is valid data too, the same file can be given for both arguments.
  5. The files may also be renamed with harmless extensions so file type checks do not look inside.
  6. Another route names a script engine and the style file through the instrumentation service, with no extra tool.

Real-world example

Imagine a post office where staff will franking any envelope you hand over, as long as the paperwork looks right. The machine is official and the clerk follows the procedure. Someone brings a parcel that is labelled as a book but holds something else, and because the label looks ordinary the clerk stamps it and sends it on. The process was correct from start to finish. Nobody opened the parcel to see what was really inside.

Key takeaways

  • Scripts can hide inside data files, so scan file contents and not just file names.
  • Watch for trusted transform tools running on machines that have no reason to run them.
  • The command line often shows the true purpose even when the file extension lies.

In more detail

XSL script processing abuses the scripting support that the Extensible Stylesheet Language standard builds into stylesheets, so that code executes as a side effect of transforming one XML document with another. Adversaries reach this capability through two common hosts. A signed Microsoft command-line transform utility can be dropped alongside two files and used to run a script embedded in a stylesheet, and because a stylesheet is itself valid XML the operator can pass the same file as both the source and the stylesheet, or give the files an unrelated extension so that content filtering and file type rules have nothing to match. Windows Management Instrumentation offers the second route, letting a script engine be named together with a stylesheet so the embedded script runs without the transform utility being present. Because the execution is proxied through a signed or built-in host, application control that trusts those binaries does not stop it, and there is no compiled payload on disk to scan. The artefacts are modest, which is part of the appeal: a process creation record for the transform utility or the instrumentation host carrying stylesheet arguments, script engine names supplied as parameters, unusual file extensions in the command line, and any child process the script then spawns. Legitimate use of the same binaries is rare on user workstations, tied to build or document pipelines, and normally points at stylesheets stored in known repository or deployment paths rather than user folders.

  • Explain how renamed files and repeated file arguments defeat file extension filtering.
  • Name the telemetry sources that record the transform process and anything it spawns.
