Rootkit

Endpoint & MalwareExtremeKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A rootkit is a set of tools that keeps harmful software hidden on a machine while leaving the attacker in control. It hides by interfering with the very tools an administrator uses to look around, such as file and process lists. Some sit deep inside the operating system, and some go deeper still, into the boot process.

Why should you care?

On a machine with a rootkit, a clean report from a tool running on that machine proves very little, because the tool itself may be fooled. You have to check from outside, using another source of evidence such as network records or remote sign-in logs. Removing a deep rootkit is usually not realistic, so most teams rebuild the machine instead of trying to clean it.

How it works, in plain steps

  1. The attacker gains high-level permission on the machine, often as an administrator.
  2. They install components that change how the system reports its own state.
  3. File lists, process lists, and settings queries start to leave out certain entries.
  4. Deeper versions load early in the boot process and hide above the operating system.
  5. A tool running on the machine therefore reports that everything looks fine.
  6. Investigators must compare the machine against external evidence to spot the difference.

Real-world example

Think of a shop where the manager is the thief. Every evening the manager writes the stock report, so the missing items never appear on paper. The accounts balance perfectly, and any auditor reading the manager's own records would find nothing wrong. To catch it, you must count the shelves yourself, at a time when the manager is not present. Checking an infected machine with its own tools is exactly like trusting that report.

Key takeaways

  • A rootkit hides by corrupting the tools you would use to find it.
  • Trust outside evidence such as network and sign-in records, not the host alone.
  • For deep rootkits, rebuilding the machine is safer than trying to clean it.

In more detail

A rootkit is a set of techniques and components designed to keep malicious presence on a system hidden while retaining privileged control, typically by subverting the very mechanisms an administrator would use to observe the machine. That subversion takes several forms. User-mode rootkits hook or patch library functions so that directory listings, process enumerations and registry queries omit the intruder's artefacts. Kernel-mode rootkits load a driver that filters system calls, hides handles, or unlinks entries from kernel data structures, which can make the compromise invisible to ordinary tooling running above them. Bootkits extend persistence into the boot chain, surviving reinstallation of the operating system on the same disk, and firmware implants sit below that in platform code. Virtualisation-based rootkits move the operating system into a guest and let a thin hypervisor mediate what the guest can observe, which is powerful but fragile in practice. The defensive consequence is that on a suspected rootkit host, a negative result from host-resident tooling proves very little. Trustworthy examination requires either an out-of-band method such as booting the system from known-good external media, offline disk analysis, or cross-referencing independent telemetry: network flow records, remote authentication logs, hypervisor-level events and endpoint agent data that does not rely on the compromised operating system's own APIs. Removal is generally a rebuild decision rather than a cleaning exercise, because a partially removed kernel implant leaves an unverifiable system. Prevention focuses on driver signing enforcement, secure boot, measured boot attestation, and blocking the privileged access that rootkit installation requires in the first place.

What you will practise

  • Differentiate user-mode, kernel-mode, bootkit, firmware and virtualisation-based rootkit approaches by their position in the stack.
  • Explain why host-resident discovery tools can return misleading clean results on an infected system.
  • Plan an out-of-band investigation using external boot media, offline imaging and independent telemetry sources.
  • Assess driver signing, secure boot and measured boot controls as barriers to kernel and boot-level persistence.
  • Justify system rebuild over in-place cleaning when kernel or boot integrity cannot be verified.
  • Describe the evidence handling steps required when firmware or boot-chain compromise is suspected.
