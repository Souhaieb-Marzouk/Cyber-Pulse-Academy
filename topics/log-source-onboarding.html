Log Source Onboarding

SOC & Detection EngineeringHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A log source is any system that writes records of what it did, such as a server, a firewall or a login service. Log source onboarding means adding one of those systems so its records flow into a central place where analysts can search them. The central place is often called a security operations centre, or SOC. Onboarding is the work of connecting and understanding that source.

Why should you care?

A detection can only work if the records it needs are arriving, complete and readable. If a firewall sends nothing, nobody sees blocked attacks from that edge. If times are wrong, the story of an incident falls apart. If fields are unreadable, every alert built on them fails silently. Skipping setup work creates quiet blind spots that an attacker can use for months.

How it works, in plain steps

  1. Decide which questions the source must answer, then pick the events and fields that answer them.
  2. Check that the device can send records and that the network path allows the traffic through.
  3. Configure a documented transport, such as an authenticated agent or a secure syslog channel.
  4. Collect the records in a central platform and parse them so each field lands in the right place.
  5. Fix timestamps and time zones, then link the source to an inventory entry that names the asset.
  6. Test the whole path with a known event, then watch for gaps, duplicates and parsing errors over time.

Real-world example

Imagine a post office that collects letters from many branch offices. One new branch starts sending boxes of paper, but the boxes arrive unsorted and the dates are written in three different styles. The sorting staff cannot file anything properly, so important letters go missing. The post office asks the branch to use one standard envelope, to write the date the same way as everyone else, and to mark the sender clearly. Then the staff send a test letter to prove the route works. Only after that test can anyone trust the mail from that branch.

Key takeaways

  • Onboarding is not finished when logs appear, only when a test event is detected.
  • Correct time and readable fields matter as much as delivery of the logs.
  • Give each source an owner and a health check so silent gaps get noticed.

In more detail

Log source onboarding is the engineering process of bringing a new telemetry source into a central logging or security analytics platform so that its events are collected reliably, parsed into a common schema and made usable by detections. It is more than pointing an agent at a server. The work spans scoping which events and fields actually answer questions, sizing and routing the transport path, agreeing a documented transport such as an authenticated syslog or agent channel, writing or tuning a parser so fields land in the right normalised slots, normalising timestamps and time zones, mapping identifiers to an asset inventory, setting retention and access, and then proving the whole chain end to end with a test event. Roughly half the effort sits after the first events appear in the console, which is where onboarding usually stalls: parsing errors, duplicated events, missing enrichment and clock skew quietly degrade every detection built on that source. The common mistake is declaring success when logs are visible, without a coverage check or a validation that a synthetic activity is detected. Mature teams therefore treat a source as a product with an owner, a documented schema, a health monitor and a scheduled review.

What you will practise

  • Explain what log source onboarding involves beyond installing a collection agent.
  • Identify the practical steps from scoping and transport to parsing, enrichment and validation.
  • Describe how timestamp normalisation, field mapping and asset context affect detection quality.
  • Recognise the operational risks of silent collection gaps, duplicate events and parser drift.
  • Describe how to validate a new source end to end and define ongoing health monitoring for it.
