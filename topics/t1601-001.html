T1601.001 Modify System Image: Patch System Image

T1601.001Defense ImpairmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

On many network devices, the whole operating system sits in a single file called the system image. This sub-technique describes an attacker editing that file. The edit can be saved to storage for the next restart, or made in memory while the device is running.

Why should you care?

The system image controls almost everything the device does, including security checks. One change there can disable encryption, weaken logins or hide new services. Worse, the attacker can edit the commands that report the device version, so the device lies about its own state. Trusting the device becomes unsafe until the image is verified and reloaded.

How it works, in plain steps

  1. The attacker first obtains administrative access to the target network device itself.
  2. They copy a modified operating system image onto the device, or edit the stored one.
  3. They change the boot setting so the device loads the altered image next time.
  4. Another route is editing live memory with built in debug commands, leaving no file change.
  5. A third route uses rogue code already in the boot loader, which patches the system as it starts.
  6. The altered system may then weaken defences, add hidden features or report false details.

Real-world example

Think of a night desk at a hospital. The rulebook on that desk tells the guard what to check and who may enter. A thief cannot remove the guard, so instead he rewrites a few pages of the rulebook. The guard still follows the book exactly, and nothing looks out of place to a visitor. Yet the new pages let the thief walk past the desk and even tell the guard that everything is fine. Patching a system image is that rewritten rulebook. The device keeps running and keeps answering questions, but the rules it follows are no longer the ones the vendor wrote.

Key takeaways

  • Verify system image hashes and signatures, not just the reported version string.
  • Log image transfers and boot variable changes on network devices.
  • A memory only patch vanishes after a restart unless the boot loader is also altered.

In more detail

Patch System Image is the sub-technique of Modify System Image in which the adversary changes the device operating system itself, either in storage so the change appears on the next boot, or in live memory so it takes effect immediately. Embedded network devices are usually monolithic: the operating system and most of the device functionality live in a single file or image, so one edit can alter routing, authentication, encryption and management at once. For the stored case the adversary uses ordinary operator procedures, transferring a replacement image over Trivial File Transfer Protocol, File Transfer Protocol, Secure Copy Protocol or a console connection, then pointing the boot variable at it. For the in memory case they use native debug commands that write to running code, or malicious code already planted in the boot loader, which is the first software to run at start up. Consequences range from weakened encryption, authentication or perimeter filtering, through added services such as hidden proxies or keystroke capture, to commands altered so they report false information, for example faking an old version number to hide a downgrade. Memory only patches disappear at reboot unless the boot loader is also modified. Detection is about integrity: image hash and signature verification, TFTP or file transfer logs on the device, configuration diffs, unexpected boot variable changes, reboots outside windows, and management sessions from unusual sources.

What you will practise

  • Explain what a monolithic system image is and why one edit has wide effect.
  • Describe how stored image replacement differs from live memory modification.
  • Identify transfer and boot records that reveal an unauthorised image change.
  • Explain how a patched command can mislead a defender checking device state.
  • Compare a vendor firmware upgrade with a tampered image.
  • Describe how boot loader code enables patching of the running system.
