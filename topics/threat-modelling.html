Threat Modelling

Secure EngineeringVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Threat modelling is a design-time exercise where you ask what could go wrong with a system and who might cause it. You map how data moves, find the weak points, and decide what to do. The result is a written list of threats and a decision for each. It happens before code is written, when changes are still cheap.

Why should you care?

Most security problems come from design choices, not from typing mistakes. Once a system is built, changing its structure is slow and expensive. A threat model finds those weak choices while they are still on a whiteboard. It also gives your team shared language about risk. Without it, you react to incidents instead of preventing them.

How it works, in plain steps

  1. You draw the system as boxes, arrows, and data stores on one page.
  2. You mark trust boundaries, where data crosses between areas with different owners.
  3. For each element and flow, you ask what an attacker could do.
  4. You write each threat as a sentence with an actor, an asset, and an impact.
  5. You rate the threats and choose to fix, transfer, accept, or remove each one.
  6. You store the model with the design and update it whenever the architecture changes.

Real-world example

Think of planning a trip before you leave home. You look at the route and ask what could go wrong. What if it rains, what if the car breaks down, what if a border is closed? For each risk you decide to carry an umbrella, buy cover, or change the route. Threat modelling is that planning conversation for software. You are still at the kitchen table, so changes cost nothing.

Key takeaways

  • Model threats at design time, when changes are cheap and fast.
  • Write each threat with an actor, an asset, and a real impact.
  • Keep the model alive and revisit it when the architecture changes.

In more detail

Threat modelling is a structured design-time technique for reasoning about what can go wrong in a system, who would want to make it go wrong, and which controls would reduce that risk, producing a documented set of threats that engineering teams can act on. The usual workflow has four parts: scope the system and draw its data flows across trust boundaries, enumerate plausible threats against each element and flow, rate them by likelihood and impact, and record a decision for each one as mitigate, transfer, accept or eliminate. Frameworks such as STRIDE help teams avoid blind spots by prompting per category, while attack-library mapping grounds the exercise in techniques that real adversaries use. For a practising engineer the value is not the diagram but the argument it forces: where does authentication actually terminate, which component can impersonate another, what happens when a message is replayed, who can read this store, and what does the audit trail miss. Good threat models are living artifacts tied to architecture decisions, reviewed when data flows or trust boundaries change, and written in language the delivery team already uses. Failures are predictable. The exercise becomes a compliance ritual with no owner and no follow-through. Models are built by a single architect and never validated against the running system. Threats are described abstractly, with no asset, actor or preconditions, so no control follows. Ratings are inflated until everything is critical and prioritisation collapses. Structured abuse-case derivation, adversarial review by a second team, and tracking threat entries to backlog items with acceptance criteria are what separate a useful model from a wall diagram.

What you will practise

  • You will be able to scope a system into components, data stores, flows and trust boundaries before enumerating any threat.
  • You will be able to derive threats from a data-flow diagram across authentication, authorisation, confidentiality, integrity, availability and repudiation concerns.
  • You will be able to write a threat statement with actor, asset, precondition and impact rather than a vague category label.
  • You will be able to rate threats using a documented scheme and defend the rating against scope creep.
  • You will be able to convert accepted threats into tracked backlog items with verification criteria.
  • You will be able to explain where threat modelling fails and why models decay when architecture changes are not fed back into them.
