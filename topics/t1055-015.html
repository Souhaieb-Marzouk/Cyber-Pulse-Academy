T1055.015 Process Injection: ListPlanting

T1055.015Privilege EscalationExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

ListPlanting hides malicious code inside a program that shows a list, such as a file browser window. Windows list controls can use a custom sorting function that the program provides. An attacker puts code into that program's memory and makes the control use it. When the list is sorted, the attacker's code runs inside the trusted program.

Why should you care?

The program that runs the hidden code is a normal trusted application with a visible window on screen. Nothing new appears in the process list, and file checks find nothing wrong at all. The attacker may also gain that program's access to files, network shares and other resources. Because the payload can be moved in small pieces using ordinary window messages, common monitoring rules may miss it. You should know that interface elements can carry code and not only display data.

How it works, in plain steps

  1. A list view control shows a collection of items inside a window on the screen.
  2. The control can use a custom sorting function, called a callback, that the program provides.
  3. The attacker copies code into the target program's memory using window messages or other methods.
  4. Some variants copy the payload two bytes at a time using ordinary window messages.
  5. The attacker makes an item or callback reference point at the planted code.
  6. Sending the sort message makes the control call that code inside the trusted program.

Real-world example

Imagine a shared flat with a chore rota pinned to the kitchen wall. The rule is simple, because whoever is listed as the sorter decides the order of jobs. One flatmate adds his own name as the sorter. Underneath his name he writes a short extra instruction. It says that when you sort the list you must first open the back door. Everyone else still sees a normal rota with normal names. On Sunday the flatmate on duty sorts the list as usual. The back door opens because the sorter's instruction ran.

Key takeaways

  • Interface controls such as list views can hold executable behaviour, not only display data.
  • Sorting callbacks are a convenient place to redirect code inside another program.
  • Small window messages can move a payload while avoiding the obvious memory write calls.

In more detail

ListPlanting hides code inside the memory of an application that uses a list view control, the standard Windows control that displays collections of items. Each list view keeps its settings inside a SysListView32 control in the owning process, and that control supports a custom comparison callback used when items are sorted. An adversary copies code into the target process, arranges for a callback slot or item data to reference that code, and then triggers the sort message so the control calls the planted code as though it were the legitimate sorting routine, which makes this a form of message passing attack. Some variants allocate memory first and then copy the payload through ordinary window messages two bytes at a time, deliberately avoiding the heavily monitored cross-process write function. Detection rests on unusual cross-process memory access, list view messages arriving from an unexpected sender, callback or item data pointing outside loaded modules, and code running in a process with no matching mapped image.
