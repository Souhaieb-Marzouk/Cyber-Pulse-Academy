DET0507 Detect browser session hijacking via privilege, handle access, and remote thread into browsers

DET0507Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This rule looks for programs touching a web browser in a way that lets them steal a live login session. A session is the short lived pass a site gives you after you sign in. The rule watches for an unexpected program reading browser memory or starting a thread inside the browser. It catches account takeover that does not use a stolen password.

Why should you care?

Attackers often skip passwords and steal the session itself, because a session is already trusted by the site. Multi factor authentication does not stop this, since the victim already passed it. The stolen session can be replayed from another machine until it expires. This makes the activity look like normal use, so it is easy to miss without memory and process telemetry.

How it works, in plain steps

  1. The endpoint agent records every process that starts, with its parent process and full command line.
  2. A second data source records when one process opens another, and which access rights it requests.
  3. The rule keeps only events where the target process is a known browser, such as Chrome or Edge.
  4. It then checks the source process. A script host or an unsigned binary is suspicious.
  5. Rights that allow memory reading or thread creation inside the browser push the score much higher.
  6. If the same host then talks to a site the browser was logged into, the two signals become one alert.

Real-world example

Imagine a gym locker room with an attendant. The attendant checks that you have a key before you open your locker. If someone borrows a key that is already inside, the attendant sees nothing wrong, because the key is real. This rule is the second attendant who also watches who is holding keys they never signed for.

Key takeaways

  • A stolen session works without a password and without a second factor.
  • Browser memory and handle access are the quietest place to steal it.
  • You must baseline how browsers use memory or the alert volume will be unmanageable.

In more detail

This detection strategy covers browser session hijacking, the technique tracked as T1185. A browser session is kept alive by cookies and tokens that live in browser memory and on disk, so an attacker who can reach those secrets takes over a logged in account without ever learning the password. The telemetry that makes this visible is process access reporting on the endpoint, where one process asks for rights over a browser process, handle requests to browser memory, remote thread creation inside a browser process, and network metadata that shows the same session being used from a different origin. In practice the strategy fails on volume rather than on coverage, because browsers constantly touch their own memory and duplicate their own handles, so any rule that does not baseline normal browser behaviour per build drowns the analyst in noise.

What you will practise

  • Explain what a browser session is and why taking it over bypasses password and second factor controls.
  • Identify the telemetry that records one process opening another process and the rights it asked for.
  • Describe which access rights over a browser are normal for helper software and which are not.
  • Baseline browser process behaviour per browser version before enabling this rule in production.
  • Correlate endpoint process access events with network use of the same session on one host.
  • Write a response step that ends the stolen session rather than only resetting the password.
