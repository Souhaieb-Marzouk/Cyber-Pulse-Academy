Content Security Policy

Application SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Content Security Policy is a set of rules that a website sends to your browser. The rules list which places the page may load code, images and styles from. If the page tries to load something from a place that is not on the list, the browser refuses. This stops a common attack where someone sneaks their own code into a page.

Why should you care?

Websites often build pages from content that users provide, such as comments or profile names. Attackers try to hide their own code inside that content so it runs in a victim's browser. A content security policy can block that code from running, even when the site makes a mistake. It also reduces the damage if a third party script you trust is changed. Without it, one small mistake can hand over your users' sessions.

How it works, in plain steps

  1. The web server adds a header to each page that lists the allowed sources for scripts, styles and images.
  2. The browser reads the list and blocks any request that does not match an allowed source.
  3. For small pieces of inline code, the server adds a random value called a nonce to each response.
  4. The page marks its own inline code with the same value, so the browser knows it is genuine.
  5. In report only mode the browser allows everything but sends a message about what it would have blocked.
  6. Teams use those reports to repair the page, then switch the policy to enforcing mode.

Real-world example

Picture a private club with a guest list at the door. The list names the few companies allowed to deliver food and drink. The doorman turns away anyone else, even if that person looks official. The club also gives each staff member a fresh paper pass every day, so an old pass cannot be reused. A content security policy works like that list and those passes. The browser is the doorman, the list is the policy, and the daily pass is the nonce.

Key takeaways

  • A policy that allows inline code or any source gives very little protection, so keep the list short.
  • Start in report only mode, repair the reported problems, then enforce the policy.
  • Use a policy as one layer, and keep cleaning and encoding user input as well.

In more detail

Content Security Policy is a browser-enforced allowlist, delivered as a response header or a meta element, that restricts which sources a page may load scripts, styles, images, frames and connections from. It works by directive. A default fallback covers unspecified resource types, script-src governs executable code, and directives such as base-uri, object-src and frame-ancestors close specific abuse paths. Because inline scripts cannot be matched by origin, modern policies attach a per-response nonce or a hash of the exact script content, and strict designs remove inline code altogether. A report-only mode lets a team collect violations without breaking the site, which is the normal way to roll a policy out safely. The policy shows up wherever reflected or stored script injection is a risk, turning a successful injection into a blocked request instead of executed code. The mistake is deploying a policy containing unsafe-inline and wildcard hosts, which satisfies a scanner while blocking almost nothing.

What you will practise

  • Explain what a content security policy is and how the browser enforces it.
  • Describe how nonces and hashes allow specific inline code while blocking everything else.
  • Explain the purpose of report only mode and of reporting endpoints.
  • Identify weak policy patterns such as broad wildcards and unsafe inline allowances.
  • Explain why a policy complements rather than replaces correct input handling.
