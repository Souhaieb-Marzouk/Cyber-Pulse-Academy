T1055.014 Process Injection: VDSO Hijacking

T1055.014Privilege EscalationExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

VDSO hijacking changes a small piece of code that Linux places inside every running program. That piece is called the virtual dynamic shared object, shortened to vdso. Programs use it to ask the system for common services very quickly. If an attacker rewrites part of it, the program calls attacker code instead.

Why should you care?

On Linux, programs share a helper library that the system maps into every process for speed. An attacker with a foothold can change how that helper behaves, so ordinary calls quietly go somewhere else. Because the program involved is a legitimate one, the activity hides under its trusted name. Tools that only look at files and process names will never see it. Defenders need memory checks and honest process maps to catch this kind of change.

How it works, in plain steps

  1. The Linux kernel maps a small shared object into every process, called the virtual dynamic shared object.
  2. Programs use the code inside it to make very common system calls without waiting.
  3. An attacker who is already inside a process rewrites those system call interface stubs.
  4. The attacker can also patch the global offset table, which stores addresses of library functions.
  5. Calls that should reach the real library now jump into code the attacker supplied.
  6. That code opens and maps a malicious shared library, and the hidden payload then runs.

Real-world example

Think of a large office building with a phone list by reception. Every department calls the front desk using the numbers printed on that list. Someone secretly replaces one number with his own extension. Now when staff dial the payroll office, they reach him instead, and he answers politely and takes the message. The printed building directory still shows the correct number, so nothing looks wrong on paper. Only a check of what is actually written on that list would reveal the change.

Key takeaways

  • The virtual dynamic shared object is shared memory the kernel maps into every Linux process.
  • Attackers redirect these fast helper calls to hide their code under a normal program.
  • Memory maps and offset tables reveal changes that file names never show.

In more detail

VDSO hijacking targets the virtual dynamic shared object, a small shared library the Linux kernel maps into every process so that common system calls such as reading the clock can be served without leaving user space. Memory protections may block an adversary from writing executable code into a process through debugger style system calls, but the same adversary can instead patch the syscall interface stubs provided by that mapping, or rewrite the global offset table entries that hold the resolved absolute addresses of library functions. Calls issued from the hijacked stub can then open and map a malicious shared object, and patched address references redirect the flow of the process into it. Detection is memory centric: a vdso region that is writable or whose contents differ from the kernel provided image, offset table entries pointing outside legitimate libraries, unexpected library preloading, and process memory maps showing executable anonymous or unexpected file backed regions.
