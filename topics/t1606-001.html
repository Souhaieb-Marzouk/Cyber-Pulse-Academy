T1606.001 Forge Web Credentials: Web Cookies

T1606.001Credential AccessExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A web cookie is a small note that a website stores in your browser so it knows who you are. This sub-technique describes an attacker writing a brand new cookie himself. He does not take yours. He invents one that the site accepts.

Why should you care?

If a site trusts a cookie only because it carries the correct signature, then whoever holds the signing secret controls every account. A fake cookie can be made for a senior administrator, so the attacker does not need that person at all. Login checks and second factors never come into play, because no login happens.

How it works, in plain steps

  1. The attacker recovers the secret value the site uses to sign its cookies.
  2. He studies the cookie format, which many common web frameworks document openly.
  3. He builds a new cookie claiming any user name, role and expiry date that he wants.
  4. He then signs it with that stolen secret, so the signature looks fully correct.
  5. He sends it to the site, which validates the signature and treats him as that user.
  6. The application sees an ordinary session and records no sign in event at all.

Real-world example

Imagine a swimming pool where members get a stamped wristband at the front desk. The lifeguard only checks the stamp, never a name list. A visitor cannot copy the wristband of a real member, so he hunts for the stamp in the manager drawer. Now he presses that stamp onto a blank band and writes any member number on it. The lifeguard checks the stamp, sees it matches and lets him into the pool. Forging a web cookie is that blank wristband. Nothing was stolen from a real member, yet the entry looks completely valid.

Key takeaways

  • Keep cookie signing secrets out of source code and rotate them after exposure.
  • Detect sessions that have no matching login or cookie issue event.
  • Compare session address and device details with the account usual pattern.

In more detail

Web Cookies is the sub-technique of Forge Web Credentials in which the adversary manufactures session cookies rather than collecting them from a victim browser. Many web applications keep a user signed in with a cookie whose contents are structured and signed: a user or session identifier, an issue and expiry time, sometimes roles or other attributes, and a signature or message authentication code produced with a server side secret. The formats are widely documented because frameworks use them in the same way, so once an adversary holds the signing secret, a private key, a password or another seed value, they can generate a cookie for any account and any role. It differs from Steal Web Session Cookie, where a real user cookie is copied out of a browser or network path: here nothing is taken from a user, and the cookie never existed before. The practical effect is that the adversary authenticates with material the application validates through its normal code path, so multi factor authentication adds no obstacle, since the second factor was satisfied earlier or belongs to another session. Detection is largely a matter of joining sessions to authentication events. Look for a session that starts with no sign in or token issue record, a cookie or session identifier that fails strict signature validation, metadata such as client address, browser or device that disagrees with the account history, a sudden first seen location, and privileges that exceed what the account normally holds. Legitimate sessions always trace back to an issued credential and a recorded login.

What you will practise

  • Recognise log evidence of a session with no preceding authentication.
  • Outline how session metadata comparison can expose a forged cookie.
