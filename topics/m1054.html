M1054 Software Configuration

M1054Enterprise MitigationExtremeMitigation

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Software configuration as a defence means changing settings away from the easy defaults and keeping them that way. It covers turning off unused features, closing legacy protocols, requiring logging, and hardening cloud services. Default settings are chosen for convenience, not safety, so they often help an attacker. The real challenge is drift, because settings quietly slip back over time.

Why should you care?

A single permissive setting can undo several other controls. If logging can be switched off by a local administrator, your audit trail is only a suggestion. If an old file sharing protocol stays enabled, an attacker gains a path that should not exist. Hardening removes these easy routes. It also stops small mistakes from growing, because a defined baseline tells you when something has changed.

How it works, in plain steps

  1. Start from a recognised hardening baseline for each type of system you run.
  2. Turn off services, protocols, and features that no one has asked for.
  3. Set logging and protection settings so they cannot be quietly switched off.
  4. Apply the same baseline to every server, workstation, container image, and cloud account.
  5. Scan continuously and alert when a setting drifts away from the baseline.
  6. Give each exception a named owner, a written reason, and an expiry date.

Real-world example

Think of a new flat with factory settings on the heating, the alarm, and the door entry. It works, but the default door code is written in the manual and the alarm is off. Moving in properly means changing the code, arming the alarm, and closing the windows that were open for viewing. Months later you check again, because the alarm can be switched off by anyone who gets annoyed by it.

Key takeaways

  • Change the defaults, then check regularly that they stayed changed.
  • Treat every exception as temporary, with an owner and an end date.
  • Preventive settings are useless if they can be switched off quietly.

In more detail

Software configuration as a mitigation is the deliberate hardening of applications, operating systems, and cloud services away from their permissive defaults, followed by the work of keeping that hardened state true over time. It covers disabling features that exist mainly as attack surface, such as legacy file-sharing dialects, name-resolution fallbacks that answer broadcast queries, obsolete scripting engines, and macro execution from internet-sourced documents; constraining command interpreters with logging and restricted language modes; requiring elevation through a separate administrative account for management tooling; and configuring services so that authentication, transport security, cipher suites, and audit settings match a defined baseline. In cloud estates the same idea appears as account-level and resource-level settings, public-access blocks, instance metadata hardening, and organisation policies that stop a workload owner from reverting a control by accident. The operational reality is drift. Baselines are applied at build time and then eroded by an application that needs an exception, an upgrade that resets a value, a container image that still ships the old configuration, or an operator under pressure who weakens a control to restore service. Teams that succeed treat baselines as code, scan continuously against them, alert on drift, and route exceptions through a named owner with an expiry date instead of leaving them undocumented. The control weakens defence-impairment attempts directly, because central logging configuration and tamper-protected agents remove the easiest routes to silencing telemetry, and it closes the autostart, macro execution, and script-interpreter behaviours that commodity intrusions depend on. Its limits are practical: an exception-heavy baseline is theatre, hardening that breaks operations gets rolled back, and no organisation controls the configuration of every third-party service it relies on.

What you will practise

  • Explain how a hardening baseline is derived, applied, and verified rather than assumed to be in place.
  • Identify default features and services that should be disabled or constrained, and the business justification each removal requires.
  • Detect configuration drift across endpoints, servers, container images, and cloud accounts using continuous scanning.
  • Assess how defence-impairment techniques exploit permissive logging and agent configuration.
  • Design an exception process with ownership, compensating controls, and expiry so that hardening stays credible.
  • Interpret the tradeoff between tightening configuration and preserving availability for legacy applications.
