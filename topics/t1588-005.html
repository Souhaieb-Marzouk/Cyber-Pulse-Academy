T1588.005 Obtain Capabilities: Exploits

T1588.005Resource DevelopmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An exploit is code that abuses a software bug to make a program misbehave. This technique is about attackers finding, buying, or stealing exploit code that already exists, instead of writing their own.

Why should you care?

Ready made exploits are widely shared and cheap, so many attackers can use them. Public exploits are usually detected quickly, but the private ones stay useful for a while. A system that is slow to patch stays exposed the whole time.

How it works, in plain steps

  1. The attacker looks for an exploit that matches software their target runs.
  2. They download it free from a public source or buy it from a seller.
  3. They may also modify it so that existing detection rules no longer match the code.
  4. They deliver the exploit through a malicious website, an email file, or a network service.
  5. It triggers the bug and gives them a way to run their own code.
  6. Defenders see crashes, strange child processes, and outdated versions on their network.

Real-world example

Think of a popular lock that many buildings use. Someone publishes a trick for opening it, and soon everyone knows the trick. A locksmith may sell a quieter version of the same trick to a few buyers. The building owner cannot stop people learning the trick, but fitting the new lock early removes the problem.

Key takeaways

  • Acquired exploits mean the attacker needs no deep knowledge of the bug.
  • Public exploits drive fast detection, so attackers modify them to evade rules.
  • Your patch speed decides how long an available exploit still works against you.

In more detail

This sub-technique covers buying, downloading, or stealing exploit code instead of writing it. It sits beside the develop capability equivalent, and the practical consequence of choosing this route is that the adversary need not understand the underlying bug at all, only how to deliver and trigger it. Sources include public proof-of-concept repositories, exploit databases, criminal marketplaces, exploit kits, and private brokers who sell to a limited number of buyers. Because a public exploit is visible to everyone, defenders fingerprint it quickly and detections appear within days, which pushes serious operators toward private or modified variants. That is also why adversaries watch exploit provider forums and vendor disclosure schedules, and sometimes target the researchers who hold unpublished findings. The window that matters is the gap between a vulnerability becoming known privately and the same vulnerability being patched widely; an exploit acquired inside that window still works against unpatched systems, and patch latency becomes the defender's real exposure. Attribution is genuinely difficult, because the same public exploit appears in unrelated campaigns, but defenders can still gain ground: exploit attempts leave crash records, unusual child processes spawned from service or reader applications, and exploitable services identified by version. Asset inventory and patch velocity therefore matter as much as any detection rule.

What you will practise

  • Explain how acquired exploits differ from self-developed ones in skill and detection.
  • Describe the public and private sources from which exploit code is obtained.
  • Explain why attackers modify public exploits and how that affects detection.
  • Identify the telemetry that suggests an exploit attempt on a host.
  • Explain how patch velocity reduces exposure to publicly available exploits.
