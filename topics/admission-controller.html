Kubernetes Admission Controller

Container & Kubernetes SecurityHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A Kubernetes admission controller is a gate inside a Kubernetes cluster. Kubernetes is a system that runs software in containers. The gate checks each request before the cluster saves it. If the request breaks your rules, the gate refuses it.

Why should you care?

Access rules alone only say who may send a request. They do not say what the request may contain. A developer with normal rights can still create a risky container. For example, one that runs as the root user. Admission control stops that before the container ever starts. Without it, your cluster policy is only advice.

How it works, in plain steps

  1. You send a request to the Kubernetes API server, for example to create a new pod.
  2. The server first checks who you are and whether you may do this.
  3. Before saving the object, the server passes the request to the admission controllers.
  4. A mutating controller may change the request, such as adding a security setting.
  5. A validating controller then reads the final object and accepts or refuses it.
  6. If any controller refuses, the object is never stored and the cluster stays unchanged.

Real-world example

Imagine a hotel where guests can send repair requests to the building manager. The front desk checks that the guest has a room key. The night manager then reads each request before it reaches the maintenance log. He refuses anything dangerous, like a request to switch off the fire alarm. Admission controllers are that night manager, and their rules are the checklist he keeps.

Key takeaways

  • Admission control decides what may exist in the cluster, not only who may ask.
  • A broken or unreachable webhook can block every matching request, so test it first.
  • Keep policy as versioned code, so every change can be reviewed and rolled back.

In more detail

A Kubernetes admission controller is a plugin in the API server request path that inspects or rewrites an object after authentication and authorisation succeed but before the object is persisted to etcd. Mutating controllers may modify the incoming request, for example injecting a sidecar or defaulting a field, while validating controllers can only accept or reject it; mutating controllers run first so that validating ones see the final object. Admission is where policy genuinely becomes enforceable, because it applies to every writer, including kubectl, controllers and continuous integration pipelines, and it can be scoped by namespace and service account. Webhook based admission lets you run your own logic, which introduces ordering, timeout and availability concerns: a webhook that cannot be reached can block every matching request, so failure policy and scope must be chosen deliberately. The common mistake is assuming that role based access control alone governs cluster state, when RBAC decides who may ask and admission decides what may actually exist.

What you will practise

  • Explain where admission control sits in the Kubernetes API request lifecycle.
  • Distinguish between mutating and validating admission and describe why the order matters.
  • Describe how policy can be enforced consistently across every writer, including pipelines.
  • Recognise the availability risk that a badly scoped admission webhook creates.
  • Explain to a developer why a request can be refused even when their access rights are sufficient.
