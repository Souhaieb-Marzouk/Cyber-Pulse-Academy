DET0063 Cross-Platform Behavioral Detection of Python Execution

DET0063Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for Python being used on computers in ways that do not match normal business work. Python is a programming language that runs from a command line. Attackers like it because it is already installed almost everywhere and can do many jobs without extra tools.

Why should you care?

A script can scan a network, collect files or talk to a control server. It leaves no compiled program for antivirus to recognise. The clue is not the language but the situation: who ran it, from which folder, and what happened next. Situation based detection survives small changes in the script.

How it works, in plain steps

  1. A host sensor records each new process and its full command line, including the interpreter name.
  2. It records the parent process, so you can see what started Python.
  3. It records network connections and file writes tied to the same process identifier.
  4. The SIEM (Security Information and Event Management system) groups these records by host and process.
  5. The rule compares each Python start against the normal pattern for that host and account.
  6. A Python run from a browser, an office file or a temporary folder followed by network traffic raises the alert.

Real-world example

Think of a hotel kitchen that owns one very sharp knife. Every cook uses it, so seeing the knife is meaningless. Seeing a guest carrying it up the stairs at midnight, however, tells you everything you need to know.

Key takeaways

  • Python itself is normal, so the detection is about context, not the interpreter name.
  • The parent process and the working folder are the strongest discriminator fields.
  • What the process does next, such as a new outbound connection, confirms the alert.

In more detail

This strategy detects the execution of Python interpreters and Python scripts across Windows, Linux and macOS endpoints, because Python is present by default on most systems and lets an intruder run complex logic without dropping a compiled binary. Instead of alerting on every interpreter start, which is unusable, it correlates the parent process, the script location, the command line switches and what the process does next, such as opening a network connection or writing a file. Telemetry comes from process creation records with command line capture, script block or module loading events where the platform provides them, and network connection events keyed by process identifier. The failure mode is that administrators, developers and automation frameworks run Python all day, so good asset and account scoping matters more than the pattern itself.

What you will practise

  • Explain why interpreted languages reduce reliance on dropped binaries for an intruder.
  • Identify the process creation fields that reveal interpreter name, parent and script path.
  • Correlate a Python process with its network connections and file writes by process identifier.
  • Build a per host baseline of legitimate Python use so that anomalies stand out.
  • Choose between broad audit logging and narrow alerting for developer heavy asset groups.
