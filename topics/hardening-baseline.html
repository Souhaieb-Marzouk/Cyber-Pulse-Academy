Hardening Baseline

Secure EngineeringHardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A hardening baseline is a fixed list of safe settings for one type of computer or program. You agree the list once, then apply it every time you build that system. It turns security advice into clear settings that a machine can check. The word hardening means making a system simpler and stronger, with fewer open doors.

Why should you care?

Default settings often favour convenience over safety. Many services start switched on, with example passwords or open network ports. A baseline closes those doors before the system meets the internet. It also makes audits faster, because you compare a system with a known list. Without a baseline, every engineer configures a machine in a different way, and nobody can say what normal looks like.

How it works, in plain steps

  1. Pick one type of system, such as a web server or a laptop image.
  2. Choose a trusted source of secure settings, such as a published benchmark.
  3. Decide which settings your team will enforce, and write down the reason why.
  4. Turn the list into a script or an image so every build receives it.
  5. Check running systems against the baseline and record each difference you find.
  6. Review the baseline on a fixed schedule, because software and threats change.

Real-world example

Think of a shared flat with a leaving checklist. Before a new flatmate moves in, you check the front door and the cooker. You also make sure the spare key is back in its box. Everyone follows the same short list, so nothing important is forgotten. A hardening baseline is that checklist for a server. It does not make the flat impossible to burgle, and a flatmate can still leave a window open later. That is exactly why you walk around again after the flat has been lived in for a while.

Key takeaways

  • A baseline is a short, agreed list of safe settings for one type of system.
  • Write the baseline as code, so every build starts from the same place.
  • Check for drift often, because a running system slowly moves away from the baseline.

In more detail

A hardening baseline is an agreed, version-controlled set of secure configuration settings applied to one class of system, such as an operating system build, a container base image, a database or a network device, and used as the reference for provisioning, auditing and drift detection. It typically constrains authentication settings, removes or disables unused services and legacy protocols, sets file and service permissions, enables audit logging, and fixes a minimum patch level. Published benchmarks and vendor security guides are the usual sources, but the baseline itself is the smaller, owned subset the organisation has decided to enforce. The mistake is treating the baseline as a document rather than as running code: systems keep getting built from an old image, nobody re-checks a live host, and the baseline quietly describes a world that no longer exists. A baseline only reduces risk when it is applied automatically at build time and verified continuously.

What you will practise

  • Explain what a hardening baseline is and why default settings are risky.
  • Describe how a published benchmark becomes an owned, enforced baseline.
  • Identify the categories of settings that most often appear in a baseline.
  • Explain how configuration drift is detected and corrected on running systems.
  • Update a baseline over time without breaking required business services.
