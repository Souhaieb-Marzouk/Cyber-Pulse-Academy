T1102.001 Web Service: Dead Drop Resolver

T1102.001Command and ControlExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A dead drop resolver is a small message that an attacker leaves on a well known website. Infected computers look there to find it. The message only shows where the real control server is. The victim machine reads it first, then connects to the real server from that address.

Why should you care?

The real control server stays hidden, so it is harder for defenders to find and block. The message sits on a trusted site, such as a social media page, which most networks allow anyway. When defenders block the control server, the attacker only edits the message to point somewhere new. Blocking the whole website would also break normal business work, so that answer is rarely good.

How it works, in plain steps

  1. The implant contains no fixed control address, only the address of a public page to check.
  2. The implant downloads that page, for example a profile, a pasted note or a file listing.
  3. A confusing or encoded string in the page is decoded into the real server address.
  4. The implant connects to that address and asks for its next set of instructions.
  5. The attacker can rewrite the page later so the same implant finds different infrastructure.
  6. Defenders must look past the website name and study which local program made the request.

Real-world example

Think of a public notice board in a library. A stranger pins a sealed envelope there with a phone number inside but no name on the outside. Your contact walks past the board each morning, opens the right envelope and learns where to meet that week. Nothing about the board looks wrong, because it is public and everyone uses it. The next week there is a new envelope with a new number.

Key takeaways

  • The resolver is only a signpost; the real control server is somewhere else.
  • The traffic often goes to a site your network already trusts, so blocking the domain usually fails.
  • Look at which process on the host checks the page, and how regularly it does so.

In more detail

A dead drop resolver hides the true command and control address behind content that an adversary posts on a legitimate public service, such as a social media profile, a paste site or a code repository. The implant does not carry the address of its handler. Instead it retrieves a page or record, decodes an embedded or obfuscated string, and only then contacts the real server. The resolver therefore acts as a pointer that can be changed at any time, so burned infrastructure is replaced without touching victims again. Because the request goes to a well known domain the victim host already used before compromise, network filtering and reputation checks rarely fire; the header, the user agent or the timing of the request is usually the only oddity. Detection leans on process attribution and beacon regularity: which local binary issued the request, and whether a host that never needed that service now polls it on a fixed schedule. The resolver is not itself the control server, so blocking the domain is usually the wrong move while the payload behind it stays unknown.

What you will practise

  • Explain how a dead drop resolver separates the address of an implant from the address of its handler.
  • Describe why content hosted on a legitimate web service provides cover for command and control traffic.
  • Identify the network and process telemetry that reveals a host repeatedly retrieving hidden address data.
  • Distinguish resolver lookups from ordinary browser and application traffic on the same service.
  • Summarise how resolver content can be edited so that blocked infrastructure is replaced without new infections.
