DET0133 IDE Tunneling Detection via Process, File, and Network Behaviors

DET0133Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Remote development means working on a computer that is not in front of you. A developer uses a tool that opens a connection from that computer out to a service. The service then sends commands back through the same connection. Attackers abuse the same feature to reach inside a network. This detection looks for those tunnels and for what they run.

Why should you care?

Many networks block incoming connections but allow almost anything to leave. A tunnel uses an outgoing connection, so it passes those controls. The tool is usually well known and signed, so it does not look suspicious. An attacker can then run commands on that machine as if sitting at it. This detection helps you spot interactive access that your firewall rules were meant to stop.

How it works, in plain steps

  1. The rule watches for a tunnel client binary being written into a user folder.
  2. It records the process that starts that binary and the arguments it uses.
  3. It looks for child processes such as shells, script hosts, or build tools.
  4. Network records show one long lived encrypted connection to the vendor service.
  5. Domain name queries to the tunnel service are counted for each host and user.
  6. An analyst then checks whether the user is a known developer on a managed device.

Real-world example

Picture an office where the front door is locked and guarded. Nobody can walk in from the street, and the company feels safe. Now imagine an employee opens a window and drops a rope. A stranger outside climbs the rope and stands in the corridor. The front door was never touched. A development tunnel is that rope. It leaves from the inside, so the guards at the front door never see anyone enter.

Key takeaways

  • A tunnel starts from inside, so inbound firewall rules cannot stop it.
  • Join the binary, the child processes, and the long lived connection.
  • Developers use these tools for real work, so identity and device health matter.

In more detail

IDE tunneling (T1219.001) covers the abuse of legitimate remote development features, such as a command line tunnel client or a hosted remote development gateway, to give an external operator interactive access to a host that never had to accept an inbound connection. It matters because the tooling is signed, vendor hosted, and encrypted, so signature checks and inbound firewall rules raise no objection, and the resulting session looks exactly like an ordinary outbound connection. The detection strategy therefore joins three individually weak signals: a tunnel client binary being downloaded or installed into a user profile, the child processes that client spawns such as shells, script hosts, and build tools, and long lived outbound encrypted or WebSocket sessions from developer tooling to the vendor service. It fails often because developers legitimately use these features daily, because sanctioned and unsanctioned use of the same product are byte for byte identical on the wire, and because the client may arrive through an approved software package rather than a download.

What you will practise

  • Explain how remote development tunnels provide interactive access without inbound ports.
  • Identify the file, process, and network events that a tunnel session leaves behind.
  • Correlate a tunnel session with the child processes that it spawns.
  • Separate sanctioned developer use from an operator on an unmanaged or non developer host.
  • Describe the containment steps for an unauthorized tunnel session.
