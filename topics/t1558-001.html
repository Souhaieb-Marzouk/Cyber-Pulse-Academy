T1558.001 Steal or Forge Kerberos Tickets: Golden Ticket

T1558.001Credential AccessExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A golden ticket is a fake ticket-granting ticket (TGT) made with the secret key that signs all tickets in a domain. Kerberos trusts any ticket that carries the right signature. The attacker can write any name and any group into that ticket, even a user who does not exist. Unlike the parent technique, this is forgery rather than theft, because nothing was copied from a real login.

Why should you care?

One stolen domain key lets an attacker act as almost anyone, including a domain administrator. The fake ticket may keep working for a long time, which gives the attacker years to return. Ordinary password resets do not help, because the signing key itself must be changed. Detection is difficult, since services see a ticket that is correctly signed. Without a baseline of normal ticket behaviour, organisations often discover this only after data has gone.

How it works, in plain steps

  1. The attacker first obtains the password hash of the KRBTGT account, usually from a domain controller.
  2. That account is the one the domain uses to sign and encrypt every Kerberos ticket.
  3. With that hash, the attacker builds a complete ticket-granting ticket offline, outside the domain.
  4. They choose the username, the group list and a much longer validity period than policy allows.
  5. They then ask a domain controller to trade the fake ticket for service tickets.
  6. Services accept those tickets, so the attacker reaches whatever the invented identity may reach.

Real-world example

Imagine a hotel where the front desk programs each room key with a secret pattern. A guest copies the master pattern that is used to program keys. With it, they can make a key for any room, and even invent a room number that does not exist. Staff at each door accept the key, because the pattern is right. The front desk still records that someone came to collect a key, so records do exist. Only by comparing those records with the keys it actually issued can the hotel notice the fake one.

Key takeaways

  • The KRBTGT key is a domain wide secret, so protect domain controllers with care.
  • Reset the KRBTGT password twice to invalidate existing golden tickets.
  • Look for tickets whose lifetime or identity does not match your policy.

In more detail

A golden ticket is a forged ticket-granting ticket (TGT) created with the password hash of the KRBTGT account, the domain account that the Key Distribution Center (KDC) uses to encrypt and sign Kerberos tickets. Because every domain controller trusts that key, a ticket signed with it is accepted as genuine, and the attacker can place any username, any group membership and a long lifetime inside it, including an identity that does not exist. Unlike a silver ticket, the attacker still talks to the KDC to exchange the forged TGT for ticket-granting service (TGS) tickets, so the domain controller does observe issuance activity. Detection therefore focuses on the mismatch between what a domain controller issued and what it can account for: TGS requests whose TGT was never issued in that domain, TGT lifetimes far beyond domain policy, encryption types or account names that do not match the directory, and Kerberos events where the ticket identity has no corresponding authentication. The nearest legitimate pattern is a long-lived service session, so policy values and the account's real existence decide it.

What you will practise

  • Explain why the KRBTGT account key is trusted by every domain controller.
  • Describe how a ticket-granting ticket can be forged offline and then exchanged for service tickets.
  • Explain how this sub-technique differs from a silver ticket and from a stolen ticket.
  • Identify the Kerberos events that suggest a ticket was forged rather than issued.
  • Describe the recovery steps that invalidate forged ticket-granting tickets.
