Patch Management

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Patch management is the work of keeping software up to date with fixes from its maker. A patch is a small update that repairs a known problem. The job includes knowing what you run, testing the fix, and installing it everywhere it is needed.

Why should you care?

Most break ins use flaws that already have a fix. Attackers simply look for the systems nobody updated. If you skip updates, one old laptop or forgotten server can open the way in. Updates also fix ordinary bugs, so the work helps stability as well as security. The hard part is doing it on time, every time, without breaking anything.

How it works, in plain steps

  1. Keep a current list of every device, operating system, application and appliance you are responsible for.
  2. Watch the security notices from your software makers and note the fixes that apply to you.
  3. Rank the fixes by how exposed the system is and whether attackers are already using the flaw.
  4. Test the fix on a small group of machines to catch problems before they reach everyone.
  5. Roll the fix out in waves, starting with the most exposed systems and keeping a rollback plan.
  6. Scan again afterwards to prove the new version is installed, and record any system you chose to delay.

Real-world example

Picture a shared block of flats with one front door. The lock maker sends a better lock cylinder to every flat. If one tenant leaves the old cylinder in place, the whole building is still easy to enter. So the building manager keeps a list of flats and orders new cylinders. She fits one as a test, then works through the rest. Afterwards the manager walks the corridor and checks each door, rather than trusting that the work was done.

Key takeaways

  • You cannot patch what you have not inventoried, so the asset list comes first.
  • Prioritise by exposure and real exploitation, not by severity score alone.
  • Always verify with a fresh scan instead of trusting the deployment job.

In more detail

Patch management is the governed process of finding out which software versions you run, learning which of them have known defects that affect security, and getting fixed versions onto those systems in a controlled way. It is a lifecycle, not an event: inventory, advisory intake, risk based prioritisation, test, staged deployment, verification, and documented exception handling. The security value comes from shrinking the window between a fix becoming available and the fix being applied, because public exploits and mass scanning typically appear quickly once a vulnerability is disclosed and a patch exists. Modern practice prioritises by exposure and exploitability rather than by severity score alone: an internet facing service with a known exploit outranks a higher scored library that is unreachable. The usual failure is organisational rather than technical. Teams own the scanning tool but nobody owns the firmware, the appliances, the container base images, or the third party managed device, so those sit unpatched for years. A second common error is treating a successful deployment job as proof of remediation, when only a fresh scan showing the new version closes the loop.

What you will practise

  • Explain what a patch is and why unpatched software is a primary route for attackers.
  • Describe the stages of a patch management lifecycle from inventory to verification.
  • Prioritise a set of updates using exposure, exploitability and business criticality.
  • Explain why testing and staged rollout reduce the risk of an update causing an outage.
  • Describe how exceptions and risk acceptance should be documented with an owner and an expiry.
  • Recognise devices that are commonly missed by patch programmes, such as firmware and appliances.
