M1027 Password Policies

M1027Enterprise MitigationVery hardMitigation

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A password policy is the set of rules that control how passwords are created, stored, checked, and retired. Modern advice favours long passwords, screening against lists of passwords already leaked, and limits on repeated guessing attempts. It no longer favours forcing people to change good passwords every month. The policy applies to every system, not only the main directory.

Why should you care?

Weak or reused passwords remain one of the easiest ways in. Attackers take a list of leaked passwords and try them across many accounts, hoping one fits. A good policy raises the cost of that guessing and blocks passwords already known to be breached. It also matters that bad storage does not undo the work: if a stolen password file is easy to crack, the policy on the front door means little.

How it works, in plain steps

  1. Set a minimum length, such as twelve or more characters, because length helps more than odd symbols.
  2. Check new passwords against lists of passwords exposed in past breaches, and refuse matches.
  3. Store passwords with a salted slow hash, which is a one-way scramble that takes real effort to reverse.
  4. Throttle repeated failed logins from one source, and alert on guessing spread across many accounts.
  5. Tune lockout carefully, because a strict lockout lets an attacker freeze any account they can name.
  6. Apply the rules to service accounts, applications, and cloud logins, not just the main directory.

Real-world example

Think of a door lock on a shared office. A short, obvious code is easy for a burglar to try, and the same code reused on every door is worse. The building manager now insists on longer codes, refuses codes already published in an old breach list, and fits a delay after several wrong tries. Staff also stop changing a good code every month, because that only pushed them to write it on a sticky note.

Key takeaways

  • Prefer long passwords and breached-password checks over forced monthly changes.
  • Slow repeated guessing, and watch for many accounts tried at once.
  • Password policy cannot fix a password you reuse on outside websites.

In more detail

Password policies are the enforced rules that govern how credentials are created, stored, transmitted, throttled, and retired across an identity estate. Current practice has moved away from mandatory rotation and character-mix requirements toward minimum length, screening against corpora of known-breached passwords, per-account throttling and lockout, and secure storage using salted, deliberately slow hashing. Forced periodic changes with symbol substitution reliably produce predictable mutations that add little entropy, while punishing users and generating helpdesk load. Implementation spans several planes that rarely share one policy: on-premises directory domains with both domain-wide and fine-grained settings, cloud identity providers with their own complexity, lockout, and banned-password controls, hybrid synchronisation that can silently preserve legacy behaviour, service and machine accounts that frequently sit under a separate or exempt policy, and application-local credential stores that no central policy reaches at all. Lockout thresholds deserve deliberate tuning because a low threshold hands an adversary a denial-of-service lever against any username they can guess, so risk-based throttling is usually the better trade than a hard lockout. The control raises the cost of online brute force and password spraying, and breached-password screening at set and change time makes credential stuffing materially less productive. It also reduces the chance that a weak or reused credential becomes the valid account an intruder needs. Its limits are decisive: once stored hashes leave the estate, policy protects nothing, spraying under the lockout threshold remains viable, legacy authentication protocols can bypass modern settings, helpdesk resets are a social-engineering target, and credential reuse on external sites is outside the organisation's control entirely.

What you will practise

  • Explain why length, breached-password screening, and throttling outperform forced rotation and character-complexity rules.
  • Tune lockout and throttling thresholds against the denial-of-service risk they create for known accounts.
  • Identify the identity planes that escape a central password policy, including service accounts and application-local stores.
  • Interpret credential storage requirements well enough to judge what a stolen password database is worth to an attacker.
  • Evaluate how password spraying evades common lockout settings and which telemetry exposes it.
  • Articulate where password policy stops being useful and multifactor authentication must take over.
