T1559 Inter-Process Communication

T1559ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Programs on one computer often need to talk to each other. Inter-process communication, or IPC, is the set of ways they do that. A program can ask another program to do work, such as fetching data or running a task. Attackers abuse these channels to run code through a program that already has permission. The parent technique is about local execution: the attacker stays on the machine but hides behind a trusted helper.

Why should you care?

Security tools often trust well known programs, and attackers borrow that trust. Because the request looks like normal software cooperation, no strange file needs to appear on disk. This makes the activity hard to spot with file scanning alone. Attackers also use IPC when they cannot start a new program directly. If you only watch network traffic, you will miss it completely.

How it works, in plain steps

  1. Two programs on the same computer need to share information or coordinate their work.
  2. The operating system offers channels for this, such as shared memory, pipes and brokers.
  3. A broker program accepts requests and performs actions for the program that asks.
  4. An attacker sends a request of their own through a channel the broker already trusts.
  5. The broker then runs the action, so the activity appears to come from a trusted program.
  6. Defenders see process relationships and object use, not a suspicious file on disk.

Real-world example

Think of an office where managers may send tasks to the IT desk by internal mail. The IT desk only checks that the request came from inside the building, not who signed it. A visitor slips a request into the internal mail tray and asks for a new door pass. The IT desk completes the task happily, because the request arrived through the trusted channel. No outsider ever entered the office, and no alarm went off. The only trace is a request form with an unusual name on it.

Key takeaways

  • Trusting a helper program means trusting everyone who can send it requests.
  • Watch process parents, not only process names, when hunting for local execution.
  • Limit which accounts may activate powerful brokers and named objects.

In more detail

Inter-process communication (IPC) is the set of mechanisms an operating system provides so that processes can exchange data, coordinate work and avoid deadlock, and those same mechanisms can be repurposed to run code. The technique covers abuse of local channels rather than a memory corruption bug: a process with the right permissions asks a broker, a named object or another running process to do work on its behalf, and the execution happens inside a process that may look trusted. On Windows the visible surfaces include the Component Object Model (COM), Dynamic Data Exchange (DDE) and named pipes, while Unix-like systems provide sockets, pipes and shared memory. Because the calls are legitimate, the artefacts are relationships rather than obvious malicious files: unexpected parent and child process pairs, a trusted host such as a spreadsheet starting a system utility, named pipe creation and connection events, and activation records for the broker that was used. Detection therefore needs process creation telemetry with command lines and parentage, plus object level auditing. The practical discriminator is whether the caller had a reason to invoke that broker.
