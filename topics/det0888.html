DET0888 Detection of Software

DET0888Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Software fingerprinting means working out which programs and which versions a company uses. Attackers do it to match a known weakness to your systems. This detection watches your web and network logs for the repeated probing that this work produces.

Why should you care?

Old software often has known weaknesses, and public lists describe them in detail. An attacker who can name your exact version does not have to guess. The probing may look like harmless requests for missing pages, so it is easy to ignore. Catching it early tells you which systems are interesting to an outsider, and often that a system needs patching or hiding.

How it works, in plain steps

  1. Web servers, reverse proxies, and load balancers log every request, including the path, the source address, and the response code.
  2. The detection builds a list of paths and headers that reveal product names and versions.
  3. It groups requests by source address so that a series of probes becomes one event.
  4. Repeated requests that return not found or forbidden codes raise the score, because they are guesses.
  5. Enrichment adds reputation and your own asset data, so you know which system was probed.
  6. An alert names the source, the targeted service, and the exact paths requested.

Real-world example

Think of a burglar checking letterboxes for the name of the alarm company. Asking one neighbour is harmless. Walking the whole street and reading every alarm box, then noting which houses have the oldest model, is preparation. Your web logs are the street, and the requests are the glances at the alarm boxes.

Key takeaways

  • Version probing shows up as requests for files that belong to a specific product version.
  • User agent strings alone prove very little, because anyone can change them.
  • Frequent probing of one service is a reason to reduce its exposure and confirm it is patched.

In more detail

This strategy detects software and version fingerprinting against your environment, mapped to MITRE ATT&CK T1592.002 (Gather Victim Host Information: Software). An adversary who knows you run a specific web framework, content management system, mail gateway, or remote access product at a specific version can choose an exploit with a high chance of success, which is why banner grabbing and path probing are common first steps. The activity is visible mainly at service edges rather than on endpoints: reverse proxy and web server access logs, firewall and intrusion detection records, transport layer security handshake metadata, and honeypot interactions. The strongest signal is repeated requests for files and paths that only exist in particular product versions, from one source, in a short window. The strategy fails when it relies on user agent strings alone, because the string is easy to fake and ordinary crawlers look similar, so path and response behaviour must carry the decision.

What you will practise

  • Explain how software and version knowledge shapes an adversary's exploit choice
  • Identify request, response, and handshake telemetry that reveals software fingerprinting
  • Distinguish version probing from ordinary crawler traffic and from application errors
  • Write a grouped detection that counts suspicious paths per source per time window
  • Map a confirmed probe back to the exposed asset and its patch status
