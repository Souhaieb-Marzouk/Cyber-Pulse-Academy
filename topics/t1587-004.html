T1587.004 Develop Capabilities: Exploits

T1587.004Resource DevelopmentExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An exploit is a piece of code that uses a bug in software to make it do something it should not do. Developing exploits means an attacker writes that code themselves. They do not wait to download someone else's version.

Why should you care?

Software you own almost certainly has unknown bugs. An exploit made for one of those bugs can be used before any fix exists. Attackers often keep these tools private, so antivirus signatures may never match them. This is why behaviour matters more than known bad files.

How it works, in plain steps

  1. The attacker learns about a weakness in a program or in a hardware device.
  2. They study the vendor's update, or they crash the program on purpose to learn more.
  3. They write code that triggers the bug in a controlled, repeatable way.
  4. They test the exploit until it works on the exact version they target.
  5. They deliver it through a malicious file, a website, or a network service.
  6. They use it to run their own code, raise their rights, or hide their actions.

Real-world example

Imagine a hospital night desk with a locked medicine cabinet. The lock was designed to open only with a specific key card. Someone notices that jamming the card slot in a certain way makes the lock pop open. Nobody sells that trick, so they practise it on a spare cabinet until it works every time. That practised trick is a developed exploit.

Key takeaways

  • A private exploit may have no antivirus signature at all.
  • Patch analysis and fuzzing are how developers find bugs to exploit.
  • Detect exploitation by behaviour and crashes, not just by file names.

In more detail

This sub-technique describes an adversary writing their own exploit code to attack a bug in software or hardware, rather than downloading or buying one. The work starts from a known vulnerability, often found through vulnerability intelligence, patch analysis of a vendor update, or fuzzing, which means feeding malformed input to a program until it crashes in an interesting way. The result is a reliable trigger that drives the target into unintended behaviour such as memory corruption or command execution. Developing an exploit takes specialised skills, so an organisation may build it in house, hire specialists, or contract the work while keeping the resulting tool exclusive. The exploit is then used at various stages of an intrusion: against an internet-facing service, against a client application, for privilege escalation, for defence evasion, for credential access, or against remote services. For a defender the practical difference between a bought and a self-developed exploit is timing and exclusivity. A bespoke exploit has no public proof-of-concept, no exploit kit signature, and no known malware family, so signature-based detection may miss it entirely. Defensive value comes from crash telemetry, abnormal process trees, and behavioural rules around suspicious child processes, not from matching known exploit code.

What you will practise

  • Define an exploit and explain what it does to a running program.
  • Describe how patch analysis and fuzzing support exploit development.
  • Explain why a self-developed exploit is harder to detect than a known one.
  • List the intrusion stages where a developed exploit is commonly used.
  • Identify the telemetry that can reveal exploitation attempts on a host.
