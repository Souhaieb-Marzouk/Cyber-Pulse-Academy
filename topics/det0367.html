DET0367 Detect Network Logon Script Abuse via Multi-Event Correlation on Windows

DET0367Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A logon script is a small program that Windows runs for a user each time that user signs in. This detection looks for someone changing which script runs, or changing the script file itself, so that their own code runs on other people's computers. It catches the change and the later execution together.

Why should you care?

Logon scripts run automatically, so nobody has to click anything. They also run with the rights of the user who signs in, which may be an administrator. A single change can therefore reach many computers at once. This is why the change itself is worth an alert. Normal help desk work rarely edits these settings.

How it works, in plain steps

  1. Collect registry monitoring events that record changes to the user logon script setting under the Windows environment keys.
  2. Collect file change events for the shared folders that hold the logon scripts.
  3. Collect process creation events, including the parent process name and the full command line.
  4. Correlate the three sources by host and by user, and keep only events that fall inside one short window.
  5. Flag the case where a script process such as a command shell or a script host is started by a logon process on several hosts in a short time.
  6. Raise an alert that shows the changed path, the account that made the change, and the hosts that then ran the script.

Real-world example

Think of a night watchman in an office building. Each evening he reads the duty list that is pinned by the door. If someone quietly swaps that list for a new one, the watchman will still follow it, because he trusts the door. This detection watches the pinboard, not the watchman.

Key takeaways

  • A logon script change is a persistence method that survives reboots and password changes.
  • The registry or policy change matters most, because execution follows only at the next sign in.
  • Correlating the change with later process starts turns a weak signal into a strong one.

In more detail

This strategy detects abuse of network logon scripts, which an adversary registers so that Windows runs attacker-controlled code in the context of every user who logs on. The technique usually leaves three traces that must be correlated: a write to the UserInitMprLogonScript registry value or to a script path referenced by Group Policy, a modified script file on a share that many hosts can read, and then a burst of script host child processes started shortly after interactive logons. Singly, none of these looks unusual, because logon scripts are a normal part of domain life. The detection fails in practice when the environment has no baseline of which script paths are legitimate, when script block logging is disabled, or when the monitoring window is shorter than the gap between the registry write and the next logon.

What you will practise

  • Explain what a network logon script is and how it differs from a normal user program.
  • Identify the registry setting and the shared script paths that this technique abuses.
  • Correlate a configuration change with the process activity that follows it on other hosts.
  • Recognise benign script management by administrators and separate it from abuse.
  • Describe which telemetry gaps would hide this technique in your own environment.
