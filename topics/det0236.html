DET0236 Detection Strategy for Spearphishing Attachment across OS Platforms

DET0236Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for harmful files that arrive as email attachments. An attachment is a file sent along with a message. The message may look trustworthy, which is why people open the file. This detection connects three things. It looks at the mail that arrived and the file saved on the computer. It also looks at the program that started when that file was opened.

Why should you care?

Email reaches everyone in the company and bypasses many technical controls. A single opened attachment can give an attacker a foothold on a workstation. The harmful action often happens seconds after the file is opened, in a different program. Joining the mail record to the computer record is what turns a vague warning into a clear alert.

How it works, in plain steps

  1. The mail gateway records each message, including the attachment name, type, and a file fingerprint.
  2. The endpoint agent records every new file, with the folder it was saved into.
  3. The rule matches a file on the computer with the attachment from the message.
  4. It then watches for a program starting from that file.
  5. It looks for risky pairings, such as a document reader starting a scripting engine.
  6. An alert opens with the sender, the attachment, and the command that ran.

Real-world example

Think of a parcel delivered to an office reception. Reception logs the sender and the box. Then a colleague carries the box upstairs and opens it. Only by joining the reception log to the person who opened the box can you trace the parcel.

Key takeaways

  • Join the mail record to the endpoint record, because neither side is convincing alone.
  • Watch the risky pairing of a document program starting a scripting engine.
  • Tell users what to do with a suspicious attachment, since they are part of the defence.

In more detail

This strategy detects spearphishing attachments, tracked as ATT&CK T1566.001, by correlating inbound mail with the attachment file that lands on the endpoint and the process that opens it. It matters because the attachment is the delivery step that turns a message into code execution, and the compromise usually becomes visible only when a document or archive spawns a scripting host, which may be several minutes after the mail arrives and on a different log source entirely. The telemetry that makes it detectable is mail gateway or mail server records of the attachment name, type and hash, endpoint file creation events in mail cache and download directories, and process creation events showing an office application or archive tool as the parent of a script interpreter. The main failure mode is that the correlation window and file naming differ across platforms, and legitimate macro enabled documents sent by finance, legal, and operations teams produce the same parent and child process pattern, so the rule needs both a mail context signal and a suspicious child process to stay useful.

What you will practise

  • Describe the delivery chain from inbound mail to attachment execution on the endpoint
  • Collect mail gateway metadata including attachment name, type, hash and recipient
  • Identify endpoint file creation in mail cache, download and temporary directories
  • Detect suspicious parent and child process relationships after an attachment is opened
  • Reduce false positives from legitimate macro enabled business documents
  • Define user reporting and containment steps for a confirmed malicious attachment
