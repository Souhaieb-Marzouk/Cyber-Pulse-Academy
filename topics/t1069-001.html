T1069.001 Permission Groups Discovery: Local Groups

T1069.001DiscoveryExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Every computer keeps its own short list of groups and their members. This is separate from any company wide directory. This technique is an attacker reading only that local list. It is a smaller version of the parent technique, which covers all kinds of groups.

Why should you care?

The local list shows who can act as an administrator on that one machine. An attacker who has a normal user account wants that name. The activity creates almost no network traffic, so network monitoring may never see it. Only the machine itself records what happened.

How it works, in plain steps

  1. The attacker lists every local group on the computer they have reached.
  2. They then list the members of the groups that carry extra rights.
  3. On Windows a built-in utility does this, and PowerShell commandlets can do the same.
  4. A second route asks the machine over the network instead of running a local command.
  5. On macOS a directory tool lists groups, and on Linux they sit in a plain text file.
  6. The results tell the attacker which account to steal or imitate next.

Real-world example

Imagine a small office with its own key cupboard, separate from the main company key system. A courier delivering a parcel steps inside and reads the label on the cupboard door. It says who in this office holds the master key. He writes one name down. He has not touched the cupboard, and head office never hears a thing. This cupboard belongs to the local office alone. Local group discovery is reading that one label.

Key takeaways

  • Local group listings leave evidence only on the machine itself.
  • Installers and helpdesk tools run the same commands, so context matters.
  • A listing of local administrators followed by other activity is a strong lead.

In more detail

Local groups discovery is the narrow version of permission group enumeration: it reads only the account and group database stored on the host the attacker already controls, with no query to a central directory. That scope matters operationally, because it produces almost no network traffic and therefore evades controls that watch directory servers. On Windows the classic behaviour is the built-in net utility listing groups and then listing the members of the local administrators group, with a scripting equivalent available through the local accounts commandlets in PowerShell. A second route reads the same information through a remote procedure call interface rather than a command line, which shows up as a network connection from a remote host instead of a local process. On macOS a directory services command line tool lists groups, and on Linux the information sits in a plain text file that can be read with a group listing utility or simply opened. The artefact trail is mostly local: process creation telemetry such as Windows Security 4688 or Sysmon 1 capturing the utility name and its arguments, PowerShell script block logging for the commandlet route, and shell history on the Unix side. The benign lookalike is real and common, because software installers, logon scripts, and helpdesk tooling run the same commands, so a useful detection either baselines which processes normally run them or looks for the pair of a group listing followed closely by membership listing for a privileged group by an interactive user session.
