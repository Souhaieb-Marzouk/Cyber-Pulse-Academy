DET0104 Detect Modification of Authentication Processes Across Platforms

DET0104Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches the parts of a system that check passwords and logins. The rule looks for changes to those parts. A change made quietly can let an attacker log in without a valid password.

Why should you care?

If you control the login check, you control who gets in. Attackers who change it can create a hidden way in and stop using noisy tools. The change often survives reboots and password resets. Because normal password checks still work, users and helpdesk staff may notice nothing at all.

How it works, in plain steps

  1. The endpoint records changes to the system settings and files that handle logins.
  2. Identity platforms record administrative actions such as adding a federation trust or changing token settings.
  3. These records are forwarded to the central log platform, often a SIEM, which means Security Information and Event Management.
  4. A rule matches the changed path or setting against a list of authentication locations that should rarely change.
  5. It then checks the process and account that made the change. It also checks whether the new file is signed by a known vendor.
  6. When a protected location changes without a matching change ticket or signed update, the rule alerts the identity team.

Real-world example

Think of a building where the front desk checks every visitor's pass. Someone replaces the desk staff with their own person, who waves in whoever says the right phrase. The door still opens normally, cameras still record, and no alarm sounds. This detection is the manager who keeps a photo of the official desk staff. The manager then notices a new face behind the counter.

Key takeaways

  • Controlling the login check gives an attacker their own accounts and quiet access.
  • The strongest signals are changes to authentication files, registry keys and federation settings.
  • Signature and author of the change matter more than the change itself.

In more detail

This detection strategy covers T1556, modification of authentication processes, where an adversary changes how a host, an application or a directory service decides whether a login is valid. On Windows this includes registry changes to authentication packages and password filter dynamic link libraries, on Linux it includes edits to the pluggable authentication modules stack, and in cloud identity it includes changes to federation trust or token signing configuration. It matters because this technique converts a one time compromise into a durable, low noise credential of its own: valid accounts keep working, and the attacker no longer needs a remote access tool. The telemetry that makes detection possible is registry modification events for authentication related keys, file change auditing on authentication module directories, cloud identity audit logs for federation and authentication method changes, and the service restart that usually follows. It fails in practice because many of these paths are changed by legitimate software installs and vendor upgrades, so the rule has to look at who made the change, the signer of the new component and the process that wrote it.

What you will practise

  • Explain why modifying authentication logic gives durable access without extra tooling
  • Name the Windows, Linux and cloud identity locations that implement authentication
  • Identify which audit events capture registry, file and federation trust changes
  • Describe how to distinguish a vendor upgrade from an unauthorised authentication change
  • List the accounts and roles that should be the only ones able to change these settings
  • Explain why password resets and reboots do not remove this kind of access
