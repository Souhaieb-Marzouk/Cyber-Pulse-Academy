T1556.001 Modify Authentication Process: Domain Controller Authentication

T1556.001PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A domain controller is the server that checks logons for a whole Windows network. This technique means an attacker changes the logon service on that server. After the change, one special password works for every account in the domain.

Why should you care?

One domain controller protects every account in the organisation, including administrator accounts. A change here can give an attacker the keys to the whole network. The attacker still appears as a normal user in the logs, which makes the activity very hard to spot. Because the change lives in memory only, it disappears at the next reboot and leaves few traces behind.

How it works, in plain steps

  1. The attacker first gains high rights on a domain controller somewhere inside the network.
  2. They insert a secret password into the running authentication service in memory.
  3. The changed service still checks real passwords, so normal users notice nothing at all.
  4. If the secret password appears, the service accepts it for any domain account.
  5. The attacker then signs in as an administrator without knowing the real password.
  6. A reboot clears the change, so the attacker may need to repeat the whole step.

Real-world example

Imagine a large school where the reception desk checks every visitor against a list. One day somebody adds a line to the desk rule book. Anyone who says the word pineapple may enter any classroom. Staff still check normal visitor names, so nothing feels different during the day. The intruder walks past the desk, says the magic word, and enters the head teacher's office. When the rule book is reprinted overnight, that line disappears, so the intruder must add it again.

Key takeaways

  • A domain controller compromise changes the scale of the incident to the entire domain.
  • Monitor which code loads inside the authentication process on domain controllers.
  • Unexplained successful logons for accounts with unchanged passwords deserve review.

In more detail

This sub-technique narrows authentication tampering to the domain controller, the server that validates logons for an entire Windows domain, instead of a component on a single host. A widely documented example injects a master password into the running Local Security Authority Subsystem Service, so the patched service accepts that value for any domain account while still validating genuine passwords normally. Because the patch lives only in memory, a reboot clears it, which is why the technique is usually paired with a way to reapply it. The result is domain-wide single-factor bypass: the attacker signs in as any user, including administrators, without knowing that user's password. Artefacts include threads or modules appearing inside the domain controller authentication process, in-memory code that no longer matches the service binary on disk, and successful logons for accounts whose passwords were never changed. Legitimate service restarts, security agents and operating system updates also load code into that process, so defenders should compare loaded module signers and hashes against a known baseline and watch for successful authentications from unusual source hosts.

What you will practise

  • Explain why tampering on a domain controller affects every account in the domain.
  • Describe how a password injected into memory can bypass single-factor authentication.
  • List host and identity evidence that suggests the authentication service was patched.
  • Explain why the change is lost at reboot and what that means for detection.
  • Contrast this sub-technique with changes to local authentication on a single host.
