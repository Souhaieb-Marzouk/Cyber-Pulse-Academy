Key Management Service

Cloud SecurityVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A key management service is a cloud service that creates, stores and uses encryption keys for you. Encryption keys are the secret values that lock and unlock protected data. The keys never leave the service, so your programs ask it to encrypt or decrypt instead of handling the key themselves.

Why should you care?

Encryption is only as strong as the protection of its key. If the key sits in a config file or a code repository, anyone who finds it can read everything. A key management service keeps keys in hardened hardware and records every use. It also lets you disable or delete a key, which instantly makes the data it protects unreadable.

How it works, in plain steps

  1. You create a key in the service and write a policy saying who may use it.
  2. Your program sends data to the service and asks it to encrypt that data.
  3. The service returns scrambled data, called ciphertext, and never shows you the key.
  4. For large files, the service first makes a data key, encrypts the file with it, then protects that data key with the main key.
  5. When someone needs the data back, the service checks permission and returns the readable form.
  6. Every use is written to an audit log, and rotation replaces keys on a schedule.

Real-world example

Think of a bank vault. You never carry the vault key around. Instead you ask a clerk to lock or unlock your box, and the clerk checks your identity first. The vault also keeps a written record of every visit. If you ever close your box permanently, nobody can open it again, not even you.

Key takeaways

  • Keep encryption keys in a managed service, never in code or config files.
  • Control who may use a key, because that controls the data itself.
  • Deleting a key is permanent, so protect that action with extra approval.

In more detail

A cloud key management service is a managed, hardware-backed system for creating, storing, rotating and auditing cryptographic keys, and for performing encryption and decryption without ever exposing the key material to the caller. Applications and services call an API to encrypt or decrypt, and the service enforces authorisation through the same identity and policy machinery as the rest of the platform, so control of a key is a control of the data it protects. Two design patterns dominate practice. Envelope encryption wraps data with a data key, then wraps that data key with a long-lived key that never leaves the service, which allows large objects to be encrypted efficiently while keeping the root secret in hardware. Customer-managed keys add an explicit policy and lifecycle that the customer controls, enabling rotation schedules, automatic rotation, grants, cross-account access and the ability to disable a key and render data unreadable. Security professionals focus on several recurring problems: keys with policies that allow broad principal access, keys shared across environments, disabled or scheduled-for-deletion keys that break services, missing audit trails on decrypt operations, and key material that is replicated into a region an organisation did not intend to use. Because destruction is irreversible, key lifecycle decisions are treated as high-risk change, and separation of duties between those who can use a key and those who can delete it is a standard control.

What you will practise

  • You will be able to explain envelope encryption and why data keys are wrapped rather than used directly on large objects.
  • You will be able to read a key policy and determine which principals can encrypt, decrypt, manage or delete a key.
  • You will be able to design rotation, cross-account access and separation of duties for customer-managed keys.
  • You will be able to triage alerts on key policy changes, disabling and scheduled deletion.
  • You will be able to describe the blast radius when a key is destroyed and how to plan for recovery.
  • You will be able to verify that audit logging captures key usage and that encrypt and decrypt events are retained.
