T1098.004 Account Manipulation: SSH Authorized Keys

T1098.004PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This is a sub-technique of account manipulation. It means an attacker adds their own public key to a server's list of trusted keys for a user. SSH is a tool for logging into another computer remotely, and it can use a key instead of a password. With the matching private key, the attacker logs in freely, and no password is needed.

Why should you care?

A key added this way survives password changes, because the account password is not used at all. It also creates no failed logins or lockouts, so many alerts stay silent. On cloud systems the key can be added through an online interface, so the attacker never needs to touch the server itself.

How it works, in plain steps

  1. The attacker generates a key pair, keeping the private half and using the public half as their mark.
  2. They append that public key to the user's authorized keys file on the victim host.
  3. For a home directory, that file lives inside the hidden .ssh folder of the user.
  4. They may also edit the SSH server settings to allow root login or enable key authentication.
  5. On cloud instances they instead add the key through the provider interface or a metadata command.
  6. The platform then writes that key into the instance, and later logins look completely normal.

Real-world example

Imagine a flat where the front door has an electronic lock that remembers fingerprints. A visitor presses their own fingerprint into the lock's memory while nobody is watching. The tenants never changed the door code, so nothing seems wrong. The visitor now opens the door at any time, and the lock happily reports a valid entry.

Key takeaways

  • Monitor the authorized keys files for additions and removals, not just for content.
  • Cloud metadata and instance APIs can change SSH keys without any command on the server.
  • Correlate a new key with the first login that used it and check the source address.

In more detail

This sub-technique of account manipulation is about adding an attacker-owned public key to the SSH authorized keys file so that the holder of the matching private key can log in as that user without a password. The file normally sits in the user's home directory on Linux and macOS, and in a per-user location on ESXi hosts, where key authentication is the usual way to manage the system remotely. Attackers add entries directly with shell commands or scripts, and they may also edit the SSH server configuration to make sure public key authentication is enabled or to permit direct root login. In cloud environments the same result is reached without touching the guest file system: metadata services and instance APIs accept new keys, which the platform then writes into the instance. The resulting login is legitimate at the protocol level, so detection depends on change visibility. File integrity monitoring on the key file, process telemetry showing writes to it, cloud audit records for metadata or instance updates, and command history give the change away, while a successful login from a new address using a key no administrator recognises confirms it.

What you will practise

  • Explain how this sub-technique differs from the parent account manipulation technique.
  • Describe how public keys are added locally and through cloud platform interfaces.

  • Distinguish an authorised key rotation from an adversary key addition.
  • Explain why key based persistence survives password rotation.
