T1558.005 Steal or Forge Kerberos Tickets: Ccache Files

T1558.005Credential AccessExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

On Linux and macOS, Kerberos keeps your tickets in a small file called a credential cache. The file lets you open many services without typing your password again. Anyone who copies that file can use your tickets from another machine. This sub-technique is about stealing those files. Unlike the forged tickets in this technique, nothing here is faked: the ticket is real and simply changes hands.

Why should you care?

A cache file is as powerful as the password that created it, until the ticket expires. On shared or poorly separated systems, one user can often read another user's cache. Attackers then use the copied tickets to move sideways, because the target service sees a valid user. No password cracking is needed, so the attack is fast. Cleaning up afterwards means invalidating those tickets, which many teams never do.

How it works, in plain steps

  1. You log in with Kerberos, and the system writes your tickets into a cache file.
  2. The file usually sits in a temporary directory and is named after your user identifier.
  3. An environment variable tells the Kerberos tools which cache file they should use.
  4. An attacker with local access copies that file, or points the variable at their own copy.
  5. They then use the copied tickets to reach services as you, with no password.
  6. Attackers may also convert the file into the Windows ticket format for further movement.

Real-world example

Imagine a theatre cloakroom where each coat is stored behind a numbered ticket. Once you hold a ticket, the attendant hands over the coat without asking who you are. A visitor copies a ticket from an unattended coat pocket. Later they show the copy and collect a coat that is not theirs. The attendant follows the rules perfectly, because the ticket is genuine. The theatre only notices afterwards, when it checks whether the same ticket was used twice.

Key takeaways

  • Treat credential cache files as secrets, with permissions that limit who can read them.
  • Clear cached tickets at logout, and invalidate them after an incident.
  • Watch for processes reading cache files that are not your normal Kerberos tools.

In more detail

Credential cache files store Kerberos tickets on disk for systems that do not keep them in a Windows style cache, and they are the Unix counterpart to the ticket material attackers dump from Windows memory. On Linux the file is usually named after the user identifier in a temporary directory, its location is chosen by the KRB5CCNAME environment variable or the Kerberos configuration file, and it is created at authentication and removed at logout. On macOS the cache is normally held in memory and addressed by a session identifier. An attacker with local access reads or copies that file and points the environment variable at the copy, which lets them authenticate as the ticket owner without the password, an instance of pass-the-ticket. Detection depends on file and process telemetry rather than network events: reads of cache files by processes that are not the user's shell or Kerberos tools, copies into unusual directories, unexpected KRB5CCNAME values, and authentications from a host the ticket owner never used. Administration scripts also read these files, so the caller and the copy destination matter.

What you will practise

  • Identify file, process and authentication evidence that reveals stolen cache files.
