T1136.003 Create Account: Cloud Account

T1136.003PersistenceExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This sub-technique is when an attacker creates a new account inside a cloud service, such as a hosted email, storage or server platform. Cloud providers call these user accounts, service accounts or roles. The account lives in the provider systems rather than on one computer, so it works from anywhere.

Why should you care?

Cloud accounts can be created in seconds and need no software on any machine. A small account with access to one service is easy to overlook among the many that already exist. If nobody reviews the cloud activity log, the account can stay unnoticed for a long time. It also survives rebuilding every server in the company.

How it works, in plain steps

  1. The attacker gains rights in the cloud tenant, which is the company space inside the provider.
  2. They create a new user, or a service identity meant for programs rather than people.
  3. Providers differ, so one may use service principals and another service accounts or roles.
  4. The new identity is given access only to a few services, which keeps it less visible.
  5. Extra access keys or roles may then be added to widen what the identity can reach.
  6. The provider logs the creation and the identity that performed it, with a time and address.

Real-world example

Think of a large shared office building with a central directory board in the lobby. A visitor with access to the directory adds a new company name to the board and a mailbox for it. The lobby system then issues a working access card. Cleaning staff and security walk past the board every day, and the new name looks like every other name.

Key takeaways

  • Cloud identities need no software on any machine, so host based defences do not see them.
  • Small identities with narrow access are harder to notice than obvious administrators.
  • Review the provider activity log for identity creation by unexpected accounts.

In more detail

Cloud account creation is the persistence variant in a hosted identity service, where the intruder adds a user, service principal or role based identity instead of a machine or directory account. Providers differ in how they model this: one directory service offers user objects plus service principals and managed identities that can be attached to applications, functions or virtual machines; another offers service accounts that can be linked to resources and impersonated; and a third has no service account concept and instead grants resources permission to assume a role. An attacker with sufficient rights in the tenant or subscription creates a small identity with access only to one or two services, which keeps it out of broad administrator reports and reduces the chance of anyone noticing. The audit record is the provider activity log rather than a host event, and the patterns worth alerting on are creation by an unexpected principal or from an unusual address, service principals added outside deployment tools, and a newly created identity immediately receiving credentials or role assignments. Baselines matter because deployment automation creates identities constantly, so the useful question is whether the creating principal normally does that job.

What you will practise

  • Explain what a cloud account is and how it differs from a local or domain account.
  • Describe how service accounts, service principals and roles differ between providers.
  • Identify the provider log that records account creation and the identity that created it.
  • Explain why narrow, service specific accounts reduce an attacker chance of detection.
  • Describe how a new cloud account is strengthened with extra credentials or roles.
