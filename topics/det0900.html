DET0900 Detection of Defense Impairment

DET0900Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Defence impairment means making protective tools stop working or see less. This detection looks for changes that switch off, weaken or hide a security control. It catches the act of disabling the protection.

Why should you care?

Security tools are what slow an attacker down. The first thing many attackers do is turn those tools off or make them blind. This step is often quiet and easy to miss. It happens before the loud, damaging actions, so catching it early gives you a chance to react.

How it works, in plain steps

  1. You collect events when a service starts, stops or changes its start type.
  2. You collect security product health events. These say whether protection is on or off.
  3. You collect registry changes. Many settings, such as real time protection, live in the registry.
  4. You check which account made the change and from which process or remote session.
  5. You check whether other controls changed at the same time, such as logging or backup.
  6. You correlate the changes into one alert with a clear timeline for the analyst.

Real-world example

Think of a museum with smoke detectors in every room. A thief does not smash the detectors, because the alarm would sound. Instead the thief switches off one loop. The panel shows a small fault light that nobody reads. The rooms look protected, but one whole wing is blind. Defence impairment is that quiet switch in the power room.

Key takeaways

  • Disabling protection is usually a planned step, not an accident.
  • Several control changes in a short window matter far more than one.
  • You must baseline legitimate administrative changes, or the alert queue is unusable.

In more detail

This detection strategy covers defence impairment as a class of behaviour: actions that stop, weaken or blind the security controls on a host or in a cloud tenancy. It covers technique T1687 and matters because impairment is both a goal in itself and a common precursor to destructive payloads, so an early detection buys time before damage. The telemetry that makes it possible is service state change events, security product health and tamper events, registry writes to control configuration, cloud audit logs for policy and logging changes, and process creation showing the utilities used to make those changes. In practice the strategy fails because administrators, patching tools and licence expiry all produce the same events, and because a disabled control often raises no alert at all while the attacker is still gathering access. The reliable pattern correlates the state change with the actor, the channel used, and whether another compensating control also changed in the same window.

What you will practise

  • List the endpoint and cloud controls whose change of state should generate a detection
  • Read security product health and tamper events to confirm that protection has actually stopped
  • Correlate a control disable event with the account, process ancestry and remote session behind it
  • Explain why multiple control changes inside a short window indicate a coordinated attempt
  • Design an alert that distinguishes a maintenance window change from an unscheduled one
  • Describe the recovery steps and evidence to capture when impairment is confirmed
