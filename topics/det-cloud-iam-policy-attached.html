Cloud IAM Policy Attached to New Principal

Detection StrategyExtremeDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

In cloud platforms, identity and access management controls what each account or role may do. A principal is any identity, such as a user, a service, or a role. A policy is the written list of permissions. This detection flags permissions being attached to a principal that never held them before.

Why should you care?

Cloud permission changes last until somebody reverses them. A password reset does not remove a role that an intruder gave to a quiet account. Such a grant survives your clean-up and becomes a way back in later. These changes are often the moment stolen credentials turn into lasting control. Watching them gives you a signal that password rotation cannot erase.

How it works, in plain steps

  1. Cloud platforms write an audit record for every identity change, naming who did it and what changed.
  2. The detection reads those records for policy attachments, new roles and trust changes.
  3. It extracts the acting identity and the identity that received the new permissions.
  4. It compares that pair against the last few months of similar changes in the same account.
  5. A brand-new pair raises an alert, with more weight when broad permissions were granted.
  6. The tool then searches the following hours for actual use of the new permissions.

Real-world example

An office building issues badges that open specific doors. An administrator adds a new door to somebody's badge, and that change keeps working for months. If an intruder reaches the badge system, they quietly add their own account to the room holding the servers. Changing every employee password afterwards does not remove that door access. Somebody must review the permissions themselves.

Key takeaways

  • Permission grants outlive password resets, so they need their own alert.
  • A permission change made outside your normal automation is worth a look.
  • Check whether the new permission was actually used soon afterwards.

In more detail

Cloud IAM policy attached to new principal detection identifies the first successful attachment of a permission policy or role to a principal that has never held that grant before in the account, which is the primary mechanism by which an intruder converts stolen cloud credentials into durable, higher-privileged access. The behaviour matters because cloud identity changes are effectively permanent until someone reverses them: a newly attached administrative policy, a trust relationship modified to allow an unfamiliar identity provider, or a role assumption path added for an external account all survive credential rotation and are frequently used to create a hidden maintenance path back into the environment. The telemetry required is cloud control plane audit logging for policy attachment, role creation, trust policy modification and identity provider changes, capturing the acting principal, its address and user agent, the target principal and the policy or role document, together with identity inventory that establishes which principals are human, service or federated, and change management records showing whether the action was requested. The signal survives common evasion because the control plane must record the state change for the platform to function; whether the operator uses the console, a command line interface, an infrastructure as code pipeline, a software development kit call or a serverless function, the resulting audit event identifies the acting identity. Persistent access created through a separate account, a token issued outside the audited organisation, or a session obtained by assuming an existing role may not be visible at the point of creation but the assumption itself produces its own audit record. The detection breaks down in practice because platform and application teams attach policies routinely and legitimately, infrastructure as code re-applies the same attachments repeatedly, and break-glass administration generates single occurrences that look identical to abuse. Baselines must therefore be per target principal and per acting principal, change pipelines must be attributed rather than excluded, and severity should depend on whether the attached permissions are administrative, whether the acting principal normally performs identity work, and whether the action happened outside a pipeline context, from an unusual address, or was followed by immediate use of the new permissions.

What you will practise

  • Explain why identity control plane changes outlive credential rotation and deserve durable detection rather than one-off review.
  • Query cloud audit logs for policy attachment, role creation and trust policy modification with actor attribution.
  • Establish per-account baselines of normal identity change authorship, including infrastructure as code service identities.
  • Identify high risk grant shapes such as broad administrative policies, cross-account trust, and external identity providers.
  • Correlate a new grant with subsequent use of the permissions it enables to distinguish planned change from abuse.
  • Draft the response steps that remove unauthorised access without disrupting legitimate deployment automation.
