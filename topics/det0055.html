DET0055 Detection strategy for Group Policy Discovery on Windows

DET0055Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for programs that ask which rules apply to a computer or to a user. Those rules are managed centrally and they are called group policy. Attackers read them to learn password rules and to find weak machines. This rule watches for the tools that read those rules.

Why should you care?

The rules tell an attacker how the network works. Password rules show how hard a guessing attack must try. Script rules show which machines allow automation. That knowledge saves the attacker time and reduces the chance of an alert. Reading the rules is quiet, so it rarely triggers other controls. Your own systems also read the rules, which makes context essential.

How it works, in plain steps

  1. The operating system records an event each time it processes its policy settings.
  2. The agent records process creation with command lines, including known policy reporting tools.
  3. The rule separates the automatic system reader from a person or script running a report.
  4. It looks at how many different policy areas one session requested in a short time.
  5. It checks the account type, because an ordinary user asking for a full policy report is unusual.
  6. A scripting host, a standard user account, and broad queries together raise the alert.

Real-world example

Picture a hotel guest who asks the receptionist for every rule in the building. The list includes quiet hours, pool access, laundry times, and staff key storage. One question is normal. Asking for all of them at once is not. Group policy discovery detection notices the guest who collects every rule in one visit. It ignores the guest who only asks about breakfast.

Key takeaways

  • The rules themselves are not secret, but the collection of all of them at once says an intruder is planning.
  • The operating system reads policy constantly, so the account type and the tool used are the keys to this rule.
  • Discovery often comes right before an attempt to change policy, so treat a match as an early warning.

In more detail

This detection strategy covers T1615, Group Policy Discovery, where an adversary queries the directory and the local machine to learn which policies, password rules, logon scripts, and software restrictions apply in the environment. It matters because the answers shape everything that follows: which accounts will break out of a password spray, which hosts permit script execution, and where the domain trusts point. The telemetry that makes it visible is endpoint and directory level: process creation showing the native policy reporting tools, script block logging for the policy reporting commandlets, registry access to the local policy cache, and directory service query records for policy container objects. The main failure is that the operating system itself reads policy at every logon, and administrators generate reports routinely, so the rule must key on the account type, the frequency, and the breadth of the queries rather than the tool name alone.

What you will practise

  • Explain what group policy is and why an attacker would enumerate it.
  • Identify the policy processing events and process telemetry that reveal policy discovery.
  • Distinguish automatic system policy reads from manual reporting by a person.
  • Write a pseudo rule that flags policy reporting tools run by non administrative accounts.
  • Describe how directory service query records add context to a policy discovery alert.
  • Explain how this activity relates to later attempts to modify policy settings.
