DET0882 Detection of Web Services

DET0882Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection looks for signs that an attacker rents web hosting and uses it against you. The hosting is normally a normal cloud service, so the service itself is not the problem. The detection watches which web addresses your computers talk to, and flags the new or unusual ones.

Why should you care?

Attackers need somewhere to run their tools and store their files. Renting web services is cheap, fast, and hard for them to trace. The rented server is far away, so your team cannot look inside it. Your only chance to notice is the traffic leaving your own network. If you never baseline that traffic, the first clear sign is usually an alert from a security tool that is already infected.

How it works, in plain steps

  1. Your proxy, firewall, and domain name system (DNS) servers record every connection your computers make to the internet.
  2. A parser turns those records into simple rows: which computer, which address, which port, and at what time.
  3. The detection compares each destination with your baseline of normal destinations for that computer and user.
  4. It adds outside context, such as how old the domain is and whether the hosting range is known for abuse.
  5. Each connection gets a score. High scores raise an alert with the destination, the host, and the account involved.
  6. An analyst reviews the alert, checks the file or page involved, and decides whether to block the destination.

Real-world example

Think of a night watchman at a warehouse gate. He writes down the registration plate of every van that enters. One strange van is not a crime, because new suppliers arrive all the time. But if the same unknown plate visits three times in one night, and the company records say the van was only registered yesterday, he calls the manager. That is what this detection does with web addresses.

Key takeaways

  • You cannot see inside the attacker's rented server, so detection works from your own network records.
  • The alert is a scored suspicion, not proof, because normal cloud traffic looks similar.
  • Baselines and outside context do most of the work. Lists alone are always out of date.

In more detail

This detection strategy covers the abuse of rented web services as attacker infrastructure, mapped to MITRE ATT&CK T1584.006 (Compromise Infrastructure: Web Services). Adversaries rarely own servers; they rent cheap hosting, serverless functions, or content delivery networks and use them for command and control, payload staging, and phishing pages. Because you cannot instrument a provider you do not own, detection depends on watching your own egress: proxy and firewall connection records, DNS resolution logs, and TLS certificate metadata, enriched with external data about recently registered domains and hosting address space. The strategy fails in practice in two ways. First, legitimate business traffic to cloud providers and content delivery networks looks almost identical to adversary traffic, so naive rules drown analysts in noise. Second, adversaries rotate destinations faster than reputation feeds update, so a purely list-based rule misses first contact. The realistic goal is scoring and prioritising new or rare destinations rather than proving malice from a single connection.

What you will practise

  • Explain how adversaries use rented web services for command and control and payload staging
  • Identify the egress telemetry that makes this technique visible without access to the remote host
  • Build a destination baseline for a host group and describe normal cloud usage in it
  • Write a scored detection rule that uses domain age and hosting reputation as enrichment
  • Triage an alert by checking the process, user, and destination before blocking traffic
