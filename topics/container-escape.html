Container Escape

Cloud SecurityExtremeKeyword

Container escape is the class of techniques by which a process confined to a container reaches the underlying host, another tenant's container, or the cluster control plane, converting a workload compromise into infrastructure compromise. Containers share the host kernel, so the boundary is enforced by kernel features such as namespaces, control groups, capabilities, mandatory access control profiles and seccomp filters rather than by a hypervisor, and escape generally follows from a configuration or kernel flaw that weakens those controls. Recurring categories include privileged containers that hold effectively all capabilities and device access, containers mounting the host filesystem or the container runtime socket, excessive Linux capabilities combined with writable host paths, host namespace sharing for networking or process identifiers, kernel vulnerabilities reachable from within a container, and misconfigured runtime or orchestration components that trust client input excessively. The consequences of a successful escape are severe because the host usually holds credentials: node identity, cluster service account tokens, cloud instance role credentials reachable through the metadata endpoint, and secrets mounted for other workloads. Defensive practice therefore concentrates on preventing the conditions rather than only detecting the technique: forbid privileged mode and host path mounts, drop capabilities, run read-only root filesystems, apply seccomp and mandatory access control, isolate with user namespaces or sandboxed runtimes, restrict access to the runtime socket, and assume that any workload with host access has already compromised the node.

What you will practise

  • You will be able to explain why containers share the host kernel and how namespaces, capabilities and mandatory access control form the boundary.
  • You will be able to identify workload configurations that make escape trivial, including privileged mode, host paths and runtime socket mounts.
  • You will be able to design admission policy that blocks the preconditions for escape before deployment.
  • You will be able to describe what credentials and mounted secrets become reachable after a node is compromised.
  • You will be able to triage container escape indicators such as host namespace access and unexpected device usage.
  • You will be able to rank escape paths by realistic exploitability and business impact for a report.
