Explained in plain language

Simple definition

API security is the work of protecting application programming interfaces. An API is a way for two computer programs to talk to each other. An API is not a page for people to click on, but a door for software. API security makes sure only the right program may use that door.

Why should you care?

Most modern applications are built from APIs. Mobile apps, websites and business partners all call them. One weak endpoint can expose every customer record at once. Attackers like APIs because a single well chosen request returns a large amount of data. Without careful checks the interface answers politely.

How it works, in plain steps

  1. A client program sends a request to an API address together with some data.
  2. The API checks the caller's token, a small credential that proves identity.
  3. It then checks whether that caller may act on that exact object.
  4. The data is validated against an expected shape before any real work starts.
  5. Limits on request rate stop one client from using all the resources.
  6. Every call is logged, so the team can see who did what later.

Real-world example

Think of a bank counter where you fill in a paper slip. The clerk checks your signature. She then checks that the account written on the slip is really yours. A lazy clerk only checks the signature and then hands over any account that you name on the slip. That is the classic API mistake, called broken object level authorisation.

Key takeaways

  • Check on the server that this caller may touch this specific object.
  • Return only the fields the client truly needs, never the whole record.
  • Keep an inventory of endpoints, including old ones nobody still maintains.

In more detail

API security is the discipline of protecting application programming interfaces, the machine to machine interfaces that now carry most application traffic, including mobile clients, partner integrations and internal service calls. It focuses on authentication and per endpoint authorisation, per object authorisation, strict input and schema validation, rate limiting and quota, safe error handling, and the logging needed to reconstruct which principal called which resource. The structural difference from a web page is that an API documents and exposes its full logic to any client, so the recurring failures are broken object level authorisation, mass assignment, excessive data exposure, unbounded resource consumption and unsafe business logic rather than injection alone. Discovery matters as much as hardening, because undocumented, shadow and deprecated endpoints usually survive the retirement of the user interface that used them. The mistake teams make is placing a web application firewall in front of the API and considering the topic closed, when the control that prevents most API breaches is a server side check that this caller may act on this specific object.

What you will practise

  • Explain what an API is and why its security needs differ from a web page.
  • Describe the difference between authentication and per object authorisation.
  • Identify the common API failure patterns such as excessive data exposure and mass assignment.
  • Explain how rate limiting and logging reduce API risk in production.
  • Describe how to find undocumented or deprecated endpoints on your own estate.
