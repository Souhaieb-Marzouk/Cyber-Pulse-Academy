DET0293 Detect Hybrid Identity Authentication Process Modification

DET0293Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Many companies let staff sign in to cloud services with their normal work account. A special service connects the cloud sign in to the company directory. If an attacker changes that connection, they can create their own way in. This detection watches for changes to that sign in service.

Why should you care?

The change gives the attacker access that survives a password reset. It often looks like an ordinary administrative setting rather than a break in. Because the same console is used for regular maintenance, the change can sit unnoticed for months. A single altered trust can affect every account in the company at once.

How it works, in plain steps

  1. The cloud identity service records every change to directory, domain and authentication settings with the acting account.
  2. The rule keeps the changes that touch federation, authentication policy or sign in method configuration.
  3. On premises records show changes to the account used for directory synchronisation, and to agent services.
  4. The rule compares the acting account with the small list of identities allowed to change authentication.
  5. Any change without a matching approved change request is scored as suspicious and reviewed.
  6. The response checks the current trust settings and the sign in logs for the period right after the change.

Real-world example

Think of a building where the front desk phones head office to confirm every visitor. Now imagine someone quietly changes the phone number that the front desk dials. Every future check still happens, and every visitor still looks approved, because the calls simply go to the wrong place. Nobody notices the problem for a long time, which is why the checking process itself must be watched.

Key takeaways

  • Authentication configuration is a high value target, so changes to it deserve immediate review.
  • A successful impersonation here survives password resets, so the fix must remove the trust.
  • Compare every change against an approved change record, because the API view looks the same.

In more detail

This strategy detects modification of the authentication process that joins a cloud identity provider to an on premises directory, which adversaries abuse to keep signing in even after passwords are reset. The target is the trust itself: federation settings, claim or policy rules, authentication agent configuration, and the synchronisation account that bridges both worlds. Detection depends on cloud audit logs that record directory and policy changes, identity server event logs for trust and agent changes, and directory change auditing for the synchronisation account in Active Directory. The strategy fails in two ways: changes made by the legitimate identity administrator look identical at the API level, and the components involved are frequently updated by approved maintenance, so the rule needs a change record comparison and a tight list of who may legitimately alter authentication configuration.

What you will practise

  • Describe how a hybrid identity setup connects a cloud provider to an on premises directory.
  • Name the settings whose modification can grant durable authentication access.
  • Explain why password resets do not remove access created this way.
  • Correlate cloud audit records with on premises directory and service changes.
  • Use approved change records to separate maintenance from hostile modification.
