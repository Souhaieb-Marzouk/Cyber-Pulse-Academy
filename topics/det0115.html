DET0115 Detection Strategy for Spearphishing via a Service across OS Platforms

DET0115Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

This detection watches for phishing messages that arrive through trusted online services instead of normal email. The sender uses a real service, so the message often looks genuine. The rule links the message to what happens on the computer afterwards.

Why should you care?

People are taught to trust messages from services they use. Attackers use that trust. They host a file or a form on a real service, then send a link. Your email filter sees a legitimate service domain and lets it through. Only the behaviour after the click shows the attack.

How it works, in plain steps

  1. Your mail gateway or cloud service logs record that a notification or share link was delivered.
  2. The rule records the sending account, the service domain and the recipient.
  3. It then watches endpoint logs for the recipient opening a file or a browser download from that service.
  4. It also looks for a newly created process in a temporary or download folder.
  5. If the process runs a script interpreter or an office application, the risk rises.
  6. A match between delivery and execution inside a short window raises an alert.

Real-world example

Imagine a hospital sign-in sheet. A visitor writes a real company name that the front desk already trusts. The sheet looks perfect. The problem only appears later, when the visitor walks to the pharmacy instead of the meeting room. The delivery record is the sign-in sheet; the walk to the pharmacy is the process creation event.

Key takeaways

  • A trusted service domain is not proof that the sender is honest.
  • Delivery records alone are weak; combine them with what the user runs.
  • Short time windows make the link between message and action clear.

In more detail

This strategy detects spearphishing that arrives through a legitimate third party service, such as a file sharing portal, a code repository, a form builder or a social platform, rather than through direct email. The technique matters because the message comes from a real service domain that already passes your email authentication checks, so traditional sender reputation and attachment scanning do little. Detection depends on mail gateway and cloud audit telemetry that records the service, the sharing link, the sender account and the recipient, plus endpoint process creation when a recipient opens the downloaded file. It fails in practice because these notifications are indistinguishable from genuine service mail at the transport layer, so the signal has to come from correlating the delivery with what the recipient does next.

What you will practise

  • Describe how attackers use legitimate services to deliver phishing content
  • Identify the mail, cloud audit and endpoint fields needed for this correlation
  • Build a rule that links a share notification to a process started by the recipient
  • Recognise why sender authentication checks do not stop this technique
  • Triage an alert by checking the sender account and the downloaded file
