DET0596 Behavioral Detection of Remote SSH Logins Followed by Post-Login Execution

DET0596Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Secure shell, usually shortened to SSH, is the standard way to log in to a Linux server. It works from another computer over the network. This detection looks at two things together. It looks at who logged in over SSH. It also looks at what ran immediately afterwards. A login on its own is normal. A login followed by unusual commands from an unknown address is what matters.

Why should you care?

Most servers allow many logins every day, so watching logins alone produces an unreadable alert list. But once an attacker has one valid account, they use it to run their tools. Those tools need a command to start. By joining the login record to the command record, you can see the whole first minute of a session. That short window often separates a routine job from someone exploring a server they should not be on.

How it works, in plain steps

  1. The SSH service writes a log line for each successful login. It records the account name, the source address and the authentication method.
  2. The audit service or process accounting records each command that runs, with a session or terminal identifier.
  3. The rule groups both kinds of record by host, account and session identifier.
  4. It keeps sessions where a command runs within a short time of the login.
  5. It compares the source address and the account with the learned history for that host.
  6. Sessions that use a new address and run unexpected commands are raised for review.

Real-world example

Think of a staff car park with a barrier and a key card. The barrier log shows every card used at every minute. That log alone tells you very little, because hundreds of staff drive in each day. But if the barrier log is placed next to the office door log, a pattern appears. A card enters the car park at three in the morning and opens the finance office two minutes later. Neither log is alarming alone. Together they point to one person and one room. This detection places two logs side by side in the same way.

Key takeaways

  • Logins are common, so the signal comes from the commands that follow them.
  • You need a session identifier to connect a login to the commands it started.
  • Learn the normal source address for each account, because a new address is often the first clue.

In more detail

This strategy detects remote interactive logins over the secure shell protocol followed by execution on the target host, which ATT&CK tracks as T1021.004. The secure shell daemon produces clean authentication records, but the interesting behaviour is what happens after a successful login, so the detection joins two streams: the authentication event with its source address, account and authentication method, and the process or command execution records that follow within the same login session. The pattern of concern is a valid account logging in from an address or at an hour it has never used, immediately running a shell, an interpreter, a download utility or a command that touches credentials or scheduled tasks. The benign cases are automation accounts running scheduled jobs, configuration management agents, backup transports and administrators working from jump hosts. The strategy fails in two common ways: session correlation is impossible when the audit configuration does not record the terminal or session identifier, and the source address is meaningless when the fleet is reached through a bastion host that hides the true origin.

What you will practise

  • Describe how the secure shell service and the audit service record a remote session
  • Correlate an authentication event with the commands executed inside the same session
  • Identify the fields that link a login to later process activity on a Linux host
  • Recognise the automation, backup and configuration management accounts that behave like this legitimately
  • Detect a valid account used from an unusual source address or at an unusual hour
  • Assess the risk of a suspected compromised account and decide on containment
