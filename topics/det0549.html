DET0549 Detect Suspicious Access to Private Key Files and Export Attempts Across Platforms

DET0549Detection StrategyVery hardDetection Strategy

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

Private keys are secret files that prove who you are, like a written signature that nobody can copy. This detection looks for people or programs opening those secret files when they should not. It also watches for anyone trying to copy a key out of a cloud key store.

Why should you care?

If an attacker steals a private key, they can log in as that identity without ever knowing the password. This is why a stolen key is more dangerous than a stolen password. Multi factor authentication may not stop them, because the key is accepted as proof on its own. Finding the theft early can stop the attacker from using it at all.

How it works, in plain steps

  1. Your systems record a small event every time a process opens a file, including the file path and the process name.
  2. A SIEM, which is a central system that collects and searches log events, gathers these events from many hosts.
  3. The rule keeps only events that touch a private key path, such as a hidden key folder or a certificate store file.
  4. It then removes events from known good processes, like the backup agent or the local certificate service.
  5. What remains is scored. A web server process reading a key file at midnight is far more interesting than an installer doing it at noon.
  6. If the same process also opens a network connection or writes a copy of the file, the alert is raised with high confidence.

Real-world example

Think of a hotel key cabinet at the front desk. Staff open it all day, so the cabinet being touched proves nothing. What you really want to know is when someone who is not on shift opens it, or when a key leaves the building. This detection is the log sheet on the cabinet door, plus a check on who is allowed to be in the room.

Key takeaways

  • A private key is proof of identity, so stealing one can skip the password step completely.
  • The alert only becomes useful when you also know which process opened the key and where it went next.
  • Most sites miss this activity because object access auditing is switched off by default.

In more detail

This detection strategy covers Unsecured Credentials: Private Keys, the practice of hunting for private key material on disk or in cloud key stores so it can be stolen and reused to sign, decrypt or impersonate a trusted identity. It matters because a single stolen private key can bypass multi factor authentication entirely, since the key itself is the proof of identity. The telemetry that makes it possible is file access auditing on key directories, command line capture where tools read or export key material, cloud key management audit trails, and subsequent authentication events that use the recovered key. In practice this strategy fails for three reasons: most hosts do not enable object access auditing at all, legitimate administrators and backup agents read key files constantly and drown the signal, and an attacker who already has root or administrator rights can often read a key without leaving any useful event.

What you will practise

  • Explain why private key theft bypasses multi factor authentication and why it is high impact.
  • Identify the telemetry sources that record file access to private key material on Windows, Linux and macOS hosts.
  • Correlate a key file read with the responsible process, its parent process and any later network connection.
  • Build a list of legitimate key reading processes so the rule can filter them out safely.
  • Recognise the cloud key management events that show a key being exported or used from a new location.
  • Describe how to tune the rule without losing coverage of interactive key theft.
