T1559.003 Inter-Process Communication: XPC Services

T1559.003ExecutionExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

XPC services are a way for programs on a Mac to send messages to each other. Some of these helper programs run with the highest permissions on the system. This sub-technique is about an attacker sending a bad message to such a helper. The helper then runs code for the attacker. It belongs to the wider technique of abusing communication between programs.

Why should you care?

A helper that runs as root can do things your normal user account cannot. An attacker may talk that helper into doing work for them. They then gain those higher permissions without stealing a password. This kind of attack is quiet, because the messages stay inside the machine and never cross the network. If nobody watches which programs start other programs, the abuse can stay invisible for a long time.

How it works, in plain steps

  1. On macOS, applications talk to helper programs through XPC, which passes structured messages.
  2. Some helper daemons run with root rights, so they can perform privileged tasks.
  3. The application defines the messages the helper accepts, and the helper should check them.
  4. An attacker sends crafted messages to that helper, hoping the checks are weak or missing.
  5. If the message is trusted, the helper may run code or act with its higher rights.
  6. Defenders spot this through the unusual child process or log entry the daemon then creates.

Real-world example

Picture an office building with a locked records room. Staff cannot enter, so they post a request form through a slot and a clerk inside fetches the file. The clerk trusts every form and never checks who sent it. A visitor learns the form layout, writes a strange request, and the clerk obeys it without asking a question. The room stayed locked the whole time, yet the visitor still got what they wanted.

Key takeaways

  • XPC is a messaging system between programs, and some helpers run with root rights.
  • The real danger is a helper that trusts its clients or their input without checking.
  • Watch which helper daemons start new processes, because that is the visible clue.

In more detail

On macOS, XPC services carry structured messages between applications and helper daemons, and many of those daemons run as root so that a normal user process can request a privileged task such as a network connection or a file operation. This sub-technique covers adversaries who hand crafted or malformed content to a listening XPC service in the hope that the daemon will execute it or act on it with its own higher privileges. The weak point is rarely the messaging system itself but the validation around it: a daemon that does not confirm the identity of its clients, or that trusts the size, type, or contents of the parameters it receives, can be pushed into work it was never meant to perform. The artefacts a defender works with are mostly process lineage and logging rather than network traffic, because the messages never leave the host. A daemon that suddenly spawns a child process, opens an unusual file, or reaches out to a new destination is the strongest lead, and the macOS unified log records XPC connection and launch activity that can be correlated with it. Because launchd, shared utilities, and update agents legitimately talk to privileged helpers all day, the useful signal is the parent process, the unexpected child process, and the fact that the daemon was never observed performing that kind of action before.

What you will practise

  • Explain what an XPC service is and why a privileged helper daemon is valuable to an attacker.
  • Describe how weak client validation or unchecked input inside a helper leads to local code execution.
  • Identify the process lineage and macOS log sources that reveal an abused XPC connection.
  • Distinguish a normal helper daemon exchange from a daemon that spawns an unexpected child process.
  • Summarise why this sub-technique differs from the broader inter-process communication parent technique.
  • Outline defensive steps such as validating clients and limiting what privileged helpers may do.
