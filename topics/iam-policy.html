IAM Policy

Cloud SecurityVery hardKeyword

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

An identity and access management policy, usually called an IAM policy, is a written rule that says who may do what in a cloud platform. It names a person or service, the actions allowed, and the resources those actions apply to. The cloud provider checks these rules on every request.

Why should you care?

Cloud accounts say no by default, so access exists only where a policy allows it. That is good, but a single careless rule can undo it. A policy that allows every action on every resource gives an attacker the whole account if they steal one key. Careful policy writing keeps each person and service to the smallest useful set of permissions.

How it works, in plain steps

  1. A request arrives at the cloud provider, such as a service asking to read a file.
  2. The provider works out who is asking, using a user, a role or a service identity.
  3. It collects every policy that applies, from the identity, the resource and the organisation.
  4. If any rule says deny, the request is refused, because deny beats allow.
  5. If a rule allows the action on that resource, the request succeeds and is logged.
  6. If nothing allows it, the request fails, since the default answer is no.

Real-world example

Think of a hotel key card. Your card opens your room, the gym and the front door during your stay. It does not open other guests' rooms or the manager's office. The front desk decides this when they program the card. An IAM policy is that programming, and a wildcard policy is like handing every guest a master key.

Key takeaways

  • Every cloud request is checked against policies, and the default answer is no.
  • An explicit deny always wins, so use denies for hard limits.
  • Give each person and service the smallest set of permissions that works.

In more detail

An IAM policy is a structured document that grants or denies permissions to a principal in a cloud platform, evaluated by the provider's authorisation engine on every API call. Policies typically bind a principal, an action or set of actions on a resource, and optional conditions such as source address, time, tags or whether multi-factor authentication was used, with an explicit effect of allow or deny. Cloud authorisation is generally default-deny, so access exists only where a policy grants it, and an explicit deny usually overrides any allow. Policies attach at several levels, including identity-based policies on users, groups and roles, resource-based policies on the target itself such as a bucket or key, permission boundaries, session policies and service control policies in an organisation hierarchy, which means the effective permission set is the intersection and union of several documents rather than any single one. Security professionals care because over-permissive policies are a leading cause of cloud compromise and because policy errors are invisible until an attacker or an auditor exercises them. Practical work includes least-privilege scoping, wildcard elimination, analysing cross-account trust relationships, reviewing role assumption chains, and detecting privilege escalation paths where one grant lets a principal modify a policy that grants more. Reviewing the effective permission of a principal, not the intent of a single document, is the discipline the topic teaches.

What you will practise

  • You will be able to read a JSON IAM policy and state precisely which principals, actions and resources it authorises.
  • You will be able to compute the effective permissions of a principal across identity, resource, boundary and organisation policies.
  • You will be able to identify privilege escalation paths created by policy modification rights.
  • You will be able to rewrite an over-permissive policy into a least-privilege form and justify each retained grant.
  • You will be able to explain how condition keys and explicit deny change authorisation outcomes.
  • You will be able to triage IAM-related alerts such as role assumption anomalies and policy change events.
