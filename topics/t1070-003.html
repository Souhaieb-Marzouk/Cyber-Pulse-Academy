T1070.003 Indicator Removal: Clear Command History

T1070.003StealthExtremeTechnique

New to this? Start here

Explained in plain language

Written for beginners. No security background needed.

Simple definition

A shell is the text window where you type commands. Most shells keep a list of what you typed so you can look back later. This technique is an attacker emptying that list. It is a small part of the parent technique, which covers all kinds of records.

Why should you care?

That list is often the quickest way to see what an intruder did. On many systems it is stored in a simple file that anyone with the same account can delete. When it is gone, you lose the clearest account of their actions. You are then left with gaps and must rebuild the story from other sources.

How it works, in plain steps

  1. The shell holds your typed commands in memory while the session is open.
  2. When you log out, it usually writes that list into a file in your home folder.
  3. An attacker can empty the in-memory list with a single built in command.
  4. They can also delete the history file, or send it to a place that is never written.
  5. On Windows, PowerShell keeps a session list and a separate permanent history file.
  6. Clearing the session list does not remove that file, so the attacker deletes it too.

Real-world example

Imagine a shared flat with a whiteboard by the door where everyone writes down what they take from the pantry. One flatmate takes three things, then wipes only their own lines from the board. The board still looks busy and the flat still runs as usual. Nobody notices anything until the shopping bill does not match the empty shelves. Clearing command history is that careful wipe.

Key takeaways

  • A missing history file is a clue, not proof that nothing happened.
  • Central logging of executed commands survives a shell history wipe.
  • On Windows, clearing history in a session does not remove the stored history file.

In more detail

Clear command history is the narrow form of indicator removal that targets only the record of commands typed into an interactive interpreter. The parent technique covers every kind of artefact, while this sub-technique covers the shell's own memory of a session. The affected storage differs by platform, and so does the attacker's approach. On Linux and macOS a shell keeps commands in memory during the session and writes them to the file named by the history environment variable when the session ends, so an attacker can wipe the in-memory list, delete the history file from the home directory, or point the variable somewhere unwritable so nothing is saved at all. On Windows, PowerShell keeps two separate records: a session only list that disappears when the console closes, and a persistent history maintained by the line editing module and written to a text file under the user's application data. Clearing the session list does not touch that file, so an attacker who knows this deletes or edits the file itself. Network device command lines and hypervisor shells keep their own logs, such as the shell log on ESXi, which can also be trimmed. Detection cannot rely on the missing history, because absence proves nothing by itself. It relies on the surrounding evidence: process creation telemetry showing a history clearing command such as Windows Security 4688 or Sysmon 1, PowerShell script block logging capturing the clear command, file deletion events against the history file, audit records of executed commands that survive a shell history wipe, and the contradiction of remote login and network activity with no matching typed commands.

What you will practise

  • Explain where Linux, macOS and Windows shells store typed command history.
  • Describe the commands and file changes used to clear or delete that history.
  • Explain how this sub-technique differs from its parent, Indicator Removal.
  • Identify the events that still record a command after the history is cleared.
  • Explain why an empty history file alongside active logins is suspicious.
