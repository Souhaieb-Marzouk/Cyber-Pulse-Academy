C1 · Scenario briefing — the 21:40 order

Meridian Cartage Co. moves real shipping containers by day. By night, its storefront meridian.example runs on a three-pier cluster: PIER-A PIER-B PIER-C. Marketing has announced a midnight flash sale — the last one took the site down for 40 minutes because every container was managed by hand.

You are the newly hired night-watch platform engineer. The harbor master (the orchestrator) is willing to work for you — scheduling, scaling, healing and re-routing containers — but only if you declare what you want instead of doing everything manually. That shift, from manual labor to orchestration, is exactly what CompTIA Cloud+ CV0-004 tests in Domain 1.0 (Cloud Architecture, workload-orchestration objectives).

Your mission: take the fleet from hand-run stand-alone containers to a fully orchestrated, self-healing, sale-proof deployment — and prove it when the sale traffic hits.

Certification relevance: this lab covers the whole “Orchestration: managing containers using orchestration techniques” area of Cloud+ CV0-004 — the four orchestrator tasks, Kubernetes anatomy, service discovery, persistent storage, rolling updates and the security rules for orchestrated workloads.

C2 · Harbor-ops manual (knowledge core)

Orchestration manages and automates the deployment, scaling and operation of containers across environments. A stand-alone container runs independently with no coordination — fine on a laptop, fragile in production: if it dies at 03:00, nobody restarts it.

  • Automation scripts a single task. Orchestration coordinates many tasks into a continuously enforced process — it doesn’t just run steps, it keeps reconciling reality toward a declared goal.
  • The orchestrator watches desired state (what you declared) and continuously corrects actual state (what is running). This is called reconciliation.
  • Cluster — all piers (nodes) managed as one unit. Control plane = the brain: API server (front desk), etcd (state store), scheduler (berthing officer), controller manager (watchkeepers).
  • Worker node — a machine running containers via a container runtime, supervised by the kubelet agent. You talk to the cluster with kubectl.
  • Pod — smallest deployable unit (one or more containers). A Deployment declares how many replicas of which image should run; the scheduler places each new pod on a suitable node.
  • Scheduling — places containers across available resources.
  • Scaling — grows/shrinks replica counts with load; auto-scaling does it without you.
  • Load balancing — spreads traffic between replicas.
  • Monitoring & self-healing — restarts or reschedules failed/unresponsive containers (fault tolerance).
  • Service discovery — a dynamic, auto-updating registry (a Service gives pods a stable DNS name), so callers never hardcode IPs that change when pods are rescheduled.
  • Rolling updates & rollback — staged image replacement with zero downtime, reversible.
  • Persistent storage — Persistent Volumes (PV) decouple storage from container life; pods claim storage with PVCs, so data survives restarts (ephemeral storage does not).
  • Images & registries — orchestrators pull images from registries (Docker Hub, AWS ECR, Azure ACR, Google GCR). Pin version tags, scan images, avoid latest.
  • Least privilege — never run containers with privileged: true you don’t need; it invites container escape to the host.
  • Secrets — passwords belong in Secret objects (or a vault), never plaintext in manifest env vars.
  • Access control — RBAC, namespaces and resource quotas keep people and workloads in their lanes.
  • Tools you may be asked to compare: Kubernetes (the industry standard, with managed services EKS/GKE/AKS), Docker Swarm (simple, ships with Docker), Apache Mesos (legacy — development halted after the 2021 retirement vote; formally retired to the Apache Attic in 2025, still listed in older exam guides).
