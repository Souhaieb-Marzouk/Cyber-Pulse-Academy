Training board · the knowledge core

What automation actually is

Automation is the practice of using tools to execute repetitive cloud operations without a human performing each step. That is the lesson in one sentence: replace manual toil with code-driven, repeatable processes. Orchestration is its big sibling — coordinating multiple automated tasks into one end-to-end workflow, often across systems (the pipeline that runs build → test → deploy is orchestration; the build step itself is automation). Attackers are not the audience here: automation is a defender's force multiplier, which is why an entire CV0-004 domain is devoted to it.

Why operators automate — speed (a 14-VM rollout in minutes, not hours), consistency (identical results every run), fewer human errors (the script does not get tired at 2 a.m.), scale (one pipeline serves 300 instances as easily as 3), and auditability (every change is a reviewed, versioned commit). Why it must be guarded — automation amplifies mistakes (one bad line can misconfigure a fleet), concentrates power in service accounts, and quietly rots when hand-edits drift systems away from their code.

Where it sits in the flow

Automation rides on the whole DevOps conveyor: source control holds the code of record (commits, branches, pull requests, reviews, merges) → a CI/CD pipeline integrates, builds, tests, secures, packages artifacts and deploys them → integrations (event-driven architectures, web services, sockets) fire the right automation at the right moment → monitoring (dashboards and logs) closes the loop. Domain 5.0 examines exactly this chain.

GitHub ActionsPipeline workflows defined directly in GitHub repositories.
TerraformDeclarative infrastructure-as-code: describe desired infrastructure, apply to converge.
AnsibleAgentless configuration automation over SSH using YAML playbooks.
DockerPackages an app with its runtime and libraries into portable container images.
KubernetesOrchestrates containers at scale: scheduling, scaling, self-healing.

What the floor taught you

Detection opportunities

  • Pipeline run logs — every stage logs status; alert on stage=package/deploy errors or first-failure-after-success.
  • Metrics — Grafana: alert when deploy duration p95 doubles or success rate drops below baseline.
  • Logs — ELK: alert on config changes made outside the pipeline identity (manual drift).
  • Drift reports — scheduled desired-vs-live diffs; a non-empty report is a finding.
  • Example logic (simplified): alert if drift_count > 0 for 2 consecutive audits.

Mitigations (illustrative ATT&CK mapping)

  • M1054Software Configuration — enforce IaC/desired state so only pipeline changes converge the estate.
  • M1026Privileged Account Management — least-privilege pipeline service accounts, scoped and rotated.
  • M1051Update Software — scheduled automated patching with test rings.
  • M1018User Account Management — automated deprovisioning of inactive accounts.
  • Mapping direction: defensive automation constrained against T1578 (Modify Cloud Compute Infrastructure) and T1078 (Valid Accounts).

Blue-team takeaways

  • Automate the repeatable; gate it with review, tests and approval — fast and controlled.
  • Every manual fix must flow back into source control, or the estate silently drifts.
  • Observe automation: logs + metrics + drift reports are its vital signs.
  • Scope service accounts like keys: least privilege, rotation, no interactive logins.

Red-team mindset (know your exposure)

  • An over-privileged pipeline account is a single key to the whole estate (T1078 pattern).
  • An ungated pipeline is an insertion point: whatever reaches main reaches production.
  • Drift = changes no one tracked; attackers love untracked surface (T1578 pattern).
  • Event-driven automations can be abused by someone who can forge the event — validate event sources.
