Reference shelf — what you are provisioning

CV0-004 Objective 2.4: “Provision and configure cloud resources effectively.” Read before or during drafting.

What provisioning is — and where it sits

Provisioning is creating and configuring cloud resources — networks, compute, storage, databases, identities — so a workload can run. It sits in Domain 2.0 (Deployment) after requirements analysis (2.1) and the IaC decision (2.2), alongside migration work (2.3); operations (3.0) and security (4.0) then run what you provisioned.

Four ways to provision

ApproachBest forTrade-off
Console (manual)One-off experimentsSlow, unrepeatable, no history — the birthplace of drift
Scripted CLICustom one-shot logicRepeatable-ish, but logic lives in someone’s terminal
IaC templatesAnything you run more than onceVersioned, reviewable, idempotent — same input, same result
Self-service catalogLocked-down standard buildsFast and safe, but only as flexible as the catalog allows

Golden image vs. bootstrapping: a golden image bakes the OS + software in advance (fast, consistent starts); user-data bootstrapping runs a script at first boot (flexible, slower, can fail mid-boot). Production stacks usually combine both.

Why it matters — real mis-provisioning incidents

Provisioning mistakes are among the most common real-world cloud breach root causes. All three cases below are public and documented; they are studied here defensively:

Microsoft, Sep 2023: 38 TB of internal data exposed via an over-permissive storage SAS token shared with an AI research dataset (Wiz Research).
Toyota, 2023: incorrect cloud settings left parts of customer data externally accessible for years.
Capital One, 2019: a misconfigured web firewall plus an over-privileged server role exposed ~100 million records.

None needed a novel exploit — the door was provisioned open. That is why “provision and configure effectively” is an exam objective.

Placement, price and governance

  • Region choice drives data residency (law), latency (users) and price — it is the least reversible provisioning decision.
  • Availability: spread redundant tiers across availability zones (Multi-AZ); 99.9% is a design decision, not a setting you find later.
  • Purchasing models: on-demand (flexible, priciest), reserved (steady baselines, big discounts), spot (interruption-tolerant batch, cheapest).
  • Tags (policy keys) turn infrastructure into accountable, automatable, allocatable resources.
  • Quotas are per-region ceilings — new regions fail at scale until you request increases.

Synthesis of objective 2.4: detection, mitigation, and the two mindsets.

Detection & verification opportunities

  • C-12 Validation gates: connectivity, isolation, egress, HA and compliance tests run automatically after every apply.
  • C-13 Drift detection: compare live resource configs against the IaC template on a schedule; alert on differences.
  • C-16 Provisioning event alerts: security-group or public-access changes by principals that are not the pipeline; spend above forecast.
  • C-15 Budget anomaly alerts catch runaway spend right before the invoice does.

Mitigation & governance recommendations

  • C-09 Default-deny security groups; open ports to named sources only.
  • C-08 Least-privilege execution roles per workload — no wildcards.
  • C-04 Private subnets for data stores; NAT for egress, never inbound paths.
  • C-10 Tag policy enforced in the pipeline (deny untagged resources).
  • C-14 Contain → assess → fix → verify as the standing remediation order.
  • C-07 All changes through versioned templates; console write access to production removed or logged.

Blue-team takeaways

  • Region, CIDR and IAM decisions are the hardest to change later — review them like code, before the first apply.
  • Every provisioned resource should answer “who owns me, what data do I hold, what do I cost” from its tags alone.
  • A failed provision is evidence, not noise: quotas, overlaps and permission errors tell you how the platform really behaves.
  • Validation tests are only worth what they assert — HA and isolation must be tested, not assumed.

Red-team mindset (defensive use)

  • Attackers do not break in when provisioning leaves the door open — exposed buckets, world-open SSH, wildcard roles are “find, not hack”.
  • Think like an enumerator: which of your resources answer from the internet, and what answer should they give?
  • Untagged forgotten resources are the ideal target — nobody watches what nobody can name.
  • Every exposure in this lab (public bucket, world-open SSH, wildcard IAM) maps to a real incident class; fix the provisioning, not just the symptom.
