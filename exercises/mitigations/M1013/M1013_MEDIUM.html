About M1013, in simple words

M1013 is a Mitigation — defensive guidance, not an attacker behaviour. It is called Application Developer Guidance. It targets the moment software is designed, written, tested, and shipped, so that exploitable weaknesses never reach applications, systems, and APIs.

The named measures are concrete. Preventing SQL injection: use parameterized queries or prepared statements, and validate or sanitize inputs. Stopping XSS: encode all user-generated content that a page displays. Secure API design: authenticate every endpoint (token-based authentication) and do not leak sensitive data in responses — the page's use case is a mobile banking app. Static analysis in the build pipeline: CI/CD tools scan each build, for example to catch hardcoded credentials before deployment. Threat modeling at design time: use STRIDE to list abuse cases such as session hijacking, then design protections like secure session management. Supporting tools: DAST (Burp Suite, OWASP ZAP) and secure-by-default frameworks (Django, Spring Security).

The ATT&CK page ties this mitigation to specific techniques. For T1212 it wants validated authentication requests (one-time passwords, signatures, random session keys). For T1195 and T1195.001 it wants careful third-party library selection and locked dependency versions. For T1593.003 it wants no credentials in public code repositories. For T1550.001 it wants token binding. For T1564.012 it wants apps installed in already-trusted folders instead of custom antivirus exclusions. For T1496.003 it wants CAPTCHA on SMS-sending forms. On mobile it wants FLAG_SECURE (T1513), minimal elevated permissions (T1626), App Links / Universal Links with PKCE (T1635.001), and caution with third-party libraries (T1474).

Where you meet it at work: developers and AppSec engineers apply it in pull requests and pipeline gates; GRC analysts map it to audits; SOC analysts see its gaps after incidents; CTI analysts use it to map actor techniques to defences. Its limits matter too: it cannot stop someone who already holds a valid password, and it cannot rebuild a vendor's binary.

How this exam works

  • Level: MEDIUM. Each exercise connects two ideas (for example: recognise the technique, then choose the practice that answers it). You decide what to look at first.
  • Pass mark: 70%. Only answered exercises count.
  • Exercise types: single-choice and multi-select questions, matching, drag-and-drop zones, ordering, fill-in-the-blank, click-the-line in code and logs (log panel has a filter box), and branching scenarios. No command-line tasks — this mitigation is guidance, not shell work.
  • Partial credit: multi-item exercises score per item with max(0, (H − W) / N): correct picks add, wrong picks subtract. Selecting everything gives zero.
  • Timer: 40 minutes, two kinds of pause: the Pause button (real break, exercise hidden) and the Check auto-pause — pressing Check stops the timer automatically while you read the feedback; it resumes when you press Next (or return to the review list).
  • Hint: one per exercise, costs 10% of that exercise's credit.
  • Skip: free; skipped exercises wait in the review list until you finish or the timer ends. Skipped-and-unanswered exercises are excluded from the score.
  • Retake: reshuffles questions and choices.
